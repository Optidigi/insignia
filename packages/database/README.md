# M3-001 durable core

`migrations/20260929000100_durable_core.sql` is the application schema source. Apply it with dbmate (`corepack pnpm db:migrate`) against a disposable PostgreSQL 18 database. Running the command twice must leave one applied migration. The `down` block drops these new-system tables and their data; use it only for an empty/disposable environment. Kysely supplies typed queries and transactions, not migrations.

The schema separates internal `shop_id` from external shop domain and keeps numbered installation generations. Composite tenant keys bind configs, revisions and publication operations. A config is unique for `(shop_id, external_product_id)`. Draft writes compare `draft_version`; the losing concurrent writer receives a conflict. The current M2 slice defined a published DTO but no mutable-draft DTO, so draft storage checks JSON safety and explicit version syntax, and returns raw versioned data. It does not decode an unknown draft version into a current domain object.

Published revisions use `m2-published-config-v1` validation on write and validated read. The trusted repository computes SHA-256 over UTF-8 canonical JSON: object keys sort by JavaScript code-unit order, arrays retain their order, and the root `revisionContentHash` field is excluded before hashing. The computed hash is inserted into the stored published value. A database trigger rejects updates and deletes of revision rows. The publication journal separately records request, acknowledgement, exact observation and activation; local generation/sequence/pointer guards prevent older operations from activating. This does not prove remote Shopify propagation or enable production publication.

Command results, inbox deliveries and outbox events are durable rows. Business writes and required outbox events share a PostgreSQL transaction. Outbox claims use `FOR UPDATE SKIP LOCKED` and a persisted lease with an attempt number that fences stale acknowledgements. Payload rows include `collected_at`, `retention_class`, `purge_after` and `erasure_state`. This slice records purge metadata; it does not run a purge worker or raw webhook ingress.

The integration suite needs `DATABASE_URL` pointing to a disposable PostgreSQL 18 database. `corepack pnpm check:database` applies the migration twice and runs the tests. The dedicated GitHub Actions job supplies PostgreSQL 18; the current local host has no PostgreSQL process/container runtime, so local runs cannot be used as database evidence.
