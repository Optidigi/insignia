# M3-001 durable core

`migrations/20260929000100_durable_core.sql` is the application schema source. Apply it with dbmate (`corepack pnpm db:migrate`) against a disposable PostgreSQL 18 database. Running the command twice must leave one applied migration. The `down` block drops these new-system tables and their data; use it only for an empty/disposable environment. Kysely supplies typed queries and transactions, not migrations.

The schema separates internal `shop_id` from external shop domain and keeps numbered installation generations. Composite tenant keys bind configs, revisions and publication operations. A config is unique for `(shop_id, external_product_id)`. Draft writes compare `draft_version`; the losing concurrent writer receives a conflict. The current M2 slice defined a published DTO but no mutable-draft DTO, so this storage boundary accepts only `m3-config-draft-v1` plain JSON object roots with recursively JSON-safe values. It returns raw versioned drafts and rejects unknown versions on read and write. Full M2 content validation remains at the later publication boundary.

Published revisions use `m2-published-config-v1` transport and domain-semantic validation on write and validated read. The trusted repository computes SHA-256 over UTF-8 canonical JSON: object keys sort by JavaScript code-unit order, arrays retain their order, and the root `revisionContentHash` field is excluded before hashing. The computed hash is inserted into the stored published value. A database trigger rejects updates and deletes of revision rows. The internal `stagePublicationIntent` seam checks draft version and atomically inserts the revision, requested operation and durable outbox event; a failure rolls back all three. The public config facade exposes reads and draft writes, not standalone revision insertion. The publication journal separately records acknowledgement, exact observation and activation; local generation/sequence/pointer guards prevent older operations from activating. Publication interfaces are intentionally not exported from the package root: a future reviewed projection builder must derive and verify policy/readiness from the revision before any Shopify write or activation path can use them. This slice does not prove remote Shopify propagation or enable production publication.

Command results, inbox deliveries and outbox events are durable rows. Business writes and required outbox events share a PostgreSQL transaction. Outbox claims use `FOR NO KEY UPDATE SKIP LOCKED` and a persisted lease with an attempt number that fences stale acknowledgements. Installation-bound inbox/outbox records carry a generation that fences processing or delivery after reinstall; events explicitly independent of an installation carry null. Inbox delivery IDs deduplicate within an installation. Payload rows include database-controlled, immutable `collected_at`, `retention_class`, `purge_after` and `erasure_state`; raw and JSON payloads are capped at 8 MiB and their purge deadline at 180 days after actual database collection. These are payload-table ceilings, not a retention rule for separately permitted minimal financial/audit facts. This slice records purge metadata; it does not run a purge worker or raw webhook ingress.

The integration suite needs `DATABASE_URL` pointing to a disposable PostgreSQL 18 database. `corepack pnpm check:database` applies the migration twice and runs the tests. The dedicated GitHub Actions job supplies PostgreSQL 18; the current local host has no PostgreSQL process/container runtime, so local runs cannot be used as database evidence.
