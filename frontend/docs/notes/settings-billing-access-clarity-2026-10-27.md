# Settings audit: Billing and app permissions

27 October 2026. Independent product-clarity audit of Billing and App permissions. I read the current source, the later owner corrections in `settings-product-truth-review-2026-10-25.md`, the Settings scope notes, and the Web app Settings and Billing checklists. I reviewed the local rendered 1440×1000 and 390×844 captures; this is not a native Shopify-hosted acceptance pass.

## Finding

### P2 — Unverified billing state uses the same alert heading as a confirmed inactive subscription

In the `Status not verified` state, the page correctly says the current price and plan could not be verified, but then shows the same amber **Subscription needs attention** alert used for a confirmed inactive subscription. The shared condition is `!view.newActionsAllowed`; the billing projection sets this false both for an inactive subscription and for any stale or unrecognized subscription. A verification/policy mismatch therefore reads like a merchant-side subscription problem even though the page cannot identify the cause. Keep the accurate consequence that new customizations and publication are unavailable, but use verification-specific alert copy for `status === 'unavailable'` (for example, “Billing status needs verification”). Leave the inactive-state wording separate.

Reproduced in [desktop unverified capture](../../../../.artifacts/admin-popup-review-2026-10-24/settings/desktop/settings-billing-unverified.png) and [mobile unverified capture](../../../../.artifacts/admin-popup-review-2026-10-24/settings/mobile/settings-billing-unverified.png); compare [inactive capture](../../../../.artifacts/admin-popup-review-2026-10-24/settings/desktop/settings-billing-inactive.png). ## Workflow and ownership assessment

- **Billing integration matches the intended boundary.** `/admin/settings/billing` mounts `MerchantBilling`, reads the authenticated subscription view on entry, and links to Shopify's hosted plan page. It does not treat redirect parameters as entitlement, does not present the Free-plus-two-paid direction as live options, and preserves the current Standard/development-test distinction. The extra `settings-plan-selection` image in the artifact manifest is labeled a Shopify-owned disabled reference, not the live Billing page.
- **App permission consent is appropriately explicit and scoped.** `ReadinessPermissions` checks current grants on demand and requests only the missing optional checkout or product subset, in separate consent actions. No scope prompt is triggered on page load. This follows Shopify's Scopes API contract: `request()` is for declared optional scopes. Sources: [ReadinessPermissions.tsx](../../../apps/web/src/islands/ReadinessPermissions.tsx#L58-L73), [ReadinessPermissions.tsx](../../../apps/web/src/islands/ReadinessPermissions.tsx#L90-L203), [Shopify Scopes API](https://shopify.dev/docs/api/app-home/latest/apis/authentication-and-data/scopes-api), and [Manage access scopes](https://shopify.dev/docs/apps/build/authentication-authorization/manage-access-scopes).
- **App scopes and staff access stay separate in the UI.** The page reports product editing/publication scopes separately from the server-checked `Can edit` / `View only` result. The Orders and artwork row says **App access allowed** and separately states that the store owner's account and Shopify order access are required; this does not claim the app-scope query verifies private-record access. Source: [ReadinessPermissions.tsx](../../../apps/web/src/islands/ReadinessPermissions.tsx#L206-L311), [MerchantPermissions.tsx](../../../apps/web/src/islands/MerchantPermissions.tsx#L10-L51), and [auth.ts](../../../apps/web/src/server/admin/auth.ts#L150-L175).
- **Known access-check dependency, not a new UI finding:** product/staff inspection is coupled to the broader readiness endpoint, so a missing checkout scope can block that check until the merchant grants the read-only checkout scope. The page says so before consent. This is the unchanged backend seam recorded in the superseding [product-truth review](settings-product-truth-review-2026-10-25.md#L9-L15); I am not proposing an endpoint or broader scope request.
- **Plan return freshness is not confirmed as a defect.** `MerchantBilling` reads on mount only ([source](../../../apps/web/src/islands/MerchantBilling.tsx#L22-L48)) and its Shopify link leaves the frame with `target="_top"` ([source](../../../apps/web/src/islands/MerchantBilling.tsx#L232-L239)); there is no `pageshow`, focus, or visibility recheck. Shopify's current App Pricing docs say to query the Partner API after a plan approval and redirect to the configured welcome URL ([Shopify App Pricing](https://shopify.dev/docs/apps/launch/billing/shopify-app-pricing)). Ordinary navigation back to Billing remounts it, but browser Back could restore a cached document or reused iframe. The local preview cannot establish which behavior the installed Shopify host uses. Verify that exact return path in the native host before making a lifecycle change; do not report stale billing as reproduced yet.

## Checklist Design audit

The checklist files are the bundled [Web app Settings checklist](https://www.checklist.design/web-app/settings) and [Web app Billing checklist](https://www.checklist.design/web-app/billing). Shopify billing and account controls remain in Shopify; statuses below describe whether the Insignia Settings surface needs each item.

### Settings — Web app

| | Item | Why |
|---|---|---|
| 🟢 | **Structure** — Organising settings controls into logical categories e.g. account, notifications, security, billing. | The current hub links to four real destinations, including separate Billing and App permissions pages; no account-control page is implied. |
| ⚪ | **Account details** — The fields where users update their name, email address, and profile photo | Shopify owns merchant identity; Insignia has no profile fields here. |
| ⚪ | **Security details** — The ability to change the password,  two-factor authentication and other security information. _Tip: These fields should require re-authentication to save changes_ | Shopify owns sign-in and account security; Insignia exposes no credential controls. |
| 🟡 | **Notification preferences** — Controls for which notifications the user receives and through which channel, grouped by type (product updates, reminders, billing). _Tip: Grouping by type and/or platform helps reduce the chances of a user disabling all notifications rather than some_ | No notification channel or preference store exists in this surface. The product specification calls for warnings before retained data expires, but the event, recipient, channel, and delivery behavior still need a product decision; do not add a dummy switch. |
| 🟢 | **Billing** — Managing payment method, upgrading or cancelling a payment — this could also be a preview of this information with a link directly to the billing page if separate | The page summarizes confirmed subscription facts and sends plan management to Shopify. |
| ⚪ | **Additional preferences (if applicable)** — Language, timezone, date format, and appearance settings like dark mode | No Insignia-owned preference is stored here; Shopify/browser settings own these choices. |
| ⚪ | **Danger zone** — Destructive actions like account deletion, clearly separated from the rest of settings. _Tip: Include a confirmation step for any destructive actions, with details on what will be lost if the user continues_ | Shopify owns store deletion and app uninstall; no Insignia account-deletion action belongs on this page. |

### Billing — Web app

| | Item | Why |
|---|---|---|
| ⚪ | **Payment method on file** — The current card or payment method linked to the account, shown with masked details. _Tip: Last 4 digits of card are enough for the user to identify which card is in use without exposing sensitive information_ | Shopify bills app subscriptions and owns the merchant's payment method; Insignia does not receive card details. |
| ⚪ | **Add or update payment method action** — A way to enter a new card or change the current one | Payment-method changes belong in Shopify billing settings, not this app page. |
| 🟡 | **Next billing date and amount** — When the next payment will be taken and for how much. _Tip: Including the plan name alongside the amount if applicable_ | The page shows the recurring rate/cadence and current billing period (plus trial/discount dates when supplied), but does not label an exact next charge. Keep the Shopify handoff for exact charge details; do not infer a discounted net amount or a charge date from the current period. |
| ⚪ | **Invoices and receipts** — A list of past charges with the ability to download a PDF invoice for each. _Tip: Ensure invoices include company name, address, and VAT number — legally required in many countries and a frequent request from business users_ | Shopify includes app subscription charges on Shopify bills and exposes bills/invoices in Shopify Admin. Insignia does not hold invoice records. |
| ⚪ | **Tax and VAT (if applicable)** — Applicable tax or VAT shown on invoices and billing history | This app view has no invoice or tax DTO; Shopify bill/invoice remains authoritative. |
| ⚪ | **Failed payment recovery** — Clear messaging and recovery instructions when a payment attempt has failed. _Tip: Surface this issue prominently in the app as it can eventually restrict access if not resolve in time_ | The current subscription projection contains no payment-failure cause. Do not label an unverified or inactive result as a failed payment; recovery remains with Shopify's billing surface until the app has a confirmed failure signal. |
| ⚪ | **Billing contact email** — The email address where invoices and billing notifications are sent. _Tip: For larger teams, this is often different from the account owner's email_ | Shopify owns the billing contact and notification destination. |

Shopify confirms that Shopify App Pricing hosts plan selection/approval and that app charges appear on Shopify bills; Shopify Admin is the place to view app-charge billing details. See [Shopify App Pricing](https://shopify.dev/docs/apps/launch/billing/shopify-app-pricing), [App charges on Shopify bills](https://help.shopify.com/en/manual/your-account/manage-billing/billing-charges/types-of-charges/third-party-charges/app-charges), and [Shopify charges on bills](https://help.shopify.com/en/manual/your-account/manage-billing/billing-charges/types-of-charges/shopify-charges). Shopify content guidance also recommends plain language, short action labels, and avoiding duplicate content: [Shopify content](https://shopify.dev/docs/apps/design/content). These references were checked on 27 October 2026.
