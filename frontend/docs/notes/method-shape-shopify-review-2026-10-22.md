# Shopify patterns for a real Methods library

UI design recommendation, 22 October 2026. This is a proposal informed by public Shopify documentation, not a claim that Methods assignments or pricing modes exist in Insignia today. No app code or shared browser was changed.

## Recommendation

Give **Methods** its own top-level app navigation item beside Products. Use a searchable Methods index and a full resource detail page for create/edit. Do not keep a two-field modal under Settings, and do not make a multi-step wizard the primary editor. Product assignments, conditions, and pricing need to remain visible together and easy to revisit. Shopify's App Home 2.0 RC guidance provides an Index template for resource collections and a Details template for individual records; Details is a dual-column editor with grouped sections, supporting status/summary in the side column, breadcrumbs, and a Save Bar. The index composition supports search, filtering, sorting, selection, and bulk actions. [App Home patterns](https://shopify.dev/docs/api/app-home/v2.0-rc/patterns), [Index](https://shopify.dev/docs/api/app-home/v2.0-rc/patterns/templates/resource-index), [Details](https://shopify.dev/docs/api/app-home/v2.0-rc/patterns/templates/details), [Index table](https://shopify.dev/docs/api/app-home/v2.0-rc/patterns/compositions/index-table).

The index should have a primary **Create method** action and a table with method name, product coverage, pricing model, and status. Show product coverage only when assignments can be queried reliably; show an explicit `No products assigned` state instead of a guessed usage count. Keep row click or the method name as the path into details. Start with search; add filters and bulk actions only when the underlying queries and actions exist. The official Index pattern includes an empty state and searchable resource table previews.

Use the same full-page Details layout for creation and editing, with these sections:

1. **Method** — internal name, customer-facing label, and short customer explanation.
2. **Products** — manually selected products for deterministic assignment. If automatic matching is supported, offer a separate rule mode with supported attributes, all/any matching, a live match count, and a preview of matched products. Keep manual assignment and rules conceptually distinct; make exclusions and precedence explicit if they are later added.
3. **Pricing** — a clear pricing-model choice, then only the fields relevant to that choice. A useful proposal is a flat surcharge for each selected placement versus per-product prices by placement and decoration size. State the unit plainly beside the amount and show a concrete example of how it is charged. Do not imply that one value is a setup fee, per order, or per garment unless that charging rule is implemented.
4. **Product use** — a table of assigned products with links to their product configuration and any product-specific price/setup state the backend can report. This helps the merchant see where a shared method is used without making the table a substitute for the Products workflow.

Keep save/discard at the page level using the App Home Save Bar. A short explanation can clarify that editing a reusable method affects future product drafts/configurations only, while published product configurations preserve their resolved values. If assignments are meant to immediately alter what buyers can select, expose that as a separate publish/review action and show its impact before applying it.

## What the Shopify examples support

- **Collections are the closest assignment analogy.** Shopify's current collections documentation supports manual product/variant selection and automatic matching conditions; rules can require all or any conditions. Manually included items remain until removed, while condition membership follows matching. The new collections model is replacing legacy manual/smart collections and also supports product sources, exclusions, and app sources. A product can be added to eligible collections from its own details page. This supports offering product selection plus an optional rule mode, with clear membership behavior. [Creating collections and adding products](https://help.shopify.com/en/manual/products/collections/create-collection), [legacy manual collections](https://help.shopify.com/en/manual/products/collections/manual-shopify-collection), [legacy smart collections](https://help.shopify.com/en/manual/products/collections/smart-collections).
- **Discounts are a useful conditional-form analogy, not a pricing model to copy.** Shopify exposes fixed amount versus percentage as a choice, then conditionally reveals product/collection eligibility, minimum requirements, customer eligibility, usage limits, combinations, active dates, and optional grouping tags. That shows how to reveal fields after a mode choice and group related controls. Discounts are checkout promotions with their own semantics, so their eligibility, usage and timing sections do not belong in decoration pricing by default. [Amount off discounts](https://help.shopify.com/en/manual/discounts/discount-types/percentage-fixed-amount), [Managing and editing discounts](https://help.shopify.com/en/manual/discounts/managing-discounts).
- **Shipping profiles are the closest reusable product-scope plus rate analogy.** A custom profile has a name, assigned products, then location, zone, and rate sections; a product or variant can belong to only one shipping profile at a time. Shopify is gradually moving merchant shipping from profiles to shipping options by market, so use this only for the established resource-editor shape and separation of product scope from rates, not as an assumption that Insignia needs Shopify's hierarchy. [Shipping profiles](https://help.shopify.com/en/manual/fulfillment/setup/shipping-profiles), [Setting up and managing shipping profiles](https://help.shopify.com/en/manual/fulfillment/setup/shipping-profiles/setting-up-shipping-profiles).

These public help pages document workflows and link to Shopify's diagrams/previews. The logged-in Shopify reference was not used here; the parent task observed only the shipping profile surface, and no new native collections or discounts observation is claimed.

## Backend boundary

The current canonical spec describes `DecorationMethod` as a stable merchant-defined label with optional storefront labels and allowed artwork constraints. Each `ProductConfig` belongs to one Shopify product; published revisions freeze the final method × placement × size price table, and editing the catalog must not mutate published revisions indirectly. New Lean offers use final per-product placement prices and exclude setup fees, quantity tiers, layered inheritance, and FX. See [implementation plan](../../../architecture/implementation-plan.md#31-configuration-and-publication) and [current method workflow proposal](decoration-method-workflow-proposal-2026-10-21.md).

Therefore, the index/detail shape is a UI recommendation, not evidence of data support. Real central assignments need stable shared method IDs plus an explicit product-assignment relationship and clear draft/publication semantics. Tag or attribute rules need persisted predicates and deterministic matching. A method-level pricing mode/default needs a specified precedence and snapshot rule, then matching domain, API, product-editor, buyer projection, and immutable revision changes. Keep current product-scoped final prices as the source of truth until that contract changes; do not present a global method price or dynamic assignment as live when it is only a copied value.
