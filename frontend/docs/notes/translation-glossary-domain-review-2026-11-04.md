# Translation glossary: domain review

4 November 2026. Source review for the localization work. This note defines the product concepts that translated copy must preserve. It does not approve Dutch terms or add locale catalogs.

## Evidence status

The English source catalogs are the current copy baseline, not proof that every label has been accepted as final terminology. Definitions below are grounded in the selected catalog strings, current domain contracts and the implementation plan. “Catalog” means the copy appears in `packages/localization`; “contract” means a type or architecture rule establishes the distinction; “selected preview” means copy or behavior belongs to the chosen design prototype, whose Shopify connection is still unverified. Where a preview’s behavior differs from the intended integration, the note says so.

## Ownership rules

| Text | Owner and translation treatment |
| --- | --- |
| Buttons, instructions, validation, statuses and generic fallbacks authored by Insignia | App-owned UI copy. Translate through the appropriate audience catalog. Never use a translated sentence as a state code or branch condition. |
| Product, variant, option and value names; method and library names; view and placement names; decoration-size labels; tags; filenames; saved descriptions; order/history labels | Merchant- or Shopify-supplied content. Preserve the exact value and interpolate it into translated sentences. Do not silently machine-translate or rewrite saved labels when the interface language changes. Existing names such as “Front” or “Small” remain saved merchant content. |
| Insignia-generated default labels | A localized name may be used when a new entity is created. After it is saved, it is merchant content. Locale switching must not rename it. |
| Translation Settings overlay | The merchant edits sparse plain-text overrides for customer/common message IDs and exact placeholders. Empty fields use shipped English. The overlay changes customer copy, not staff language, product data or Shopify’s published language. |
| IDs, enum values, coordinates, currency codes, amounts, file types, URLs and request/cart identifiers | Technical or domain data. Keep values stable and localize only their surrounding explanatory copy. |

## Translation traps to carry into implementation

- Keep labels for merchant product choices distinct from Insignia interface wording. Use provenance from the data model, never English-word matching, to decide which text is translatable.
- Keep `view`, `position`, `size`, `method`, `default`, `remove`, `restore` and `save` contextual. The definitions above apply to the stated owner and workflow; identical English words elsewhere may have a different domain meaning.
- Preserve named placeholders and supplied names as values. The customer wording validator requires plain text and exact placeholder names; translated text must not modify interpolation values or add markup. See [localization README](../../../packages/localization/README.md#merchant-authored-customer-wording).
- Keep the local customer preview, the selected editor-launched preview, and the separate `apps/storefront` integration UI as distinct evidence. A preview success does not establish Shopify host behavior or cart mutation. See [localization inventory](localization-step1-inventory-2026-11-03.md#text-ownership-and-migration-map) and [cart audit](customer-cart-state-audit-2026-10-28.md#scope-correction-shopify-owns-the-customer-cart).

## Follow-up review of the translation-review skill

4 November 2026. Read-only cross-check of `.agents/skills/insignia-translation-review/` against this source review and the current wording runtime.

- Override reset and fallback statements are accurate. Resetting a form removes only that form from the in-memory draft. Resetting a locale clears that locale’s custom messages while retaining the locale and other records. Both remain unsaved until Save. A missing/blank override falls back to the English catalog; the customer translator applies an overlay only when its canonical locale exactly matches the requested customer locale. See `customer-translations-state.ts`, `customer-wording.ts`, `customer.ts` and the [package guide](../../../packages/localization/README.md#merchant-authored-customer-wording).
- Buyer host scope is accurate. Shopify owns product page, cart and checkout. The selected Designer is still a local preview with test completion receipts; an Add/Update action there is not evidence of a Shopify cart mutation. The glossary points to both [customer prototype status](../../../../designer-prototype/README.md#L11) and [repository boundary](../../../AGENTS.md#L5).
- The initial audience ambiguity is resolved in the current [Dutch brief](../../../../.agents/skills/insignia-translation-review/references/dutch.md#L3): it now states that the current Settings editor overrides customer/common copy only, and that Dutch authoring does not translate the admin Settings screen or add a bundled Dutch catalog. No Dutch UI catalog is inferred from this brief.
- The glossary’s short catalog/file references resolve through its new source map. The Dutch terminology choices are explicitly proposed, and the Shopify/Microsoft references support terminology/register evidence without claiming native review.
