# Independent translation options review

30 October 2026. Research only. No dependencies or application code changed.

I recommend **i18next core with a small native Preact provider and hook**. Keep the library responsible for message lookup, language fallback and plural selection. Keep Insignia responsible for choosing the correct Shopify locale, loading the right catalogues and rendering translated text safely. A React wrapper is unnecessary.

## Fit with this repository

The merchant UI uses Astro with native Preact islands and Polaris Web Components. The selected customer design is the sibling `designer-prototype`, currently native Preact 10.29.8 and Vite 6.4.4. `apps/storefront` is a separate integration UI. The translation boundary must work in all three without changing their framework or confusing their design responsibilities. Existing admin components already use locale-aware number/date formatting, but that does not translate their English UI copy. The current backend label maps do not constitute locale-keyed product translations.

These priorities determine the recommendation, in order: preserve native Preact and Astro rendering; prevent untranslated or incorrectly pluralized UI; keep types and extraction maintainable for agents; then optimize translator tooling and delivered catalogue size. The comparison below is an engineering judgment, not a benchmark.

| Option | Strongest fit | What Insignia would still own | Assessment |
| --- | --- | --- | --- |
| i18next core plus native Preact adapter | Framework-independent runtime, fallback and plural rules, typed resource support | Locale ownership, context subscription, initial loading, extraction configuration and completeness checks | Best fit for the current repository |
| Lingui core plus native Preact adapter | ICU messages, extraction and compiled catalogues | Native Preact adapter, macro/compiler integration across build and test paths | Credible alternative if its translator workflow becomes a priority |
| Custom typed catalogue plus IntlMessageFormat | A small application-facing API with ICU formatting | Lookup, fallback, resource loading, extraction, type generation, diagnostics and context integration | More maintenance responsibility than the initial wrapper suggests |

## What the libraries actually provide

i18next core has no React runtime requirement. Its API supports independent instances, initialization promises and resource events, so a small native Preact adapter can subscribe and unsubscribe without `react-i18next` or `preact/compat`. Use a fresh server instance per request. Do not change the language on a process-wide singleton. Client instances should also be independent where separate embedded configurators can have different locale contexts. [Package source](https://raw.githubusercontent.com/i18next/i18next/master/package.json), [instance and initialization API](https://www.i18next.com/overview/api).

i18next uses `Intl.PluralRules` categories and expects `count`; one/other is not sufficient for every language. It supports language variants and explicit fallback languages. Set production fallback deliberately to a shipped language instead of accepting the development-language default. Missing resources can still end in a visible raw key, so runtime fallback must be backed by CI checks. [Plural rules](https://www.i18next.com/translation-function/plurals), [fallback behavior](https://www.i18next.com/principles/fallback).

Type safety requires setup. Current i18next types support resource augmentation and selectors; newer versions add stricter namespace selectors and interpolation parsing. Preserve literal resource types or generate declarations from JSON. Enable strict checking and test that wrong keys and missing required arguments fail compilation in our chosen version. Do not promise parameter safety merely because JSON exists. The repository documentation and source are more current than parts of its website. [Current TypeScript documentation source](https://github.com/i18next/i18next-gitbook/blob/master/overview/typescript.md), [type options source](https://raw.githubusercontent.com/i18next/i18next/master/typescript/options.d.ts).

The official i18next CLI supports extraction, type generation and linting, including translation parameter checks. Its default parser covers JS, TS, JSX and TSX. Adding `.astro` to a glob does not teach it Astro syntax; that needs a plugin or a deliberately supported extraction path. Polaris text attributes and Insignia's helper names also need explicit lint/extraction configuration. Verify this against actual files before claiming full coverage. [Official CLI](https://github.com/i18next/i18next-cli).

Lingui is not React-only. Its core can work with ordinary JavaScript and independent instances. However, the official React binding has a React peer dependency, and the examined documentation does not provide a first-party native Preact binding. Using `@lingui/react` would contradict the native Preact direction. Using core with our own adapter is possible. [Core API](https://lingui.dev/ref/core), [core package](https://raw.githubusercontent.com/lingui/js-lingui/main/packages/core/package.json), [React package](https://raw.githubusercontent.com/lingui/js-lingui/main/packages/react/package.json).

Lingui's extraction and compiled ICU catalogues are useful. Current tooling supports Node 22.19 or later and Vite 6.3, 7 and 8, so the sibling's Vite 6.4.4 is within its published peer range. This is an integration cost, not an incompatibility claim. Its opt-in typed message IDs check IDs; separately verify placeholder contracts. Macro transformation must also work in Astro and the repository's direct esbuild test paths. [Installation](https://lingui.dev/installation), [Vite plugin manifest](https://raw.githubusercontent.com/lingui/js-lingui/main/packages/vite-plugin/package.json), [typed IDs](https://lingui.dev/guides/typed-message-ids).

IntlMessageFormat is framework-independent and handles ICU messages and plural selection. It can consume precompiled message ASTs. Its typed values contract does not automatically infer required arguments from an arbitrary message string; generated contracts or tooling must connect the two. It is a formatter, not an entire translation system. A custom implementation would still need catalogue management and all the failure behavior described below. Hand-writing plural grammar with `Intl.PluralRules` is unnecessary when an established message engine already handles it. [IntlMessageFormat documentation](https://formatjs.github.io/docs/intl-messageformat/).

## Proposed implementation rules

Use one shared localization package for supported locales, source catalogues, generated types and formatting policy. Keep separate merchant, customer and common namespaces so the buyer does not download admin copy. Avoid one enormous provider that makes the application state machines depend on localization.

Keep stable status/error codes and values in reducers, persisted state and API payloads. Translate at rendering time. A language change must not rewrite a saved configuration, change a cart identity or recompute accepted prices. Merchant-authored product, placement and method names are content, not translation keys. Translating those later requires locale-keyed backend content and API contracts.

Resolve and load the initial language before marking a page or island ready. If Astro renders translated content, its client must hydrate with the same language and initial resources. During an explicit language switch, keep the current usable screen until the next catalogue is ready, then activate it atomically. Ignore stale load completions. If loading fails, retain the previous usable language or the already bundled fallback instead of a blank screen or a page of keys. i18next supports bundled resources and lazy resource loading; the exact readiness and retry behavior remains application logic. [Resource loading](https://www.i18next.com/how-to/add-or-load-translations).

Use an allowlist of local language/namespace imports. Do not build arbitrary fetch paths from user input or require a remote translation service for runtime availability. The main research should define Shopify's merchant versus customer locale precedence. Browser detection must not silently override a locale already selected in Shopify.

Render translated strings as text or component properties. Do not introduce raw catalogue HTML or `dangerouslySetInnerHTML`. i18next escapes interpolation by default; native Preact text rendering also escapes. Choose the rendering-specific setting deliberately to avoid double escaping while preserving safety. Rich links need an explicit structured component mechanism, and dynamic URLs still require their own validation. Never mark merchant names or uploaded content as safe HTML. [Interpolation and escaping](https://www.i18next.com/translation-function/interpolation).

Before rollout, verify key and placeholder parity, required plural forms, empty strings, accessible labels and locale-specific formatting. Include initial-load failure, missing namespace, stale language-switch completion, concurrent SSR requests, long translations, direction changes and number inputs in tests. Check representative EN/NL copy plus a language with more plural categories, even if that language is only a test fixture. Reuse the existing meaningful reducer tests, and add focused rendering checks rather than duplicating every UI test for every language.

The result should be a thin custom integration around an established engine. Building our own translation engine would save a dependency and make Insignia responsible for the difficult parts that dependency already solves.

## Main research decision and Shopify ownership

The main review agrees with the independent recommendation. Use i18next core behind a small shared API and a native Preact adapter. No paid translation service is necessary. Start with complete interface catalogues and keep the existing English source as the bundled fallback. The frontend can adopt this before backend integration, using an explicit locale in the local host and later receiving that locale from Shopify.

The merchant interface should follow the admin user's language. Shopify's browser-side config API identifies this as the user's chosen language, explicitly distinct from the shop's customer-facing locale. Do not assume that browser-side App Bridge config is already available to Astro on the server. When the server cannot establish the same locale, resolve it and load its catalogue before the existing page readiness coordinator reveals localized content. [Shopify config API](https://shopify.dev/docs/api/app-home/latest/apis/authentication-and-data/config-api).

The customer configurator should receive the selected storefront language from its Shopify host. Liquid exposes that language through `localization.language`; country is a separate value. Preserve language-region and script information during resolution. Never infer language from currency, Market or country alone, and never let browser detection override an explicit Shopify selection. Language changes must not alter the order currency or accepted monetary amounts. [Shopify localization object](https://shopify.dev/docs/api/liquid/objects/localization).

Theme app extensions have their own storefront and schema locale files. These should translate the Personalise trigger and extension settings where appropriate. Shopify states that merchants cannot edit theme app extension storefront locale files, so those files are not a merchant override editor for Insignia's private product configuration. The backend's current single-language `MerchantLabelsSchema` maps need an explicit per-locale content model if translated merchant names become part of scope. Interface localization alone does not require building that feature or a new Settings page. [Theme app extension configuration](https://shopify.dev/docs/apps/build/online-store/theme-app-extensions/configuration).

The first implementation should verify the chosen pinned library version against real Astro, TSX and Polaris text attributes, then cover catalogue completeness, interpolation contracts, plurals, load failure, request isolation and locale changes during an active design. Include expanded-text checks on desktop and short phones. Do not promise right-to-left support until layout, directional controls and product geometry have been reviewed separately.
