# Reducer and state-machine audit

27 October 2026. Read-only audit of the current Insignia working tree, prepared as a proposal for making frontend state easier to read and change with AI coding tools. No application code or tests were changed or run for this audit. The repository already had extensive unrelated local edits; findings refer to the files as they exist in this checkout.

## Recommendation

Use reducers where a small set of events must keep one workflow's coupled state coherent. Do not replace local state wholesale, and do not put domain drafts, server snapshots, side effects, canvas instances, or undo history into one page reducer. The strongest low-risk pilot is the local placement preview's manual photo-picker session, after the owner has finished reviewing the current frontend design. Follow with movement-area or image-measurement edit sessions if the first extraction makes their transitions clearer.

This follows the deep-module test: give callers a short event interface and put transition rules behind it. A reducer should own one meaningful workflow, not become a forwarding layer for every setter. Do not claim a coding-speed or defect-rate gain without measuring it.

## Bounded candidates

### 1. Manual variant-photo picker session — recommended pilot, preview only

The preview editor represents the shared Add views, Change view image, and manual variant-photo assignment dialog with related flags and selections. The relevant state is spread across `addingView`, `replacingImage`, `variantImageTargets`, `viewImage`, `viewImages`, `imageSelectionReady`, and `imageProcessing` in `apps/web/test/admin/support/placement-workflow-preview.tsx:223-233,280-304`. The mode is opened and reset through separate setters at `:377-418,1045-1056`, and the same dialog branches on those flags to choose its heading, actions, selection shape, and commit behavior at `:3445-3576`.

Those fields jointly define one picker intent and a short lifecycle: open for a purpose, select, wait for the selected image to load, commit or cancel, and optionally continue to the next missing group. They are more valuable to model together than independent gallery query/filter state. The visual/media `ImagePicker` already guards callbacks by active component, image ID, URL, and retry attempt (`apps/web/test/admin/support/placement-image-picker.tsx:133-147`); any parent readiness callback added to the reducer should also carry a picker-session ID so an old image event cannot enable a newly opened session.

Keep `product` out of this reducer. `setProduct` is the existing owner of immutable draft updates and history: it prunes assignments, records one history entry, updates the current-product ref, and renders the new product (`placement-workflow-preview.tsx:128-135`). On Use, the event handler should call the existing `setVariantPhotoImage` with all target keys and the staged image in one candidate (`placement-variant-photos.mts:345-369`), then pass that candidate through `setProduct` once. Use and next should commit that same single assignment once, then move the picker session to the next blank target. Cancel should close the session without changing product or history. Keep newly uploaded `pickerImages` staged until Use; do not publish them into `product` in a separate write.

A minimal interface could be a discriminated picker intent (`closed`, `add-views`, `replace-view`, `assign-variant-image`) plus named events for opening, selecting, readiness, next, cancel, and commit completion. It should not own product snapshots, history, or a queued command interpreted from an effect. This gives the test seam a pure transition function while preserving the existing owner and per-assignment atomicity. The recently corrected manual flow's explicit targets, optional next, same-photo bulk behavior, and per-image recovery are documented in `manual-photo-assignment-2026-10-27.md`; do not reopen its UI decisions as part of a state-only pilot.

### 2. Movement-area and measurement editing — second local preview candidate

These canvas tasks have mutually exclusive modes and separate uncommitted drafts. Drawing mode/target and movement draft/error live at `placement-workflow-preview.tsx:283-287`; measurement mode, point line, distance text, coordinate-entry state, point text, and error live at `:289-299`. Start/cancel/complete transitions are implemented as setter sequences at `:1136-1188,1215-1249,458-465`; `select` cancels measurement, movement editing blocks selection, and save/publication also check active edit modes (`:1610-1617,1685-1701,1777-1783`). This is a good follow-up if the photo-picker seam proves useful, but it touches canvas behavior and has more geometry and validation paths.

If modeled, keep movement and measurement drafts inside an interaction/session state until validated Apply. `completeMovementAreaEdit` currently validates containment, then patches the product once; `applyMeasurement` parses the calibration schema, patches the view once, and closes the session. Preserve those commit points and `setProduct` history semantics. Keep Konva/Visualizer refs, pointer capture, animation frames, focus, and canvas DOM state outside the reducer. The persisted product geometry remains the domain draft; the reducer owns only the active interaction and its temporary text/rectangle/error.

### 3. Methods dialogs and staged product selection — mostly explicit already; low priority

The local `PlacementMethodManager` already declares its navigation as a `PriceScreen` union (`methods`, `prices(methodId)`, `create`) and its method-catalog request as `loading | ready | error` (`placement-method-manager.tsx:7-8,47,80-84`). Its local `draft` remains separate from product state; the parent applies it once through `setProduct` in `placement-workflow-preview.tsx:3352-3387`. The Methods product picker also stages `ids` and collection selection locally and has an explicit Apply/close seam (`method-product-picker.tsx:32-58,280-301`; parent callback at `method-workflow-preview.tsx:779-789`). Search, filters, and pagination are independent navigation state and need not move into a reducer merely because they sit in the same dialog.

These existing unions and commit seams already communicate much of the workflow. Consider a reducer only if a concrete follow-up adds transitions that must reset or retain several values together. Avoid a page-wide modal reducer that combines price editing, product browsing, route confirmation, and unrelated delete/duplicate dialogs.

### 4. Merchant product draft save/publication — valuable state-machine seam, production and high consequence

The production `MerchantConfigEditor` already has a `SaveState` union (`clean | dirty | saving | saved | conflict | ambiguous`) at `apps/web/src/islands/MerchantConfigEditor.tsx:93`, while save behavior also depends on `busy`, `pending`, `requestId`, `editLocked`, and their refs at `:487-525`. The save handler at `:932-1087` validates the acknowledged version, retains an exact idempotent request, distinguishes validation rejection from 409 conflict and uncertain transport outcomes, then reconciles against a fresh read. Publication has a separate pending request and a separate read/continuation lifecycle at `:595-649,1089-1212`.

This is a plausible future state-machine extraction, but a broad reducer that merges save and publication would obscure distinct server histories and retry rules. If pursued after the frontend presentation work is accepted, start with a pure save-transaction transition model and preserve request keys, version checks, stale-request guards, and server readbacks as they are. Do not place `Visualizer`, refs, fetches, storage, or the saved active revision in reducer state. One review target for implementation is the unguarded `setBusy(false)` in the save `finally` at `:1085-1086` after multiple stale-epoch early returns; this audit did not establish that a newer operation can overlap that finalizer, so treat it as a reachability question, not a confirmed bug.

Draft edits, saved draft baseline, latest server conflict, and active publication are different authorities. Dirty state should remain derived from draft versus its baseline where possible; immutable accepted/published history must not become a mutable reducer snapshot.

### 5. Buyer quote/cart lifecycle — existing reducer to learn from, tighten only with qualification

The buyer storefront already uses `buyerReducer` in `apps/storefront/src/customizer.tsx:24-110,162`. Its state includes config/group, selected view/placement/variant, proposal/accepted cart, workflow phase, and error; the action union names the main changes. The generic `phase` action accepts every phase value at `:42,104-105`, so transition legality is less visible than it could be. This is a maintainability opportunity, not evidence of a user-visible bug. The phase set also serves different valid operations: clear can end in `applied` without an accepted quote (`:48-55`), and removal uses `applying` without the add/replace acceptance path (`:484-509`). Model the operation context explicitly if this is changed; do not assert one payload is required for every terminal phase.

The quote workflow includes repricing, authorization, cart mutation, uncertain mutation recovery, and renewal; examples are at `:380-555`. Keep these effects and request identities outside a pure reducer. `createRequestLane` already centralizes abort/generation handling at `apps/storefront/src/buyer.ts:83-99`. The wizard index, close confirmation, preview sheet, artwork upload and canvas refs are presentation or imperative state (`customizer.tsx:153-187`) and should remain separate unless a demonstrated transition requires otherwise. Buyer visual fidelity is currently deferred in `docs/delivery/state.md:224`; do not use a state refactor to redesign it.

## State placement rules

- **Reducer state:** mode and payload that must change together; temporary, local workflow state; transitions with explicit commit/cancel outcomes.
- **Independent local state:** search text, current filters, expanded rows, preview zoom, and input text that has its own editing/validation cadence. Keep text fields locally controlled unless they participate in a multi-field transaction.
- **Domain/server state:** merchant product draft, saved baseline, publication, buyer proposal/accepted quote/cart, and photo assignments. Keep the existing domain functions and server adapters as the authorities; reducers can decide when a commit is allowed, not duplicate the domain record.
- **Effects and refs:** request IDs, `AbortController`, idempotency keys, timers, session storage, DOM modal/field refs, renderer instances, pointer capture, and focus restoration remain in the effect/adapter layer. Reducers stay pure and do not dispatch writes from `useEffect`.
- **History and dirty state:** preserve the existing history owner and commit granularity. Derive dirty state against the saved baseline rather than maintaining another synchronized boolean when practical. A picker cancel must not add history; one chosen photo assignment must remain one history step.

## Scope and evidence limits

The placement workspace, manual photo flow, Methods explorations, image picker, and their tests under `apps/web/test/admin/support` are injected only by the loopback preview host. `README.md` describes them as frontend-only; the placement implementation note states that retiring the preview host removes these modules and restores the production route. They are useful low-risk design/test seams, not production data flows. `MerchantConfigEditor` and `apps/storefront/src/customizer.tsx` are actual application source. `designer-prototype` is a separate sibling; this audit does not treat it or `masking-editor-lab` as production Insignia source.

The repository guidance says the merchant UI remains owner-unaccepted and assigned to a presentation rebuild (`AGENTS.md`, `README.md`, `docs/delivery/state.md:223-224`). That makes this a proposal only. Keep the user's frontend-design-first ordering: settle the screens and interaction contract first, then make a state-only pilot with no visual changes, using the existing preview workflow/browser test seam. This audit did not rerun the historical tests described in delivery notes and does not establish owner acceptance, Shopify-native behavior, or production qualification.
