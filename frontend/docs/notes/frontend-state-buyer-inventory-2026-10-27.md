# Buyer frontend state inventory

Read-only inventory supplement for the frontend reducer/state-machine adoption plan, 27 October 2026. No application code changed. This records the production buyer surface, adjacent preview/prototype surfaces, current state/effect owners, and a proposed grouping for a complete frontend plan. It is not approval to implement a refactor.

## Production buyer state and effect ownership

### Entry, customizer, and current state

- The theme element dynamically imports `BuyerCustomizer` on first use, checks a generation token after the import, and renders it inside a shadow root. The repair custom element listens for `insignia-cart-updated`, reads `/cart.js` with an `AbortController`, rejects stale/disconnected callbacks by controller identity, then offers a repair-mode buyer control when it observes an Insignia cart line ([`element.tsx`](../../../apps/storefront/src/element.tsx#L39-L83), [`element.tsx`](../../../apps/storefront/src/element.tsx#L85-L132)).
- The production buyer already has one typed reducer: [`State`, `Action`, and `buyerReducer`](../../../apps/storefront/src/customizer.tsx#L24-L110). It stores config, the current `DesiredGroup`, active view/placement/variant, quote proposal and accepted-cart observation, plus a `phase` union. The `phase` event accepts any phase from any current state, and fields such as `config`, `group`, `proposal`, and `accepted` are optional independently, so the type does not currently encode which combinations or phase/event transitions are valid. This is a modeling opportunity, not proof of a checkout defect.
- `accepted` and `proposal` are legitimate UI observations of server-issued data. The boundary to preserve is that displayed workflow context is not server authority: the server still validates proposal acceptance and Shopify Functions authorize the purchase. Do not impose a blanket rule that reducers cannot contain these observations.
- Separate hook state holds dialog open/close confirmation, preview sheet and zoom, wizard index, default artwork/method, override/error lists, uploaded asset and preview records. Refs hold DOM/canvas/renderer, the latest render scene, retained groups/cart baseline, editing index, restored quote, deferred-art intent ID, override assets, and accept/renew idempotency keys ([`customizer.tsx`](../../../apps/storefront/src/customizer.tsx#L153-L189)). Some state is transactional draft context; some is presentation, resource ownership, or a synchronous handle. A future pass should assign each fact one owner rather than mechanically replacing every `useState` with reducer events.
- The wizard and previews cover upload, placement, size/preview and quantity/review; editing a retained design, reviewing all retained groups, accepting the offer, applying the vector, removing customized lines and renewing a previously accepted offer are separate routes through the same component ([`customizer.tsx`](../../../apps/storefront/src/customizer.tsx#L793-L838), [`customizer.tsx`](../../../apps/storefront/src/customizer.tsx#L1121-L1403)). There is no in-browser draft undo/history here. `retained.current` is a set of restored design groups from server cart state; the cart mutation journal is recovery state, not user undo.

### Async request and artwork ownership

- Opening the modal starts a request lane, loads buyer config, reads the current native cart, and restores server cart-state. A stale request ID is checked before setting the baseline/retained groups and dispatching `loaded`; cleanup cancels the lane, closes the dialog, restores scroll state and returns focus ([`customizer.tsx`](../../../apps/storefront/src/customizer.tsx#L198-L238)). `createRequestLane` aborts its previous controller and increments a generation on `next()` or `cancel()` ([`buyer.ts`](../../../apps/storefront/src/buyer.ts#L83-L99)).
- `review()` reads the cart, checks the captured fingerprint when editing a retained group, reloads cart state, fetches current configs, validates each group against current policies and then requests a server quote. It dispatches the proposal/error only while the request lane still owns the operation ([`customizer.tsx`](../../../apps/storefront/src/customizer.tsx#L380-L453)). This is an existing suitable owner for read/review cancellation and stale-result rejection; do not recreate a generic request controller inside a reducer.
- The buyer calls the shared guest artwork component with an injected buyer API. Upload lifecycle stays in [`useArtworkUpload`](../../../apps/web/src/islands/use-artwork-upload.ts#L11-L49): it owns upload/preview/pending values, active `AbortController`, lease expiry timers, selection changes, preview renewal and stale-completion checks against the current asset ID. [`createArtworkUpload`](../../../apps/web/src/islands/artwork-upload.ts#L46-L203) validates file/admission/preview/status data and runs upload completion/status polling. Keep those commands and timers out of `buyerReducer`; the buyer should store the committed artwork choice in its design draft, not a second authoritative copy of the upload lease.
- The standalone `<insignia-artwork-upload>` element emits only asset ID and expiry in a non-bubbling/non-composed custom event; its host is not the buyer’s cart/quote flow ([`element.tsx`](../../../apps/storefront/src/element.tsx#L4-L37)).
- Persistence is deliberately split: the buyer API stores a private session capability/session ID/expiry hint in `sessionStorage` and treats invalid hints as non-authoritative; the cart journal stores unresolved/digest intent state in `localStorage`; the design groups/cart snapshot remain server/cart observations or in-memory refs ([`buyer.ts`](../../../apps/storefront/src/buyer.ts#L154-L207), [`buyer.ts`](../../../apps/storefront/src/buyer.ts#L231-L245), [`customizer.tsx`](../../../apps/storefront/src/customizer.tsx#L181-L188)). The React prototype’s nonce-keyed `sessionStorage` cache is a separate preview transport ([`admin-preview.tsx`](../../../../designer-prototype/src/admin-preview.tsx#L301-L356)).

### Canvas and render state

- The buyer creates and destroys the visualizer from an effect, stores it in a ref, forwards placement-selection commands as reducer events, derives a scene with `buildBuyerScene`, and updates the imperative renderer ([`customizer.tsx`](../../../apps/storefront/src/customizer.tsx#L240-L277)). Keep the renderer, DOM focus, touch/pointer mechanics, and visual scene updates in their existing imperative/presentation owners. Keep semantic selected view/placement and committed design facts in buyer state where they affect later user-visible decisions.
- The buyer uses the visualizer for preview and selection; the editor geometry command model in [`geometry.ts`](../../../packages/visualizer/src/geometry.ts#L342) is a separate merchant authoring concern. It should not be introduced as a second buyer store merely because both surfaces render the same geometry package.

### Quote acceptance, cart mutation, and recovery

- `accept()` checks proposal expiry, calls server acceptance with an idempotency key retained per proposal, then passes the returned `AcceptedCart` into `apply()`. `apply()` updates the browser cart via the Ajax adapter and sends a best-effort server confirmation; it distinguishes an applied-but-late-effect warning from a clean applied result ([`customizer.tsx`](../../../apps/storefront/src/customizer.tsx#L455-L483), [`customizer.tsx`](../../../apps/storefront/src/customizer.tsx#L512-L533)). `renew()` rechecks the observed cart fingerprint and uses a quote-scoped idempotency key before applying the newly issued accepted cart ([`customizer.tsx`](../../../apps/storefront/src/customizer.tsx#L535-L556)).
- The cart adapter is an independent stateful effect/recovery owner. It documents that Ajax is non-transactional and only Shopify Functions authorize purchase; it validates cart input, takes a browser lock where available, compares fingerprints, writes a digest-only intent before dispatch, performs native `cart/update.js`/`cart/add.js` calls, rereads the cart to verify the resulting vector and returns `review_required` for changed/unresolved/mismatched outcomes ([`cart.ts`](../../../apps/storefront/src/cart.ts#L1-L22), [`cart.ts`](../../../apps/storefront/src/cart.ts#L118-L147), [`cart.ts`](../../../apps/storefront/src/cart.ts#L158-L176), [`cart.ts`](../../../apps/storefront/src/cart.ts#L240-L407)). `cartJournal` persists intent flags/digests in local storage; it does not persist a draft or cart payload ([`buyer.ts`](../../../apps/storefront/src/buyer.ts#L231-L245)).
- Removing customized items and `repair` use the same verified adapter with an empty desired vector, then clear restored UI context only after observed success; a recovery warning explicitly says an earlier update may still arrive ([`customizer.tsx`](../../../apps/storefront/src/customizer.tsx#L484-L510)). Cancellation, reducer reset, or closing a dialog cannot roll back an already dispatched server/theme mutation. Any future reducer should report an operation’s observed result and leave reconciliation to this adapter/server boundary.
- Current tests already pin key behavior: request-lane stale response ownership, complete-cart price review/acceptance and customer dialog behavior are in [`buyer.test.mts`](../../../apps/storefront/test/buyer.test.mts#L26-L33) and [`buyer-browser.test.mts`](../../../apps/storefront/test/buyer-browser.test.mts#L41-L100); lost cart acknowledgement is refetched but never automatically re-dispatched, and external cart changes invalidate review, in [`cart.test.mts`](../../../apps/storefront/test/cart.test.mts#L96-L132). Browser tests also cover renewal, incompatible configuration, repair and mobile preview; see the named cases in [`buyer-browser.test.mts`](../../../apps/storefront/test/buyer-browser.test.mts#L650-L729) and [`buyer-browser.test.mts`](../../../apps/storefront/test/buyer-browser.test.mts#L799-L873). These tests evidence current semantics; they do not mean a new state model is already verified.

## Proposed classification for the complete frontend plan

This classification is buyer-specific. It complements, and should not silently replace, a separate audit of production merchant islands.

| Area | Proposed approach | Scope boundary |
| --- | --- | --- |
| Buyer edit/review/accept/apply/repair UI | Refine the existing `buyerReducer` into a typed event transition model for the coupled lifecycle: a small finite workflow implemented as a plain reducer, with meaningful events/results and states that prevent impossible proposal/acceptance combinations. Carry request/operation identity on async result events where stale completion can still reach UI. Keep proposal/accepted response data as observed context. | Keep `review()`/accept/remove/renew network and cart commands outside the pure transition function. Make accepted cart application, removal completion, unresolved mutation and late-effects warning explicit outcomes; do not require an accepted quote for cart-removal completion. |
| Product/config/cart data and authority | Keep API parsing, current config compatibility checks, exact-money formatting, server quote/accept/renew, and observed native cart in their existing domain/API/service boundaries. | Reducer state describes the UI’s current observation and intent. It does not authorize access, create a quote, set a price, guarantee availability, or validate checkout. |
| Artwork upload and preview lease | Keep the shared `useArtworkUpload`/`createArtworkUpload` lifecycle separate. If future work needs a stricter tagged upload status, model it within that upload owner after mapping pending, usable, failed, renewed and expired semantics. | Do not move file bytes, timers, `AbortController`, signed URLs, or preview lease ownership into the buyer workflow reducer. The buyer design draft may refer to the selected immutable asset/revision. |
| Native Shopify cart + recovery | Keep `createAjaxCartAdapter`, lock, journal, read-after-write checks and server confirmation as an external effect owner. Model its typed result as a buyer workflow event. | An aborted/lost Ajax response is not rollback. Only return to a clean state after observed adapter result; keep the existing no-automatic-redispatch recovery rule. |
| Canvas, preview sheet, modal and wizard | Leave refs, renderer, focus management, animation/touch details and mostly independent presentation values local/imperative. Keep semantic design selections in buyer data; keep navigation guards simple and testable. | Do not put high-frequency pointer state, DOM nodes, object URLs, or every boolean into a global machine. |
| Production theme custom elements | Keep their custom-element lifecycle and repair detector as host/controller logic; emit domain-relevant buyer events only where the integration contract requires them. | Treat Liquid settings and host attributes as input boundaries and keep product/currency/cart facts validated at the server boundary. |
| React prototype and test preview bridge | Leave as separate contracts. Preserve nonce, `origin`, `source`, schema, timeout and session cache checks if the preview harness remains useful; prototype already validates message data with Zod before use. | TypeScript unions are not runtime validation for JSON, persisted state or `postMessage`. Do not infer that the live Preact buyer is integrated with this React prototype. |

### Suggested state/effect contract for later implementation planning

1. Treat review as a cancelable read/quote operation owned by the current request lane. Results that do reach the transition layer should carry request identity, and only current ownership may update buyer state.
2. Treat accept, cart apply, remove and renew as commands with server/cart-specific idempotency and reconciliation. Trigger them from the user handler/command boundary; send typed result events back. Do not replay commands by placing them in reducer state and draining a generic effect queue.
3. Keep the cart adapter’s durable uncertain-mutation intent, idempotency keys and native cart observations outside React/Preact state. A reducer can model what the UI should show for `review_required`, `applied`, `cleared` and warning outcomes, but does not become the recovery journal or authority.
4. Keep state placement scoped: buyer workflow facts in the buyer reducer; upload lease facts in the upload owner; cart transaction and recovery in the cart adapter; DOM and renderer in refs/effects; server-authoritative pricing/acceptance on the server and Shopify Functions.
5. Prefer a small model/event table plus focused reducer and command-boundary tests before changing UI. Preserve existing browser checks for native cart mutation, stale reads, expiry, recovery, customer-facing review and responsive preview. Do not claim speed or defect-rate improvements without before/after evidence.

No inspected buyer workflow currently requires XState specifically. The production buyer has linear user steps, a useful existing request lane, and a dedicated cart recovery adapter; a plain typed reducer can express the UI transition rules without moving those effect owners. Reconsider a state-machine library only against a concrete need in the complete frontend plan, using the version-qualified research in [state-machine options](state-machine-options-research-2026-10-27.md).
