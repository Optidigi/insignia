# Orders reference diagnosis

20 October 2026. Follow-up to the owner's rejection of the first Orders overview. The task agent inspected Shopify's live Orders page in Chrome and reported the current admin appearance: an Orders heading with order icon, a compact All menu, Search and filter and Display options controls, an open table with a subdued rounded header, tight rows and status badges with icons. This note records research against that reference. It does not claim that this research agent independently observed the native screen or that local fixtures reproduce Shopify's host.

## Why the first page missed the reference

The implementation followed the generic App Home resource-index example too literally. That example uses `s-section padding="none"` around the table. It does not reproduce every detail of Shopify's own Orders screen. The inspected implementation added a prominent labeled page-local select, a result-count line and a footer explanation. Those additions consumed space and changed the information hierarchy compared with the live reference. Its first screenshot also omitted the visible heading and header action because the preview supplied an incomplete host double.

Component validation checks supported element names, properties and types. It does not compare the rendered page with Shopify Orders, judge density or establish visual acceptance. Successful validation and browser behavior checks therefore did not establish the requested visual fidelity. No evidence here says that an automated validator failed.

The correction is to compare the composed page with the native reference, then choose supported components for the needed interactions. Shopify remains the primary source. A component catalog is a constraint on implementation, not a screenshot specification.

## Public composition and supported controls

Shopify's [index-table composition](https://shopify.dev/docs/api/app-home/v2.0-rc/patterns/compositions/index-table) supplies a scannable collection with search, filters, sorting, responsive headers and optional bulk actions. Its example uses a `filters` slot grid, a search field and icon button opening a sort popover. The public composition still contains a section wrapper. Treat that wrapper as an example, not proof that native Orders must have an outer card.

The [Table API](https://shopify.dev/docs/api/app-home/v2.0-rc/web-components/layout-and-structure/table) documents a header row followed by a body containing rows and cells. It does not list `s-section` as a required parent. The checked unmodified runtime also has no section-ancestor requirement in the table implementation. Putting `s-table` directly in the page or a neutral supported layout is therefore a reasonable composition to validate and inspect. Preserve `variant="auto"`, mobile `listSlot` assignments, currency alignment, `loading` and native pagination. There is no documented table density property; do not invent one or patch its shadow styles to force a match.

Use a small toolbar with only working controls. Avoid the large always-visible form row from the first pass. Supported building blocks are:

- A [menu](https://shopify.dev/docs/api/app-home/v2.0-rc/web-components/actions/menu) triggered by `s-button commandFor`. Menu children are buttons or sections. It provides keyboard navigation and compact related actions.
- A [popover](https://shopify.dev/docs/api/app-home/v2.0-rc/web-components/overlays/popover) for filter controls. Its documented display-options example contains `s-choice-list multiple` with selected choices for visible columns and a button with `command="--hide"` to apply and close. Only render a Display options control if column visibility actually works.
- [Button](https://shopify.dev/docs/api/app-home/v2.0-rc/web-components/actions/button) accepts `icon`, `accessibilityLabel`, `commandFor`, `command` and `variant`. An icon-only toolbar button needs an accessible name. The documented API does not provide a disclosure-suffix property.
- [Icon](https://shopify.dev/docs/api/app-home/v2.0-rc/web-components/media-and-visuals/icon) uses a predefined set. The installed exact types support `order`, `search`, `layout-columns-3`, `bullet`, `incomplete`, `select` and `status-active`. Broad catalog guidance suggested `complete`, which the installed types rejected; it was corrected before the successful build. `layout-columns-3` matches the reference's column glyph; `bullet` supplies a filled payment/completed-status dot. A live internal Shopify glyph need not have a one-for-one public equivalent. Validate the chosen supported icon and compare it visually.

The current endpoint supports only cursors and limits, not collection-wide search, sort or artwork filters. Shopify's [IndexFilters migration](https://shopify.dev/docs/apps/build/app-home/migrate-from-polaris-react/index-filters) couples query controls, table, pagination and backend query, and says to omit saved views when persistence is absent. A compact All dropdown must not imply saved views or global filtering that Insignia lacks. Page-local search or filters still need an explicit scope. Adding a global query requires backend work before such controls can promise all-order results.

## Badges

[Badge](https://shopify.dev/docs/api/app-home/v2.0-rc/web-components/feedback-and-status-indicators/badge) supports `tone`, `color`, `icon`, `iconPosition` and `size`. Use base size in tables and short self-contained labels. The [badge migration guide](https://shopify.dev/docs/apps/build/app-home/migrate-from-polaris-react/badge) explicitly removes React's `progress` property. It recommends clear labels and a supported icon when it reinforces the meaning. A native filled or partial pip is not permission to reintroduce `progress` or a custom SVG.

For Insignia's artwork column, evaluate `incomplete` with Artwork needed and a supported completed-state icon with Artwork complete. Keep locking and expiry distinct. A Payment column can use the actual DTO financial status if added; a native Unfulfilled badge cannot be inferred from artwork readiness. Check actual glyph appearance, tones and density beside the live reference.

## Why the local heading disappeared

The checked runtime fixture is the unmodified public `polaris-2.0-rc.js`, SHA-256 `89dd2052b7b8cc6b042900f5c044e1f5754e31bf769d205b6e2399992bdb0c7b`. Its Page implementation derives embedded mode from the presence of `window.shopify`. In embedded mode it suppresses its local header. The existing preview's `{idToken, loading}` object triggers that mode but does not implement the surrounding Shopify title bar. This explains the missing painted heading and Refresh action; it does not establish a product rendering defect in the real host.

[Page](https://shopify.dev/docs/api/app-home/v2.0-rc/web-components/layout-and-structure/page) owns the page heading and page actions. [App Bridge title bar](https://shopify.dev/docs/api/app-home/v2.0-rc/app-bridge-web-components/title-bar) controls the surrounding Shopify header when a styled page layout is unnecessary. Keep the production Page heading and action slots. Do not duplicate them in the body or override Polaris CSS merely to compensate for the test double.

For reliable local preview, use one of two explicit approaches. A standalone component harness can render the real Polaris component without `window.shopify`, with synthetic data and request behavior injected through a test-only transport. This paints Polaris's standalone header, but remains standalone evidence. An embedded fixture can keep the host double and render a clearly identified preview host outside the app frame, reflecting the Page heading/actions and forwarding supported clicks. That frame is a test tool, not a replica proving native acceptance. The current token-only double should not be called a complete embedded visual preview.

The documented qualification path remains real App Home in Shopify Admin. Shopify's [Polaris 2 migration guide](https://shopify.dev/docs/apps/build/app-home/polaris2) says to test the new appearance on a dev store created with the `new_admin_design` feature preview and the current appearance on a store without it. App Bridge supplies the appearance before Polaris initializes; Shopify documents no application theme override. Real app URL, tunnel, store or installation changes require their existing resource scope. Local preview is not a substitute for native observation.

## Applied correction

The task agent inspected the real Shopify Orders tab and the revised synthetic preview in Google Chrome using native app controls. The populated list now has a compact menu/search/column toolbar, an open table, one-line order/test labels, neutral payment/completed-artwork badges with filled dots and yellow pending-artwork badges with an incomplete icon. Display options change actual column visibility. Search and artwork filters explicitly apply to the current page because the endpoint exposes cursors and limits only. Columns use the retained DTO: Order, Date, Total, Payment status, Artwork status and Customized items. Analytics, customer data, selection and bulk actions are omitted where the application lacks their supporting behavior.

Amounts use exact BigInt-backed locale formatting, including non-Latin fractional digits. Historical dates retain their year when outside the current year. Production Page and authentication behavior remain intact. The local tool now renders a separate preview host reflecting Page heading/actions, forwards Refresh to the real island read and synchronizes navigation/query state. The preview continues to isolate ambient credentials and reject API commands. Public Polaris runtime bytes remain unchanged.

The project guidance now requires reference comparison and records Chrome's native-control fallback. A valid component tree alone no longer serves as evidence of visual fidelity.

## Toolbar and control correction

The owner's seven annotations prompted another inspection of the live Shopify Orders page in Chrome, including its display-options and nested sort menus, inline search, search date suggestions, header sort arrow, status pips, button treatment and pagination. The earlier `bullet` icon recommendation and the statement that collection-wide sorting is absent describe the earlier implementation. This pass supersedes both.

| Owner observation | Applied correction |
| --- | --- |
| Display options differs | Sort-by Date with newest/oldest choices, compact columns with show/hide eyes, drag handles, pointer reordering and keyboard Move up/down menus. Order remains the primary column. Unsupported native grouping and archived-order settings are omitted. |
| Search differs | An editable inline `s-search-field` replaces the search-launching text. Focusing it opens available filter choices beneath it without moving typing into a second field. Browser autocomplete is disabled. Search and artwork scope remains explicitly page-local. |
| All disclosure icon differs | Public `select` supplies the observed up/down glyph rather than the menu's automatic single chevron. |
| Payment pip differs | Public `enabled` supplies the larger filled rounded pip; pending artwork retains `incomplete`. Visible-column eyes use `view` and `hide`. No custom SVGs. |
| Date control missing | The Date header toggles collection-wide ordering. Search filters expose Today, Last 7/30/90 days and a custom range using actual Polaris date fields. Bounds use the authenticated store time zone. The full timestamp uses `s-tooltip`. |
| Shadows differ | Refresh explicitly uses the supported secondary variant. Popovers and controls retain public Polaris elevation and appearance. No shadow-DOM CSS or forced theme has been added. |
| Extra count/footer | The custom result-count line is removed. Table pagination appears only when a next page or known previous page exists. The initial skeleton does not invent pagination. |

The backend now implements date ordering and half-open date bounds, using `(order_created_at, purchase_id)` for both ordering and tenant-scoped keyset cursors. The default changes from purchase ingestion time to Shopify order creation time. An additive migration adds the matching `(shop_id, order_created_at, purchase_id)` index and retains the ingestion-date index. Strict request validation rejects invalid sort/bounds. The synthetic read-only preview applies the same query behavior. Sort or date changes clear the previous page before loading, so a failed query cannot leave stale cursor controls operating against a new query. Empty date ranges offer clear-filter recovery rather than the first-order empty state.

Keyboard review found and corrected unconditional search refocusing, removed-control focus when opening custom dates, unannounced date validation, and stale cursors after failed sorting. Search suggestions also reopen after Escape when the field is already focused. Custom ranges require both dates and preserve committed field values through validation; immediate Apply no longer reads stale Preact state or clears a corrected start date. Column ordering uses semantic native list wrappers around Polaris controls because App Home exposes no sortable-list component. The presentation guard now permits `ul`/`li` as structural wrappers while still rejecting replacement controls on them; a focused regression verifies both cases.

The observed local font is loaded ShopifyInter at 13px, with order labels at weight 500. A 390px check found no document overflow and a fitting display-options popover. Pointer dragging and keyboard Move up/down both reorder the table. Search typing remains in its original field while filter choices are open. Native Chrome inspection confirmed the revised toolbar and column controls. These observations concern the synthetic preview, not the embedded Insignia app.

Public App Home does not expose Shopify admin's private contenteditable search/filter builder or a borderless search-field variant. This implementation uses supported public components for the corresponding tasks; it does not claim an exact reproduction of that private control. Shopify's [Polaris 2 migration guide](https://shopify.dev/docs/apps/build/app-home/polaris2) states that App Bridge selects appearance at initialization with no application theme configuration. The local preview's secondary button computes no box shadow. The actual Insignia host appearance, including its button treatment, still needs native qualification in both Shopify appearances. Do not override private styles to make a synthetic host look accepted.
