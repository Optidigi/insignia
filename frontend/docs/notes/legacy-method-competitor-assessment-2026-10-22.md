# Legacy method reuse and competitor pricing models

Research note, 22 October 2026. This compares documented data and pricing behavior, not competitor interface quality. Local statements below come from source inspection; vendor statements link to first-party help docs.

## Insignia Legacy code facts

- Legacy has separate Methods and Products navigation. A shared `DecorationMethod` stores its name, base price, zero-price display flag, customer copy, and artwork constraints. Product configurations reference that row by foreign key; a nullable product-method override inherits the method base price, while a set value replaces it. See `insignia-legacy/app/lib/services/methods.server.ts` and `insignia-legacy/prisma/schema.prisma` (`DecorationMethod`, `ProductConfigMethod`).
- Legacy computes a per-unit decoration fee as method base price + selected placement charges. Each placement's method-specific value replaces that placement's default; the selected size step then adds its own price adjustment. The method base is applied per garment, while the method-detail Pricing section says “Base price added to every order using this method.” This is a unit-label mismatch. See `insignia-legacy/app/lib/services/storefront-customizations.server.ts` around `computeCustomizationPrice` and `app/routes/app.methods.$id.tsx:448`.
- A buyer draft has one `methodId` for all selected placements, so the configuration may offer multiple methods but one order customization cannot mix methods across its placements. See `app/lib/services/storefront-customizations.server.ts` (`CreateDraftInput`).
- Product-config duplication keeps the same shared method IDs and copies product overrides, placement overrides, and size steps. A later shared-method edit remains live wherever the product override is null; deletion is blocked while a method is linked. One Legacy config can also group several Shopify product IDs. See `app/lib/services/product-configs.server.ts` (`duplicateProductConfig`) and `app/lib/services/methods.server.ts` (`deleteMethod`).
- Legacy can vary a placement's base price by method, but its size-step adjustment belongs to the placement, not the method. Every method at that placement therefore gets the same incremental size price; it cannot express a different size-price slope for each method without more pricing structure.

## First-party vendor documentation

- **DecoNetwork** has shared decoration-process pricing defaults for products, with per-product pricing overrides. It supports price structures by area, garment color, quantity and process variables. Decoration-area definitions hold dimensions and supported processes and can be shared across products; changing a shared area affects all products that use it. Product setup can set pricing per area and process. [Decoration Pricing](https://help.deconetwork.com/hc/en-us/articles/236150748-Decoration-Pricing), [Manage Decoration Areas](https://help.deconetwork.com/hc/en-us/articles/115000381228-Manage-Decoration-Areas), [Set Up Decoration Pricing Per Location](https://help.deconetwork.com/hc/en-us/articles/360019586573-Set-Up-Decoration-Pricing-Per-Location).
- **InkSoft** supports reusable account-level screen-print pricing grids. Its product Decoration settings activate account-enabled methods, assign a print-price grid, and configure product sides and print regions. The grid requires a value in every cell, with `0.00` used for free. The docs explain assignment but do not establish whether later grid edits update assigned products live or through a snapshot. [Screen Print Pricing](https://help.inksoft.com/hc/en-us/articles/46724059783579-Screen-Print-Pricing), [Edit Products – Decoration (Blank Products)](https://help.inksoft.com/hc/en-us/articles/46724037237787-Edit-Products-Decoration-Blank-Products).
- **Zakeke** separates Printing Methods, which control customer tools and print-ready output, from Pricing Rules. A method can be assigned to multiple products or to a variant or side. Pricing Rules can target customization properties and be assigned to a product or method; when both overlap, the product rule takes priority and Zakeke warns that it ignores the method rule. [Printing Methods](https://zakeke.zendesk.com/hc/en-us/articles/360016836099-Printing-Methods), [Pricing Rules](https://zakeke.zendesk.com/hc/en-us/articles/360015984779-Pricing-Rules).

## Insignia rewrite implication

The rewrite's current method catalog stores a reusable name and copies values into independent product drafts (`packages/database/src/repositories/method-catalog.ts`); it is not a live pricing source. Lean pricing accepts one final nonnegative price for each offered method × placement × size tuple, with a missing tuple unavailable and explicit zero free (`packages/domain/src/pricing/lean.ts`).

For MVP, keep the method catalog as a lightweight reusable name and optional buyer guidance, and keep eligibility and final prices on the product configuration. Do not silently reintroduce Legacy's global method base, location overrides, and shared size deltas: that changes copied setup into live inheritance and adds precedence questions, while still failing to model method-specific size increments. DecoNetwork, InkSoft, and Zakeke show that richer reuse is viable, but as distinct product models with explicit assignment or override rules; their docs do not establish it as a requirement for Insignia. No verified source establishes InkSoft's live-versus-snapshot grid update behavior, and vendor documentation alone cannot support a judgment about which interface is easier to use.

**Insignia Legacy workflow assessment (not a competitor UX score):** its central methods plus product-level links and overrides are structurally closer to DecoNetwork and InkSoft's documented reuse patterns than to the rewrite's copied templates. I rate the reuse structure 7/10 and the clarity of the pricing layers 4/10: method base, product override, placement/method replacement, and placement-wide size add-on require the merchant to understand several interacting scopes. This is a code-and-copy assessment, not a live usability test.
