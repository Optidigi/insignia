# Shopify operational app Home references

26 October 2026. Primary-source research for Insignia Home following the initial four-app scan. The selected references are Shopify Flow, Shopify Subscriptions, Shopify Digital Products (called Digital Downloads in the App Store URL), Shopify Order Printer, and Fraud Control. The question is what each app puts at its landing surface, where the full work/detail lives, what its numbers mean, and what can carry over to Insignia.

This note distinguishes three kinds of evidence: **official documentation** describes product behavior and routes; **official App Store media** is promotional screenshots/video, not proof of current live app state; and **native observation** is a live logged-in view. In the authorized dev store on 26 October, Flow's first-use Workflows view and `/apps/flow/activity` loaded. After that view, one unconfigured draft named `Home research — inactive example` was automatically saved. The Workflows list showed it as **Inactive**, **Not recently run**, and **Trigger not defined**; its detail showed draft/version history and an empty history scoped to that workflow. No trigger or action was configured, no workflow was activated, and no run was executed. The screenshots are linked below. An earlier blank embedded view is superseded by this successful recheck; opening the public iframe origin without Shopify App Bridge showed `shopify is not defined`, which is expected for a standalone origin and does not explain embedded behavior. The other apps below have documentation, listing, or public reference-code evidence, not native dev-store observations.

## Shopify Flow: configuration list, workflow summary, run log

### Workflows list and re-entry

Shopify Help Center routes the Flow app through [Apps > Flow](https://help.shopify.com/en/manual/shopify-flow/manage/organize-workflows) and links the app at `admin.shopify.com/apps/flow`. Its help link for the global Recent runs surface resolves to `admin.shopify.com/apps/flow/activity`. In the dev-store navigation, the parent saw the embedded Recent runs link at `/apps/flow/web/activity`; use the actual in-app navigation for this store, rather than hard-coding a detail route. A separate error-trigger reference documents a generated run URL form, `/admin/apps/flow/web/overview/activity/{{workflowRunId}}`; this is a deep-link template, not the best generic re-entry path. See the official [error trigger URL fields](https://help.shopify.com/en/manual/shopify-flow/reference/triggers/workflow-error-occurred).

### Recent runs and detail boundary

Shopify distinguishes three layers. The live Workflows list in this dev-store observation had columns **Workflow**, **Status**, **Last run**, **Latest updated**, **Trigger**, and **Tags**. Its only row was the inactive unconfigured research draft; **Not recently run** is list metadata, not a record of a run.

1. **Workflow list:** Active/Inactive is a workflow activation state. Turning a workflow off leaves it Inactive and it can be reactivated. Turning it off can also cancel its in-progress runs.
2. **Workflow summary:** Select a workflow to see its Recent runs, inspect them, and perform supported bulk retries after correcting a problem. The summary is not just another version of the global workflow list.
3. **Run detail:** Select one run for Status, successful action count, an execution-path preview, per-step results/logs, and expandable step data. Order/customer IDs and other payload data can appear here; this is the troubleshooting view.

The [run-monitoring guide](https://help.shopify.com/en/manual/shopify-flow/manage/monitor) names run states **In progress**, **Waiting**, **Rate limited**, **Canceled**, and **Completed** in the Recent runs table; its Results column lists successful actions and step errors. The troubleshooting guide calls error runs **failed**, so failure is run-level evidence distinct from workflow Inactive. The table also shows start time, retries, and trigger type. Completed runs are retained for only 14 days. The Recent runs search supports workflow, error, actions-taken, time, trigger, retry, run ID, tags, and text included in step data. Tests do not appear in the normal Recent runs list.

Recovery remains on the owning workflow/run surfaces. [Retry guidance](https://help.shopify.com/en/manual/shopify-flow/manage/manual-retry) says a run must no longer be running/waiting and the workflow must be active; retry uses the original trigger data but re-fetches Get data and uses current data for conditions/actions. Fix the workflow or resource first. A canceled run cannot resume; start or retry a new run as supported. Turning off a workflow also cancels its in-progress runs. These are concrete operational actions, unlike a generic “recent activity” tile.

**Insignia mapping:** An order's artwork issue can be a specific work item, while an Insignia product configuration is reusable setup. Keep those independently represented. A short recent customized-orders section can route each order to existing `/admin/orders/:purchaseId`; the full list, filters, authorized artwork inspection, upload/review, and recovery stay in Orders detail. Do not clone Flow's workflow editor, deep run logs, or automation capabilities into Home. Flow status terminology is not directly transferable because Insignia's artwork states and allowed actions have different meanings.

## Shopify Subscriptions: contracts, not a generic failed-payment queue

The [Subscriptions analytics guide](https://help.shopify.com/en/manual/products/purchase-options/subscriptions/shopify-subscriptions/analytics) places a **Performance** section on the app index page. Its four metrics are recurring subscription revenue, active contracts, new contracts, and canceled contracts for the selected timeframe. The date control offers 7, 30, or 90 days; comparison defaults to the prior 7 days. Clicking a metric opens the complete report for that metric. Shopify defines Active subscriptions to include **paused contracts and skipped orders**, so that total does not equal currently charging customers or work that needs action.

The [contracts guide](https://help.shopify.com/en/manual/products/purchase-options/subscriptions/shopify-subscriptions/manage-subscriptions/manage-contracts) describes a list sorted by last-purchased date, newest first, filterable by status. A contract detail supports editing products, quantity and frequency; editing contact/address/payment details; skipping and resuming a next order; and pausing, resuming, or canceling a contract. Cancellation cannot be undone. For insufficient-inventory errors, a Contracts filter and warning icon identify affected contracts; detail shows missing products and an uncreated upcoming order with **Create order** and **Bill contract** paths. Those actions have operational consequences, including possible overselling for Create order.

The [billing settings guide](https://help.shopify.com/en/manual/products/purchase-options/subscriptions/shopify-subscriptions/manage-subscriptions/manage-app-settings) lets merchants configure retry counts/intervals and the resulting action for Payment method failure or Not enough inventory. The separate [customer subscription guide](https://help.shopify.com/en/manual/products/purchase-options/subscriptions/manage-subscriptions/manage-customer-subscriptions) documents **Failed payment** as a customer subscription-status filter, alongside Active, Paused, Canceled, Expired, and Never subscribed. The corresponding recovery is usually on the customer/payment profile: send a payment-method update link or replace the card. Do not conflate this customer status segment with an app-index dashboard status or with an inventory error.

**No subscriptions:** Shopify says subscription sales reports show no data if no subscriptions have been sold, and the Active product subscriptions block is omitted from a customer profile when no subscription-based products are sold. The Help Center does **not** specify the exact current production app-index no-contract empty-state copy/layout. The public reference app has a specific empty state, documented below, but that does not verify the production app's state. Likewise, no metric value of zero should be invented when the source state is “no data.”

### Public reference app source: useful states, not a production build guarantee

The official [Shopify Subscriptions Reference app repository](https://github.com/Shopify/subscriptions-reference-app) describes itself as an **example** and a starting point for building subscriptions applications; it says submitted apps based on it must be substantively different. I inspected `main` at commit [`575a825f9f38aca9b0a1880e0fac10121b572a1c`](https://github.com/Shopify/subscriptions-reference-app/commit/575a825f9f38aca9b0a1880e0fac10121b572a1c). This proves what that public reference snapshot implements. It does not prove the currently deployed Shopify Subscriptions app uses the same code, screen, or version. No production build identifier was verified. The Help Center's documented index **Performance** section and the reference repo's contract-list Home are therefore separate pieces of evidence, not one combined screen.

- **Home/index:** the embedded app's `Home` nav item points to `/app`, whose index route loads subscription contracts and renders a **Subscription contracts** page. With no contracts and no saved filter, it shows “Manage your subscription contracts” and “When a customer purchases a subscription from your store, the contract will appear here.” With contracts, it renders the contract table; each row opens its contract detail. See the [app shell navigation](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/app/routes/app/route.tsx#L90-L102), [Home loader and empty/table branch](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/app/routes/app._index/route.tsx#L35-L60), [Home rendering](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/app/routes/app._index/route.tsx#L79-L137), and [empty-state copy](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/public/locales/en/app.contracts.json#L1-L8).
- **No plans vs. no contracts:** the Home loader fetches contracts; it does not query selling-plan groups or make its empty state conditional on whether plans exist. A separate Plans route checks plan groups and, when none exist, shows “Get more repeat business,” explains recurring purchases, and offers a **Subscription plan** action to `/app/plans/create`. So this implementation distinguishes “no contracts” on Home from “no plans” on Plans; Home alone cannot tell whether the merchant has plans that have not yet sold. See the [Plans empty branch and create action](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/app/routes/app.plans._index/route.tsx#L129-L177) and [Plans empty-state copy](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/public/locales/en/app.plans.json#L1-L12).
- **Filtered empty state:** if a saved status view returns zero rows, the app keeps the table and shows a scoped “No contracts with this status” empty result instead of the no-contracts setup state. The test suite explicitly covers both the base no-contract state and an empty Paused view. See the [table-scoped empty state](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/app/routes/app._index/components/ContractsTable/ContractsTable.tsx#L123-L131) and [empty-state tests](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/app/routes/app._index/tests/ContractsList.test.tsx#L69-L100).
- **Active vs. failed:** the reference list has All, Active, Paused, Cancelled, and conditional Inventory error views. Its Active query combines `status:ACTIVE OR status:FAILED`; a test asserts that a contract whose API status is `FAILED` is displayed with the **Active** badge. Inventory error is a separate view using `last_billing_attempt_error_type:inventory_error`; there is no distinct failed-payment queue in this Home list. This is a reference-app design choice, not proof of production status semantics. See [view query construction](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/app/routes/app._index/utilities.ts#L32-L53), [list tabs and loading indicator](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/app/routes/app._index/hooks/useContractListState.ts#L36-L92), and [failed-contract test](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/app/routes/app._index/tests/ContractsList.test.tsx#L181-L203).
- **Loading and failed reads:** the route loader awaits its contracts request before rendering. The table's Polaris filter loading indicator is only set while Remix is loading the same pathname (for example, a same-route filter/sort change); this source does not show an initial loading skeleton. The contracts loader/model has no route-specific retry/error component and does not inspect GraphQL `errors`; a thrown route error reaches the app shell's Shopify boundary first, then its generic fallback card offers a page reload. This is source behavior, not a verified runtime failure screen. See [awaited loader](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/app/routes/app._index/route.tsx#L35-L60), [loading flag](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/app/routes/app._index/hooks/useContractListState.ts#L36-L85), [contract query handling](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/app/models/SubscriptionContract/SubscriptionContract.server.ts#L62-L112), [app error boundary](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/app/routes/app/route.tsx#L110-L137), and [reload fallback](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/app/components/ErrorBoundaryCard/ErrorBoundaryCard.tsx#L1-L30).

The repo includes contract rows with contract ID, customer, product, price, delivery frequency, status, and an inventory warning where applicable. Selecting a row opens the contract detail; pause/activate/cancel operations belong to bulk actions on the list, while billing/inventory repair lives on the contract. These are workflows in the reference implementation, not a general analytics home. See the [contracts table and row navigation](https://github.com/Shopify/subscriptions-reference-app/blob/575a825f9f38aca9b0a1880e0fac10121b572a1c/app/routes/app._index/components/ContractsTable/ContractsTable.tsx#L123-L229).

The Subscriptions App Store gallery captions include “View and manage subscription orders” and “Flexible customer subscription management”; these are first-party promotional images from the [official listing](https://apps.shopify.com/shopify-subscriptions), not verified app-home states. Its customer account and contract actions are lifecycle management, distinct from a report trend. The official [sales reports guide](https://help.shopify.com/en/manual/reports-and-analytics/shopify-reports/report-types/default-reports/sales-report) describes subscription-sales reports and notes no data displays when the store does not sell subscriptions.

**Insignia mapping:** Insignia's access/billing eligibility is app authorization, not a recurring purchase contract, and is already summarized in Settings. Don't import subscription revenue, lifecycle metrics, billing-retry controls, or customer payment details to Home. Reuse the principle of status-specific recovery: only show an artwork task when the underlying reason and the permitted next action are known, with its order detail as destination.

## Shopify Digital Products: products, delivery settings, and per-order access

The [Digital Products Help Center page](https://help.shopify.com/en/manual/products/digital-service-product/digital-downloads) says the app has Products, Orders, and Settings. Products is the app's home and displays Active digital products by default, with status and “has digital file / no digital file” filters plus search and sort. If the merchant has not added a digital product, the page offers **Add file** and **Add link**; after a product exists, the control becomes **Add assets**. This is documented app navigation and setup behavior, not a screenshot-derived claim.

The product page owns file/link assets and per-variant **Delivery method** and **Access limit**. Delivery can be automatic or manual. Automatic assets are emailed after successful payment and non-shipping items are marked fulfilled. Manual delivery waits for fulfillment in Shopify Admin. In a mixed order, a physical item with a file follows physical fulfillment settings. Access defaults to unlimited; a limit applies per link and is shared across that variant's files. Resending a download email reuses its link and existing count; an update email or newly generated share link starts a new count. Editing/removing an asset does not necessarily revoke earlier purchased links; deactivation is the documented per-order access control.

Orders is a separate searchable list of digital-product purchases with order number/date, customer name/email, fulfillment status and download/link-open count. An order detail can update customer email, resend the fulfillment email, show download links, deactivate/reactivate access, and review individual downloads/opens with date, IP, referrer, and user agent. An all-orders CSV export is a separate report. These details and actions are documented; the app's exact no-products/no-orders page copy is not.

The [official App Store listing](https://apps.shopify.com/digital-downloads) uses the name Shopify Digital Products and has gallery media captioned “Create digital products” and “Dashboard.” The listing's feature description says it adds files/links to new or existing products and tracks orders. Because `digital-products` is not the current App Store slug, use the linked `digital-downloads` URL to reach the current listing.

**Insignia mapping:** The closest structural parallel is product setup plus order-specific customer file work. Keep `/admin/products` as configuration and `/admin/orders` as order/artwork work. Insignia's underlying “artwork needed” state can mean a not-yet-supplied upload or expired/erased retained artwork; never replace that with a generic delivery/fulfillment label. Do not add shipment, download counts, customer email delivery, or access-revocation concepts to Insignia Home. Only offer artwork recovery where an existing upload/review action is valid for that reason.

## Shopify Order Printer: templates configure documents; Orders initiate printing

The [Order Printer overview](https://help.shopify.com/en/manual/fulfillment/managing-orders/printing-orders/shopify-order-printer) describes invoices, packing slips, pick lists, and other order documents. Its [template guide](https://help.shopify.com/en/manual/fulfillment/managing-orders/printing-orders/shopify-order-printer/creating-templates) identifies default Invoice, Packing slip, and Pick list templates. Merchants can create up to 15 templates; invoices and packing slips use HTML/CSS/Liquid, while the pick list editor has native selection controls. Template detail has code/editor, Preview, and Save, with restore defaults supported for built-in invoice/packing-slip templates.

The key boundary is execution: the [printing guide](https://help.shopify.com/en/manual/fulfillment/managing-orders/printing-orders/shopify-order-printer/printing-documents) starts from Shopify **Orders**, where merchants select one or more orders and choose Print with Order Printer. The [pick-list guide](https://help.shopify.com/en/manual/fulfillment/managing-orders/printing-orders/shopify-order-printer/pick-list) can include Unfulfilled, Fulfilled, On hold, or Scheduled orders and can organize by product or order. Up to 50 orders can be printed at once. This is not a Home-level order-attention queue or a separate fulfillment system. The app's own exact first landing screen is not described in Help Center docs.

The current Shopify Order Printer listing (launched 15 May 2024) has App Store images labeled “Instant access to free order document templates,” “Customize templates with Liquid and preview using your orders,” and “Print documents for one or many orders.” Treat them as promotional screenshots, not live state proof. The official [listing](https://apps.shopify.com/shopify-order-printer) distinguishes the current app from the older legacy Order Printer references in migration/template docs.

**Insignia mapping:** A direct task action can live on the resource page that owns it. Home can point to a customized order, while selection, full order list, and work sequencing stay in `/admin/orders`. Don't introduce pick/pack, shipping, bulk fulfillment, or invoice/report features; Shopify owns those order workflows.

## Fraud Control: the analytics dashboard is separate from blocking rules

The [Fraud Control app guide](https://help.shopify.com/en/manual/payments/fraud-prevention/fraud-control-app) defines an analytics dashboard with acceptance rate, high-risk order share, fraudulent chargeback share, Shopify Protect protection value, Shopify Protect coverage value, and value of orders canceled/refunded due to fraud. The figures are for the chosen date range. The default range is 30 days and comparison is the preceding period of equal length. Shopify Protect protection value is delayed ten days. Without Shopify Payments, only acceptance rate, high-risk orders, and orders canceled due to fraud are available. The chargeback health status, when available with Shopify Payments, is a rate of chargebacks to orders: good standing under 0.4%, at risk 0.4–0.6%, elevated risk above 0.6%.

The same Help Center page explicitly cautions that Fraud Control's dashboard provides insight but **does not actively protect against chargebacks**. The intervention is a separate Rules area: rules can filter/block checkout based on email, address or IP conditions, are available only to Shopify Payments merchants, and are activated on save. Merchants can deactivate or delete a rule. From the dashboard, the chart icon opens an expanded metric view. Flow templates for fraud are a third surface; the [Flow/Fraud Control section](https://help.shopify.com/en/manual/payments/fraud-prevention/fraud-control-app#shopify-flow) describes examples such as notifying on high-risk orders or canceling/restocking.

The [official App Store listing](https://apps.shopify.com/fraud-control) includes promotional images for built-in analytics, block lists, Flow automation, and rules. It labels the app free and Shopify-developed. It does not establish the native empty-data state, nor does an aggregate rate identify a particular order needing action.

**Insignia mapping:** Do not copy fraud analytics or a rule editor. Insignia has no supported store-wide conversion, risk, chargeback, or protected-value data. The useful pattern is to make scope, period, and source availability explicit when a metric exists, while putting a specific actionable task beside the appropriate destination. A missing/expired artwork record is not an aggregate “risk” metric and should not be made to resemble a fraud alert.

## Practical V1 boundary for Insignia Home

These references broaden the original small set of Home examples but support the same simple composition: current operational work first, a compact recent customized-orders list, and clear routes to existing product/order workflows. The apps do **not** point toward a universal analytics grid. Flow is a task/log system; Subscriptions mixes lifecycle management and time-bounded performance; Digital Products manages products and customer delivery/access; Order Printer configures documents but invokes printing from Orders; Fraud Control mixes store-level trends with separate rule actions. Their metrics and statuses are domain-specific.

For Insignia, a Home order row should display the reason only when the server/read model can support the specific action and the current user can access it. Use order detail for artwork inspection, upload/review, and recovery. A recent list is useful without a complete attention count; don't announce a total queue, all-caught-up state, revenue, fulfillment backlog, or broad readiness from a partial/paginated source. Keep setup/product context distinct from order work; do not add inventory/shipping, customer account, digital fulfillment, subscription billing, payment methods, fraud, or automation features.

This is comparative design research only; it did not implement Home or validate runtime routes in Insignia. Native Flow inspection created the single automatically saved, unconfigured inactive draft described above. No Flow trigger or action was configured, and no workflow was activated or run.
