## Findings and decisions

No new blocking design defect was established in the reviewed customer layouts and local ordering path. The adaptive controls avoid presenting one-option choosers; long labels wrap; the portrait product keeps its own geometry; size and method costs are visible; final review allows editing. Those are observations about the inspected states, not a blanket approval of all interactions.

Before connecting the storefront, decide the cart handoff explicitly. The local confirmation offers Return to product, Add another design and Edit this design, while the product page shows a cart summary. There is no View cart route. The host storefront should provide a clear View cart or Continue to cart action once an actual cart exists. This is a known integration/design decision, not a newly broken production cart. A separate app checkout, card form, security badge or coupon field would duplicate Shopify's responsibility.

Cross-session drafts are also an integration decision. Closing this designer preserves the local design while visiting the product page, and ordinary reload/navigation with artwork is guarded. It does not promise a persisted draft. Do not label it Saved or imply that a later visit restores the design until persistence and recovery have been designed. The current artwork-later choice already supports proceeding without a ready file where the merchant allows it.

The exact-price merchant-preview labels and incremental-price demo labels deserve a separate consistency check before integration. Their arithmetic is different by design; this audit does not claim a wrong total. See the independent skeptic note for the final disposition.

## Checklist audits

Present means directly supported in the reviewed scope. Partial names a specific limitation, often a prototype or evidence boundary. Not needed requires a product reason. Can't tell names evidence still required. A partial row is not automatically a proposed feature or prioritized defect.

### [Multi-step form — Web app](https://www.checklist.design/web-app/multi-step-form)

| Status | Item and description | Why |
| --- | --- | --- |
| Present | **Progress indicator** — A clear visual showing how many steps exist and which one the user is currently on | Three named steps show the current and completed stages; one-size products use Quantities. |
| Present | **Step heading and context** — A clear title and brief context for each step, so users know what they are being asked to provide. | Artwork, Quantities and Review name the task; the empty Artwork screen supplies its first action. |
| Present | **Field grouping** — Each step containing only fields that belong together logically e.g. phone and email for contact details | Artwork, variant quantities and final review are separate; single-option groups collapse to facts. |
| Present | **Step-level validation** — Validation happening at each step before the user proceeds, not surfaced all at once at the end | An empty quantity attempt focuses a linked summary. Source also validates artwork and allowed bounds before progression. |
| Present | **Back navigation** — The ability to return to a previous step to review or change answers without losing subsequent progress | Previous step, completed-step navigation and review edits preserve later local quantities and artwork choices. |
| Partial | **Save and resume** — The ability to save progress and return to the form later | Closing preserves the local design on the product page; persisted cross-session drafts are a known integration decision, not a current Saved promise. |
| Present | **Final review step** — A summary of all entered information before final submission, giving the user a chance to review and edit | Review lists artwork/method/size, colour and quantities, exposes edits and a per-item breakdown, and keeps the final total beside Add to cart. |

### [Uploading media — Flows](https://www.checklist.design/flows/uploading-media)

| Status | Item and description | Why |
| --- | --- | --- |
| Present | **Empty state** — Show a clear visual placeholder with an upload icon and simple text that indicate a file can be dropped into the area to upload. It’s also suitable to offer a click to upload route incase a user prefers that option. | The live chooser has an upload icon, Drop a file here and browse files. |
| Partial | **Drag and drop interaction** — When a file is across the interaction canvas, there should be a clear visual state change to indicate it has detected a file attempting to be dropped. This lets the user know it’s safe to release the file at this point. | Source toggles a dragging state; a real OS file drag was not exercised, so current rendered drag feedback is unverified. |
| Partial | **Progress indicator** — Display progress that updates in real-time so users know their upload is working. If a percentage is not possible to show, a loading indicator can at least show that something is happening. Include file names and show overall progress when uploading multiple files to keep users informed throughout the process. | Source shows Opening file and disables browsing during the local read. The transient busy appearance was not freshly captured; no network upload exists. |
| Present | **File restrictions & constraints** — Clearly state limits to what files can be uploaded. This is commonly file size and format, shown in the upload area before users attempt to upload files. If a user tries to upload a file outside the constraints, an error message should show explaining it does follow the constraints. | PNG/JPG/SVG and 5 MB limits are visible. Source rejects other types and oversized files with specific correction text. |
| Partial | **Outcome status** — Use visual indicators like green checkmarks for successful uploads and red warning icons for failures. For failures, include an error message explaining what went wrong and what users can do to fix it. | Selecting a sample visibly changes the preview. Failed-file messages and alert semantics are source-confirmed; failure appearance was not freshly induced. |
| Present | **Upload actions** — Ways to interact with an upload. Choose which actions to show by default vs on hover based on available space, aiming to avoid overwhelming users with too many visible options. Common actions include: Retry failed uploads Cancel upload in progress Delete files Rename files | Retry browsing, Close and contextual Remove artwork cover the task. Closing invalidates pending local reads; renaming is unnecessary for selecting one file. |
| Present | **Showing multiple uploaded files** — Display files in a clean list or grid with thumbnails when possible, and ensure the layout you choose is scalable. What information you show about each file depends on the context of the upload. A file name or size can be relevant in one case, while seeing the images uploaded can be the relevant detail in another. | The chooser lists files with thumbnails and names. The local sample library is visible; no server artwork library is implied. |

### [Adding to cart — Flows](https://www.checklist.design/flows/adding-to-cart)

| Status | Item and description | Why |
| --- | --- | --- |
| Present | **Outline variant selection for product** — Whether it’s size, colour, amount or something else, it must be clear what details must be picked to be able to add an item to cart. | Artwork, size/method and variant quantities are explicit; invalid or unavailable choices have validation or disabled controls. |
| Present | **Primary action on product page is add to cart** — One of if not the most prominent button on the page to draw the user’s attention. This may change if you want an 'add to cart' button on a grid view of multiple products. | Final review gives Add to cart prominence beside its total. A configurable product opens its designer before it can be added. |
| Present | **Feedback once added** — Immediate confirmation the item has been added. This can be done several ways and depends on the amount of intrusion you want to have, which is why 2 options are shown. | The local confirmation immediately shows item count, position count and total with edit/continue actions; this confirms local state only. |
| Partial | **Link to cart view** — Typically in a primary navigation, so that if the user continues shopping but is then ready to checkout, the cart is easily accessible. Showing the number of products is a way to catch their attention that they have items added but not purchased yet. A total price can also be considered to be shown. | The local product page has a cart summary and edits, but no cart route. Design the host cart handoff before integration; no real checkout is currently connected. |

### [Showing input error — Flows](https://www.checklist.design/flows/showing-input-error)

| Status | Item and description | Why |
| --- | --- | --- |
| Present | **Keep the input in default state** — The text field should be checked for errors only after the information has been entered. | Untouched quantities start neutral; an attempted step reveals field errors and a linked summary. |
| Present | **Allow user to enter information** — Let the user type without interruptions and submit the information aka don't assess as changes are made. | Typing is not interrupted. Source retains quantity strings and validates on the attempted transition. |
| Partial | **Signal error after loss of focus** — After the input has lost focus (user has clicked another element), the field should be assessed. Looks like we have an error here! In this case, explain why the error happened, and what is required to resolve it. For accessibility, combine the text with a visual icon that indicates an error was found. | Validation occurs on step submission rather than every blur. Fresh evidence shows specific text, field styling and a focused linked summary; blur validation is not prescribed here. |
| Partial | **Return to default state upon reattempt** — Once the user focuses on the field again, the error message should disappear. If there is an error again, the process will simply repeat until they are able to continue. | An unresolved error stays visible on focus and clears after correction. The linked summary focuses the field; hiding the error merely on focus is not recommended. |
