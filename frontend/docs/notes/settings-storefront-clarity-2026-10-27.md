# Settings and storefront setup clarity audit

27 October 2026. Auditing [Settings — Web app](https://www.checklist.design/web-app/settings) for the hub and using [Onboarding — Web app](https://www.checklist.design/web-app/onboarding) as a partial lens for this revisitable setup guide. I reviewed the current source and the actual desktop, phone, and narrow captures. Storefront setup is a task guide inside Settings, not a first-run onboarding wizard.

## Finding

### P1 — “Added” can describe a customization block outside a product template

[`themeSetupStatus`](../../../apps/web/src/shared/storefront-setup.ts#L20-L43) returns `active` whenever the expected block has any activation. It validates each activation's `target` as non-empty, but never checks whether a customization-block placement is on a product template. Shopify's [App API](https://shopify.dev/docs/api/app-home/latest/apis/authentication-and-data/app-api) returns the placement target for each activation (with product-template targets such as `template--product...`) and defines `active` as present in a theme. Shopify's [theme extension configuration](https://shopify.dev/docs/apps/build/online-store/theme-app-extensions/configuration) permits app blocks in compatible sections; this Insignia block has no product-only `enabled_on` restriction in [`customize.liquid`](../../../extensions/insignia-theme/blocks/customize.liquid#L1-L4).

The active capture consequently shows **Added** with the product-page benefit copy ([StorefrontSetup.tsx](../../../apps/web/src/islands/StorefrontSetup.tsx#L201-L251), [desktop capture](../../../../.artifacts/admin-popup-review-2026-10-24/storefront/desktop/settings-storefront-active.png), [phone capture](../../../../.artifacts/admin-popup-review-2026-10-24/storefront/mobile/settings-storefront-active.png)), even though the source would also show that state if Shopify reported a placement only on another template. The ready-product test then offers **Preview in theme editor** based on product publication alone ([StorefrontProductTest.tsx](../../../apps/web/src/components/StorefrontProductTest.tsx#L174-L179), [lines 245–285](../../../apps/web/src/components/StorefrontProductTest.tsx#L245-L285)). A merchant can be told the customization is added, then open a product preview where the customization button is absent.

Use the returned placement target to distinguish “added to a product template” from “added elsewhere”; if a target cannot be classified, keep the status neutral. When the selected product's template is not covered, make the preview handoff say that theme placement is the next step instead of presenting the customer-flow instructions as ready. Keep the selected-product preview as the final manual check and do not imply that one product-template placement covers every product template. This is a source-derived state gap; the current gallery has active and non-active captures, but no capture of the combined case where the product is published and the block is active only outside product templates.

## What already reads clearly

- The hub has four real destinations and no duplicated Methods link. The normal capture presents Storefront setup, App permissions, Billing, and Customer data requests in one compact list at [desktop](../../../../.artifacts/admin-popup-review-2026-10-24/settings/desktop/settings-hub-normal.png), [390 px](../../../../.artifacts/admin-popup-review-2026-10-24/settings/mobile/settings-hub-normal.png), and [320 px](../../../../.artifacts/admin-popup-review-2026-10-24/settings/narrow/settings-hub-normal.png). Their task descriptions identify the destination; no extra heading, preferences page, or icon tile is needed.
- The storefront page separates two independent Shopify theme tasks from the customer test. The not-added capture places each action beside its instruction and keeps the product test below; the active and unknown states remain distinct ([not added desktop](../../../../.artifacts/admin-popup-review-2026-10-24/storefront/desktop/settings-storefront-not-added.png), [not added phone](../../../../.artifacts/admin-popup-review-2026-10-24/storefront/mobile/settings-storefront-not-added.png), [unknown at 320 px](../../../../.artifacts/admin-popup-review-2026-10-24/storefront/narrow/settings-storefront-unknown.png)). No forced progress meter or “setup complete” label is warranted: block/embedding tasks can be done in either order, and neither proves a working buyer journey.
- Error and unsupported-host states preserve manual editor guidance and contextual Retry; narrow captures keep the banners and actions readable ([check error](../../../../.artifacts/admin-popup-review-2026-10-24/storefront/desktop/settings-storefront-error.png), [outside Shopify at 320 px](../../../../.artifacts/admin-popup-review-2026-10-24/storefront/narrow/settings-storefront-outside.png)). The inactive and active rows retain the Shopify handoff and reminder that Shopify saves theme changes. This matches Shopify's [theme-extension UX](https://shopify.dev/docs/apps/build/online-store/theme-app-extensions/ux): merchants position blocks and activate embeds in the Shopify theme editor, preview, then save there.
- The cross-page product path is explicit: an unpublished product shows **Open product setup**; the editor breadcrumb returns to Storefront setup with the chosen product rechecked. A published product opens its product-specific theme preview in a new tab with the two actual test steps. Access-denied product checks link to App permissions. Source: [StorefrontProductTest.tsx](../../../apps/web/src/components/StorefrontProductTest.tsx#L142-L180), [test states and return action](../../../apps/web/src/components/StorefrontProductTest.tsx#L237-L313), [editor return breadcrumb](../../../apps/web/src/islands/MerchantConfigEditor.tsx#L1487-L1488). The earlier independent interaction review records the product setup return and fresh recheck; this audit did not repeat its browser interactions.
- The Settings hub remains a directory for app-owned tasks. Staff roles, merchant identity, authentication, theme editing and billing approval remain Shopify-owned; the app checks relevant access and links to Shopify instead of recreating account controls. Shopify's [App Design Guidelines](https://shopify.dev/docs/apps/design) and [content guidance](https://shopify.dev/docs/apps/design/content) support the native App Home composition, mobile behavior, task-oriented actions, and plain, consistent copy.

The older `settings-storefront-button-help` and `settings-storefront-cart-help` images include the rejected example illustrations and are superseded. I excluded them from the visual assessment; the current not-added, active, unknown, and expanded-guidance captures reflect the owner correction that removed those examples ([correction record](storefront-setup-v1-2026-10-26.md#owner-correction-remove-synthetic-examples)).

## Checklist Design audit

### Settings — Web app

| | Item | Why |
|---|---|---|
| 🟢 | **Structure** — Organising settings controls into logical categories e.g. account, notifications, security, billing. | The four rows group distinct real tasks; the single list avoids a heading for a one-item group. |
| ⚪ | **Account details** — The fields where users update their name, email address, and profile photo | Shopify owns merchant identity; Insignia has no account profile fields. |
| ⚪ | **Security details** — The ability to change the password,  two-factor authentication and other security information | Shopify owns sign-in and account security. |
| ⚪ | **Notification preferences** — Controls for which notifications the user receives and through which channel, grouped by type (product updates, reminders, billing) | No Insignia notification preference store or optional channel controls are evidenced; do not create a switch for required retention notices. |
| 🟢 | **Billing** — Managing payment method, upgrading or cancelling a payment — this could also be a preview of this information with a link directly to the billing page if separate | The hub links to the actual subscription summary and Shopify-hosted management. |
| ⚪ | **Additional preferences (if applicable)** — Language, timezone, date format, and appearance settings like dark mode | These are Shopify/store or browser preferences; no Insignia preference store is present. |
| ⚪ | **Danger zone** — Destructive actions like account deletion, clearly separated from the rest of settings | Insignia does not own store deletion or uninstall; customer-data export is not account deletion. |

### Onboarding — Web app (partial lens)

| | Item | Why |
|---|---|---|
| ⚪ | **Progress indicator** — An indication of how many steps are involved and where the user currently is in the sequence | The two theme tasks are independent, so a numbered sequence or completion percentage would invent dependencies. |
| ⚪ | **Welcome message** — A brief message acknowledging this is a new experience and orienting the user toward what the product does. | This is a revisitable Settings guide for an installed app, not a new-user introduction. |
| ⚪ | **Account setup** — The minimum information needed to personalise the experience, gathered at the start | The merchant is already signed in; no profile fields are needed for theme setup. |
| ⚪ | **Product highlights** — Key features introduced through short contextual tips or a visual walkthrough. *Tip: Offer a skip route for user who has seen content before or prefers to learn by doing.* | A generic feature tour would add steps; the current inline tasks lead to Shopify's real editor and the buyer-flow test. |
| 🟢 | **First action prompt** — A clear prompt directing the user to an action or feature | Not-added states put **Add to theme** and **Enable in Shopify** beside each task; the test starts with **Choose a product**. |
| ⚪ | **Completion confirmation** — A clear acknowledgement that setup is complete, transitioning the user into the main product | A published-theme status cannot prove placement on every product template or a successful customer journey; the separate test should stay unmarked until tried. |
