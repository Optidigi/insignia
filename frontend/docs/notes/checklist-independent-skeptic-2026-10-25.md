## Focused Data Table checklist

Items retain the bundled checklist order. These judgments cover the selected Products and Orders evidence. Other audit notes own broader state coverage.

| Status | Item and description | Why |
| --- | --- | --- |
| 🟡 | Sortable columns. Column headers that sort rows by that value on click, toggling ascending and descending | Orders supports date sorting in Display options. No need to invent unsupported column sorts. Current direction is not visible in the closed control. |
| 🟡 | Column visibility and order. Controls to show or hide individual columns and drag to reorder them | Orders exposes show/hide controls in the inspected popover. Drag ordering is absent; no demonstrated task requires it in this review. |
| 🟢 | Row selection and bulk actions. Checkboxes on each row and a persistent action bar appearing when rows are selected | Orders phone shows 2 selected and the selected rows. The existence of selection is visible; cross-page selection behavior was not exercised. |
| ⚪ | Row actions on hover. Contextual actions (edit, delete, view) appearing when hovering over a row | Hover is not a phone requirement. The source retains real resource links and row delegation; this review does not establish desktop hover behavior. |
| 🟢 | Search and filter. A search input for quick lookup alongside filter controls for narrowing by specific attributes. | Both inspected page toolbars show search and a filter trigger. Orders honestly labels the search scope as this page. Filter outcomes were not independently exercised. |
| ❔ | Pagination. Controls to navigate between pages of results, with an option to choose how many rows show per page | Shared source supplies Previous/Next controls, but the inspected views do not exercise pagination. More pages would settle rendered behavior. The absence of a page-size selector alone is not a demonstrated usability problem. |
| 🟡 | Frozen columns. The first column pinned so it remains visible when the user scrolls horizontally | Products visibly loses identity and Orders uses the same scrolling structure. Keep the context problem; do not turn a particular pinned-column implementation into the requirement. |
| ❔ | Export action. A way to download the visible or selected rows as CSV, spreadsheet, or another format | Export belongs to the Orders audit's reviewed states. I did not inspect enough of that workflow to independently confirm output scope or recovery. |
| ❔ | Empty and loading states. The states shown when the table has no rows or when data is being fetched | The selected table captures contain rows. The empty assignment picker is a different component and cannot establish list loading behavior. More specific captures would settle this. |

## Buyer confidence check

The inspected review views keep artwork files, placement, method, size, item colour/quantity, total and Add to cart together. Long placement and method labels wrap in the long-content phone capture instead of forcing horizontal reading. The short phone viewport initially hides later review content below the fold; a still image alone does not show that it is inaccessible or covered during scrolling. I would not report that as a defect without a scroll check.

The apron and phone-case examples use Quantities and One size rather than demanding garment sizes. Their different preview shapes are handled visibly. The small default image is useful as placement context; these captures do not establish that close-reading artwork inspection is required here. No new buyer defect is sufficiently established by this subset. This is neither blanket approval nor evidence of a working Shopify cart handoff. The planned View cart integration and the deliberately fitted A4 production preview are excluded from new findings.

### Follow-up challenge on price-label meaning

I also inspected [current-draft customer preview desktop](/Users/pc/Development/Insignia/.artifacts/admin-popup-review-2026-10-24/customer-preview/customer-preview-1440.png), [phone](/Users/pc/Development/Insignia/.artifacts/admin-popup-review-2026-10-24/customer-preview/customer-preview-390.png), and [classic artwork phone](/Users/pc/Development/Insignia/.artifacts/checklist-audit-2026-10-25/buyer/classic-390-artwork.png). The bridge shows Standaard +€15.00, Groot +€17.50 and Embroidery From €15.00, with a matching +€15.00 placement subtotal. Classic shows Small Included, Medium +€2.50 and a +€7.50 placement subtotal. These labels express full placement contribution in one representation and size upgrades in the other. [designer.tsx:459](/Users/pc/Development/Insignia/designer-prototype/src/designer.tsx:459) and [model.ts:105](/Users/pc/Development/Insignia/designer-prototype/src/model.ts:105) confirm the distinction and the correct arithmetic.

The bridge's repeated €15 could make someone pause over whether method and size amounts stack. But From €15.00 differs from an additive +€15.00 method fee, and the matching placement subtotal provides a nearby readback. The two examples are different products with different pricing rules; their representation difference alone does not prove a buyer-facing inconsistency within one product or transaction. I would keep this as a copy question, not a separate P3 finding on present evidence. If labels are refined, identify the actual basis, such as placement price or size upgrade, instead of forcing every value into the same number format or changing correct totals. Confidence is high in the representation difference and low in a demonstrated user misunderstanding. An observed buyer interpreting the two amounts as additive would warrant reconsideration.

## Basis

The primary guidance is Shopify's current [content](https://shopify.dev/docs/apps/design/content), [layout](https://shopify.dev/docs/apps/design/layout) and version-targeted [index table composition](https://shopify.dev/docs/api/app-home/v2.0/patterns/compositions/index-table), read for this review. Clear terms, scannable resources and responsive task context support the findings. The current [Vercel Web Interface Guidelines](https://vercel.com/design/guidelines) supplement focus, keyboard and forgiving interaction expectations; no keyboard pass is claimed. Grouping effective access with its explanatory scope is also consistent with progressive disclosure, but no supplementary author establishes a platform requirement.

Untouched homepage, Storefront setup, masking and the old Reusable Methods library are outside this review. Known local-preview versus production boundaries are not new UI findings. Owner acceptance and native host verification remain separate.
