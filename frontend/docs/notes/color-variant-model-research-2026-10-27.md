# Colour variants in the current model

Source inspection on 27 October 2026. This note covers the underlying catalog, geometry, design, cart and purchase code. It does not establish that the newer polished admin or buyer prototype exposes all of these capabilities, or that native Shopify integration has been qualified. No implementation changed.

## What is implemented in the model

- Shopify catalog projection retains each variant's ID, title, selected option names/values and optional image. Detail reads page through variants separately from the eight-variant product-list summary. See [catalog.ts:9](../../../packages/shopify/src/catalog.ts#L9), [queries:34](../../../packages/shopify/src/catalog.ts#L34), [projection:80](../../../packages/shopify/src/catalog.ts#L80), [detail pagination:145](../../../packages/shopify/src/catalog.ts#L145). The admin projection preserves selected options and variant image URL at [production.ts:53](../../../apps/web/src/server/admin/production.ts#L53).
- Each configured view has one shared/default image and explicit `variantImages` overrides keyed by the full variant ID. Each placement has one shared rectangle and optional variant-specific rectangles. The renderer chooses the matching variant override, then falls back to the shared value. See [geometry shape:24](../../../packages/visualizer/src/geometry.ts#L24) and [resolution:293](../../../packages/visualizer/src/geometry.ts#L293).
- These overrides are per variant combination, such as Blue/S and Blue/M, rather than a first-class Blue colour group. The inspected geometry has no colour-value key or automatic application to every size of a colour. A merchant can reuse the same image reference for several variant IDs, but the stored mapping is explicit. This is a conclusion from the shape and matching logic above.
- Selecting a variant in the older MerchantConfigEditor does not automatically overwrite the saved image. Explicit adoption is tested: an unconfigured selected variant keeps the shared background until “Use selected product image” is clicked; saving then persists a `variantImages` entry. See [editor browser test:559](../../../apps/web/test/admin/editor-browser.test.mts#L559) and [saved assertion:617](../../../apps/web/test/admin/editor-browser.test.mts#L617).
- Geometry selector IDs such as `variant_123` are deliberately converted to decimal `123` for buyer and purchase use. This applies to images and placement overrides, and is called when serving the buyer configuration. It is not an observed ID mismatch. See [normalization:4](../../../apps/web/src/server/merchant-preview/geometry.ts#L4), [buyer call:188](../../../apps/web/src/server/buyer/service.ts#L188), [historical purchase call:76](../../../apps/web/src/server/purchase/service.ts#L76).

## One design across several garment variants

The design group contains one product/config revision, one production specification, and multiple `{variantId, quantity}` entries. Artwork, decoration method and decoration size are selected per placement in that production specification; they do not vary independently per garment colour inside one group. See [group contract:71](../../../packages/contracts/src/v1/pricing-config.ts#L71).

Consequently, the same artwork/method/decoration size can cover Blue/S, Blue/M and Black/L quantities. A different logo or method for black garments is a different design group. Canonical identity includes the artwork/method/step/options but excludes the garment quantity vector, and normalization merges identical design groups while retaining their variant quantities. See [identity:48](../../../packages/domain/src/customization/identity.ts#L48), [normalization:128](../../../packages/domain/src/customization/identity.ts#L128) and the explicit [red-s/black-l test:96](../../../packages/domain/src/customization/identity.test.ts#L96).

The published placement eligibility and pricing scopes are product/placement/method/decoration-size choices. They have no colour/variant eligibility key in the inspected contract. There is no automatic dark-shirt/light-shirt artwork conversion or colour-dependent decoration rule in these structures. See [published shape:51](../../../packages/contracts/src/v1/pricing-config.ts#L51) and [pricing scope:28](../../../packages/contracts/src/v1/pricing-config.ts#L28).

## Real variants survive checkout and historical preview

- Buyer catalog output exposes each variant as `{id, label: variant.title, available}`. It does not expose selected-option metadata as a separate colour model. Availability is read and checked against every chosen variant before issuing/accepting the quote. See [buyer catalog:441](../../../apps/web/src/server/buyer/production.ts#L441), [flattened output:501](../../../apps/web/src/server/buyer/production.ts#L501), [readiness guard:123](../../../apps/web/src/server/buyer/service.ts#L123).
- Cart application adds the actual variant ID and quantity with customization properties. Accepted quotes retain the physical variant vector. See [cart/add:359](../../../apps/storefront/src/cart.ts#L359), [accepted quote:669](../../../packages/application/src/quote/accept-quote.ts#L669).
- Purchase payloads use retained revision geometry and the original selected variant vector, not the current product setup. See [historical revision read:743](../../../packages/database/src/repositories/purchase.ts#L743) and [purchase projection:116](../../../apps/web/src/server/purchase/service.ts#L116).
- Production-sheet previews are shared only when the effective image and placement rectangles match. Different variant overrides therefore produce separate preview batches. See [batch construction:435](../../../apps/web/src/shared/production-sheet-render.ts#L435).
- Copying setup to another product deliberately clears source product/variant imagery and variant geometry overrides. New product images must be assigned separately. See [copy transform:230](../../../apps/web/src/server/merchant-config.ts#L230).

## Limits and evidence

The current buyer configuration rejects products with more than 250 variants or incomplete catalog pagination, each buyer design group accepts at most 32 selected variants, and a view accepts at most 100 explicit image/geometry override entries. See [catalog guard:449](../../../apps/web/src/server/buyer/production.ts#L449), [buyer bound:16](../../../packages/contracts/src/v1/buyer.ts#L16), [geometry bounds:158](../../../packages/visualizer/src/geometry.ts#L158). These are implementation limits, not Shopify platform limits.

Ran the existing focused suites: `@insignia/visualizer` geometry, 8 tests passed; `@insignia/domain` customization identity, 5 tests passed. The former explicitly checks red image switching with shared geometry and a per-variant geometry override at [geometry.test.ts:148](../../../packages/visualizer/src/geometry.test.ts#L148) and [172](../../../packages/visualizer/src/geometry.test.ts#L172). Existing browser-test assertions were inspected, not rerun in this research task. Native Shopify checkout, current polished UI authoring and end-to-end colour switching were not tested here.
