# MVP review: methods, configuration reuse, and image calibration

Research and product review for the merchant garment-placement editor, 23 October 2026. The recommendations below fit the current Lean V1 product model. They are design guidance, not implementation claims or owner acceptance.

## Recommendation

Keep decoration methods as product-local buyer choices copied from the shop's name library. Make the active placement's offered methods easy to find and edit with search when the list grows. Do not add tag rules, live inheritance, or a second layer of method defaults to solve the many-method problem.

Support copying one saved product draft to several products from either entry point. The editor already has a fixed source product; the Products page already owns product selection. Confirm the exact targets, create each target through the existing independent-copy command, refuse occupied targets, and report partial results per product. A copy keeps placement structure and prices, but the target must choose its own product images and review alignment.

Add one A-to-B scale calibration per selected garment image. The merchant marks two points on the image and enters their known distance in centimeters. Use the resulting scale to show approximate physical dimensions for that view's placement boxes. Treat the scale as image-specific and clear it when that image changes. Keep the current manually entered `physicalMm` values separate: they belong to product-wide decoration-size steps, while a calibrated measurement can differ by view and placement. Do not claim manufacturing fit from one image scale.

## Decoration methods

Insignia has two distinct records today. The shop method library stores an ID, name, and version. Adding a library method to a product copies its name into the draft with a new product-local method ID. Renaming or deleting the library entry does not update that draft. A product method becomes a customer option only when a placement allows it and the corresponding price is valid. The product editor already removes a removed method's placement references and prices together. Preserve these identity and cleanup rules. [Method catalog repository](../../../packages/database/src/repositories/method-catalog.ts#L4), [product import control](../../../apps/web/src/islands/MerchantConfigEditor.tsx#L1700), [method-removal cleanup](../../../apps/web/src/islands/MerchantConfigEditor.tsx#L1580), [Lean product contract](../../architecture/implementation-plan.md#72-screens-and-use-cases).

For a manageable list, show method choices inline with the selected placement. Once there are several methods, show a short enabled summary and open a searchable picker to add or remove methods and review their size prices. Keep search, selection count, missing-price state, and Done/Cancel visible while the result list scrolls. Filtering must not clear selections, and Cancel must leave the draft untouched. The existing placement exploration already follows this shape above six methods; it is a good scale pattern, subject to the production draft and save contracts. Do not render a product × placement × method × size matrix. Edit prices for the active placement and summarize readiness elsewhere.

Use stable method IDs, never labels, for checked state, price rows, cleanup, or copy. Two methods can have the same name and still be distinct choices; flag the duplicate name for clarity instead of merging records. Make the source explicit when adding a method: `From your method library` versus `Add product method`. Once imported, say `Product copy` and let the merchant rename it locally. A global library edit should never silently rewrite saved drafts or published revisions.

Shopify's Resource Picker is for Shopify products, variants, and collections. Shopify directs apps to the separate Picker API for app-specific resources. That makes Resource Picker appropriate for product reuse, but not for choosing Insignia's decoration methods. A focused Insignia-owned searchable list is simpler for the current name-only library; the generic App Bridge Picker is only worth adding if methods later gain app-managed metadata that warrants Shopify's picker composition. [Resource Picker API](https://shopify.dev/docs/api/app-home/latest/apis/user-interface-and-interactions/resource-picker-api), [Shopify App Home modal guidance](https://shopify.dev/docs/api/app-home/latest/apis/user-interface-and-interactions/modal-api).

Do not add global method tag-matching, automatically apply rules, or method-level pricing to this MVP. The production library has no such behavior today, the specification keeps final prices on a product, placement, and size tuple, and a tag match is not proof that a product has usable geometry or prices. If rule-based scope returns later, saving a rule and applying it to product drafts must remain separate actions with a preview of exact targets and effects. [Lean product and price contract](../../architecture/implementation-plan.md#72-screens-and-use-cases), [method library contract](../../../packages/database/src/repositories/method-catalog.ts#L4).

## Reusing a product configuration

**From the editor.** Keep the current product as the source. Add a `Copy to products` action that opens Shopify's product Resource Picker in multiple-select `select` mode, excludes the current product, and returns real product IDs. Shopify supports a numeric selection limit, preselection, product filters, and returns `undefined` on cancel. Show selected target names and count before starting. [Resource Picker options and selection](https://shopify.dev/docs/api/app-home/latest/apis/user-interface-and-interactions/resource-picker-api).

**From Products.** Add a `Copy configuration` bulk action to the existing product table. The selected rows are targets; then ask for one source product with the single-select Resource Picker. State clearly that this copies the source into the selected targets. Exclude the source if it is among the target rows and show how many remain. Selection must be backed by stable Shopify product IDs and the current list's actual page/filter state. Shopify's App Home migration guidance puts selected IDs, page-selection calculations, result handling, and selection clearing in the app. For the MVP, keep select-all page-scoped rather than inventing cross-catalog selection. Preserve selected products after a copy failure so the merchant can inspect the result or retry. [Shopify bulk selection guidance](https://shopify.dev/docs/apps/build/app-home/migrate-from-polaris-react/unstable-bulk-actions), [resource-list selection guidance](https://shopify.dev/docs/apps/build/app-home/migrate-from-polaris-react/resource-list).

Only copy a clean saved source draft. Before sending writes, show a compact review with source, targets, and outcomes known from a preflight read: `Will copy`, `Already configured`, or `Unavailable`. Never silently overwrite or merge a target's saved configuration. The current backend rejects an occupied target and uses one idempotent copy command per target. It creates a new config ID and remaps method, placement, size, option, price, and view IDs. Preserve that behavior. Do not add a bulk transaction endpoint for the first version. Run the existing command for each target and keep a per-product result list; if some calls fail, say which copies succeeded and leave failed targets available for retry. A multi-product copy is not atomic. [Copy service](../../../apps/web/src/server/merchant-config.ts#L484), [clone and ID remapping](../../../apps/web/src/server/merchant-config.ts#L150), [copy contract](../../architecture/implementation-plan.md#72-screens-and-use-cases).

The server currently strips the source view image and variant-image overrides when cloning, and it clears variant geometry overrides. It retains the normalized placement rectangles. Do not match media by filename, alt text, array order, or image URL; Shopify media IDs identify resources associated with a product, and media connections are paginated. On each target, ask the merchant to choose from that product's own image gallery, then show the retained rectangles over the chosen target image for alignment review. Keep a view with no target image in a visible `Choose image` / incomplete state. Do not carry an image-scale calibration to a different target image. [Insignia copy transform](../../../apps/web/src/server/merchant-config.ts#L205), [Shopify Product media connection](https://shopify.dev/docs/api/admin-graphql/latest/queries/product), [Shopify Media IDs and images](https://shopify.dev/docs/api/admin-graphql/latest/interfaces/media).

Copying should create drafts only. It does not synchronize later source edits, adapt a placement to another garment, or publish the destination. The current spec explicitly requires independent copies and per-product publication. After a successful copy, open one target editor so the merchant can select media and inspect geometry; keep the remaining targets listed with their result state. If the source has unsaved edits, require the normal Save/Discard decision first, since the existing command copies the saved record.

## A-to-B image calibration

The interaction has a useful first-party product example. Zakeke asks the merchant to drag ruler points A and B to two places on the product image, enter their real-world distance, and then uses that scale for the print-area editor and dimensions. That is close to the smallest interaction that addresses the request. [Zakeke: How to define a Print Area](https://zakeke.zendesk.com/hc/en-us/articles/360016879139-How-to-define-a-Print-Area). InkSoft also keeps a side's image and its print regions together, and only offers a side when its default-color image exists. [InkSoft: Edit Products, Decoration](https://help.inksoft.com/hc/en-us/articles/46724037237787-Edit-Products-Decoration-Blank-Products).

For Insignia, the merchant should:

1. Choose the view image, select `Calibrate image`, and place A and B on a known garment measurement visible in that image.
2. Enter a positive known length in centimeters. Use image-intrinsic coordinates, not CSS pixels, so zoom, pan, canvas resize, and device pixel ratio cannot change the scale.
3. See the measured reference line and resulting centimeters for the active placement outline. Changing the placement should update the readout immediately. Keep position and calibration on the same view and image revision.
4. Recalibrate after replacing the image. Leave variant-specific images uncalibrated until their own reference is supplied; do not borrow the default image's scale for a different color/size photograph.

One line establishes a single pixels-per-centimeter scale. This assumes the photographed surface is approximately flat and viewed without material perspective or unequal stretching. It is suitable for an approximate on-screen dimension readout, not proof that a technique, garment size, or production process can fit that area. Print providers document product-, location-, technique-, and variant-specific limits; Printful also warns about artwork resolution and actual print size. [Printful Design Maker placement and resolution guidance](https://help.printful.com/hc/en-us/articles/50264179910673-How-does-the-Design-Maker-work), [Printful variant scaling example](https://help.printful.com/hc/en-us/articles/50264397552657-How-is-my-design-scaled-for-different-garment-sizes), [Printful embroidery requirements](https://help.printful.com/hc/en-us/articles/50263985175953-How-should-I-prepare-my-design-for-embroidery).

The current model has an important level mismatch. `physicalMm` is stored on a product-wide decoration-size step, and the visualizer calls it display calibration only. A calibrated image gives dimensions for a particular view and normalized rectangle. The same size step can be offered on two placements over differently scaled images, so one step-wide pair of physical numbers cannot represent both. In the MVP, store scale with the view's image revision and use it for a clearly labeled approximate editor readout. Keep explicit `physicalMm` as a separate merchant-declared production size. If merchants need calibrated dimensions to become production facts or published choice bounds, define and validate dimensions at the placement × decoration-size level with variant applicability first. That is a contract change, not a field-label tweak. [Geometry model](../../../packages/visualizer/src/geometry.ts#L24), [visualizer semantics](../../../packages/visualizer/README.md#insignia-visualizer).

Minimum validation is straightforward: reject coincident A/B points, blank/non-finite/zero/negative lengths, and points outside the selected image; show the entered unit next to the length; retain the original input if validation fails; and never silently clamp. Show an explicit `Uncalibrated` state. Treat calibration as invalid when the image revision changes. Do not add multi-point perspective correction, global calibration profiles, automated garment recognition, or technique-specific fit rules to the MVP.
