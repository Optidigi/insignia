The custom-element API is a distinct extraction surface: Polaris Web Components take app-owned text through properties such as `label`, `placeholder`, `accessibilityLabel`, `heading`, `subheading`, `error`, and `helpText`, while native markup uses `aria-*`, `title`, labels, options, tooltips, and live-region nodes. An extractor that visits text nodes alone will miss much of the merchant UI. Astro markup, support components used for the selected previews, and text assembled in TypeScript helpers also need deliberate coverage.

## Copy versus content and protocol data

Keep app-owned UI labels translatable even when they interpolate runtime values. Keep the values separate: Shopify product/variant titles and selected option values; merchant-created view, placement, method, size and price-rule labels; uploaded filenames; order names; and accepted purchase details are content, not message keys. Existing presentation labels in the saved product/order contracts are merchant-authored content and must not be silently translated or re-keyed.

Translate the presentation of stable states, not their identities. Examples already surfaced through label maps are configuration states in `ProductsOverview.tsx` and `product-configuration-export.ts`, payment states in `OrdersOverview.tsx` and `PurchaseArtwork.tsx`, artwork states in `shared/artwork-status.ts`, publication states in `MerchantConfigEditor.tsx`, theme states in `shared/storefront-setup.ts`, and billing states in `MerchantBilling.tsx`. Keep enum values, database state, IDs, Shopify variant IDs, status predicates and URLs unchanged. Do not translate raw JSON, revision IDs, API paths, `aria-keyshortcuts` key tokens, file extensions, hashes or currency codes; translate their nearby captions and descriptions.

## Locale and backend findings

- No i18next runtime, translation catalogue, or application locale directory is present in the inspected `apps`, `packages` or extension sources. The dated plan is the first implementation proposal.
- Merchant locale handling already exists only for formatting in a few client islands: `MerchantHomeContainer.tsx`, `HomeActivity.tsx`, `OrdersOverview.tsx` and `MerchantBilling.tsx` read `shopify.config.locale` with browser fallbacks. `shared/purchase-view.ts` accepts a locale for order dates, relative day names and exact-money display. Other detail/history dates use hard-coded `en` or the browser default, and some number formatters use the environment default. These are partial formatting facilities, not message translation or an SSR locale bootstrap.
- The customer prototype's `ProductConfig.locale` currently drives currency formatting and search normalization; it does not receive a distinct host-selected language prop. Production host language must be explicit and separate from the order currency, Shopify country/Market, and store timezone. The theme block currently passes country/market and a locale-aware cart root, but does not pass a language code. Treat that as an integration contract gap for the chosen customer modal, not a reason to build another store-facing translation system.
- Server boundaries are not a localization layer. `apps/web/src/server/admin/http.ts` and `server/artwork/http.ts` return English `error`/`message` text and HTTP statuses; `shared/admin-request.ts` turns response text into `Error.message`; `merchant-config-editor-workflow.ts`, `method-library-workflow.ts`, upload flows and order views can display those messages. Validation responses carry English `validationIssues[].message` alongside paths. Customer workflow state in `designer-prototype/src/designer-state.ts` stores recovery/upload/cart `message` strings, while `runtime.ts` dispatches English failure messages.
- Migration should keep domain/API semantics stable and localize at the rendering boundary. For server failures, map a bounded, known response code/status and validation path to a catalogue message with typed values. Do not show arbitrary transport exception text as translated UI copy; if the current response contract cannot identify a user-presentable condition safely, add an explicit semantic code rather than teaching i18next about server prose. For customer reducers, store a message identifier plus interpolation values (or a typed state reason), not the resolved translation or translator; resolve under the current locale so a language change updates an active notice without replaying an operation.

## Text and layout edge cases visible in source

- Plural-sensitive copy appears in products, methods, orders, designs, placements, quantities, files and validation counts (`1 issue` versus multiple, selected options, pages, rows, orders and products). Use i18next plural forms, including required locale categories, rather than English `count === 1` branches. Add interpolation types for product/placement names, maximum quantity, counts, prices, filenames and expiry times.
- Unit and formatting copy is mixed with values: `cm`, `mm`, `%`, `MB`/`MiB`, `UTC`, per-item/per-30-day terms, dimensions, and formatted currency. Localize the unit-label construction and number/date formatters without changing exact integer minor amounts, configured physical sizes, accepted quote values or actual Shopify variant identities.
- Customer `FileName` keeps a full filename in its accessible text while clipping the visible stem and conditionally offers “Full filename”; merchant `AdminTruncatedLabel` and `AdminResourceName` also combine content with constrained layouts. Long translated headings/actions and merchant-supplied names need separate truncation and accessible-name checks.
- The selected customer modal has an existing `long-content` fixture, long unbroken option codes, large option lists, a 200-character filename stress case, and responsive evidence at 320/390/1440 widths (documented in the sibling README). Reuse that content stress intent and add a pseudo-locale/representative expansion. Pay special attention to the sticky footer, narrow quantity controls, dialogs, option searches, inline artwork controls, and translated screen-reader announcements. Existing fixture wording is test content, not an actual shipped language.
- Merchant product editor and support previews have longer names, dynamic status/validation text, menus/tooltips and image controls; test the actual preview components at narrow viewport widths and zoom, not only the main body copy. PDF canvas output is independently laid out: expanded translations, long merchant labels, and pluralized headings must be checked for wrap/overflow because the on-screen DOM's truncation checks do not cover the rendered PDF.

## Source-grounded completion checks

Keep the plan's compile-time key/parameter, fallback/loading, request isolation, state-preservation, no-raw-HTML, and readiness checks. In addition, make the inventory mechanically reviewable by:

1. Extracting all shipping app text from the Astro shell/routes, live merchant islands/components, selected preview presentation sources, customer modal sources, and PDF/CSV/ZIP builders. Explicitly exclude test assertions, fixture content, gallery controls, technical identifiers and merchant/Shopify content. The `apps/web/test/admin/support` location is not itself an exclusion rule.
2. Checking every user-visible enum fallback and every error/validation path that crosses from API/workflow state into a banner, field, live region, download panel, or export. Include missing/unknown status cases and ensure raw server strings cannot bypass the map.
3. Verifying Shopify theme extension schema labels through Shopify locale resources, while keeping the editable button label as content and outside app i18next resources.
4. Rendering representative expanded/pseudo-localized Home, Methods, product editor, orders/export, and customer modal states at 1440, 390 and 320 px. Include long names, 200-character filenames, multi-category plurals, modal footer/actions, keyboard instructions, live regions, truncation disclosure, and PDF/CSV/ZIP readability.
5. Verifying the initial Astro shell/skeleton and Preact island share one admin locale, and that the connected modal receives the Shopify storefront language on its owned root without changing the Shopify parent document. Confirm a locale change re-renders current UI feedback while leaving the design, requests, undo history, cart idempotency and accepted totals untouched.
