# Frontend workflow state: typed reducer first, XState by evidence

Researched 27 October 2026 against current Insignia code and primary framework, language, and Stately sources. This is an options note; no application files or dependencies were changed.

## Recommendation

Use a local typed reducer as the default for a **coupled, finite UI workflow** when its transitions need to be explicit and unit-tested. Keep ordinary independent controls in local `useState`. Keep the reducer pure, and run asynchronous work in the event handler or a narrowly scoped effect/service that owns the request lifecycle. Put results back into the reducer as events carrying the identity of the operation they belong to.

Do not make “use a reducer for every screen” or “move all frontend state into a machine” a rule. The practical gain comes from making a specific workflow’s states, accepted events, and recovery paths reviewable. A discriminated union can prevent invalid combinations of workflow data at compile time; it cannot prove that every runtime event sequence is legal, nor validate untrusted network or browser messages.

Consider XState v5 for a workflow whose behavior actually benefits from hierarchical/parallel states, state-owned invoked work, child actors, timers, state-gated events, or generated graph/path coverage. Adopt it in one bounded workflow and keep it optional. Do not introduce Redux or migrate the application’s overall state model as part of that choice.

## Options matrix

| Need | Preact/React typed reducer | XState v5 |
|---|---|---|
| Small finite flow: idle/loading/success/failure, a few retries or decisions | **Best default.** `useReducer` exists in both frameworks; React specifies a pure reducer over current state and action, and Preact describes it as useful when next state depends on previous state. | Usually extra machinery unless the flow already has statechart-specific needs. |
| Keep state data valid by construction | A tagged union can make `loading` carry a request identity and `success` carry data, while avoiding unrelated optional fields. An exhaustive `switch` with `never` detects newly added cases at compile time. | `setup(...)` can infer typed context, events, actors, and snapshots. Stronger workflow notation does not make TypeScript a runtime validator. |
| Reject an event that is inappropriate in the current state | The reducer must explicitly decide which events each state accepts; an unknown or out-of-phase event can leave state unchanged. Typed event names alone do not enforce event/state pairing. | State configuration selects transitions from the active states; an event without a transition is unhandled. This makes state-gating a first-class runtime rule. |
| Async work, cancel/retry, stale results | Own `AbortController` and a request/target key at the smallest scope that can replace the work. Ignore or reject completions whose identity is no longer current. This is already used for product search. | Invoked actors start/stop with their owning state. `fromPromise` receives an `AbortSignal`; pass it to abort-aware APIs. XState v5 source also ignores promise settlement after the actor is no longer active. |
| Nested phases, independent concurrent regions, child workflows | Can model explicitly, but more cross-cutting flags and hand-coded coordination may accumulate. Consider splitting genuinely independent substate into separate reducers/hooks. | **Strong fit.** Statecharts make parent/child states and simultaneous regions explicit, reducing hand-enumerated combinations when the regions are truly independent. |
| Pure transition tests | Call `reducer(state, event)` and compare the next state; no renderer or actor runtime is needed. | Test actor transitions and outcomes. XState v5 exposes pure `transition`/`initialTransition` from v5.19 onward; model/path testing is useful when the graph’s branching justifies the extra model and bounded test paths. |
| Insignia integration cost | No new package or adapter. Supported in both current UI stacks. | Core XState has zero runtime dependencies, but it is still a new state runtime and vocabulary. React has official bindings. Merchant Preact would need a small integration seam; no app-wide rewrite is needed. |

Framework guidance: [React `useReducer`](https://react.dev/reference/react/useReducer), [Preact hooks](https://preactjs.com/guide/v10/hooks/). TypeScript’s [discriminated unions and exhaustiveness checking](https://www.typescriptlang.org/docs/handbook/2/narrowing.html) are available with either approach.

## Async effects: explicit ownership, not “put every command in an effect”

Reducers and state-transition functions should compute next state only. Start user-commanded work from the event handler or a workflow service; use an effect when the work is genuinely tied to render/state lifecycle or is an external subscription. React explicitly distinguishes effects from event logic and says fetch cleanup should abort a request or ignore its result; Preact likewise supports cleanup returned from `useEffect` ([React effects](https://react.dev/learn/synchronizing-with-effects), [Preact hooks](https://preactjs.com/guide/v10/hooks/)).

For agent-authored code, make the async boundary reviewable: record the owner (component/workflow, product/page, and request or generation ID), who aborts it, which success/failure events it emits, and how stale completions are ignored. Keep ownership narrow. Replacing product A’s request should not cancel product B’s independent work. The existing product-list sequence counter is an example of correlating a response to the active query rather than relying on timing ([ProductsOverview request guard](/Users/pc/Development/Insignia/insignia/apps/web/src/islands/ProductsOverview.tsx:114)).

Client cancellation controls client-side work and acceptance of its result. It cannot roll back a server mutation that already arrived. For a mutating operation, interruption may mean “outcome unknown”; resolve that with the server’s idempotency/reconciliation contract and a fresh read, not a UI assumption that abort undid the write. XState’s `AbortSignal` helps with cooperative work and late actor results; it is not a transaction boundary ([XState v5.33.3 promise actor source](https://github.com/statelyai/xstate/blob/xstate%405.33.3/packages/core/src/actors/promise.ts), [React’s fetch cleanup explanation](https://react.dev/learn/synchronizing-with-effects)).

## Static types versus runtime input checks

Use a discriminated union for trusted in-process reducer state and action payloads, and an exhaustive `never` branch so adding a state/event case requires updating the transition logic. This does not guarantee that the reducer refuses every impossible sequence: that is a runtime property of its transition branches. It also does not validate JSON, browser `postMessage`, DOM events, persisted state, or server responses. TypeScript erases types from emitted JavaScript, so values crossing those boundaries still require runtime parsing/validation. The prototype already demonstrates `unknown` plus Zod `safeParse` for window messages; keep that boundary even if the workflow underneath gains a reducer or XState ([TS erased types](https://www.typescriptlang.org/docs/handbook/2/basic-types.html), [TS narrowing](https://www.typescriptlang.org/docs/handbook/2/narrowing.html), [preview message validation](/Users/pc/Development/Insignia/designer-prototype/src/admin-preview.tsx:333)).

XState v5’s `setup({ types })` provides TypeScript inference; it does not turn event types into runtime checks. Do not treat machine typing as input validation. This does not mean reducers must exclude domain observations such as a proposal or accepted quote: they can hold data needed by the current workflow. Keep server authority, validation, and immutable accepted history at their existing owners, and avoid a second competing copy ([Stately XState v4-to-v5 migration guide](https://stately.ai/docs/migration), [TypeScript type erasure](https://www.typescriptlang.org/docs/handbook/2/basic-types.html)).

## Testing and review bar for agent-authored workflow logic

- Before implementation, write a small state/event table: valid states, accepted events, state data requirements, blocked/ignored events, async effect owner, cancellation boundary, stale-result key, and retry/unknown-outcome handling.
- For a typed reducer, test the initial state and each meaningful transition, including invalid/out-of-phase events and the “old request finishes after new request” ordering. Test async ownership/cancellation at the adapter boundary; do not test framework plumbing when pure transition tests cover the rule.
- For XState, first test the machine’s actor transitions and resulting side effects with deterministic actor implementations. Use generated/model-based path coverage only when there are enough guarded branches or lifecycle combinations to justify a second model. Bound unbounded data domains such as counters, dynamic uploads, or arbitrary event payloads; path enumeration otherwise has no finite completion criterion.
- Test the actual browser interaction where focus, page visibility, Shopify bridge behavior, or server mutation semantics change the outcome. A reducer or machine unit test cannot establish those integration behaviors.
- Review claims that “TypeScript makes this impossible” against runtime entry points and casts. `unknown` plus a parser at the edge is the safe default; a type assertion is not validation.

Stately documents actor tests as arrange/send/assert and graph-generated path testing, while warning that unbounded values need a traversal bound ([XState testing docs](https://stately.ai/docs/testing), [model-based testing](https://stately.ai/docs/xstate/v6/model-based-testing)). The current Stately documentation navigation displays an XState v6 alpha masthead on these pages. The behavioral recommendation here is about XState v5: the v5-tagged source and API are checked separately below; do not copy v6-only configuration into a v5 machine.

## Version and adoption qualification

The live npm registry check on 27 October 2026 returned XState `latest` = `5.33.3` and `alpha` = `6.0.0-alpha.70` (`npm view xstate dist-tags --json`). The package page identifies the current published package, and the v5.33.3 tagged source confirms that promise actor logic receives an `AbortSignal`, aborts it when stopped, and ignores a resolve/reject after leaving the active status ([XState on npm](https://www.npmjs.com/package/xstate), [v5.33.3 promise actor source](https://github.com/statelyai/xstate/blob/xstate%405.33.3/packages/core/src/actors/promise.ts), [v4-to-v5 migration guide](https://stately.ai/docs/migration)). The v5 migration guide states that XState v5 requires TypeScript 5.0+; Insignia currently uses 5.9.3, so its declared TS minimum is met.

For XState v5, actor lifecycle/invoke, setup typing, nested and parallel state concepts, and pure transition testing are available. The current Stately site is moving its reference material to v6 alpha, so pin the stable v5 major and consult v5-specific examples before any implementation. Model-based test APIs have changed across XState generations; verify the installed v5 package’s graph/testing exports rather than copying a v6 page’s imports. There is no reason to add XState to the project merely to validate the reducer-first approach.

## Decision rule

For Insignia, make a reducer the default only when several events update one finite, coupled workflow and a state/event table would help reviewers or tests. Keep unrelated UI and domain data outside that reducer. Choose XState v5 for a named workflow when nested or parallel regions, state-lifetime work, child actors, timing, resumability, or graph-wide testing materially simplify coordination. Otherwise, the typed reducer and a clear async owner provide the useful guarantees with less integration and conceptual cost.
