# Insignia Settings V1 product scope

27 October 2026. Research note for the Settings-screen inventory. This records product scope and current source behavior; it does not change the application. The implementation plan is the product/contract authority, while the settings product-truth review records the more recent owner direction and validated current UI behavior.

## Recommended Settings hierarchy

Keep Settings as a small index of four child destinations. Remove the **Decoration methods** row from the hub: Methods already has its own primary app-navigation destination, and the current hub's `/admin/methods` row duplicates it. Keep a Settings breadcrumb on the existing child pages.

| Destination | V1 content that is supported by the product | Boundary |
|---|---|---|
| **Storefront setup** | Check the published theme's customization button and cart-review embed; link to the relevant Shopify theme editor actions; explain product-template coverage and compatibility. | Shopify performs theme changes. The page reads extension status and opens Shopify; it is not a theme editor or publication permission. |
| **App permissions** | Explicitly check product/staff access, checkout setup scopes, and order-scope availability; request only the currently missing optional scope subset after a merchant action; explain owner/staff recovery. | App scopes, signed-in staff authority, and readiness are distinct. Shopify owns the full grant-management screen. Customer-data export has its own owner check. |
| **Billing and plan** | Show only verified provider subscription state, recurring price/discount facts, trial/cycle dates, scheduled cancellation or pending change, access consequence, and the Shopify management/selection handoff. Include exact technical limits once their merchant-facing wording and governing entitlement are settled. | Shopify App Pricing owns plan approval, charges, cancellation and invoice facts. No local card editor, invented net charge, or client-side entitlement authority. |
| **Customer data requests** | Shopify-supplied request inbox and due dates; request details; per-order JSON export of available retained Insignia records; link to the order for retained artwork. Add a short read-only explanation of the real retention limits and export-before-expiry when product wording is approved. | This is an operational request/export utility, not a privacy-policy editor, customer contact database, customer-facing delivery/fulfilment action, or erasure control. Only the authorized store owner can access/export. |

The current hub already has four destinations after removing the duplicate Methods row: Storefront setup, App permissions, Billing, and Customer data requests. The source hub groups the first three under “Customization” and Billing/data requests under “App and account”; the Methods link is redundant because [the primary navigation has a separate Methods item](../../../apps/web/src/components/AdminNavigation.astro#L2-L8). The current hub source lists all five rows at [MerchantSettings.tsx](../../../apps/web/src/islands/MerchantSettings.tsx#L3-L42). Actual setup and access behavior is in [StorefrontSetup.tsx](../../../apps/web/src/islands/StorefrontSetup.tsx#L27-L60) and [MerchantPermissions.tsx](../../../apps/web/src/islands/MerchantPermissions.tsx#L30-L53); the read-only theme actions and Shopify handoff are explicit in [StorefrontSetup.tsx](../../../apps/web/src/islands/StorefrontSetup.tsx#L108-L170).

## Methods is a primary workspace; its defaults snapshot into products

Keep Methods outside the Settings hub as a primary app destination, but preserve the richer owner-designed Methods workflow as the product direction. Two different implementations exist:

- The **integrated production `MethodLibrary`** currently persists `{id, name, version}` and supports adding, renaming, searching, and removing reusable names. Product import copies a selected name into the draft; the production library itself has no price or assignment fields. See [MethodLibrary.tsx](../../../apps/web/src/islands/MethodLibrary.tsx#L14-L20), [its edit controls](../../../apps/web/src/islands/MethodLibrary.tsx#L245-L300), and the product editor's [library import flow](../../../apps/web/src/islands/MerchantConfigEditor.tsx#L1701-L1756).
- The **owner-designed canonical Methods preview** is broader: reusable default fixed pricing per location/per garment or product-specific pricing, manual product selection or live tag matching, product coverage/readiness, and explicit product-price editing. Its controls and saved state are local preview behavior; they do not write production prices, assignments, or publication. See the [README Methods scope](../../../README.md#L48), [product workflow audit decisions](admin-product-workflow-audit-2026-10-24.md#L24-L37), and the [preview direction and implementation record](method-configuration-direction-2026-10-22.md#L78-L86).

Retain the designed separation: **default pricing seeds new product-level method additions/copies; changing that default does not rewrite existing product prices.** Existing products can receive a price change only through an explicit product-price edit. Product assignment is managed separately through manual selection or the method's tag rule; it does not silently overwrite a product's own setup, published revision, or order history. Assignment identifies products using or eligible to use a method; it does not create print-area geometry, valid prices, buyer-ready setup, or publication on its own. These rules are explicit in the [24 October audit](admin-product-workflow-audit-2026-10-24.md#L24-L33). Any production integration must snapshot resolved method defaults into each product's final price table with provenance rather than use live inheritance or guess usage by matching names ([audit's integration gap](admin-product-workflow-audit-2026-10-24.md#L35-L38)).

Keep product-specific work in Products: optional/required mode; product method details; images/views and print-area geometry; decoration-size choices; allowed combinations; and the final price per method × placement × size. Each Shopify product has an independent config and published immutable revision; copying creates another independent config ([plan §3.1](../../architecture/implementation-plan.md#L146-L158), [§7.2](../../architecture/implementation-plan.md#L383-L391)). The product editor uses separate Product rules, Images and print areas, Prices, and Review/publish steps ([MerchantConfigEditor.tsx](../../../apps/web/src/islands/MerchantConfigEditor.tsx#L361-L366)); shop currency is read-only context and changing a draft's currency does not convert existing amounts ([lines 1678–1696](../../../apps/web/src/islands/MerchantConfigEditor.tsx#L1678-L1696)). The product spec says merchant-wide settings remain untouched for currency/Market behavior ([plan §4.2](../../architecture/implementation-plan.md#L216-L220)). The logical schema groups `method_catalog` and `merchant_settings` as mutable merchant defaults ([plan §10.1](../../architecture/implementation-plan.md#L510-L518)); it does not make the current names-only implementation the approved ceiling for the richer Methods design.

## Pricing, limits, and retention: designed versus missing

The current billing implementation still recognizes one Standard recurring contract: USD $49.99 per 30 days and an authoritative 14-day trial, with no usage meter, 100-order allowance, overage, or per-order app charge ([plan §6.6](../../architecture/implementation-plan.md#L351-L357)). The owner’s later direction is a **Free plan plus two paid plans**. That three-slot direction takes precedence for future presentation; names, prices, inclusions, and trusted entitlement mappings are still unspecified. Existing subscriptions are not converted, and the current single-plan contract is not silently changed ([product-truth review](settings-product-truth-review-2026-10-25.md#L33-L39)). Thus the three-card page under test support is structural preview only, with selection disabled and terms explicitly undecided ([settings-plan-preview.mts](../../../apps/web/test/admin/support/settings-plan-preview.mts#L1-L11)). Do not copy that mock into production Billing or invent plan features/quotas. Shopify remains the plan-selection host; final plan setup and server entitlement mapping are dependencies before a real comparison or selection flow can make claims.

The live Billing screen already presents provider-backed price, discount, cycle/trial dates, pending/cancellation states, new-action consequences, and the Shopify handoff ([MerchantBilling.tsx](../../../apps/web/src/islands/MerchantBilling.tsx#L49-L65), [lines 98–239](../../../apps/web/src/islands/MerchantBilling.tsx#L98-L239)). A product gap remains: the product specification requires honest technical-limit disclosure and released-feature/entitlement context ([plan §6.6](../../architecture/implementation-plan.md#L353-L357), [§7.2](../../architecture/implementation-plan.md#L389-L393)), while the current billing view exposes no feature map or limit fields ([billing-view.ts](../../../apps/web/src/shared/billing-view.ts#L1-L20)). Before a commercial tier rollout, define and disclose actual supported features/limits; do not use UI text as an entitlement source.

Retention is a real product policy, not a merchant setting. The current artwork policy limits an individual file to 5 MiB, 100 admissions per day, seven days of retention, five unfinished uploads, and 100 MiB/day / 500 MiB retained per shop ([artwork.ts](../../../packages/application/src/artwork/artwork.ts#L4-L12), [artwork repository](../../../packages/database/src/repositories/artwork.ts#L158-L173)). Purchased design payloads have a separate six-calendar-month maximum in the product-truth review ([review](settings-product-truth-review-2026-10-25.md#L21-L31)) and product spec ([§10.4](../../architecture/implementation-plan.md#L552-L560)). The spec requires warnings before deletion at 30 and 7 days plus authorized export/download; it does not define merchant-controlled durations or notification preferences. Keep exact record expiry and warnings in the order/artwork workflow. A read-only policy explanation can fit Customer data requests, but warning delivery/content is a dependency to resolve, not a new notification-settings surface. Downloads must not renew retention ([review](settings-product-truth-review-2026-10-25.md#L25-L31)).

Customer-data access/export has stronger boundaries than ordinary Settings: the page labels the owner-only requirement ([MerchantPrivacy.tsx](../../../apps/web/src/islands/MerchantPrivacy.tsx#L317-L326)); request detail shows received/due/order count and per-order retained JSON export, with artwork linked through the order ([lines 441–519](../../../apps/web/src/islands/MerchantPrivacy.tsx#L441-L519)). The review confirms that exports are fresh, authorization/retention checked, do not include artwork binaries, and do not mark a Shopify request fulfilled or erase it ([settings product-truth review](settings-product-truth-review-2026-10-25.md#L27-L31), [follow-up](settings-product-truth-review-2026-10-25.md#L72-L84)).

## Out of scope and dependencies

- Shopify owns merchant identity, staff accounts/roles, password and two-factor security, payment methods, invoices, theme edits, tax, and billing. No Insignia profile, team, card, or theme editor is supported here.
- No Insignia notification preferences, language/date/appearance preferences, shop currency/Market controls, analytics/usage dashboard, data-deletion toggle, or configurable retention-period control is evidenced by current product behavior.
- Before three-plan Billing claims ship: decide the two paid prices, all plan names/inclusions, Free-plan entitlement, trial policy, limits, migration treatment for existing Standard subscriptions, and versioned server entitlement mapping; configure and qualify the matching Shopify App Pricing offers. The app’s current fixed Standard UI/reader must be reconciled before rollout.
- Before retention copy/notifications ship: bind wording and notices to actual persisted expiry dates, settle who receives the required 30-/7-day warnings and how delivery failures are handled, and keep authorized export available. Do not imply preferences or extend deadlines.
- Source map cleanup for later implementation: [implementation-plan §7.3](../../architecture/implementation-plan.md#L395-L412) says the root Settings route includes readiness and omits the `/admin/settings/permissions` row, but the actual hub only renders navigation and the separate permissions page is routed at [settings/permissions.astro](../../../apps/web/src/pages/admin/settings/permissions.astro#L1-L14). The map should be reconciled when that implementation inventory is next edited.
