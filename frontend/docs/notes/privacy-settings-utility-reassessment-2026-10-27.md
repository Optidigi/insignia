# Customer data requests: minimal useful Settings surface

27 October 2026. Independent product and UX reassessment against current Shopify documentation, Insignia's webhook/export path, and the refreshed desktop, 390 px, and 320 px captures. No application, test, or store changes made.

## Recommendation

Shopify requires the compliance webhooks and the app's handling of the requested app-held data; it does not require a dedicated Settings page, inbox, initiation card, email, export format, or completion button. Keep **Customer data requests** as Insignia's current owner-facing retrieval path because it exposes records Shopify does not hold. Keep it explicitly supplemental: the owner opens the Shopify-originated request in Insignia, downloads the available Insignia records, and uses the order page for artwork that remains available.

The prominent **Start a request in Shopify** card was confusing and redundant. Shopify owns that initiation flow; Insignia's part starts when the webhook arrives. It also contradicted the empty state's “No action is needed.” The refreshed source and captures remove it. The current empty state, two-column request/due list, request-specific detail, and optional **About data requests** help action are a minimal honest screen. No extra settings page or pseudo-fulfillment step is warranted.

## Supported owner route and limits

1. The owner starts the request from Shopify's customer profile. Shopify provides Shopify-processed data on the profile and emails that Shopify data to the owner; the merchant decides what to provide to the customer. Shopify's guide does not say that this export or email includes Insignia-held design records. [Shopify merchant guide](https://help.shopify.com/en/manual/privacy-and-security/privacy/processing-customer-data-requests)
2. Shopify sends the app a `customers/data_request` webhook. The app must provide its requested data to the store owner directly; Shopify's developer guidance does not prescribe the app's UI or delivery channel. Shopify also requires the app's three compliance topics and says to complete the action within 30 days. [Shopify privacy compliance](https://shopify.dev/docs/apps/build/compliance/privacy-law-compliance), [privacy requirements](https://shopify.dev/docs/apps/launch/privacy-requirements)
3. Insignia verifies and durably receives the webhook, then processes it into a request ID, order links, and requested/matched counts. Processing erases the raw contact-bearing webhook body and captured fields. The merchant API is read-only; request and export reads are scoped to the authenticated shop, and current app auth requires the account owner for order and artwork access ([webhook route](../../../apps/web/src/server/shopify-webhook.ts#L61-L75), [merchant route](../../../apps/web/src/server/purchase/http.ts#L49-L73), [owner authorization](../../../apps/web/src/server/admin/auth.ts#L168-L174), [privacy repository](../../../packages/database/src/repositories/customer-privacy.ts#L12-L20), [privacy migrations](../../../packages/database/migrations/20261017000100_customer_privacy.sql#L118-L150), [export migration](../../../packages/database/migrations/20261017000200_privacy_merchant_export.sql#L1-L66)).
4. In Insignia, the owner opens the request, downloads fresh JSON for matched Insignia orders, and opens the related Insignia order for available artwork. The downloaded file stays with the owner; it is not sent to the customer, and Insignia records no completion state ([MerchantPrivacy.tsx](../../../apps/web/src/islands/MerchantPrivacy.tsx#L388-L526), [purchase service](../../../apps/web/src/server/purchase/service.ts#L168-L174)).

The visible “Request 19” is Shopify's data-request ID, not a customer-profile locator. The persisted records do not retain customer ID, name, or email. Matched orders provide Shopify order IDs that an owner can use to find an order manually; the current screen offers no direct Shopify customer link, and a zero-order request has no order-based locator. Do not imply a customer identity is available. A direct customer locator would require a deliberate data-retention decision; the webhook already includes customer identity, but the current design intentionally discards it after processing.

There is no app email or other outbound request notification in the inspected web/worker implementation. The existing request inbox is owner-pulled. That is a product discoverability dependency, not a reason to add instructions or a notification preference. If proactive alerting becomes a requirement, choose and implement a real owner-facing alert that links to the existing detail; do not infer that Shopify's export email carries Insignia's records or add an unsupported “fulfilled” action.

## Pixel evidence

The refreshed [desktop empty state](../../../../.artifacts/admin-popup-review-2026-10-24/settings/desktop/settings-privacy-empty.png), [desktop request list](../../../../.artifacts/admin-popup-review-2026-10-24/settings/desktop/settings-privacy-requests.png), [desktop detail](../../../../.artifacts/admin-popup-review-2026-10-24/settings/desktop/settings-privacy-detail.png), [390 px empty state](../../../../.artifacts/admin-popup-review-2026-10-24/settings/mobile/settings-privacy-empty.png), and [320 px empty state](../../../../.artifacts/admin-popup-review-2026-10-24/settings/narrow/settings-privacy-empty.png) were inspected after regeneration. The initiation card is gone, the short purpose copy remains visible, and the empty state wraps without clipping. The detail keeps the request due date and order-specific available/unavailable data together. No new pixel defect was confirmed in these captures.

This is a focused retrieval utility, not an end-to-end privacy workflow. The existing UI should not claim otherwise.
