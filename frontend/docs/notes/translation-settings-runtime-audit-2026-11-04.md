# Translation settings runtime audit

4 November 2026. Read-only architecture audit for the newly authorized merchant UI for choosing customer translation languages and editing customer wording. This request supersedes the earlier plan's decision that interface localization alone did not need a Settings page. No application source, tests, builds, catalog artifacts, or Shopify resources were changed.

## Recommendation

Keep three kinds of text separate:

1. **Staff admin language** continues to come from Shopify App Bridge (`shopify.config.locale`) and is owned by the admin localization controller. A merchant setting for buyer copy must not change the language of the person using Shopify Admin.
2. **Customer UI copy** is app-owned text in the `common` and `customer` namespaces. Merchant-authored translations should be an overlay keyed by stable catalog message IDs, not edits to the shipped source catalog.
3. **Shopify and merchant content**—product, variant, option, placement, method, size and filename values—stays supplied content. Editing that content is a product-configuration/content workflow, not translation of app messages. The buyer UI's fixed theme button label is also a Shopify block setting, not a catalog message.

The localization foundation already enforces the first two audiences in its entry points, but it has no runtime override source or persistence contract. The package advertises only English; `en-XA` is a development stress catalog. A Settings screen can author records, but it cannot truthfully promise storefront delivery until the customer runtime consumes them and a shared persistence path exists.

The observed Shopify Translate & Adapt editor is a useful content pattern: language/category navigation and a three-column table for field label, read-only source/reference, and editable target text. It exposes accessible copy, plural forms and variables such as `{{count}}`; empty target fields use the source value. Reuse that manual-entry model, with no automatic translation. Keep coverage visible so sparse overrides are explicitly shown as a partial customer copy set, not a shipped or fully supported language.

For a frontend-only iteration, store only non-sensitive copy overrides in browser storage, label them **saved in this browser**, and preview the current in-memory draft in the local customer prototype. Do not label that state as saved to the shop or visible to customers. A future customer overlay can use the exact storefront locale selected by Shopify and fall back per missing key to the English source, matching the blank-field behavior in Translate & Adapt. Keep `SUPPORTED_LANGUAGES` as the registry of shipped/advertised catalogs; a merchant overlay for `en-US` or another tag is per-shop copy, not a new built-in catalog. Because partial overlays produce mixed-language screens, show per-language coverage and test the actual `lang`/direction and assistive behavior before claiming full language support.

## Current source contracts and gaps

- `packages/localization/src/core.ts` declares `SUPPORTED_LANGUAGES = ['en']`. `resolveLocale()` keeps an English regional tag for `Intl`; unsupported language families use English text, English formatting and `lang="en"`. Pseudolocale support is opt-in and development-only in the customer app.
- `packages/localization/src/customer.ts` bundles only `common` and `customer`; `admin.ts` separately owns admin and editor-preview catalogs. `createCustomerTranslator()` currently creates an i18next instance from compiled-in JSON, with complete English fallback. There is no API for passing merchant overrides.
- Generated catalog types and parameter contracts cover the compiled English catalog. Runtime message parameters are checked, but user-edited message text is not validated for placeholder parity. Customer plurals include `_one`/`_other`; a new language may require more categories. `i18next` handles plural selection, but current code does not validate a merchant-authored plural family.
- The package guide says English is the only advertised language, and the implementation record says no additional language, native Shopify acceptance, or live customer-cart integration is established. The approved plan says catalogs are source-controlled, namespaces are allowlisted, missing/empty keys fail checks, values are plain text, and Shopify's buyer language is separate from country, Market and currency.
- There is no translation settings route, Settings API, application/domain record, database schema, typed DTO, or customer storefront read path for merchant translations. `merchant_settings` is mentioned in architecture as existing mutable settings but no translation feature is exposed through it. Do not invent an endpoint or reuse product-label storage without a contract change.
- Shopify's `shopify.config.locale` is the current staff language, not a list of the shop's published customer languages. The theme blocks now pass `localization.language.iso_code` and direction in source, but source markup does not prove a deployed theme, selected buyer design, or native Shopify runtime consumes merchant overrides. Do not discover translation targets from the staff locale or imply Shopify language-management behavior.

## Proposed module and state model

Keep the UI thin around one deep settings module, for example `apps/web/src/islands/customer-translations-workflow.ts`, with its reducer in `customer-translations-state.ts` and a small storage adapter in `apps/web/src/shared/customer-translations-storage.ts`. The workflow should own catalog-version validation, normalization, persistence outcomes, dirty tracking, stale-operation guards, and derived coverage so that the page does not repeat these rules.

Keep the caller interface small: `getSnapshot()`, `subscribe()`, `load()`, `selectLanguage(tag)`, `editMessage(key, form, value)`, `resetMessage(key, form)`, `resetLanguage(tag)`, `save()`, `discard()`, and `dispose()`. Inject a storage port. Production's first adapter may be browser `localStorage`; tests can use an in-memory adapter. This seam is useful for the two actual adapters, not an API transport abstraction for a backend that does not exist yet.

Suggested state:

| Field | Meaning |
| --- | --- |
| `phase` | `loading`, `ready`, or `storage-unavailable`; successful absence is `ready` with an empty saved record. |
| `saved` / `draft` | Last confirmed stored record and the editable copy, both keyed by canonical target-language tag and approved customer message ID. |
| `revision` / `savedRevision` | Monotonic in-memory edit revision and the revision associated with the stored baseline. |
| `operation` | `idle`, `saving` with request ID and immutable submitted snapshot, or `failed` with a reason code. |
| `catalogRevision` | Shipped message-contract version against which overrides and plural forms were reviewed. |
| derived selectors | `isDirty`, `canSave`, `coverageByLanguage`, `missingRequiredForms`, `languageStatus`, and `effectivePreviewCopy`. |

Events should represent facts (`load-started/succeeded/failed`, `language-selected`, `message-edited`, `message-reset`, `language-reset`, `save-started/succeeded/failed`, `discarded`, `catalog-updated`, `storage-unavailable`), not translated sentences. The UI maps reason codes to current admin-locale messages at render time. The customer translator consumes only a validated, immutable customer overlay snapshot.

Save a snapshot and its revision when a write starts. If the user keeps editing while that write is pending, a successful response updates the saved baseline to the submitted snapshot but preserves later edits as dirty. A failed write leaves the full draft intact. Do not let a stale load or save response replace a newer language choice or draft. While a write is pending, either disable Discard/Cancel or define a real cancel contract; a UI button cannot claim to cancel storage that may already have committed. With synchronous `localStorage`, writes are atomic in one task, but keeping these reducer semantics makes the UI safe if a future remote adapter is approved.

Treat storage access as a result, not a boolean: `missing`, `loaded`, `invalid-record`, `unavailable`, `saved`, or `write-failed`. Accessing `window.localStorage`, `getItem`, `setItem`, JSON parsing and quota failures can all fail. If storage is denied, retain session edits for preview if useful, show a persistent unsaved state, and never report success. Use a loading state until the first client read settles; a failed read should still reveal a usable page with the storage warning. Use a validated shop domain for a browser-local storage key, as `home-guidance-preference.ts` does. That key only scopes a local preference; it is not authorization or tenant proof.

## Locale, key, interpolation and update rules

- The language picker needs an explicit source. Current package support gives it only `en`; development `en-XA` must not appear as a merchant language. There is no Settings API that lists the store's published languages. Do not use `shopify.config.locale` as that list: it is the current staff locale. Until a Shopify-owned language read is implemented, treat any manually entered canonical BCP 47 tag as a **translation target** only, display its exact tag, and do not say Shopify has enabled or published it. A future store-locale read is a separate integration and permission decision.
- A customer-only overlay can be keyed by the exact storefront locale supplied by Shopify (for example `en-US`) without adding that tag to the global supported-catalog registry. On that one buyer instance, use the matching manual entries and fall back to the English source for blank/missing fields. Show coverage and state that remaining copy is English. Do not claim the overlay is a bundled or fully reviewed language catalog. Keep staff Admin and guest resolution unchanged. The source/reference column is read-only; editing `en-US` creates an overlay and never mutates canonical `en` JSON.
- Partial per-message fallback is honest in the editor if coverage and source fallback are explicit. Before live use, verify document `lang`/`dir` for the Shopify-requested locale and English fallback pronunciation for screen readers. If the runtime cannot mark the source language for fallback fragments, record that as a mixed-language accessibility limitation rather than claiming a complete localized screen. The existing package resolver by itself will still render complete English for non-English request tags; it needs the separate customer-only overlay path described above to render custom entries.
- Use only message IDs from the customer translator's `common` and `customer` tables. Do not expose `admin-shell`, Settings, `admin-preview`, guest copy, IDs, API errors, or development labels through this editor. Generate or validate the runtime message manifest from the canonical catalogs so the editor cannot drift from typed keys. Include hidden accessible names and announcements when eligible; a visual-text-only list is incomplete.
- Overrides are sparse plain-text values. Blank or whitespace-only target means “use the read-only source/reference”; resetting a key deletes its override. Reject HTML/markup and render values as normal text. For each parameterized message, require the same named placeholders as the source (allow reordering), preserving the generated parameter contract. Keep parameter values as values; do not concatenate translated fragments or let edited copy change action logic.
- Plural messages are one family. Show each required form separately; source English `one`/`other` are references, while a target language needs the forms reported by `Intl.PluralRules(tag)`. Keep each missing form on source fallback and show it in coverage; do not copy one authored count form into all categories. Keep raw safe integer `count` for selection, and use the current formatting path for displayed digits.
- Persist a schema/catalog revision and retain unknown or obsolete entries for review instead of applying them to a similarly named new message. If source meaning, placeholders, or plural categories change, mark affected overrides as needing review. Reset language/all removes only the custom overlay and restores shipped defaults; it does not rewrite product labels, base catalogs, or Shopify content.

## Settings and preview integration points

The natural entry is a new `/admin/settings/translations` child route and a row in `MerchantSettings.tsx`. The proposed UI can mirror the observed Shopify pattern: a language target selector, category navigation from a curated customer-message manifest, and rows with a field label, read-only English reference and editable target value. Expose plural forms and placeholder names clearly without requiring merchants to edit raw i18next JSON. Add its title/route/loading keys to `packages/localization/src/catalogs/en/admin-shell.json` and `settings.json`, wire `apps/web/src/pages/admin/settings/translations.astro`, and add the new path to `shared/admin-route.ts`, `components/AdminPageSkeleton.tsx`, and the title list in `shared/admin-i18n.ts`. Keep the page's `locale` prop on `withAdminLocale`: that is the staff-facing Settings language. Add a breadcrumb back to `/admin/settings`. The existing Settings hub has three live destinations; customer-data requests were removed, and `/admin/settings/methods` is a legacy redirect, not a template to clone.

The local Settings preview is the loopback harness in `apps/web/test/admin/preview.mts`, `support/settings-preview-fixtures.mts`, and `support/settings-preview-browser.mts`; `settingsArea()` currently knows only Storefront, Billing and Permissions. Add a language-editing scenario there only as a local fixture. It must not fake an application endpoint or Shopify permission. Browser tests should inject a memory/denied storage adapter or explicit local scenario and state the local-only behavior.

For buyer preview, the selected `designer-prototype` already has a per-mounted-Designer customer locale controller (`src/customer-locale.ts`, `src/designer.tsx`) and `DesignerProps.locale`; its catalog entry point is the immutable `@insignia/localization/customer` artifact. The editor-launched `AdminPreview` uses the admin translator for preview wrapper copy and passes a locale to the buyer `LocalDesigner`. The older loopback customer-preview bridge (`apps/web/test/admin/support/placement-customer-preview.mts`) uses a nonce, expected source/origin, and a product-only `postMessage` snapshot. None of these paths accepts a merchant override today.

Send the current **draft** to a local buyer preview through an explicit validated prop or the existing same-origin-checked, nonce-bound preview handshake. Do not try to read admin `localStorage` from the buyer preview: the selected app runs on another origin/port. Keep separate `adminLocale` (wrapper/Settings) and `customerLocale` (buyer text); `AdminPreview` currently uses one locale for both. Update preview on edits, reset it on Discard, and label it as local. A live storefront requires a shared shop-scoped storage/API read path, customer package support for overlays, and the appropriate installed theme/runtime; this note does not establish any of those.

If the selected customer runtime is changed later, edit the canonical `packages/localization` source first and update the immutable artifact/lockfile with the sibling app in the same delivery. The generated tarballs in `designer-prototype/vendor` are distribution artifacts, not editable catalog sources.

## Focused verification cases

- Pure state transitions for empty/malformed/version-old storage, canonical language tags, sparse/blank overrides, per-key and whole-language reset, catalog update/review, and selectors for coverage and plural completeness.
- Interpolation tests prove exact placeholder-name parity per form, safe count values, plain text output for `<`, `>`, `&` and quotes, and fallback to shipped English for missing/invalid entries. Reject admin keys and supplied product/config names from the override schema.
- Workflow races cover two out-of-order loads, save failure retaining edits, a new edit while a save snapshot is pending, stale save completion, discard/cancel during save, disposal/navigation while reading, and denied/throwing/quota storage. A success status is emitted only after the storage adapter confirms the exact snapshot.
- Browser coverage checks staff language changes without changing the customer target, edited draft versus saved preview, reset/discard propagation, translated accessible labels, long wording at narrow widths, and a `localStorage` denial message that still permits honest in-session preview.
- Preview bridge checks wrong source/origin/nonce rejection and bounded schema validation for the copy snapshot. No local test should be reported as proof of Shopify Market configuration, persisted shop-wide settings, a deployed buyer bundle, native theme language propagation, or cart mutations.
