# Localization step-one inventory

3 November 2026. The owner authorized step one of the [complete frontend localization plan](localization-implementation-plan-2026-11-02.md). This records current text ownership, source boundaries and responsive/reveal concerns. No application, dependency, translation catalog, store setting or user workflow was changed.

## Result and evidence

The recommended i18next/Preact approach still fits. Before replacing strings, fix the boundaries where English prose currently controls behavior, distinguish supplied names from generic app fallbacks, and preserve each existing full-name disclosure path. Translation itself must not reset an editor, change variant identity or alter accepted commerce facts.

The maintained [file inventory](i18n-inventory-2026-11-03/files.csv) maps **379 files**, including source, styling, fixtures, assets, generated output and the unselected integration boundary. It records each path, source hash, area, scope, proposed message owner and migration disposition. It is not a claim that 379 files contain translatable messages. The [summary](i18n-inventory-2026-11-03/summary.json) records the exact discovery scope; [layout candidates](i18n-inventory-2026-11-03/layout-candidates.csv) link wrapping/clamping rules to their source lines.

Discovery parsed 263 TypeScript/TSX/MTS/JavaScript sources using the installed TypeScript AST and 16 Astro files using the installed Astro compiler. There were no parser diagnostics. Liquid and its schema were inspected separately; the line-candidate scan is not a Liquid parser. Generated/minified theme bundles were excluded from extraction. The raw discovery found 4,957 text candidates and 162 layout-policy candidates. These include technical prose, fixtures and repeated/dynamic expressions, so **neither number is a translation-key count or a list of defects**. Message-by-message acceptance belongs to catalog migration.

Three independent Luna Max source audits cover the requested families:

- [Admin, selected Methods/editor presentation and shared controls](i18n-step1-admin-luna-2026-11-03.md).
- [Selected customer modal, quantities, state and editor preview](i18n-step1-customer-luna-2026-11-03.md).
- [Orders, artwork, generated output and theme boundaries](i18n-step1-outputs-luna-2026-11-03.md).

The main agent checked their findings against current source, corrected scope/citation mistakes and made the inventory's audience assignments explicit. Separate current-language browser observations are described below. The agent source notes and candidate scans do not prove translated fit.

## Responsive and truncation rules for migration

Use wrapping and flexible control groups for essential app messages. Do not shrink type, shorten a precise error or ellipsize a primary action merely to preserve the English geometry. W3C recommends flexible reflow and notes that short labels can expand particularly strongly. [Text expansion](https://www.w3.org/International/articles/article-text-size.en.html), [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html).

1. Keep actions, field labels, errors, prices and option distinctions readable. Check native component internals and shadow DOM as well as outer wrappers. Fixed popovers, pinned table cells, editor sidebars and sticky modal footers are the main constrained groups in this source snapshot.
2. Preserve valid existing truncation. Resource names already use shared overflow measurement with resize/font observation; filenames retain full screen-reader text and the extension. The artwork library and Review have full-filename disclosure. The compact artwork-choice button reaches the library through Change. Check each context rather than declaring every ellipsis a defect or adding repeated reveal buttons.
3. Verify full-text access for keyboard and touch. An accessible name or native `title` alone does not prove a visible reveal path. `AdminTruncatedLabel` deliberately relies on its owning selection/detail field on touch, so its outline/image-picker contexts need separate acceptance checks.
4. Use actual clipping to decide whether a single summary needs disclosure. Preserve multiple-value summaries and their complete list. The measured condition must update after translated text, resize and font changes.
5. Keep the quantity layout stable during UI-only translation. Its twelve-code-point size-label heuristic operates on supplied content, not on translated UI labels. If Shopify supplies newly localized content that changes the layout choice, preserve the focused cell/dirty value or deliberately restore them. Do not replace every existing length limit with grapheme counting: file-extension recognition, persisted maximum lengths and layout heuristics have different contracts.
6. Preserve long-name distinctions and original text. Do not truncate a stored filename, SKU or variant value. Use display-only bidi isolation around supplied names; never mirror product/artwork geometry as a language effect.
7. Translate full statuses and count messages, including hidden quantity/search/validation announcements. The quantity no-results paragraph is not currently a live status. Verify its actual announcement behavior before choosing the smallest appropriate change; avoid noisy duplicate announcements.

These are requirements for the translation migration, not evidence that all current layouts are broken. The [Checklist Design typography](https://www.checklist.design/design-system/typography), [tooltip](https://www.checklist.design/design-system/tooltip) and [button](https://www.checklist.design/design-system/button) checklists were read from the installed skill. The [item-by-item source/baseline audit](i18n-step1-checklists-2026-11-03.md) records the applicable checks and limits without treating source inspection as translated-screen approval.

## Current-language baseline and verification limits

Captured Products, Orders, Methods, Settings and the selected customer modal at **1440, 390 and 320 CSS pixels**, using fresh local browser contexts and the existing installed browser. All 15 final observations have document width equal to viewport width. Internal horizontal table scrolling remains intentional. DOM overflow checks found expected product-name/summary clamping on narrow Products and filename-stem clipping on the 320px customer example.

The main agent inspected representative actual PNGs and DOM measurements. Independent Luna reviewers inspected Products 390, Methods 320, Settings 390 and customer 320. No new current-language defect was established in those captures. The Methods outer-host title pressure and local demo footer are preview chrome, not grounds to change shipping app copy. Resource tooltip relationships were observed, but the tooltips were not activated; filename reveal routes were checked in source, not exercised.

Artifacts: [baseline measurements](../../../.artifacts/i18n-step1-2026-11-03/baseline.json), [customer 320](../../../.artifacts/i18n-step1-2026-11-03/customer-320.png), [Products 390](../../../.artifacts/i18n-step1-2026-11-03/products-390.png), [Methods 320](../../../.artifacts/i18n-step1-2026-11-03/methods-320.png), [Settings 390](../../../.artifacts/i18n-step1-2026-11-03/settings-390.png). The raw [text candidates](../../../.artifacts/i18n-step1-2026-11-03/text-candidates.csv), AST discovery helper and baseline capture helper are local evidence, not shipping source or translation catalogs.

Two initial capture-harness assumptions were corrected: the preview's iframe document can briefly have no documentElement, and the standalone Designer component uses `.app[data-step]` rather than supplying its embedding host's dialog wrapper. The four affected observations were rerun successfully. These were harness failures, not application fixes. The Playwright MCP lacked its requested browser executable; the audit used the repository's already-installed Playwright/browser instead, without installing anything.

No translated or pseudo-localized UI, 400%-zoom pass, complete keyboard/screen-reader pass, actual translated PDF, native Shopify host language propagation or live cart mutation was tested. No application unit/build suite was necessary for these documentation-only changes. The next implementation stage must retain these acceptance checks, especially full-value access and draft/focus preservation.

## What step two needs from this inventory

Build the shared typed catalogs/runtime and locale boundary with these dispositions, then migrate complete message families. The English-comparison and warning-classification sites need semantic reasons at the same time as their messages are moved. Keep saved merchant labels and protocol/export representations out of the catalog, include the selected preview app copy, and supply the editor preview's merchant-language context separately from storefront language. There is no need for another page, automatic product-type inference or a new backend translation feature to complete this step.
