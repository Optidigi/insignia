# Admin localization inventory: step one

**Date:** 2026-11-03
**Scope:** Source inventory of the Insignia merchant admin and the selected admin presentations under `apps/web/test/admin/support`. This is an audit, not an implementation or localization test.

## Scope and source method

Read `AGENTS.md`, `docs/delivery/notes/localization-implementation-plan-2026-11-02.md`, and `docs/delivery/notes/i18n-text-inventory-luna-2026-11-02.md`, then checked the current source tree and route mounts directly. The repository has unrelated pre-existing working-tree edits; this note records the current checkout and makes no app changes. No dependencies were installed and no translation, target-locale render, or fit validation was run. I reviewed the existing current-English baseline captures `products-390.png`, `methods-320.png`, and `settings-390.png` under `.artifacts/i18n-step1-2026-11-03/`; these are layout baseline evidence only, not translation validation.

In those three captures, product resource names visibly ellipsize and capture metadata records the overflow-tooltip relationship; I did not activate or evaluate the tooltip. The Methods 320px view uses the narrow-screen details layout, and Settings copy wraps without obvious clipping at 390px. These are current baseline behaviors; I found no new defect in these views. Longer translated strings and reveal accessibility remain untested.


The product boundary matters: the merchant admin is in `apps/web`; `apps/storefront` is a backend-integration surface, and the customer-facing preview is a sibling modal/prototype. The selected local-only methods and product-setup presentations below are inspected because they were requested, but they are not represented as deployed admin screens.

In the coverage table, paths abbreviated as `src/...` or `test/...` are relative to `apps/web`. Coverage is exhaustive by the requested live/admin and selected-preview families, not a literal key-by-key extraction. Other Orders/detail and artwork-management screens, the sibling customer modal itself, and `apps/storefront` are outside this admin audit (except live artwork upload embedded in the product editor and the specifically requested historical-preview comparison below).

Source establishes that a string, prop, route, state mapping, or CSS rule exists. It does **not** establish its translated rendering, actual host-component speech, truncation outcome in a locale, or visual usability. Those are marked as rendered-validation risks below.

## Consequential correction to the prior inventory

The live Methods page currently mounts `src/islands/MethodLibrary.tsx` (`apps/web/src/pages/admin/methods.astro:1-15`). Its support workflow, searchable/filterable method index, editor modal, picker, and local fixtures are separate loopback preview code: the preview file explicitly says the workflow is frontend-only and saved in the browser tab (`apps/web/test/admin/support/method-workflow-preview.tsx:1-3`); the preview host serves and swaps that bundle (`apps/web/test/admin/preview.mts:153-160,371-390,625-634`). Likewise, the live product editor mounts `MerchantConfigEditor` (`apps/web/src/pages/admin/products/[productId]/config.astro:32-34`), whereas the selected placement workflow explicitly says it is local-only and makes no Shopify writes (`apps/web/test/admin/support/placement-workflow-preview.tsx:1`). The preview host builds and substitutes that support bundle only in its local preview path (`apps/web/test/admin/preview.mts:88-98,335-369,611-623`).

This is a route/runtime and packaging boundary, not a reason to defer inventory. The owner-selected preview-designed Methods and editor presentations are included in the localization inventory under the same `admin.methods.*` and `admin.editor.*` workflow namespaces as the live features, even though their current implementations are served only from loopback preview. Keep the preview host, developer bridge/bootstrap, harness controls and fixture/demo content out of the releasable application bundle/catalog. Do not represent the preview implementation as the current production route mount.

## State and error mapping gaps

1. **Raw request copy leaks into some live views.** `admin-request.ts:39-56` preserves a response message/error in `Error.message`. Live `MethodLibrary.tsx:211-244` renders workflow error text, and `method-library-workflow.ts:45-119,190-230` stores raw error messages. The editor workflow similarly returns raw message text and validation details (`merchant-config-editor-workflow.ts:131-138,560-587,734-783`; `MerchantConfigEditor.tsx:2702-2708`). Add a finite code-to-message map at the app/API boundary; use a generic translated fallback for unknown errors. Preserve safe interpolation values only where their contract is defined.
2. **Validation issue paths are not labels.** Editor renders `${issue.path}: ${issue.message}` (`MerchantConfigEditor.tsx:2702-2708`). Paths are technical and messages can be server-authored. Map known paths to field keys and known issue codes to translated messages; never expose an untranslated path as if it were user prose. Unknown issues should retain a safe localized fallback without hiding which field needs attention where possible.
3. **Preview event messages are arbitrary strings.** `ProductsOverview.tsx:55-62` accepts a `CustomEvent.detail.message` string and stores it in `selectionMessage`; state accepts arbitrary strings (`islands/products-overview-state.ts:9-18,87-89`). Local preview bridge currently emits English `Error` messages (`placement-setup-copy-entry.tsx:20-43`). This is a preview event contract, not API-authored copy; map the surfaced failure through the selected Products preview workflow’s `admin.products.*` message keys and keep event/bridge code in the development entry point.
4. **Several stable enums already have display maps; audit completeness rather than translating enum tokens.** Products maps config states (`ProductsOverview.tsx:27-45`); live Home maps order statuses (`merchant-home.ts:133-154`); permissions state is reduced before display (`permissions-state.ts` and `ReadinessPermissions.tsx:134-217`); billing has status branches (`MerchantBilling.tsx:54-128`). Ensure every discriminant and fallback is represented once, while technical enum values remain stable.
5. **Model fields blur data and app-authored strings.** Home renders `task.reason`, `task.actionLabel`, `model.notice` and `model.message` (`MerchantHome.tsx:347-364,721-726,749-754; unavailable branch 592-609). Trace their source: locally constructed task/action copy should resolve through message IDs; Shopify/product/order labels stay content; API-provided text needs an explicit allowlist/map. `HomeActivity` formats numbers in Shopify/browser locale but can consume `periodLabel` (`HomeActivity.tsx:24-39`); formatting alone does not localize its labels.
6. **Pluralization and locale formatting are mixed.** Method preview summary, live Home activity, billing cycles and product result/count text contain manually selected singular/plural or interpolated strings. Use localized plural rules for user counts. Billing uses locale-aware date formatting (`MerchantBilling.tsx:9-14`) but manually concatenates currency/period/cycle wording (`:120-163`); preview EUR formatting is demo code and should not become the live implementation contract.
7. **Status text is not uniformly semantic.** `StorefrontSetup` derives labels/actions from task state, `ReadinessPermissions` constructs status messages in UI, and publication code exposes `publishEligibility.reason`/raw status fallbacks (`MerchantConfigEditor.tsx:2585,2711-2742`). Normalize each enum/code at its source; do not rely on English status phrases as backend state.
8. **Live editor artwork upload carries a second raw-message path.** `ArtworkUpload.tsx:34-58,60-78` displays requirement/status text plus retry and download actions; line 34 chooses a compact requirement by exact comparison with an English sentence, so changing the copy independently can make this logic miss. `use-artwork-upload.ts:118-129` forwards any `Error.message`, and `:164-210` creates successful/error messages including a timestamp via `Date.toLocaleString()` without the Shopify-configured locale used elsewhere. The helper (`artwork-upload.ts:108-192`) has app-authored failure messages and protocol-validation errors. ## Recommended admin namespace and sequencing

Use contextual admin namespaces at the route/shared-component boundary, for example:

- `admin.shell`, `admin.routes`, `admin.recovery`, `admin.shared.*`, `admin.shared.loading`;
- `admin.home.*`, `admin.products.*`, `admin.methods.*`, `admin.editor.*`;
- `admin.settings.*`, with `admin.settings.billing`, `admin.settings.permissions`, and `admin.settings.storefront`;
- `admin.states.*` for finite cross-route semantic status/error families and separate `admin.exports.*` for file output.

Prefer keys for complete messages, plural rules for count-dependent copy, and structured interpolation for data. Use the established `admin.methods.*` and `admin.editor.*` namespaces for app-owned strings in the owner-selected preview-designed workflows as well as their live routes. Keep the developer preview bridge, harness-only controls and fixture content separate from the releasable catalog/bundle. Do not introduce a generic key solely because two strings happen to share English wording if their action/state context differs.

Suggested inventory implementation order after this audit: (1) finite app-owned shell, settings, state, and shared-control strings; (2) full Home and Products plus live and selected preview-designed Methods workflows; (3) live editor plus selected preview-designed product-setup editor and error-code/validation normalization. Keep their route/runtime distinction intact while extracting the app-owned workflow copy. The current plan’s shared runtime approach may still be suitable, but this audit does not verify package configuration or translated rendering.
