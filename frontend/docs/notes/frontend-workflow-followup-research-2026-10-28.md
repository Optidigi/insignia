## Initial findings

### P2 — Fixed: A second buyer review canceled and replaced the first

`buyerReducer` accepts another `review-started` event while already reviewing ([buyer-state.ts:147-163, 283-291](../../../apps/storefront/src/buyer-state.ts#L147)). The controller's `isBusy()` only covers authorization, cart application and removal, and the presentation selector maps `reviewing` to ordinary `editing` ([buyer-state.ts:203-205, 541-578](../../../apps/storefront/src/buyer-state.ts#L203)). In the component, each `review()` calls `lane.next()`, which aborts the previous request ([customizer.tsx:331-335](../../../apps/storefront/src/customizer.tsx#L331), [buyer.ts:83-99](../../../apps/storefront/src/buyer.ts#L83)). The review button remains enabled because it is disabled only by that `busy` selector, and the status region does not announce a pending review ([customizer.tsx:842-853, 1323-1338](../../../apps/storefront/src/customizer.tsx#L842)).

The request is a `POST /quote-proposals`. The server creates a new UUID and stores each proposal before replying, so a request already received can continue after the browser aborts it ([buyer/http.ts:71-76](../../../apps/web/src/server/buyer/http.ts#L71), [buyer/service.ts:254-270](../../../apps/web/src/server/buyer/service.ts#L254)). Rapid repeat clicks can therefore issue duplicate proposal work and consume the request limit.

Keep editing available so an edit can cancel the current review, but claim the current review submission until that attempt settles. Render a pending status and disable only the duplicate review action. Add a browser regression that holds the quote response, presses Review twice, and observes one POST plus a pending status through the actual custom element. The existing reducer test covers stale review results but not this caller wiring ([buyer-state.test.mts:76-107](../../../apps/storefront/test/buyer-state.test.mts#L76)).

### P2 — Fixed: The prototype dropped its unload warning for a dirty empty edit

`hasUnappliedDraft` compares an edited design's placements and quantities with the saved cart snapshot ([designer-state.ts:322-329](../../../../designer-prototype/src/designer-state.ts#L322)). The `beforeunload` effect instead registers only while `prints.length` is nonzero ([designer.tsx:685-692](../../../../designer-prototype/src/designer.tsx#L685)). If a merchant edits a saved design, removes every placement, and retains the dirty edit, `prints.length` becomes zero while `hasUnappliedDraft` remains true. A page reload or close then loses the in-memory draft without the warning that this effect is meant to provide.

Use the same draft predicate for the unload guard, keeping the current preview exclusions. Add a browser check that edits a saved design, removes all placements, and verifies the unload event is still blocked. The model already owns this decision, so it does not need another state machine.

### P3 — Fixed: An expired proposal left an enabled Add to Cart action

When acceptance begins after expiry, the buyer reducer moves to recovery but retains the proposal ([buyer-state.ts:292-300](../../../apps/storefront/src/buyer-state.ts#L292)). The UI renders Add to Cart whenever a proposal exists and disables it only while busy or after application ([customizer.tsx:1340-1349](../../../apps/storefront/src/customizer.tsx#L1340)). Clicking the stale action again repeats the same local expiry rejection. The Back action can clear the proposal and let the buyer request a fresh review, but the primary action still presents itself as Add to Cart.

Show a direct fresh-review action once the proposal expires, or clear the stale proposal while retaining the expiry message. Cover that state in a browser check that advances time beyond expiry and confirms the visible next action requests current prices rather than trying the same expired proposal again. A reducer test currently confirms the proposal remains available for a fresh review ([buyer-state.test.mts:156-169](../../../apps/storefront/test/buyer-state.test.mts#L156)); the gap is how the UI presents that recovery.

## Persisted merchant editor review

The editor review found and verified three concrete issues: configuration creation could run against a stale retained empty view after authorization was cleared; malformed persisted pricing could be exposed as an editable draft if geometry alone passed; and an uncertain publication key could remain stuck after its exact retry was definitively rejected against a newer saved draft. These are fixed. Creation now requires an observed current view ([merchant-config-editor-workflow.ts:775-783](../../../apps/web/src/islands/merchant-config-editor-workflow.ts#L775)); drafts are parsed against `MerchantDraftSchema` and geometry before exposure ([merchant-config-editor-workflow.ts:159-167](../../../apps/web/src/islands/merchant-config-editor-workflow.ts#L159)); and the stored publication identity is retired only after that exact request returns 409 and a product/config/generation-matched read proves the server is in DRAFT on another draft version ([merchant-config-editor-workflow.ts:728-754](../../../apps/web/src/islands/merchant-config-editor-workflow.ts#L728), [transaction test](../../../apps/web/test/admin/merchant-config-editor-workflow-transaction.test.mts#L297)). A matching or still-progressing publication remains recoverable with its original key. Independent Node 24 verification passed 18/18 editor workflow and transaction tests; the editor agent separately reported its focused browser checks green.

The buyer's accepted Add to Cart command also remains in flight if the custom element is disposed after server acceptance: unmount clears UI ownership, but the user already authorized the accepted cart application. `apply()` intentionally continues after `acknowledgeAcceptance()` returns false; stopping there could strand a server-accepted command. Removal and renewal check ownership before mutation/issue because they are still at a precondition stage ([customizer.tsx:411-447, 449-516](../../../apps/storefront/src/customizer.tsx#L411), [controller disposal test](../../../apps/storefront/test/buyer-state.test.mts#L280)). A later review reproduced the advisory-fingerprint rejection edge after cart application. Root moved fingerprint creation and optional confirmation into the same best-effort `try/catch`, so notification and workflow completion follow the already verified application ([customizer.tsx:434-449](../../../apps/storefront/src/customizer.tsx#L434)). An independent Sol review reran the injected failure regression and observed completed cart status ([final Sol review](frontend-workflow-final-sol-review-2026-10-28.md#final-advisory-confirmation-correction)). This edge is fixed; accepted in-flight cart work still continues if the UI is disposed.

## Local preview icon transport

The current Admin layout loads Polaris with an async script ([AdminLayout.astro:30](../../../apps/web/src/layouts/AdminLayout.astro#L30)). The preview harness previously looked only for a `defer` tag after replacing the Polaris URL, so its app iframe loaded Polaris with native `fetch`; the outer preview frame had the shim, but app icons still requested the CDN. The local browser reproduced 11 direct app-frame icon requests and only three same-origin outer-frame requests. The harness now matches the localized runtime script independent of its original loading attributes, then loads the transport and pinned runtime as ordered deferred scripts ([preview.mts:583-590](../../../apps/web/test/admin/preview.mts#L583)).

The icon transport redirects only HTTPS `cdn.shopify.com` requests with the exact fixed Polaris icon path/hash and no credentials, port, query or fragment; it creates a same-origin URL and sends no caller headers or body ([preview-icon-transport.mts:4-31](../../../apps/web/test/admin/support/preview-icon-transport.mts#L4)). The server accepts only the fixed `icons|experimental` five-hex SVG route and GET, and the loader constructs the fixed public CDN URL with redirect rejection, a timeout and a bounded SVG body ([preview.mts:435-460](../../../apps/web/test/admin/preview.mts#L435), [preview-assets.mts:8-77](../../../apps/web/test/admin/support/preview-assets.mts#L8)). The blocked-CDN browser regression now passes: all asserted app and host icons render from local assets, no direct browser CDN request occurs, and malformed namespace/hash/query and non-GET paths remain rejected ([preview.test.mts:494-584](../../../apps/web/test/admin/preview.test.mts#L494)). The companion preview navigation and no-command/no-production-credential checks also pass; the stale-expectation cleanup target passed 5/5.

Shopify's current [Admin UI extension Icon reference](https://shopify.dev/docs/api/admin-extensions/2026-10-rc/web-components/media-and-visuals/icon) documents `s-icon` as the Polaris component for its predefined icon set. The local pinned runtime fixture is the unmodified Polaris 2.0 RC source, with its retrieval date and digest recorded in [the fixture README](../../../apps/web/test/fixtures/README.md#L1). This implementation changes the local preview only.
