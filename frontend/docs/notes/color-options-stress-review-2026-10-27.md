# Color-option authoring stress review

Independent Luna Max review, 27 October 2026. This is a model and interaction review of the two color-variant research notes and the inspected source. It does not change or verify application behavior. The scenarios below are hand-worked acceptance cases, not test results.

## Recommendation

Use explicit Shopify-option grouping as an authoring shortcut, with the actual Shopify variant IDs remaining the identities used by geometry, inventory, quotes, and purchases. Let the merchant choose which catalog option fields distinguish garment appearance. Build groups from the exact values present in the current product, such as `Color=Black + Fit=Tall`. A group is a compact image assignment, not an arbitrary condition.

This is a narrower and safer version of color grouping. It handles `Pattern`, `Material`, or `Fit` when those fields change the garment photo. It does not guess that an English option called "Color" exists, and it does not require a new view for every value. Front and Back stay views. A view has a shared photo and one photo per appearance group. A placement keeps its shared artwork rectangle unless the merchant adds a visible group or exact-variant alignment exception.

I agree with grouping authoring and full variant IDs underneath, with three qualifications:

1. If grouped assignments expand to `variantImages` entries, the current 100-entry per-view limit still applies. For example, assigning one image to Blue across 12 sizes uses 12 entries under today's schema. The group editor cannot claim to solve that limit. A group-native persisted mapping would avoid size-by-size repetition, but it needs a geometry contract and resolver change.
2. An ID-only saved map cannot infer that a newly added size should inherit an image. Retain the exact option-group definition in the draft and re-expand it against the current Shopify catalog on save/publish, or stop and require the merchant to assign the new variant. Never silently treat a stale ID map as complete.
3. The current catalog projection only supplies selected option names and values, not a stable option identity. Names can be translated or renamed. Add a stable source option key before promising durable option grouping; if no stable key is available, flag the grouping as stale when the source options change and ask the merchant to confirm it again.

For a first bounded implementation, I would save group definitions in the draft, compile them to exact variant-ID image and rectangle entries for the existing renderer, and show the expanded entry count before save. Stop at the current limit of 100 per view or placement. If real products need more than 100 mappings, change the geometry contract deliberately to store group assignments directly. Do not expand the limit implicitly by hiding IDs behind a nicer editor.

## Model comparison

| Model | Where it works | Where it breaks | Verdict |
| --- | --- | --- | --- |
| A. Edit each full variant | Exact control for unusual crops, construction, and images; matches the current geometry key. | Blue/S, Blue/M, and Blue/L need repeated work. It reaches the 100 image or placement-override entry cap quickly and makes a normal color palette look like a long SKU checklist. | Keep as the exception mechanism, not the only authoring path. |
| B. Color groups, shared geometry, exceptions | Fast when one option value maps to one photo and all sizes share the same composition. | Color alone is not a reliable appearance key. Fit and material can change the cut; patterns may be colors in the catalog without being hex colors; a view can be missing for just one group; and photo crop does not prove shared placement alignment. Expansion to IDs still hits the current limits. | Do not ship the naive form. Retain only the explicit grouping and exception parts. |
| C. Product/config per color | Works when the merchant already has separate Shopify products with genuinely separate setup, prices, or production methods. | Splitting a combined product duplicates view and placement setup, separates mixed-color quantities, and makes config drift likely. It also does not make different colors in one Shopify product independently eligible for methods or prices. | Support existing separate products as they are. Do not require a split for ordinary colors. |
| D. General conditional rules | Can describe many combinations on paper. | Adds precedence, overlap, fallback, and coverage questions to every view and placement. A merchant would need to predict which rule wins for each real SKU; publishing can be correct syntactically and wrong visually. It still does not define variant-specific methods/prices. | Reject for this scope. No arbitrary predicates, wildcards, or priority stacks. |
| E. Exact option-tuple groups plus exact exceptions | Groups real catalog variants by chosen fields, e.g. `Color × Fit`. It can reuse one image for all sizes and lets one placement exception handle a crop difference. | Needs stable source-option identity and a clear stale-catalog check. In the current ID-expanded contract, it remains bounded by 100 entries. | Recommended. This is a bounded form of B, not an inference engine. |

## Scenario decision matrix

`A` is per full variant; `B` is naive color grouping; `C` is a separate product/config per color; `D` is an unrestricted rule engine; `E` is the recommended exact option-tuple partition. The last column gives the concrete resolution expected from E.

| Scenario | A | B | C | D | E and expected recovery |
| --- | --- | --- | --- | --- | --- |
| One color option and six garment sizes, same front/back photos and alignment | Correct but six repeats per view. | Good default. | Unnecessary duplicate product setups. | Works, with needless machinery. | Choose `Color`; one group image per view covers the six actual size variants. Keep all six variant IDs and prices. Show the number of covered variants. |
| `Color × Size × Fit`, where Tall has a different body cut | Precise if the merchant edits every SKU. | Wrong when Color alone applies the regular-fit photo to Tall. | Works only if Tall and Regular are already separate products. | Can match Fit, but introduces rule priority and preview burden. | Choose `Color + Fit`; enumerate only tuples that exist. Assign each group a view photo. A newly added size in an existing tuple can inherit its photo after catalog refresh; a new Fit or Color value is unmatched and blocks publish until assigned. |
| Material changes the garment photo, or the option is `Pattern=Floral` rather than a color | Exact but repetitive. | Color-only grouping misses the real visual dimension and may invent hex swatches. | Requires another product split. | Can express it, but arbitrary conditions add no value here. | Choose `Material` or `Pattern` as an appearance field. Use an assigned product photo or text label if the catalog supplies no color swatch. Never fabricate a hex chip from the value string. |
| Option labels are localized or renamed (`Color`, `Colour`, `Couleur`) | Full IDs avoid matching by translated name. | Hard-coded English detection selects the wrong or no field. | Separate products do not solve field matching. | String matching can silently change behavior after rename. | Select the exact Shopify option field once and bind the group definition to a stable source option key. Names are display text. With the current name/value-only projection, a changed field name is stale and requires confirmation, not a guessed remap. |
| Front image exists but Back image is absent for one group | The missing SKU can be found, if the merchant checks each one. | Shared fallback can show another color's back and look valid. | A separate product may still lack its back image. | Fallback rules can hide the hole. | Coverage is tracked per group per view. Show `Back: missing for Black + Tall`; do not fall back to another group. The merchant assigns the correct back image, explicitly marks a shared image intentional, or removes the unsupported back placement before publish. |
| One group photo has a different crop; the logo area should move | Exact per-SKU rectangle works but repeats across sizes. | Shared geometry places the logo incorrectly; changing the base rect may not fix all photos. | Separate configs can have separate rectangles but copy work. | Can add conditional geometry with priority ambiguity. | Keep the shared rectangle as the base. Add a `Black + Tall` alignment exception for this placement, or an exact variant exception for one unusual SKU. Preview each exception. Editing the base rectangle must preserve and label existing exceptions. |
| A new size is added under an existing Color+Fit tuple | New ID has no mapping until assigned. | May appear to inherit, but that depends on undocumented propagation. | Another product/config only if the catalog was split. | A broad rule can match it, perhaps unintentionally. | Refresh the catalog, re-expand the saved tuple, and show the new size in coverage. Review the preview before publish. If using only materialized IDs without the retained tuple definition, reject publish as stale. |
| A new Color or Fit value is added | New ID is unconfigured. | Color-only may incorrectly reuse another group's photo. | Requires new product/config if the catalog was split. | A wildcard may catch it accidentally. | The tuple is absent, so report `new appearance group: Color=Green + Fit=Tall`. Require an image for each configured view and alignment review. Existing published revision and accepted purchases remain unchanged. |
| Two manually assigned groups can match the same variant | One exact variant entry is unambiguous. | Overlap can silently pick a group or shared fallback. | Separate product configs avoid overlap by separation. | Requires a precedence rule. | Prefer generated disjoint groups from exact option tuples. If manual membership is allowed, reject save/publish with the conflicting variant and group names; never pick a winner. |
| Same garment image is used by two artwork designs or by another product | Image mapping remains separate from design identity. | Usually works, but grouping must not merge designs. | Encourages copying configs and may cause drift. | Rules do not improve media identity. | Reuse the media reference freely. Keep it product-scoped in setup; keep artwork/method/size in design identity and actual variant IDs in the quantity vector. Sharing a photo must not merge or couple designs. |
| One selected variant is sold out, or variant prices differ | Exact SKU identity preserves status and price. | A group can make an unavailable size look selectable if it collapses variants. | Separate product does not solve availability. | A price rule can accidentally conflate image grouping and SKU pricing. | Show a shared group image, but expose availability and price per real Shopify variant. Disable the sold-out combination. Grouping only changes imagery/alignment. |
| Material variants need different methods, print sizes, or decoration prices | Current model cannot express this per variant. | Image grouping does not solve it. | Separate Shopify products/configs can support genuinely different setup if merchant accepts losing one mixed-variant product. | Rules could add it, but this is a separate model expansion. | Do not duplicate Methods, sizes, or prices inside image groups. Require methods/prices valid for every variant in this product. If they are not, block readiness and split the Shopify products or define a separate variant-eligibility/pricing change. |
| 250 catalog variants, with 20 visual groups and 10 sizes per group | A hits 100 image entries if every SKU has a photo. | If expanded to IDs, B also reaches 200 entries and fails current geometry validation. | 20 product configs are operationally expensive. | Could use 20 predicates, with the rule risks above. | Group-native storage needs only 20 group images, but that requires new geometry support. With current geometry, reject save at 101 expanded entries and report the count. Catalog eligibility remains capped at 250 variants either way. |
| Customer selects 33 actual size/color combinations in one design | Per-variant authoring does not change cart capacity. | Grouping may falsely make 33 SKUs look like a few choices. | Product splitting changes the purchase model. | Rules do not change the cap. | Keep the 32 selected-variant limit visible and count actual variant IDs. Reject the 33rd selection before quote creation with a recoverable message. Image groups never count as one cart variant. |

## Where the interaction belongs

Keep the product setup as one configuration. Choose the appearance fields once in the product's existing variant summary. The field picker should list the product's actual Shopify options and show how many groups they produce before the merchant applies them.

Assign images from the existing selected View's image control. Front, Back, and Side stay separate views; each view shows a shared image and the groups that differ. A missing group/view pair is visible in that view's readiness summary. Assigning an image to one group must not add another view tab.

Edit alignment in the existing selected Placement's artwork-area controls. The base rectangle stays shared. Reveal a group or exact-variant override only when the merchant asks for a different alignment. Preserve overrides when the base rectangle changes and show which group still has its own alignment. This is photo alignment only. It does not change physical print bounds, artwork size, method eligibility, or price.

Keep Shopify garment Size distinct from Insignia decoration Size. Keep Shopify variant options distinct from the buyer's production `design.options`. Keep product/placement Methods and prices where they already live. Do not repeat those settings for every appearance group.

The latest placement editor is a local preview workflow, not production persistence or a live Shopify authoring feature. These locations describe a fit with that workflow; they do not claim implementation exists.

## Invariants and reject/resolve states

1. Every configured view resolves an image for each current variant, either through an exact group/variant mapping or an explicitly intentional shared default. Missing images never fall through to an unrelated color's image.
2. Every view/placement resolution starts with the shared image/rectangle and applies an exact group assignment, then an exact Shopify-variant exception. The order is fixed. There is no generic rule priority.
3. Editing a base placement rectangle does not erase a group or variant rectangle exception. The preview identifies the active exception so the merchant can decide whether to retain or reset it.
4. One product variant belongs to one appearance group for a selected view. Overlapping manual groups reject save/publish and name the actual conflicting variant. Prefer deriving disjoint groups from exact tuples so overlap is not a normal authoring state.
5. New size under a known tuple can be matched after catalog refresh; the editor marks the new variant and previews it before publication. A new option value creates an unmatched group and blocks publication until resolved. A renamed/translated source option without a stable option key marks the saved grouping stale instead of silently shifting it.
6. Catalog count is checked independently from image mapping. More than 250 catalog variants remains unavailable to the current buyer projection. A group does not bypass that limit.
7. Buyer selection count is based on actual variant IDs, not appearance groups. The 33rd selected variant is rejected under the current 32-variant design limit before quote creation.
8. Availability and base price stay per actual Shopify variant. A shared image does not indicate stock, price, or method compatibility.
9. A material-driven method/price difference is outside photo grouping. Current product methods and prices apply across variants. If one product cannot use a common valid method/price setup, readiness must fail; do not imply that the image group handles it.
10. A published configuration and accepted purchase retain their revision and variant IDs. Catalog changes produce a stale/new draft review; they do not rewrite accepted history.

## Proposed-model experiment

I ran a small standalone Python model with independent sample catalog rows and expected results. The [script](../../../../.artifacts/color-variant-research-2026-10-27/proposed-model-experiment.py) and [saved output](../../../../.artifacts/color-variant-research-2026-10-27/proposed-model-experiment.out) live outside product source. All 11 proposed-model checks passed. Two checks print the unsafe alternative directly: a Color-only mapping sends `blue-s-tall` to the regular-fit photo, and 11 color groups expand to 110 per-variant image entries, above the current 100-entry cap. The missing Blue Back case resolves to missing even though a Black Back photo exists.

The script uses its own resolver and geometry records. It imports no Insignia code. These results check whether the proposed rules are internally consistent; they do not establish current application behavior, product integration, or merchant usability.

## Evidence and limits

The current Shopify catalog projection preserves a variant's Shopify ID, title, selected-option `name`/`value` pairs, and image, but not a stable option ID ([catalog DTO and projection](../../../packages/shopify/src/catalog.ts#L7-L18), [projection](../../../packages/shopify/src/catalog.ts#L80-L98)). The buyer projection currently emits `{id, label, available}` for variants rather than a structured Color/Size/Fit matrix ([buyer catalog](../../../apps/web/src/server/buyer/production.ts#L499-L506)). Therefore stable option grouping is a data-model requirement, not a capability demonstrated by the current buyer UI.

Geometry currently stores one shared image, up to 100 explicit variant image entries per view, one shared rectangle, and up to 100 per-variant rectangle overrides per placement ([geometry shape](../../../packages/visualizer/src/geometry.ts#L24-L35), [validation](../../../packages/visualizer/src/geometry.ts#L152-L184)). The renderer selects exact variant values and then falls back to shared values ([image and rectangle resolution](../../../packages/visualizer/src/geometry.ts#L293-L309)). That fallback is convenient for intentionally shared products but cannot prove the photo or alignment is right for every variant.

The buyer accepts up to 250 catalog variants, rejects a truncated catalog or more than 250 in the service, and limits each selected design to 32 actual variants ([buyer contract](../../../packages/contracts/src/v1/buyer.ts#L10-L16), [catalog limit](../../../packages/contracts/src/v1/buyer.ts#L90-L100), [service guard](../../../apps/web/src/server/buyer/production.ts#L447-L455)). A customization group stores a separate design and `{variantId, quantity}` vector ([contract](../../../packages/contracts/src/v1/pricing-config.ts#L71-L84)). Canonical design identity uses placement/method/step/artwork and production options, not the garment image mapping ([identity](../../../packages/domain/src/customization/identity.ts#L48-L86)).

The existing research note records that design quantities preserve actual Shopify variants, variant availability and prices remain authoritative, and purchase previews read retained revision geometry. These facts support grouping as a display mapping only, not as a new commerce identity ([model research](color-variant-model-research-2026-10-27.md)). No product source changed and no application tests were run in this review.
