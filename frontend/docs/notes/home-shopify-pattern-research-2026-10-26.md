# Shopify App Home pattern research

26 October 2026. Official Shopify design and Polaris research for Insignia's hosted iframe App Home. The assignment covered the landing page across first use, setup, no-orders, active, collection and error states; it did not change application code or validate a new composition. The Shopify-native browser inspection is recorded separately by the parent task.

## Source and version boundary

I used the installed Shopify `polaris-app-home` skill and its documentation-search helper with `--api polaris-app-home --version 2.0-rc` and `OPT_OUT_INSTRUMENTATION=true`. Results linked to Shopify's current `/v2.0/` documentation. The local app still selects [`polaris-2.0-rc.js`](../../../apps/web/src/layouts/AdminLayout.astro) and [`@shopify/polaris-types` `2.0.0-rc.3`](../../../apps/web/package.json); the pinned declarations confirm the Section and Empty state elements described below.

Shopify's current [web component versioning page](https://shopify.dev/docs/api/app-home/v2.0/web-components/versioning) now says Polaris 2.0 is stable, recommends the `polaris-2.js` channel for production, and documents `polaris-2.0.js` as the frozen release. The page says a release candidate URL is not promoted in place; an app must change its script URL to move. This differs from the 20 October project guidance that described 2.0 as a release candidate. Treat the installed RC pin as the app's current state; this research does not make a runtime migration decision. The `2.0-rc` search request resolving to `/v2.0/` pages also means the official web-component docs are a current 2.0 contract, not an independently preserved RC snapshot.

## Decisions for the Home page

Shopify describes Homepage as the first landing page and an opportunity for useful daily value. It calls out actionable information, attention items, setup guidance, status and possibly metrics. This supports a task-focused operational overview. It does not require a dashboard full of cards, promotion, news, integrations or numbers. The [Homepage template](https://shopify.dev/docs/api/app-home/v2.0/patterns/templates/homepage) models card-like content as `s-section`s: identify each section, put its whole-section actions in its header, use the supplemental area for section status, keep simple rows directly in the section with dividers, and reserve bordered tiles for independent items in a grid. A section with no visible heading still needs an accessible label.

Use the app's real state to select the content. Keep first-use setup, a successfully loaded empty collection, a populated collection and an error as different states. Shopify's [Empty state](https://shopify.dev/docs/api/app-home/v2.0/web-components/feedback-and-status-indicators/empty-state) guidance explicitly covers empty lists, tables, unconfigured features and filtered results; it distinguishes those from non-empty status messages, for which it recommends a banner.

| Home state | Shopify pattern fit | Insignia decision |
| --- | --- | --- |
| No setup yet | The [Setup guide](https://shopify.dev/docs/api/app-home/v2.0/patterns/compositions/setup-guide) is for essential onboarding/configuration tasks and completion tracking. | Show only the few real prerequisites that get a merchant to a working setup. Derive checkmarks and progress from saved state. Link steps to the existing Products, Methods or Settings workflow that owns them. Keep the list directly in one named section, with dividers, rather than boxing every step. |
| Setup underway | Setup guide tracks completion and can be placed on Home or a dedicated onboarding page. | Keep the guide while it helps the merchant complete a real task. Do not show a second callout for the same first action. A dismissible section is an example, not an obligation; only hide it if the app can remember that choice and still leave a clear way back to setup. |
| Setup done, no orders | Empty state is for a resource that loaded successfully and has no records; it can explain the situation and offer up to two actions. | Use a concise empty state in an Orders or recent-orders section. Offer only a real next step, such as opening an existing setup workflow if it can help create a sellable product. Do not render fake zero-valued metrics, a success banner, or an error message for a legitimate no-orders result. |
| Active shop | Homepage is intended to surface actionable items and daily value. A [Metrics card](https://shopify.dev/docs/api/app-home/v2.0/patterns/compositions/metrics-card) is specifically for useful numbers or trends, with trend indicators only when comparison adds context. | Prioritize true operational attention and a small, useful order summary if current APIs support it. Add a metric only when its data is available, scoped and meaningful to the merchant. Link to the owning collection for full work; Home should not become a second Products or Orders index. |
| Products, Orders, Methods or Settings content | Shopify's [Index template](https://shopify.dev/docs/api/app-home/v2.0/patterns/templates/resource-index) is for managing resource collections; its [Index table](https://shopify.dev/docs/api/app-home/v2.0/patterns/compositions/index-table) supports collections and capabilities such as search/filter or bulk operations. [Resource list](https://shopify.dev/docs/api/app-home/v2.0/patterns/compositions/resource-list) is a compact way to browse/select a smaller set and navigate to a full representation. | Keep editing and collection management on their route. A Home section may link to that route or show a compact, supported summary; do not duplicate the full table, filters, or editor there. Shopify names Products, Orders and Settings as common navigation destinations. Methods is Insignia's domain-specific destination, not a Shopify-mandated page. |
| Load or action error | [Banner](https://shopify.dev/docs/api/app-home/v2.0/web-components/feedback-and-status-indicators/banner) is for important status, errors, success or warnings; [Spinner](https://shopify.dev/docs/api/app-home/v2.0/web-components/feedback-and-status-indicators/spinner) is for asynchronous loading. | Keep an error separate from the empty state. Place a banner in the affected section or at page top, state the actual problem, and expose only a recovery action that exists (for example, retry or reopen from Shopify). For a delayed in-place read, use a scoped spinner with an accessibility label; Shopify says to show it when work takes longer than 500 ms. Preserve the project's silent route-transition skeleton convention from [admin UI guidance](admin-ui-guidance-2026-10-20.md). |

This state mapping is an Insignia recommendation from Shopify's pattern criteria, not Shopify's required copy or a claim that every summarized datum/action exists. Validate each proposed count, completion flag, route link, retry and sales-readiness phrase against the live app's query and action contract before showing it.

## Optional compositions: when they fit

- **Setup guide:** use for a short sequence of essential setup steps that the app can truthfully mark complete. It is an interactive checklist, not an onboarding illustration. Shopify describes it for Home or a dedicated onboarding page.
- **Metrics card:** the pattern describes displaying important numbers/statistics/trends, and says to include trends when historical comparison adds context. It does not prescribe a metric for every Home. The pattern search lists Index as its recommended template, so a metric card should not be assumed to belong on Home just because Homepage mentions metrics generally.
- **Callout card:** Shopify says to use sparingly for a new feature/opportunity, app capability adoption, or a common first action, and remove it once the merchant has engaged. It should not become a permanent promotional hero or duplicate the Setup guide.
- **Media card:** pairs visual media with actionable text when visual context helps a merchant understand a feature, tutorial, theme/preset or real product thumbnail. In this product, skip fabricated diagrams, tiny app screenshots and decorative media; only use genuine imagery when it improves a decision.
- **App card:** recommends complementary apps, partners or integrations. It is not a Home requirement and has no clear role for an Insignia workflow overview, so omit it unless the product later has a concrete, relevant integration to recommend.
- **Footer help:** the Homepage template lists it as a composition, not a requirement. Use it only if the page needs a durable help destination not already clear from the actual task.

The Puzzlify Home example includes a dismissible feature callout, template tiles, app recommendations and news. Those are illustrative content for that example, not requirements for every app. Shopify's Homepage page lists App card, Callout card, Media card, Setup guide and Footer help as recommended compositions, while its use cases also mention dashboards with metrics. Metrics card itself lists Index as its recommended template. That split reinforces treating metrics as conditional information, not a required Home tile. In particular, Shopify's own Homepage guidance says to keep lists as rows separated by dividers and reserve bordered grid tiles for items that stand alone, such as templates or apps. This is the strongest official support for avoiding a decorative card grid and excessive nested containers.

## Polaris shell, sections, state components and navigation

The [Page component](https://shopify.dev/docs/api/app-home/v2.0/web-components/layout-and-structure/page) coordinates its heading, breadcrumbs and actions with the Shopify title bar in an embedded app. Use one page heading. Put a single primary page action in `primary-action` only when there is a real dominant task; use `secondary-actions` for supporting route or section actions. Do not repeat the page name as a second body heading. Shopify's [Card migration guidance](https://shopify.dev/docs/apps/build/app-home/migrate-from-polaris-react/card) says to use `s-section` for a normal page region, use the App card pattern for an action-oriented composition, and avoid wrapping every block in a card. The [Section contract](https://shopify.dev/docs/api/app-home/v2.0/web-components/layout-and-structure/section), confirmed against the pinned local types, is:

- Properties: `heading`, `subheading`, `padding`, and `accessibilityLabel`. `subheading` is supporting copy; it does not create a semantic heading or replace a distinct `heading`.
- Slots: `primary-action`, `secondary-actions`, `graphic`, `accessory`, and `supplemental`, plus the section's content children.
- `supplemental` is status/metadata for the whole section, not an action. It accepts Badge, Avatar, Text, Icon, Thumbnail or Tooltip (with the Section contract's prop constraints). Actions belong in the action slots. The Homepage template requires an accessible label when there is no visible heading.

The [Empty state component](https://shopify.dev/docs/api/app-home/v2.0/web-components/feedback-and-status-indicators/empty-state) is supported by the pinned types as `s-empty-state`. Its contract provides a heading, optional supporting text/graphic, and up to one primary plus one secondary action. The [Banner component](https://shopify.dev/docs/api/app-home/v2.0/web-components/feedback-and-status-indicators/banner) is for important messages and recovery/next steps. Do not use a banner as a substitute for an empty list. The [Spinner component](https://shopify.dev/docs/api/app-home/v2.0/web-components/feedback-and-status-indicators/spinner) has an `accessibilityLabel`; scope it to the loading operation rather than blocking unrelated page content.

Use Shopify's [App nav](https://shopify.dev/docs/api/app-home/v2.0/app-bridge-web-components/app-nav) for route navigation: it appears in the left sidebar on desktop and a title-bar dropdown on Shopify mobile. The app name already opens Home, so a visible second Home menu item is unnecessary. If Home is not `/`, one link with `rel="home"` sets the landing path and is hidden from the rendered menu. The docs recommend short noun labels, one navigation level, and matching labels to destination page titles. The [Navigation API](https://shopify.dev/docs/api/app-home/v2.0/apis/user-interface-and-interactions/navigation-api) covers programmatic navigation; ordinary route links should remain real anchors/links.

At research time, the local [`AdminNavigation.astro`](../../../apps/web/src/components/AdminNavigation.astro) designates `/admin/products` as `rel="home"`, then exposes Products, Orders, Methods and Settings. If the proposed work adds a distinct Home route, the app's `rel="home"` destination needs to move there while Products remains a visible destination. Home summaries can then link to the full routes using each section's secondary action. That is an Insignia routing consequence of Shopify's App nav contract, not a requirement to create a new route.
