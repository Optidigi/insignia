# Astro translation options

30 October 2026. Research only; no packages installed or application behavior changed. This supplements [the independent translation review](translation-options-independent-2026-10-30.md).

I would keep the previous recommendation of i18next core with a thin native Preact integration. Intlayer is a credible alternative that removes more integration work. Astro's built-in i18n and the Astro routing wrappers do not remove the need for a message engine inside interactive islands. These are fit judgments based on documentation and source, not results from running competing implementations.

## The actual application boundary

The inspected web manifest pins Astro 7.3.5, `@astrojs/preact` 6.0.5 and Preact 10.29.8. Its config uses Node standalone SSR and native `preact()`, without compatibility aliases. The selected sibling designer is a separate Preact 10.29.8/Vite 6.4.4 app. An Astro-only integration cannot cover the designer by itself. See [web manifest](../../../apps/web/package.json), [Astro config](../../../apps/web/astro.config.ts), and [designer manifest](../../../../designer-prototype/package.json).

The merchant language comes from the admin user's `shopify.config.locale`, which Shopify explicitly distinguishes from the storefront locale. The buyer's selected storefront language is exposed through Liquid `localization.language`. For Insignia, these host values should determine the translation locale. A browser-language or URL detector must not override them. Merchant admin and a product customizer modal gain little from separate `/nl/` routes, multilingual sitemaps or search-engine language alternates. That last assessment follows from the embedded product architecture, not a library limitation. [Shopify config API](https://shopify.dev/docs/api/app-home/latest/apis/authentication-and-data/config-api), [Liquid localization](https://shopify.dev/docs/api/liquid/objects/localization).

## What the candidates add

| Candidate | Actual benefit | Fit here |
| --- | --- | --- |
| Astro `astro:i18n` | Locale route configuration, URL helpers, routing middleware and fallbacks | Useful if Insignia later needs public localized pages. It does not supply a message catalogue, pluralized string lookup or a reactive Preact provider. |
| `astro-i18next` | i18next setup, Astro translation components and generated localized pages | Adds Astro page and URL conventions while leaving native Preact reactivity to us. Its age and broad compatibility claim need caution. |
| `astro-i18n-aut` | Reuses `.astro` templates across locale routes without copying files | Solves page duplication, while explicitly leaving string translation to the application or another library. |
| Intlayer | Shared typed content declarations, generated dictionaries, native Preact provider/hooks and Astro/Vite integrations | The strongest alternative if avoiding our adapter and gaining colocated authoring tools matter enough to adopt its content/build system. |
| Paraglide JS | Compiles catalogues into typed, tree-shakable message functions; Astro SSR middleware | A real framework-independent alternative. Still needs Preact state integration for language changes without document reload. |

Astro documents its built-in API as URL/routing support and expects applications to bring their multilingual content. `Astro.currentLocale` follows the URL, while preferred-language detection follows request/browser preferences. That differs from Insignia's host-owned locale. Neither helper automatically synchronizes island language state with Shopify. [Astro routing guide](https://docs.astro.build/en/guides/internationalization/), [Astro i18n API](https://docs.astro.build/en/reference/modules/astro-i18n/).

`astro-i18next` remains at published `1.0.0-beta.21`, released 9 March 2023. Its manifest allows `astro >=1.0.0`, but its development pin is Astro 2.0.17 and its i18next dependency is `^22.4.10`. A permissive peer range does not establish tested Astro 7 compatibility. Its documented components are Astro components; the React example is not evidence of a native Preact binding. I would use current i18next core directly instead of adopting this wrapper for Insignia. [Published package metadata](https://registry.npmjs.org/astro-i18next), [manifest](https://github.com/yassinedoghri/astro-i18next/blob/master/package.json), [maintainer README](https://github.com/yassinedoghri/astro-i18next).

`astro-i18n-aut` is more current. Published 0.8.1 declares Astro 5, 6 and 7 peers. Its README states that translation content remains our responsibility and suggests passing translated values or locale props into framework components. It renders `.astro` pages in additional locale paths, does not translate URL slugs, and excludes endpoints from this responsibility. This could help a public multilingual Astro site; it provides little for the current embedded screens. [Published metadata](https://registry.npmjs.org/astro-i18n-aut), [README](https://github.com/jlarmstrongiv/astro-i18n-aut#readme).

## Intlayer deserves a real comparison

Intlayer has an official Astro + Preact guide. It uses `astro-intlayer` for Astro content and `preact-intlayer` for interactive islands, backed by the same dictionaries. The server-selected locale is passed into the island provider. That provides the shared content model we want without writing a Preact binding. Its colocated typed declarations and generation tooling are a concrete advantage for agent maintenance. The guide also adds locale routing and SEO examples, which are optional concerns for our embedded application. [Official Astro + Preact guide](https://intlayer.org/doc/environment/astro/preact).

This is native Preact support. Provider source imports context from `preact` and hooks from `preact/hooks`. It supports explicit locale state, a custom setter and cookie control. Its current controlled `locale` prop takes precedence over internal state, so a host-controlled wrapper must update that prop when switching languages. Copying a URL-navigation example into the stateful customizer would be the wrong integration. [Provider source](https://github.com/aymericzip/intlayer/blob/main/packages/preact-intlayer/src/client/IntlayerProvider.tsx).

Published 9.7.0 has peers of Preact `>=8.0.0` and Astro/Vite `>=4.0.0`, respectively. Those ranges include the inspected versions; this is not an integration test. It adds configuration, dictionary generation, generated types and build plugins across both apps, rather than just a runtime dependency. Its source also includes optional editor/analytics integrations, so confirm production feature flags and emitted bundles in a trial. [Preact metadata](https://registry.npmjs.org/preact-intlayer), [Astro metadata](https://registry.npmjs.org/astro-intlayer), [Vite integration manifest](https://github.com/aymericzip/intlayer/blob/main/packages/vite-intlayer/package.json).

My decision is about cost rather than missing capability. For a small interface catalogue, i18next plus our thin adapter keeps the established runtime and avoids adopting a second content toolchain. If colocated content, generated authoring support and integrated editorial tooling are priorities, trial Intlayer against one actual merchant island and one designer panel. It could reasonably win that comparison. Both can share one catalogue model across Astro and Preact; Intlayer's documentation contrast with separate handwritten dictionaries does not establish that i18next requires duplicate catalogues.

## Paraglide is also viable, with a switching caveat

Paraglide emits ordinary typed JavaScript message functions and provides a framework-independent Vite plugin. These functions can be called from native Preact. Published 2.29.3 declares Vite `>=5.0.0` and TypeScript `>=5.6`, covering the sibling's declared versions. Its Astro recipe uses Node SSR middleware, and its SSR implementation uses AsyncLocalStorage for request isolation. These are credible technical matches, without proving our Astro 7 build. [Vite guide](https://paraglidejs.com/vite), [package metadata](https://registry.npmjs.org/@inlang/paraglide-js), [Astro guide](https://paraglidejs.com/astro), [SSR guide](https://paraglidejs.com/server-side-rendering).

Its documented `setLocale()` normally navigates or reloads the document. The documented `reload: false` escape hatch permits owned client-only embedded interfaces, but does not trigger framework reactivity. Insignia would still own state updates and any document settings, and should avoid URL-based locale switching in the customizer. Explicit per-message locale arguments are available. The extra compiler/project setup can be worthwhile for generated message contracts and unused-message removal, but it does not eliminate all adapter work. [Locale switching and explicit message locales](https://paraglidejs.com/basics).

## Decision boundary

Keep host locale resolution, message translation and translation authoring as separate decisions. Use routing tools when there is a real public-route requirement. Choose Intlayer over the current recommendation if its native adapter and authoring workflow remove enough project work to justify the extra build system. Choose Paraglide if generated message functions and compilation are the priority. Neither choice changes the Shopify locale contract, safe text rendering, catalogue completeness checks or the requirement to preserve an active design during language changes.

No installed-version trials or bundle benchmarks were performed. A final implementation choice should verify SSR/hydration locale agreement, concurrent request isolation, Polaris text properties, native Preact rendering and failure during a language change with the selected pinned versions.

## General Translation can complement the runtime

General Translation offers both runtime libraries and translation production tools. Its official CLI supports third-party i18next projects and standalone JSON, preserves supported message syntax, and saves translations locally by default. Publishing to its CDN is optional. This means we can use i18next in Insignia and later use GT to prepare translations without replacing the runtime or making production availability depend on GT. [CLI quickstart](https://generaltranslation.com/en-US/docs/cli/quickstart), [generating translations](https://generaltranslation.com/en-US/docs/cli/guides/generating-translations), [JSON format](https://generaltranslation.com/en-US/docs/cli/reference/formats/json-files).

GT's companion metadata supplies per-key terminology/context, requested character limits and surrounding source code. That could help distinguish a decoration method from a payment method or a product view from a page view. Character limits are best-effort, not proof that labels fit our controls. Generated translations still need review of meaning, placeholders, plurals and actual rendered layouts. For Insignia, prepare reviewed catalogue changes independently of production builds, then build from those committed files. This keeps service availability and automatic wording changes out of deployments. [Keyed metadata](https://generaltranslation.com/en-US/docs/cli/reference/keyed-metadata).

The current `gt-react` manifest requires React and React DOM 18 or later. `gt-i18n` is a pure JavaScript runtime without that peer requirement, so GT is not inherently unusable in Preact. However, adopting its plain runtime would still require native Preact integration; the React component-wrapper workflow is not a drop-in native Preact solution. These findings do not justify replacing the current i18next recommendation. [React manifest](https://github.com/generaltranslation/gt/blob/main/packages/react/package.json), [plain JavaScript package](https://github.com/generaltranslation/gt/tree/main/packages/i18n).

Recommendation: use i18next core and local typed catalogues as the first implementation. Consider GT as optional authoring automation when maintaining several languages warrants it. Its hosted translation workflow has usage-based pricing, separate from using an open-source runtime. No service account, keys, uploads or dependencies were introduced during this review. [GT pricing](https://generaltranslation.com/pricing).
