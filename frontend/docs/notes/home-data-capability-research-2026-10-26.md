# Home data capability research

Research date: 26 October 2026. Scope: repository code and current specification only. This is a capability audit for the App Home presentation stage; it changes no application behavior and makes no live Shopify account or browser observations.

## Finding

There is no implemented Home dashboard or Home data contract. [`/`](../../../apps/web/src/pages/index.astro#L2-L4) redirects to `/admin/products` while preserving the query string, and the Polaris navigation's `Home` item also targets Products ([navigation](../../../apps/web/src/components/AdminNavigation.astro#L1-L7)). The available sources can support a few carefully scoped work summaries and links. They do not support store-wide analytics or complete cross-page counts. Current specification calls for product configuration/publication, customized-order artwork work, storefront setup and settings, while explicitly leaving Shopify fulfillment to Shopify and excluding a usage dashboard ([implementation plan](../../architecture/implementation-plan.md#L381-L395), [billing scope](../../architecture/implementation-plan.md#L351-L367)).

## Counts, filters and aggregates

- Product listing is cursor-paginated at 20 products per request. `nextCursor` only answers whether another page exists; neither the endpoint nor its browser DTO returns total catalog/configuration counts. The configuration filter is applied to that fetched page and is labeled “on this page” ([list contract](../../../apps/web/src/server/admin/http.ts#L200-L205), [filter logic](../../../apps/web/src/islands/ProductsOverview.tsx#L193-L196), [filter label](../../../apps/web/src/islands/ProductsOverview.tsx#L320-L350)). A Home count computed from one request must say it covers that page; traversing the whole catalog is not an aggregate and still lacks a stable count snapshot.
- Orders accepts `limit` 1–50, cursor, creation-time bounds and date sort, but returns page items plus `nextCursor`, not totals ([request](../../../apps/web/src/server/purchase/http.ts#L77-L103), [response](../../../apps/web/src/server/purchase/service.ts#L175-L223)). The current 20-row Orders UI derives the artwork filter and search locally. A “needed” count or filter link only reflects the current page; it cannot claim all older orders are clear.
- A globally correct count of published configs, draft work or all orders needing artwork is not available from the existing endpoint responses. A future global count or queue needs an explicit server-owned aggregate/filter result with its scope and unknown/error behavior; a frontend count over whichever pages happen to be loaded is not equivalent. This is a contract gap, not a reason to show an estimated count.
- Product `configurationSummary.state` is not a publication-queue count: existing effective publications mask later draft edits. No draft timestamp or sorted-by-activity field exists in its row shape ([DTO](../../../apps/web/src/shared/admin-view.ts#L1-L22), [summary function](../../../apps/web/src/shared/product-configuration-summary.ts#L22-L39)).

## Empty, denied and unavailable states

Treat data absence, permission denial and read failure as distinct states. A successful empty product page is about the Shopify catalog query; a successful empty Orders first page means no tracked Insignia customizations were returned. Neither should be reused after a 401/403, 503, timeout, malformed response or stale-request failure. The APIs return these HTTP failures separately from normal page DTOs ([admin boundary](../../../apps/web/src/server/admin/http.ts#L109-L142), [purchase boundary](../../../apps/web/src/server/purchase/http.ts#L45-L52)).

For billing, distinguish body `status: inactive` from body `status: unavailable`, HTTP 503, and access/session errors. For theme setup, `unknown`/`failed` is different from a positive `active` or an observed `available` state. For permissions, a browser scope query is not a fresh server authorization result. A Home card that cannot load its source should show its read/permission problem and recovery destination, never a fabricated `0`.

## Claims these sources cannot support

- **Revenue, conversion, traffic, visits or usage:** no analytics/session/visitor metric API or Home visit baseline exists. Purchase rows carry an original order amount and refund records, but do not define a revenue aggregate or reporting policy ([purchase fields](../../../packages/contracts/src/v1/purchase.ts#L47-L76)); the specification excludes a usage dashboard ([plan](../../architecture/implementation-plan.md#L351-L367)).
- **All shop orders / sales:** the list contains Insignia's tracked customized purchases, not every order in Shopify. Empty results mean no returned customized purchase rows, not no Shopify orders.
- **Unfulfilled orders or fulfillment performance:** `PurchaseView` has no fulfillment status, and Shopify owns fulfillment rather than Insignia ([DTO](../../../packages/contracts/src/v1/purchase.ts#L47-L91), [plan](../../architecture/implementation-plan.md#L381-L395)). A `financialStatus` is payment context, not fulfillment state.
- **New since last visit:** there is no Home last-visit/read marker or change feed. `orderCreatedAt` is the Shopify order creation time; billing/readiness `observedAt` is a provider observation time, not a visitor baseline.
- **All product setups published or storefront fully working:** catalog status, effective config revision, theme activation, technical function observations, billing entitlement and customer journey are separate sources. No current DTO collapses them into a verified end-to-end state.

## V1 evidence-backed bounds

The source can support a Home that routes merchants to existing work, shows a small sample of recent tracked customized purchases, links to observed draft-only product configs from the fetched catalog page, optionally repeats the two published-theme setup states with explicit unknown handling, and exposes a fresh subscription or current product-access state when that read succeeds. Treat every number as page-scoped unless a future API explicitly returns an aggregate. Do not use “published products” where the source means “products with an effective Insignia configuration,” do not use a general order/revenue/fulfillment metric, and do not interpret missing, denied, partial or unavailable data as zero.

These bounds are source research, not a UI design or new backend specification. The existing App Home UI guidance rejects invented metrics and requires sorting/filter controls to match the endpoint's actual scope ([admin UI guidance](admin-ui-guidance-2026-10-20.md#copy-and-design-checks)).

## UI/UX research versus live integration

The missing aggregate DTO is an implementation precondition for live, exact cross-catalog/order counts; it is not a reason to omit otherwise useful Home states from UI/UX research. A design prototype may model the intended facts with explicit fixtures, then leave their production source/integration as a later qualification. Do not put backend limitations in merchant-facing copy. Design copy should describe the supported domain scope (for example, customized Insignia orders), and show unknown/denied/unavailable states with useful recovery.

Minimum evidence the future Home view should represent, independent of endpoint shape:

- **Collection presence:** products and customized orders each have `present`, `empty at this read`, and `unknown/unavailable` states. An authorized, successful, unfiltered Orders read with an empty first page and `nextCursor: null` can prove there were no tracked customized purchase rows at that read; it does not prove the merchant has no Shopify orders. A bounded recent-orders preview needs only the ordered rows and whether more exist, not a global count.
- **Effective configuration facts:** represent Shopify product status separately from Insignia configuration status; distinguish no configuration, draft-only configuration and an effective published revision. If a published product also has later unpublished edits, represent both facts rather than collapsing it to “published.” Do not present a count unless the represented product collection is complete for that stated scope.
- **Known, reasoned work:** a task should identify a supported next action and its reason. For artwork, keep awaiting/deferred customer upload distinct from expired or unavailable retained artwork, expired payload, erased data and unknown status. A page-scoped preview can show a bounded sample; a full queue or exact work count requires evidence covering that entire queue.
- **Effective permitted actions:** show an action as available only when the current actor can perform it. Product edit access, order/artwork read access and upload access are distinct; denied and unverified are not “no work.” A mock may include these actor capabilities to explore the interaction, while live presentation must use current server-authorized facts.
- **Independent availability:** billing eligibility, technical Function observations and published-theme setup are separate states with separate observation/unknown/error handling. Do not infer an end-to-end “ready” state from one of them.

Exact counts are optional design content. If explored, fixtures should make clear whether a number means a complete collection total or a bounded sample, and whether the source is empty or unknown. This evidence checklist does not select an API or commit backend work; it defines what the interface should mean when later connected to live reads.
