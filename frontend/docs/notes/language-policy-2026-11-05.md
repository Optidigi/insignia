# Language defaults and preference state — 5 November 2026

The admin and buyer preferences are independent. An explicit Insignia choice wins until Automatic is selected. Admin Automatic follows the Shopify staff locale, with English as its existing unsupported/missing-language fallback. Customer Automatic follows the current Shopify page locale. Only when that host value is missing or malformed does the customer adapter use the first supported browser language, then English. A valid but unsupported Shopify page language retains the complete English fallback policy; it is not replaced by a different browser guess.

## Shopify ownership and research

[Shopify localization guidance](https://shopify.dev/docs/apps/build/localize-your-app) distinguishes app-user and buyer locale sources. The existing theme launcher supplies `localization.language.iso_code`, rather than inferring language from products, location or staff preferences. The selected modal is not connected yet; that Liquid attribute establishes the integration contract, not proof of a live end-to-end connection.

[Shopify automatic language redirection](https://help.shopify.com/en/manual/international/automatic-redirection) can match a visitor's browser language when the merchant enables Language under Online Store → Preferences → Automatic redirection, and the language is translated, published and available to that market. [Shopify's localization overview](https://help.shopify.com/en/manual/markets/getting-started/localization) says manual country/language choices are retained. Therefore Insignia should follow the resulting page language, rather than run a second detector that contradicts the page or a customer's deliberate selection. A Dutch browser on a French Shopify page gets a French configurator unless an explicit Insignia preference overrides it.

The browser fallback is a small local policy function, not an additional language-detection plugin or a store-wide redirect. It reads browser preferences at mount, validates/canonicalizes tags, keeps supported regional formatting and never changes the Shopify document, URL, market, currency value or product content. The existing picker names, visuals and store-language reset text remain unchanged.

Separate optional browser keys remain `insignia.admin.language.v1` and `insignia.customer.language.v1`. Blocked storage leaves the mounted session usable. Choosing an app language does not edit a Shopify account or publish store languages.

## Audit and corrections

Independent Sol source review identified two concrete races. A delayed customer German request could activate after the customer returned to already-active English, because the old shortcut skipped the English request and only suppressed its callback. The customer adapter now always issues the current request, so the existing locale controller invalidates earlier preparation.

An unrelated/customer storage event could cancel an admin preference handler while leaving its locale request running, producing translated French content with Automatic selected and no saved preference. Settings now listens only to its own storage key (or a clear event). Root extended the regression to the initial non-persisted `pageshow`: that event must not cancel a pending choice either. Startup restoration already occurs in the layout effect; only persisted history returns trigger that listener. Both issues were reproduced before correction; the expanded admin case passed afterward.

The scattered preference flags are now one pure `languagePreferenceReducer` in `packages/localization/src/language-preference.ts`, re-exported through `core`. Its discriminated states are `ready`, `changing` and `failed`. Events represent a manual request, context change, external restoration, activation, failure and cancellation. Each request has a revision; stale completions cannot change the active preference. Pending intent is separate from the last activated preference, so failure restores the actual active choice. Context refresh preserves manual intent that is still pending.

Admin UI derives its selected value, pending and failure presentation from that reducer. The selected customer adapter lives in `designer-prototype/src/use-customer-language.ts`, extracted from the large Designer component. It keeps one stable locale controller and feeds pure transitions; preparation, storage and successful-choice callbacks stay outside the reducer. A generation guard prevents expired effects and completion side effects. Completion does not launch another effect, and only the current activated manual request persists/notifies. `customer-language-policy.ts` owns the Shopify/browser fallback policy. The small controller factory port lets the typed browser probe delay real locale preparation without adding a test prop to the customer UI.

No commerce state moved into this reducer. The existing design, upload and cart reducers still own artwork, quantities, steps, operation identities and retry identity. Exact-locale wording remains in the existing customer controller. No global state library, event bus, detector dependency or replacement async framework was added. This follows the earlier [Pocock research](reducer-pocock-primary-research-2026-10-27.md): pure, independently testable transitions with effects in audience adapters; use a reducer where coordinated state actually warrants one.

## Verification

Five pure preference-transition tests cover retained active values on failure, stale completion, returning to the active preference, automatic reset and context/external restoration. Five admin browser tests cover the native picker, separate islands, persistence/reset, blocked storage, history return, focus and the unrelated-event race. The existing customer suite plus source/policy checks passes 20 cases: 16 browser checks, two policy checks and two copy checks. It includes real locale controllers with deliberately delayed preparation, manual changes during pending cart work, exact wording scope, once-only persistence/callbacks, browser/Shopify precedence, independent keys, regional reset, retained drafts and all six languages across desktop/narrow light/dark layouts. Three new customer browser cases were also rerun after the final generation guard.

The new `tsconfig.locale-test.json` type-checks both customer locale fixtures and production source. The complete frontend runner now includes that check and the standalone language-policy tests. Shared localization runtime/catalog tests, strict builds/types, copy coverage and canonical source coverage also pass. The customer consumes a fresh immutable package and passes a clean install/build. Independent Sol reviewed the corrections and independently reran the meaningful reducer/admin/customer policy cases; no scoped findings remain. Artifacts are under `.artifacts/language-policy-2026-11-05/`.

The visible picker composition is unchanged from the independently reviewed prior delivery. Current desktop/narrow automatic states receive a local render spot check. These checks do not enable Shopify redirection, publish a store language, connect the selected modal to Shopify or prove real cart mutations. Those remain integration/store configuration work.
