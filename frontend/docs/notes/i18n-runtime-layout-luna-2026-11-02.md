# i18next runtime and layout review

2 November 2026. Independent plan-only review of [the localization implementation plan](localization-implementation-plan-2026-10-30.md), the Astro/Preact admin shell and the selected Preact customer sibling, `../designer-prototype`. No application files, dependencies, catalogs or tests were changed or run.

## Recommendation

Keep the direction: i18next core, reviewed catalogs stored in source control, one framework independent localization package and small native Preact integrations. Both selected frontends use Preact; the customer sibling is a separate Vite/npm project. Do not include React bindings in the runtime design. [Preact’s hook guide](https://preactjs.com/guide/v10/hooks/) documents the `preact/hooks` state, effect and context primitives needed for an adapter.

Before implementation, make five contracts explicit: how the separate sibling consumes one canonical catalog package; how the admin shell gets a host locale before it becomes visible; how request and browser translator instances avoid shared mutable language; how UI errors stay as stable codes in workflow state; and how translated text is allowed to reflow without changing quantity identity or losing focus.

## Findings against the current code

### 1. The package boundary between repositories is still unresolved

The plan proposes `packages/localization` and correctly says to verify the sibling’s import/build path first. Today, Insignia uses a pnpm workspace (`packages/*`), while `designer-prototype` has its own npm lockfile and Vite build. A `workspace:*` dependency will not resolve from that sibling. [Workspace declaration](../../../pnpm-workspace.yaml) · [Insignia web manifest](../../../apps/web/package.json) · [sibling manifest](../../../../designer-prototype/package.json).

Keep one maintained source in `packages/localization`, with ESM that is safe to import in the browser and type declarations. Give it `core`, `admin`, and `customer` exports, plus a native Preact hook entry point if the adapter is shared there. The catalog and type source stays shared, while each app export exposes only its allowed namespaces. Let the Preact entry point list Preact as a peer dependency. Do not move the selected app just to share translations or keep a second catalog in the sibling.

For the initial handoff, pack a versioned immutable artifact from that package. The sibling lockfile should pin the exact package version and artifact integrity. Its clean install should consume the packed artifact that CI produces from the canonical source. Add a sync check that fails if the packed version or digest no longer matches the sibling lock entry. Pass the artifact through a declared relative path in CI, not an absolute developer path. A local `file:` bridge may help iteration, but it does not qualify a release. The packed artifact is the release unit today; a registry can carry the same package later.

### 2. Locale readiness currently gates islands, but the SSR shell can still speak the wrong language

`AdminLayout.astro` currently emits `lang="en"`, an English title, English failure copy and an English skeleton; `AdminNavigation.astro` also sends English labels to App Bridge. The route is revealed only after the page island calls `useAdminPageReady()` and `admin-navigation.ts` sees both the page-ready flag and the Polaris `s-page` definition. Those are useful existing seams, but no locale/catalog readiness is part of that gate yet. [Layout](../../../apps/web/src/layouts/AdminLayout.astro#L13-L40) · [navigation](../../../apps/web/src/components/AdminNavigation.astro#L1-L8) · [readiness hook](../../../apps/web/src/shared/admin-page-ready.ts#L1-L10) · [reveal gate](../../../apps/web/src/shared/admin-navigation.ts#L22-L40).

The plan says the merchant locale comes from Shopify admin config, which is only known client-side in the current flow, and says to resolve it before revealing the island. Cover the **whole Insignia shell**: App Bridge nav, route title, failure state, skeleton labels, and every independently hydrated Preact island. A Preact context provider inside one island does not cross into another Preact root or Astro markup. Use a page locale controller/event or pass an explicit resolved locale/bootstrap object to every island. Keep it separate from authority and commerce data. If later HTML navigation sends the locale, accept only an allowlisted locale as presentation input; it must never select a shop, permission or price context.

The selected customer sibling currently mounts with `preact.render()` from Vite. Keep Astro request handling separate from its browser-only startup; the modal does not need SSR as a localization prerequisite. [Customer entry point](../../../../designer-prototype/src/main.tsx#L1-L9).

For a first request where the server cannot know the host locale, make no promise of perfectly localized SSR. Keep the current shell/content hidden until App Bridge resolves the locale and the required bundled namespace is ready. Then update `html.lang`, the app direction, title, nav, skeleton text and islands before reveal. If bootstrap or catalog resolution fails, show a clearly marked English fallback and set the document language to English for that fallback. Do not leave a visible English `aria-label` or skeleton under a non-English `lang`. The existing readiness gate can own this condition; a new router or arbitrary delay is unnecessary. Astro middleware can carry context in `locals` for SSR, but derive it per request instead of caching it globally. [Astro middleware](https://docs.astro.build/en/guides/middleware/) · [on-demand rendering](https://docs.astro.build/en/guides/on-demand-rendering/).

### 3. Use separate i18next instances for server requests; guard browser language switches

i18next documents that `init()` is asynchronous, should be awaited before translation, and should not be called repeatedly on the same instance. It also provides `createInstance()` for a separate instance and `getFixedT()` for a translator bound to a chosen locale/namespace. `cloneInstance()` shares the resource store by default. [i18next API](https://www.i18next.com/overview/api).

For Astro SSR, create and initialize an instance per request using the resolved locale, required namespaces and immutable bundled resources, then render with `getFixedT(locale, namespace)`. Do not call `changeLanguage()` on a process singleton to render a request. Do not cache initialized translator instances by locale; cache only immutable catalog data or its import promise. An instance per request keeps overlapping merchant requests with different locales independent.

In the browser, scope one instance/controller to the admin document and one to each customer modal root. The native Preact hook should subscribe to `languageChanged` and resources-loaded events, trigger a render and unsubscribe on cleanup. `changeLanguage()` is asynchronous and mutates its instance’s active language, so the locale controller should apply an increasing generation and commit only the latest requested locale after its resources resolve. Keep the old locale visible until then; a stale result must not reactivate an older locale. [Preact effects and cleanup](https://preactjs.com/guide/v10/hooks/).

### 4. Catalog types need per-app namespace limits and complete-resource checks

The plan already calls for typed keys, required interpolation parameters and catalog parity. Add a boundary so “shared types” do not make merchant-only keys appear valid in the customer modal. Export a customer translator restricted to `customer`/`common` and an admin translator restricted to `merchant`/`common`. Do not rely on one i18next global type augmentation to enforce which namespaces each app loads. i18next’s TypeScript guide supports inference from typed resources and interpolation values, but says distinct instances/resources may need separate declarations or configuration. JSON catalogs alone do not preserve literal types. [i18next TypeScript guide](https://www.i18next.com/overview/typescript).

Use the canonical English catalog as the key/placeholder type source, with strict key checks and generated declarations if catalogs remain JSON. CI should compare every approved locale/namespace against that source for missing/extra keys, placeholder names and plural forms. Keep the English fallback bundled per required namespace, set `fallbackLng` explicitly, and use `common` fallback only for truly shared meanings. Load `customer + common` or `merchant + common` as a unit before readiness; never silently render a key as a customer-facing message. i18next supports explicit fallback languages and namespace fallback, but those options do not replace completeness checks. [fallback](https://www.i18next.com/principles/fallback) · [configuration](https://www.i18next.com/overview/configuration-options).

Make the interpolation sink rule explicit too. i18next escapes interpolated values by default. Translations and parameters should be returned as ordinary strings and rendered as Preact text or supported text properties; never turn catalog output into raw HTML. For that adapter, choose one escaping layer and test `<`, `>` and `&` through both browser rendering and any SSR path, so i18next escaping plus renderer escaping does not show entity text to users. [i18next interpolation](https://www.i18next.com/translation-function/interpolation) · [Preact SSR](https://preactjs.com/guide/v10/server-side-rendering/).

### 5. Keep errors and validation as codes/data, not rendered English in reducer state

The plan mentions mapping upload/recovery strings, but the selected reducer also stores English in failed commits and recovery state. Quantity validation issues are built as English strings, including interpolated product names and `maxQuantity`. [workflow state/events](../../../../designer-prototype/src/designer-state.ts#L26-L43) · [commit/upload events](../../../../designer-prototype/src/designer-state.ts#L125-L159) · [English recovery messages](../../../../designer-prototype/src/designer-state.ts#L495-L560) · [quantity validation](../../../../designer-prototype/src/designer.tsx#L370-L403).

Broaden the plan from upload/recovery to all user-visible workflow errors/notices: validation issues, upload failure, cart commit failure, remove/undo notices, unavailable states and constraint copy. Store stable problem/event codes plus safe parameters in state, then map codes to catalog keys at render. Keep provider/API error codes at the boundary and map them there to a reviewed message; never store a translated message in a reducer or display an arbitrary provider string. Pure reducers remain locale-free. This lets an already-visible error change language without reissuing a request or changing the operation outcome.

### 6. Quantity messages use English singular tests, and quantity search ignores the selected locale

The selected customer code has `count === 1 ? "item" : "items"` in quantity rows, review and footer. That is incorrect for many languages. Use one cardinal plural message with required `count` and a locale-formatted number; use an explicit zero form only when the approved copy calls for it. Use ordinal forms only for real rank/order wording. i18next uses CLDR plural categories through `Intl.PluralRules`; verify supported runtimes or add a polyfill only if the actual browser set needs one. [i18next plurals](https://www.i18next.com/translation-function/plurals).

The same rule applies to lists: keep selected methods/options as data, then use `Intl.ListFormat` when a sentence names them. This avoids hand-building English comma/“and” punctuation. “Step 2 of 3” is a formatted count; add ordinal catalog forms only when the wording uses an ordinal. [i18next Intl formatting](https://www.i18next.com/translation-function/formatting).

The current model formats currency with `Intl.NumberFormat(config.locale, {currency})`, but `money(cents)` always divides by 100. That is a two-decimal currency contract, not a general locale formatter. The product model must keep language, currency and Market separate and format the authoritative exact amount; the canonical spec defines money as `{currency, minor: bigint}` paired with a currency exponent. Preserve that contract for quote/review and cart data. If this prototype continues to accept a fixed two-decimal `cents` fixture, label it as such; do not imply that changing locale supports JPY/KWD-style exponents. Editable whole-number quantity inputs should remain numeric controls, not be rewritten with grouped/decimal display strings. Localize the count and validation message around them, and format `maxQuantity` for display. [prototype formatter](../../../../designer-prototype/src/model.ts#L83-L90) · [minor-unit contract](../../../docs/architecture/implementation-plan.md#L194).

The shared color search already accepts an explicit locale and normalizes case/diacritics, while quantity search calls `toLocaleLowerCase()` without one. Admin method search/sort also uses the runtime default locale. Pass a declared locale to the shared search normalizer rather than relying on ambient browser settings. Use `Intl.Collator(locale, {numeric: true})` only for presentation sorting where locale order is intended, with a stable ID tie-break. Do not localize or reorder stable variant IDs, protocol states or merchant-authored names. Search status codes, not translated status text. The admin `ArtworkStatus` union plus English label map is a useful starting seam: keep `needed`/`complete` as state and translate only the label. [color search](../../../../designer-prototype/src/color-search.ts#L1-L29) · [status codes/labels](../../../apps/web/src/shared/artwork-status.ts#L1-L11) · [method search/sort](../../../apps/web/src/islands/MethodLibrary.tsx#L104-L108).

### 7. Layout selection and focus should not depend on translated text length

`quantityLayout()` currently picks single/compact/grid from option counts and switches to list when any size label exceeds 12 code points. `quantity-entry.tsx` changes its rendered branch based on that result. UI translation of “Quantity,” “Unavailable,” the errors and accessible names will affect wrapping even when the layout kind is stable; localized product/size labels can also cross the current 12-character boundary. A layout-kind change can replace the focused input branch. [layout rule](../../../../designer-prototype/src/quantity-layout.ts#L13-L41) · [focused quantity input and label](../../../../designer-prototype/src/quantity-entry.tsx#L55-L95) · [grid/list branch](../../../../designer-prototype/src/quantity-entry.tsx#L228-L294).

Keep row/size IDs and quantity maps independent of rendered labels. Prefer layout decisions from configuration shape and actual available inline size (responsive CSS/container measurement) rather than translated string length; let labels wrap, clamp only when an explicit reveal remains available, and avoid fixed widths that assume English. A tooltip may supplement a full accessible name, but it must not be the only way to read a long label, especially on touch screens. If a real content-label change forces a layout switch while editing, restore focus to the same stable `(rowId, sizeId)` input and preserve its selection/caret. Language changes must not dispatch a quantity selection or write to the reducer.

The sibling already has 320/390px checks and long-content fixtures. Add a focused localization layer instead of multiplying every scenario by every locale, theme and width. W3C Reflow centers on a 320 CSS pixel viewport, equivalent to 400% zoom from 1280 CSS px. Vercel’s guidelines call for locale-aware formats, layouts that handle long content and fixes for unwanted overflow. [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow) · [Vercel Web Interface Guidelines](https://vercel.com/design/guidelines).

### 8. RTL is a root-direction and bidi problem; keep garment geometry LTR

The plan appropriately defers claiming RTL support. When it is reviewed, derive direction from an allowlisted locale registry, set `lang` and `dir` in markup on the merchant document and on the customer-owned modal/portals, and use CSS logical properties for app chrome. Do not modify the Shopify parent document. Wrap or isolate LTR amounts, product/variant IDs and codes in bidi-safe markup; use `dir="auto"` on isolated merchant-authored labels when their direction is unknown. Do not use CSS `direction` to set the document’s base direction. W3C’s guidance calls for `dir="rtl"` on the document, `dir="auto"` for inserted text and logical start/end properties for direction-aware spacing. [W3C structural direction guidance](https://www.w3.org/International/questions/qa-html-dir) · [inline bidi guidance](https://www.w3.org/International/articles/inline-bidi-markup/bidi_examples.en.html).

RTL should reverse text flow and chrome alignment only. Do not `scaleX(-1)` the product image, garment, artwork, print placement, variant geometry or canvas. Keep domain geometry in its existing coordinate system and check icon direction individually; only icons whose meaning is directional should change. The sibling CSS currently contains physical `left`/`right`, `border-left`, and `text-align:left` declarations, some likely intentional for canvas/media; scope the review to interface chrome rather than bulk-rewriting them. [sibling CSS](../../../../designer-prototype/src/style.css).

## Efficient acceptance matrix to add to the plan

Keep the planned catalog checks across all shipped locales as fast data checks. Add only these rendering/concurrency cases:

| Check | Fixture and viewport | What it proves |
| --- | --- | --- |
| Customer quantity stress | One representative compact case and the existing long-content/list case; English baseline plus a deterministic expanded pseudo-locale; 320 CSS px (including one 400% zoom path from 1280 CSS px) and 390 px | No horizontal overflow, clipped count/error/accessibility text, hover-only labels, or changed row/variant identity. Include unavailable/recovery and an over-limit quantity in the long case. |
| Focus during language update | One grid/list case with a focused input; resolve a newer locale before an older async result | Focus/caret remain on the same stable variant cell; stale locale cannot win; the numeric draft, reducer state and pending operation IDs do not change. |
| Plural/format semantics | Data checks for every shipped locale; one browser smoke for a locale with non-English cardinal categories | 0, 1, 2 and a larger count use correct message forms and locale digits; exact minor amount/currency/economics are unchanged. Do not enumerate every quantity × currency × screen combination. |
| Admin shell readiness | One route with an island in two concurrent SSR requests carrying different allowlisted locales; one initial host-locale-unavailable fallback | SSR requests do not leak language; title/nav/failure/skeleton/island agree on locale and `lang` before reveal; explicit English fallback is internally consistent. |
| RTL boundary (only if offered) | One customer quantity state and one admin table at 320 CSS px, with mixed Arabic/Hebrew text plus LTR IDs/prices | Text and controls follow `dir`; IDs/prices are isolated; garment/photo/canvas coordinates are unchanged. No support claim until this passes. |

For screen captures, use a pseudo-locale to exercise longer strings and an explicit real-locale RTL smoke only if RTL is in the launch set. Do not run the entire existing 12-scenario × theme × width suite for every locale. Keep bidi, plural categories and length stress as separate targeted dimensions, since a pseudo-locale does not prove plural or RTL behavior. [WCAG 2.2 Reflow](https://www.w3.org/TR/WCAG22/#reflow) defines the 320 CSS pixel width and zoom equivalence used above.
