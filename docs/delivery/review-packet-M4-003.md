## Keys, durable quote metadata and readiness

[Migration 20260930000100](../../packages/database/migrations/20260930000100_m4_key_lifecycle.sql) adds installation/authorization-generation-scoped numeric u16 signing keys and auditable idempotent epoch commands. It rejects a preexisting nonnumeric/out-of-range accepted-set key ID instead of rewriting immutable history. The key's 32-byte public value/fingerprint and validity window are immutable; only one active issuer is permitted. The private 32-byte seed is sealed in a version-1 AES-256-GCM envelope with fresh 12-byte nonce and 16-byte tag under an injected wrapping key. AAD includes shop, installation generation, authorization UUID, key ID and envelope version. The wrapping key stays outside PostgreSQL. The application creates/imports pending keys, activates a new issuer while the old one retires, revokes with a command/reason audit, destroys private envelopes after the conservative expiry window, and idempotently increments the u32 emergency epoch under the active-installation lock. Revocation does not silently increment epoch. Reinstall fences old keys; deactivation can destroy their private envelopes. Synthetic raw-row PostgreSQL tests confirm seed hex/base64 absent, and missing/tampered wrapping keys fail.

Accepted authorization sets now carry a checked numeric u16 key ID. New acceptance verifies the exact signature, fingerprint, key validity window and active state against the durable public key under the same installation lock before insert. An arbitrary injected signer with the same key ID cannot persist an unusable set. The database decodes every persisted envelope/member carrier and compares key ID, generation, epoch, quote/set UUIDs, context, total, physical quantity, member order, variant and unit price to the immutable quote before insert. It keeps the signer's actual first/last key days separate from quote D+2 validity. Retiring-key same-command replay remains valid; a revoked/destroyed/missing or fingerprint-mismatched key blocks replay in both pre-read and serialized transaction paths. The existing historical M4-002 JSON evidence retains its text key ID for provenance; the current synthetic composition test converts that one historical spelling only when comparing against the new numeric result.

The trusted [public config builder](../../packages/application/src/keys/public-config.ts) generates deterministic JSON from active durable installation/key rows, admits canonical non-weak Ed25519 public points through pinned `@noble/curves`, transactionally refuses a fifth non-destroyed key and allows at most four Function-visible keys and caps its value at 8,000 bytes. A synthetic single-key example is `{"generationHex":"11111111111141118111111111111111","epoch":0,"maxBuckets":32,"maxPhysicalQuantity":10000,"allowNoMarket":false,"keys":[{"id":7,"publicHex":"<synthetic valid 32-byte point>","revoked":false,"firstDay":100,"lastDay":104}]}`; the test asserts the exact bytes with an actual generated public point. Pending and retiring keys remain visible as unrevoked for prior offers, while only the active key can be selected for new issuance. Revoked keys project `revoked:true` and stop replay/issuance. The production [server readiness composition](../../apps/web/src/server/production-readiness.ts) checks the current installation/generation/epoch, selected active key and D..D+2 window, exact fresh observed Shop config, all effective activated revisions and the Function pair before signing. Its read-only Function reconciler checks exposed handles, app key, API version, input-query hash and active objects; Admin does **not** attest deployed Wasm identity or global propagation, so it reports `runtimeIdentity:unverifiable` and production readiness remains fail-closed. Only explicit synthetic tests inject READY.

## Publication, recovery and activation boundary

The [production publication facade](../../packages/database/src/durable-core.ts) accepts only a revision ID, required/optional mode and operation ID. Its [coordinator](../../packages/database/src/repositories/production-publication.ts) loads the exact immutable revision, locked current installation/key state and numeric Product sequence to derive the expected projection; callers cannot provide a body/digest. It compares any existing remote registration/policy pair with the durable **effective** operation and refuses coherent rollback or drift. A single transaction writes the M3 intent and outbox plus the [M4 progress row](../../packages/database/migrations/20260930000200_publication_progress.sql) before the first Admin mutation. The exact product anchors are `<authorization-generation-hex>:<sequence>:pending`, then `...:ready` with `<authorization-generation-hex>:<sequence>:required|optional` policy. The current stage writes Shop config, pending registration, policy, then ready registration, always with an explicit prior `compareDigest`, exact owner/namespace/key/type/value/digest readback and durable phase/version. Ambiguous write responses trigger observation before any retry; stale CAS becomes conflict/hold. A competing or deleted pending anchor is never overwritten to ready. Stale generation/epoch/key projection or exact readback failure persists terminal operator-hold so a replacement operation can be prepared; it does not leave a permanently open prepared row.

Each bounded provider stage holds the same shop/active-installation lock used by key rotation, epoch increments and reinstall until its progress commit. It rechecks the desired public key projection before dispatch and before final M3 acknowledgement; paused-write PostgreSQL tests show revocation waits for the in-flight stage and the next stage holds on drift. A request already accepted by Shopify but still in flight after an ambiguous local timeout cannot be globally fenced by PostgreSQL; the operation stays pending/hold and quote readiness rejects drift until reconciliation. This is not a Function propagation claim. First publication and required↔optional transitions require separate all-channel/in-flight admission evidence; the default production adapter supplies none. After exact remote ready the M3 journal is acknowledged/observed and the result is `REMOTE_READY_ACTIVATION_PENDING`, **never** M3 activation. The M3 activation repository now rejects any M4 operation until its progress is `active` with separate durable activation evidence; a PostgreSQL test calls it directly at remote-ready and confirms `stale`. M5 must later supply a reviewed admission/availability boundary and attest expected Function artifact identity before activation; an Admin read alone is insufficient. The approved Option A complete-state-loss/coherent-rollback residual remains.

The [2026-07 Shopify adapter](../../packages/shopify/src/publication-admin.ts) fixes all GraphQL documents and `$app` Shop/Product fields; it requires `compareDigest` for every `metafieldsSet`, bounds request/response/body time, fences credentials to the exact installation, classifies provider failures without logging bodies/secrets, and verifies exact readback. Shopify's [metafieldsSet contract](https://shopify.dev/docs/api/admin-graphql/latest/mutations/metafieldsSet) states up to 25 inputs, atomic submitted mutation, and CAS via `compareDigest`, including explicit `null` for absent prestate. The [Function query](https://shopify.dev/docs/api/admin-graphql/latest/queries/shopifyFunctions) exposes input query and app ownership, not a deployed Wasm hash. No Function is deployed or activated by this slice.
