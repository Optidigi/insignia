# M5 transient webhook retention supporting slice

**Local supporting correction; deployment readiness BLOCKED.** This does not fix generic uninstall authority, complete privacy handling/M10, authorize an installation, or qualify any deployed processor. Base: `d9ba6383a6e15958419ecf8e26d9182f08078e41`. Independent integrated review and exact-head CI belong to the parent orchestrator.

The raw Shopify inbox already records a seven-day `purge_after`; it previously had no erasure executor. Resolution, deactivation and queue recovery could use overdue bodies. Erasing such a body also broke the managed-installation fence with a JSON parse error. Queue replay explicitly reset failed jobs with `retry()` and could recreate a deleted job with a new retry budget.

## Implemented contract

| Boundary | Current behavior |
| --- | --- |
| Resolution / uninstall | Database `clock_timestamp()` checks retained state, exact source/class and finite non-null deadline after inbox/shop lock waits. Unavailable bytes return typed `expired`; durable exhausted queue work returns `exhausted`. Neither is successful processing. |
| Business effects | The source repository's optional `beforeDeactivate` callback runs after acquiring shop, generation, credential and affected config row locks, immediately before effects. It is a repository method argument, hidden by the package-root `DurableCore` signature; no SQL executor is exported. Expiry throws an internal exception and rolls back the business transaction. Ordinary tenant callers retain their contract. |
| Bootstrap | Relevant expired/erased uninstall evidence retains a conservative `ManagedInstallationError(state_changed)` fence without parsing unavailable bytes. Processed/stale evidence is still considered. Erasure never establishes provider installation authority. |
| Duplicate identity | Retained bodies still require byte equality plus immutable metadata/digest. Erased duplicates use the preserved digest/metadata, return `expired`, never restore bytes or refresh collection/deadline. Conflicting bodies remain rejected. Ingress does not enqueue expired receipts and returns 503 with `transient_payload_expired_unresolved`. |
| Queue reservation | Migration adds `unknown/unconfirmed/confirmed/exhausted`, separate from payload erasure, and a cleanup marker. Existing rows become **unknown**; new receipts default unconfirmed. Before any send, a separate committed transaction reserves unconfirmed → unknown. Only that invocation receives one-shot send permission. |
| Queue ambiguity | Unknown/confirmed callers only resolve the exact existing singleton. Missing becomes durable unresolved exhaustion; it never creates another budget or means processed. A crash before transport can leave unknown with no job and requires operator follow-up. An ACK lost after send can recover the existing job. No cross-pool atomicity is claimed. |
| Queue budget / errors | Automatic pg-boss retryCount/retryLimit remain authoritative. No explicit `retry()` occurs. Terminal failed/cancelled work stays excluded even after deletion. pg-boss stores failure output; new webhook worker failures throw only a fixed coarse error, preserving failure visibility without arbitrary payload-bearing text. Historical output is not globally scrubbed. Refresh/outbox semantics are unchanged. |
| Nonprivacy byte erasure | Source-owned maintenance selects only `source=shopify`, `retention_class=shopify-webhook`, finite overdue deadlines and indexed nonprivacy topics. At most 100 eligible rows per pass; row locks use SKIP LOCKED. It empties payloads, records erased state, clears leases, preserves routing/digest/timestamps and leaves unfinished work failed with `transient_payload_expired`. Already processed facts remain processed. |
| Associated queue cleanup | A committed erasure/exclusion marker precedes cleanup. Only the configured webhook queue and exact inbox job identity are deleted through pinned pg-boss APIs. CommandResponse is not assumed to prove deletion; exact absence is checked. Failed/lost cleanup acknowledgement keeps a durable retry marker. Refresh/unrelated jobs remain untouched. |
| Bounded accounting | Blockers are sampled separately, at most 100 combined privacy/unknown rows, so blocked old receipts cannot starve eligible erasure. Results expose opaque inbox IDs privately. New public alerts use fixed categories and bounded counts, without subject/shop/body IDs. Counts are bounded observations, not global absence or fulfillment claims. |

The existing worker reconciliation loop performs maintenance before uninstall recovery, immediately and every 30 seconds. Both web and worker compositions supply the required durable handoff port. Omission fails before a job lookup/send; production has no test bypass. The synthetic handoff fixture used by standalone queue permission/schema tests is explicitly only a queue capability fixture. Real core + PostgreSQL tests qualify the application boundary.

The periodic bounded executor does not prove punctual deletion/liveness: backlog, locked rows, transport failure or stopped workers leave deadlines overdue. It never extends them. Queue readiness remains the existing queue/credential readiness check and is not privacy or deployment acceptance.

## Required decision and remaining blockers

All three mandatory privacy topics (`customers/data_request`, `customers/redact`, `shop/redact`) currently defer; no structured request/subject obligation mapping or qualified fulfillment processor exists. Their raw body may contain the only subject IDs. The narrow executor therefore preserves their exact body/deadline and reports `blockedPrivacyIds`, including already overdue work. Unindexed Shopify payloads report `blockedUnknownIds`. **This is an acknowledged overdue privacy/retention violation, not permitted indefinite retention, fulfilled erasure, or a deadline waiver.** Existing handling remains unsafe for deployment.

The owner must establish the authorized obligation processor and a minimal Shopify-subject/tombstone retention basis and deadline, including handling of already overdue receipts, before this can become deployable. That decision must satisfy fulfillment and timely erasure together. Retained routing/domain/digest and backup/log/derivative copies likewise need their actual basis, erasure path and ownership qualified. This slice does not invent that basis or copy subject data to a new indefinite store.

The actual production web role is unknown. Current web core and queue use the same configured DATABASE_URL; this source does not provision a different topology. Enqueue-only queue privileges cannot acknowledge application metadata. Local controls prove a narrow metadata-only handoff grant can do so without reading raw payload; they do not qualify all web ingress permissions. The consumer role script adds only required payload/lease and handoff/cleanup column grants, without collection/deadline/digest/routing or immutable-history rewrite grants. Deployed grants and all alternative processors remain unqualified.

Old unknown rows with missing jobs and reservation-before-transport crashes may never enqueue automatically. They remain unresolved obligations; no genuine uninstall handled claim is made. Populated retention schema cannot roll back and lose exclusion metadata. Historical trusted-release rollback tests now run their exact migration era; production/historical migration bytes and assertions remain intact.

The unchanged unexpired generic uninstall replay characterization remains **RED as a security property**: a replayed signed body with later unsigned metadata can still deactivate a newer generation. Passing its characterization is not an authority fix. M5/G7, native installation/publication safety and full privacy remain blocked.
