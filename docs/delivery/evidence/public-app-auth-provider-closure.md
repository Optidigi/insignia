## App Events token contract, with zero event sends

The four earlier setup acquisitions already showed HTTP 200 with `access_token` and `token_type`, omitting top-level `scope` and `expires_in`. The current [Shopify App Events API reference](https://shopify.dev/docs/api/app-events/latest) documents the `POST https://api.shopify.com/auth/access_token` JSON client-credentials request, those two metadata fields and a 60-minute token lifetime. The local adapter's request construction uses that exact endpoint/body, no redirects and a bounded response.

One **additional** direct request in this continuation used the new app's existing user-only secret, Python's verified HTTPS transport, `POST` to `https://api.shopify.com/auth/access_token`, JSON `client_id`/`client_secret`/`grant_type=client_credentials`, a 12-second timeout, redirects disabled and a 16 KiB response ceiling. At `13:47:06Z`, it returned HTTP **200**, `application/json`, with exactly `access_token:string` and `token_type:string` (`Bearer`); `scope` and `expires_in` were absent. The bearer and secret were not logged, copied to an artifact, sent to a decoder, cached or used for an event. No second additional acquisition was needed. The prior JWT payload read remains historical and was not treated as independent signature/permission verification.

The candidate `AppEventsTokenClient.acquire()` now distinguishes `ISSUED_INCOMPLETE` from `REJECTED` and a complete `READY` token, reports missing Bearer type, scope or lease without returning the bearer, and rejects contradictory supplied values. The explicit final-review regression showed that a response with scope/lease but no `token_type` previously became `READY`; the candidate now keeps it incomplete. Its `getToken()` returns null when any of those fields is missing. `AppEventsClient` separately accepts an operator-supplied credential; it is not wired to this token client, so this result does not establish a universal event-send guard. The disposition for **this acquired token** is **discard, do not cache, do not send**, pending provider clarification/principal review. A documented nominal 60-minute lifetime is not a measured lease for this particular response; no JWT-derived fallback or guessed permission was adopted. Resource-server acceptance, App Pricing eligibility, processing and billing remain **NOT_RUN**. Event count: **0 unique events / 0 event POST attempts**.

Sanitized provider question: for the documented client-credentials request from a new Dev Dashboard Public app, is a 200 response containing only `access_token` and `token_type` intentional? What authoritative scope and expiration fields should clients use when `scope` and `expires_in` are absent? The token client deliberately provides no usable bearer for this response.
