# M8 independently read Shopify order facts

Investigated 13 October 2026 against the **2026-07** Admin GraphQL contract and the locally pinned `@shopify/shopify-api@15.0.0`. No native order query, scope change, payment, refund, fulfillment, deployment or storage action was performed. Local wire tests use a synthetic loopback HTTP provider.

## Historical economics and payment

[Order](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/Order) exposes `originalTotalPriceSet`, the creation-time total before edits, returns and refunds. `totalPriceSet` or a current balance is unsuitable for reconstructing the original first-full-payment threshold. The adapter uses presentment money, the application's bounded currency exponent table and exact BigInt conversion; no floating point or tolerance. `edited` is independently observed and unsupported order-edit history must remain an explicit exception.

[LineItem](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/LineItem) distinguishes `quantity`, including subsequently removed/refunded units, from `currentQuantity`, excluding those units. `originalUnitPriceSet` is the creation-time unit price before discounts. Preserve both quantities; a refund does not rewrite a purchased authorization member. Product/variant references can become null, so missing historical identity is explicit rather than reconstructed from current catalog data. Selling-plan presence remains visible even when its ID is unavailable; it must not become a one-time line. Native Transform/child/order normalization and original-price transport are still G1/G3/G5 observations, not established by these synthetic tests.

[OrderTransaction](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/OrderTransaction) distinguishes kind, status, amount and nullable `processedAt`. Authorization or a pending sale is not paid authority. The adapter never substitutes creation/observation time for unavailable processing time. The application resolves chronological successful SALE/CAPTURE and REFUND amounts against the original order total; a refund before full settlement matters, while later refunds do not erase an already established first-paid fact. Current `displayFinancialStatus` supplies context only.

[Refund](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/Refund) explicitly warns that the record alone does not establish money returned. Associated transaction status establishes financial processing; failed/pending transactions remain visible. Refund totals and original-line subtotals are retained as observed, without any Insignia garment/customization refund split. Refund line details and transaction connections are independently paginated; their parent order, refund IDs and update time are checked.

## Completeness and resource boundaries

The versioned Order `transactions` field is an array with `first` truncation, not a cursor connection. The adapter requests at most 250 and requires `transactionsCount.precision === EXACT` with count equal to returned unique identities. Larger/uncertain transaction histories are explicitly incomplete; no invented `after` pagination. [Count](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/Count) supplies count precision.

All order line connections and each refund's line/transaction connections follow `hasNextPage`/`endCursor` until complete. Empty advancing pages, duplicate identities, repeated cursors, changed order/refund identity or version and oversized results fail closed. The bounded reader permits at most 2,000 order lines, 100 refund headers, 2,000 nodes per refund connection, 100 requests, 1 MiB per response and a hard ten-second whole-read deadline. These are supported engineering bounds, not an assertion that Shopify cannot produce larger histories. A final header read compares original total, transaction facts, refund versions and order update time before returning a complete observation. HTTP 401/403 and GraphQL ACCESS_DENIED are explicit permission failures; null/inaccessible orders do not imply deletion. HTTP 429 remains throttling, not a successful empty result.

Practical leads: a [community transaction-array report](https://community.shopify.dev/t/get-all-transactions-of-a-given-order-in-graphql/1301) reports that `edges` is invalid, corroborated by the versioned Order schema. A [Shopify maintainer explanation of removed/refunded quantities](https://community.shopify.dev/t/graphql-api-still-shows-removed-line-item-on-order/23120) distinguishes original and current quantity, corroborated by the versioned LineItem definitions. These reports guide investigation; official contracts and tests bind implementation.

## Context and permissions remain separate

The versioned **2026-07** Order fields do not expose a Market identity. Shipping/billing country is not proof of checkout Market or necessarily checkout buyer country, so the query does not collect addresses. The adapter returns `country:null`, `marketId:null`, `contextVerified:false`. It never copies an authorization carrier's context into an independently observed Shopify fact. Production binding requires a separately qualified authoritative context source; the current application reports CONTEXT_UNVERIFIED rather than silently accepting that gap. This is an implementation/platform-source limitation, not a browser-only deferral.

`read_orders` and protected customer/order data access must actually be available to the installation. Orders older than sixty days require approved `read_all_orders` in addition to the relevant read permission; missing access does not erase retained purchase snapshots. No order-write, fulfillment-write, inventory-write or refund permission is required merely to read these facts. App TOML, release scopes and API version remain unchanged in this slice.

The existing generation-fenced `AdminCredentialSource` is reused; fixed HTTPS myshopify domain, fixed endpoint, bounded credential expiry, no redirects, bounded UTF-8 streaming and hard cancellation match the existing Admin adapter boundary. The pinned SDK's `lib/clients/admin/graphql/client.mjs` was inspected: its request API uses configured API version and supports explicit retries; no SDK version change or new retry loop is adopted. ## Local qualification

`packages/shopify/test/orders/read-order.test.ts` verifies historical quantities/prices, settled and unavailable payment times, complete order pagination, duplicate/drifting pages, refund status separation, failed/truncated observations and explicit edited-order facts, scope errors, ordinary gift-message attributes, bounded credential expiry, ignored-signal timeout, response bytes and final coherence. A real localhost HTTP test exercises fixed request method/path/query/header and two independent reads. Provider payloads remain synthetic; native query/schema acceptance, protected data grants, actual transformed order facts, multi-currency checkout context and older-order access are NOT_RUN.

Missing-webhook discovery uses [orders](https://shopify.dev/docs/api/admin-graphql/2026-07/queries/orders) with the same bounded `updated_at` lower/upper window for every page and [UPDATED_AT sort](https://shopify.dev/docs/api/admin-graphql/2026-07/enums/OrderSortKeys). Each page reads at most 20 order IDs/update timestamps and returns an opaque next cursor; duplicate, outside-window, unsorted or stalled pages fail closed. The worker must still perform the complete independent order read and maintain/overlap its durable discovery watermark; the page itself proves neither purchase nor payment. Access scope and sixty-day limitations also apply to discovery.

Discovery pages are limited to20 order IDs so the bounded per-order10-second reads fit the10-minute durable cursor lease. Cursor advances only after the complete page succeeds; no fetched page is truncated after dispatch.

## Authenticated webhook body purpose

The [pinned 2026-07 webhook samples](https://shopify.dev/docs/api/webhooks/2026-07) include matching root `id` and `admin_graphql_api_id` of type Order for orders/create, orders/paid and orders/updated. Refunds/create instead has a Refund GID matching its root refund ID, plus separate `order_id`. App/uninstalled has a shop ID; a coinciding numeric ID cannot make it an order notification. Require these typed body identities before selecting the order-read hint. Missing/mismatched identity stays deferred and unprocessed; a topic header cannot manufacture body purpose. Neither a valid hint nor orders/paid topic grants payment authority.

Samples contain numeric IDs beyond JavaScript's safe integer range. Reject unsafe parsed numbers rather than round; exact canonical strings may be supported separately. Local runtime/function-setup/M5-019r TOMLs declare webhook API version 2026-07 without `include_fields` or a custom payload reduction. This local observation does not prove live subscription settings. No native webhook capture/query occurred.
