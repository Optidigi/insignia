## Documented grant choices

**Client credentials:** Shopify documents server-side access to stores in the app's own organization, using a Dev Dashboard app with configured scopes and an existing installation. App and store must both appear under the same Dev Dashboard organization; ownership or installation alone is insufficient. `POST https://{shop}.myshopify.com/admin/oauth/access_token` takes `grant_type=client_credentials`, `client_id` and `client_secret`, without a merchant redirect. The response includes token, scope and lifetime. Scope reflects the configured app version; the request does not ask for scopes. Missing scopes would require a separately authorized version/consent change. The current guide does not establish this exact Public/Draft app's eligibility from its distribution label. [Official client-credentials guide](https://shopify.dev/docs/apps/build/authentication-authorization/client-credentials-grant?lang=node), requirements, response and `shop_not_permitted` sections.

**Lifetime and privilege:** the client-credentials token has documented `expires_in=86399` (about 24 hours), no refresh token, and renewal repeats acquisition. Read the returned lifetime rather than assume a fixed value. Admin requests use `X-Shopify-Access-Token`; scopes authorize API access. Such a token is not inherently restricted to read-only operations. New public apps require expiring offline tokens for ordinary GraphQL Admin access. Offline exchange/acquisition can retire older expiring offline tokens for the same app/store; this does not establish the coexistence effects of a client-credentials request. [Official access-token reference](https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens), types, lifetimes and grants.

**Token exchange:** an embedded app gets a short-lived App Bridge ID token and exchanges it server-side, with app credentials, for online or offline access. Validate signature, audience, expiry/not-before and issuer/destination. Online tokens are staff/session scoped; offline tokens support background work. The documented embedded flow needs installed-app/frontend access and therefore is not a substitute for this no-launch/no-exchange inventory phase. [Official embedded authentication guide](https://shopify.dev/docs/apps/build/authentication-authorization/implement-token-exchange?lang=node), requirements and exchange sections.

## Separate bounded resource option — recommendation, not authority

If no existing valid capability can be supplied, the smallest candidate is **one explicit client-credentials acquisition**, conditional on independently confirmed current same-org app/store membership, installation and scope/config identity. No conversion to a custom app, new store, installation, scope approval or app release is proposed.

Before execution, obtain an owner grant naming the exact app/shop, one token-endpoint POST in addition to the existing at-most-three fixed Admin reads, private existing app-secret operator channel, token creation/audit and possible coexistence effects, shared window, retention/closure and stop conditions. Freeze a locally tested narrow operator and independently review it. Do not retrofit acquisition into the accepted existing-token allocation.

The proposed operator would reserve once, acquire once, validate the bounded response and returned scope/lifetime, then privately pass the in-memory bearer to the fixed collector. No persistent token store, refresh, retry, redirect, application auth/bootstrap or additional API document is proposed. Identity/grant drift, absent authority, unavailable credentials, provider error, missing scope/lifetime or ambiguous acquisition stops; it does not trigger scope repair, token exchange or another request. The acquisition would create a credential and provider audit effects; documentation cannot qualify all native effects in advance.

If same-org applicability cannot be established, retain the current credential stop. Token exchange is a separate larger resource/authentication phase requiring its own effect qualification. Neither option supplies uninstall-generation authority, privacy completion, commercial eligibility or M5/G7 acceptance.
