# Purchase proof without a historical localization receipt

13 October 2026. Research requested by the owner after declining the Shopify inquiry. Source entry is integrated main `1ec836c94c256c5eba4ac15ef9aa8e315cdd95f2`, tree `2f4dbd8a3ab729d4539fc2ddde13662e1a890a5b`. This is a recommendation for a consequential acceptance decision, not its adoption. No production behavior, protocol bytes, resource permissions or native state changed. No inquiry was sent.

## Purpose and answer

The product needs a durable record of which authorized customization belongs to the actual purchased merchandise: design, historical configuration, artwork, real variants, quantities and prices, followed by independently reconciled payment/refund facts. Checkout country and Market matter to the pricing authorization. They are not themselves manufacturing instructions.

Research supports a useful distinction: a signature plus an independent complete Shopify order read can establish that the observed merchandise matches an authorized offer. It cannot alone establish the actual historical checkout country/Market, or prove a particular validation invocation ran. The alternative is therefore an explicit change to what purchase binding claims, not a way to set the existing `contextVerified` flag to true.

Recommendation: consider a narrowly supported Online Store purchase path that relies on correctly operating Shopify checkout enforcement for the context lock, independently verifies the resulting order against the signed offer, and records historical checkout localization as unavailable. Exclude unsupported or uncertain origins from automatic handling. This avoids depending on analytics receipts for transactional records, while preserving all observable economic and production checks. Adoption needs principal/owner adjudication of the existing independent-context requirement and residual enforcement risk; research authorization does not adopt it.

## What is established

| Evidence | What it establishes | What it does not establish |
|---|---|---|
| Insignia Ed25519 whole-quote authorization and immutable offer history | Insignia authorized this complete design/economic offer, including its intended country/Market, generation and bounded lifetime. | That a particular checkout used that country/Market, or that a buyer-controlled carrier is an execution receipt. |
| Authenticated, complete, coherent Admin order read | Shopify recorded these real merchandise identities, quantities, original prices, currency, order identity and payment/refund facts. | Missing historical localization or whether the Insignia validation executed. |
| Enabled validation with `blockOnFailure:true` and qualified code/input | Server enforcement rejects mismatches on supported checkout surfaces, including accelerated checkout. | Historical per-order execution proof from a later configuration read; coverage of every way to create an order. |
| `Order.app.id`, source attribution and checkout token | Documented origin/correlation facts useful for routing and investigation. | Validation-success attestation. Native origin classification still needs qualification; `sourceName` alone is insufficient. |

The [2026-07 Validation contract](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/Validation) distinguishes validation errors from runtime failures controlled by `blockOnFailure`. The [2026-07 Function surface matrix](https://shopify.dev/docs/api/functions/2026-07/cart-and-checkout-validation) supports checkout and accelerated checkout, while excluding Create Order API, POS, order edits and recurring subscription orders. Draft orders have support, but the [official merchant guide](https://help.shopify.com/en/manual/checkout-settings/checkout-customization#adding-cart-and-checkout-validation) permits overriding their validation rules and deactivating normal checkout rules. Those statements are compatible: surface support is not an unbypassable guarantee across all administrative actions.

The [pinned Order contract](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/Order) provides creation-app and checkout correlation, without the required localization tuple or an Insignia validation-success field. [OrderApp](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/OrderApp) identifies the creation app; it is a stronger investigation lead than a source label, but no app ID is guessed or promoted to a qualified Online Store allowlist here. [Order creation inputs](https://shopify.dev/docs/api/admin-graphql/2026-07/input-objects/OrderCreateOrderInput) expose source attribution, and [line inputs](https://shopify.dev/docs/api/admin-graphql/2026-07/input-objects/OrderCreateLineItemInput) expose properties, variants, quantities and price. An authorized administrative writer can therefore populate order facts without proving a normal checkout occurred. This is a documented privileged path, not a claim that an ordinary buyer can call Admin APIs.

## Actual source and bounded local checks

- [Validation source](../../../../crates/cart-validation/src/main.rs) permits cart repair at CART_INTERACTION, then uses Shopify localization, current public keys/generation/epoch/date, the complete physical member set and observed exact pre-discount economics at checkout. It returns errors, not a persisted success receipt. Its input query requests the country and Market directly from Shopify.
- [Function ownership inspection](../../../../packages/shopify/src/function-ownership.ts) checks the expected app/handle/input and requires validation enabled plus `blockOnFailure:true`. This is point-in-time readiness, not a continuous historical ledger proving configuration stayed unchanged until a specific order.
- [Order reader](../../../../packages/shopify/src/orders/read-order.ts) reads original quantities/prices, payment/refunds and a checkout-token digest; it returns null localization and `contextVerified:false`. It currently has no qualified creator-app routing or per-order Function execution evidence.
- [Purchase reconciliation](../../../../packages/application/src/purchase/reconcile.ts) checks signature, issuance/lifetime, installation history, key revocation, complete members, real product/variant IDs, quantity, original unit price, currency, one-time purchase and unsupported edits. It separately rejects unavailable or mismatched provider country/Market. Removing only that rejection would silently change the accepted evidence standard.

Executed on unchanged source: `corepack pnpm --filter @insignia/application exec vitest run src/purchase/reconcile.test.ts` — **26 passed**. Includes unavailable-context and context-mismatch rejection, historical-key/generation/time and economic failure controls. `cargo test -p cart-validation zero_based_cartline_does_not_bypass_economics_or_trust_at_checkout --locked` — **1 passed**, 23 filtered; checks real Function rejection of country mismatch, price/quantity/variant tampering, incomplete members and bad keys/carriers at both checkout steps. After the independent challenge identified unsigned-required exposure, `cargo test -p cart-validation --locked` also passed all **24 controls**, including carrier removal and unsigned-required rejection. These are local synthetic controls, not native checkout evidence or validation coverage proof. No new maintained test harness was added for prose research.

## Why the naive replacement fails

1. A valid reusable offer can be copied into another order within its lifetime. Its signature still authenticates the original offer, not that order's checkout. Matching amount and currency do not uniquely identify country or Market; different contexts can share prices.
2. A merchant or privileged integration can create an order outside validation, or override draft validation, while retaining valid signed properties and matching real merchandise. The current independent order projection does not classify that path. Do not describe this as a public buyer bypass.
3. A normal web checkout can occur while validation is disabled or runtime failure is permitted. A successful setup check before issuance and another after order receipt do not rule out a change in between. Signed quote issuance is not a Shopify checkout execution record.
4. A new receipt per accepted quote, a timestamp match or matching cart contents cannot fix per-order correlation because the whole-quote contract intentionally allows repeated complete purchases. Making offers single-use or adding an order-bound signature would be a separate protocol/product change.
5. Loss of validation can also permit an unsigned purchase of identifiable required merchandise while its required policy is still present. The current purchase reconciler skips lines with no Insignia markers; completeness of a signed subset does not prove every other required product was authorized. This can produce a plain required purchase or an unauthorized extra required line alongside a valid signed set. The alternative is not a repair for this checkout incident and does not make that line a verified customization. This risk is distinct from Option A's accepted complete loss of trusted product-policy evidence.

Consequently, inference from correctly enforced supported checkout is conditional. The [approved Option A boundary](../../../architecture/OPTION-A-APPROVED.md) already trusts correctly operating app-owned policy and Shopify inputs for checkout enforcement, but its accepted joint-policy-loss residual does not automatically approve a new post-order localization inference or arbitrary Function deactivation risk.

## Proposed smallest decision and implementation boundary

Proposed decision, **not approved**: allow automatic purchase binding for a separately qualified supported Online Store one-time flow using complete signed-offer verification and independent original-order economics under the stated checkout-enforcement trust boundary, without a separate historical localization receipt. Keep intended country/Market in the immutable accepted quote. Keep actual checkout localization unknown unless a genuine independent source establishes it. Never restamp unknown facts as independently verified. Unexpected validation loss/change is an incident requiring containment, with the possibility of an undetected purchase during the gap explicitly accepted or rejected by the decision. That exposure includes unsigned identifiable-required purchases as well as signed offers used in a mismatched context; it is not covered automatically by Option A. No new unsupported-source fulfillment, plain-required purchase acceptance or billable customization is inferred from this proposal.

Preserve signature and whole-set verification, historical generation/key/date checks, original price/quantity/currency checks, unsupported edit/selling-plan rejection, complete authenticated reads, immutable snapshots, privacy deadlines and independent business/payment idempotency. Refunds and later observation must not rewrite what was bought. A test order remains a test order; commercial usage qualification and M9 dispatch are unchanged.

Before implementing this alternative, qualify creator-app/order-origin routing for Online Store and accelerated flows against independently obtained actual order metadata. Null, unknown, Admin/API/draft/POS/recurring origins must not become automatic supported-checkout proof. If a reliable origin predicate cannot be qualified, the proposal's scope cannot be enforced and automatic adoption must stop. A name, writable source label or token presence is insufficient by itself.

After a decision, use a separate typed evidence representation for offer/order matching rather than overloading `contextVerified`. Add meaningful behavior controls for origin rejection, same-price/different-context ambiguity, disabled validation and reusable offers in distinct orders. Qualify the representative native happy path plus wrong-country/Market, price clipping, marker tampering, unsigned identifiable-required merchandise (alone and alongside a complete signed set), missing member, runtime failure, unsupported-origin and changed-rule controls under actual grants. Required-product protection and incident response remain independent acceptance obligations; order reconciliation cannot undo an unauthorized checkout. No deployment, order creation or administrative mutation is authorized by this research.

Alternative if that residual risk is unacceptable: retain the independent context receipt requirement and keep automatic binding disabled, with a separately designed merchant exception flow if approved. The owner has declined the Shopify inquiry; it is no longer the active prerequisite. This research does not conclude every possible Shopify source is impossible, and does not propose another inquiry loop.
