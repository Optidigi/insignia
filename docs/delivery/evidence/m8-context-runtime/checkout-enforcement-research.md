# Checkout enforcement as purchase-context evidence

Researched 13 October 2026. Research only: no native writes, credentials, provider contact, implementation or decision changes. Primary versioned contracts below are Shopify 2026-07; merchant Help and build guides are unversioned and explicitly identified. Read AGENTS, operating model, complete plan/ledger/state, M8 continuation authority, whole-quote adoption and Option A. This note does not qualify native behavior or supersede the authority's independent order-time country/Market requirement.

## Finding

**A viable conditional alternative exists:** on a demonstrably supported, continuously enforced checkout path, a correctly operating independent Validation Function can establish that signed context matched checkout; an independently authenticated Order read can establish that the resulting physical merchandise/economics match that signed offer. That is a logical inference from enforcement plus observed outcome, not a historical per-order execution receipt and not something the signature alone proves. The examined public contracts do not supply the missing historical premise for an arbitrary incoming order.

This is a narrow gap, not proof Shopify cannot supply such evidence through another mechanism. The owner declines support contact; this research makes no contact recommendation a prerequisite to considering the alternative.

## Documented coverage and controls

The [2026-07 Validation surface matrix](https://shopify.dev/docs/api/functions/2026-07/cart-and-checkout-validation) lists B2B, cart, checkout, Draft Order Admin, Draft Order Checkout, Shopify Admin, Storefront and Storefront Accelerated Checkout as supported. It explicitly includes express Shop Pay, PayPal, Google Pay and Apple Pay. Create Order API, Order Edit Admin and Checkout, POS, pre-order/try-before-you-buy, and subscription recurring orders are unsupported. Its input exposes buyer-journey steps, including checkout completion, and localized context; the exact input query and its interpretation still need qualification. Maximum active validations: 25. The network fetch target is limited to Enterprise custom apps with requested access and unavailable on development stores. **Supported does not mean every administrative completion is mandatory enforcement.**

The unversioned [merchant checkout-customization Help](https://help.shopify.com/en/manual/checkout-settings/checkout-customization) expressly says draft-order rules apply by default but all validation rules may be overridden before completing a draft. Merchants can turn a rule off or remove it; the UI can allow checkout despite rule errors. Therefore exclude draft/manual completion from any mandatory-enforcement alternative unless a separately proven non-override path is selected. Do not describe all Admin orders as unsupported: the matrix says otherwise.

[Validation, 2026-07](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/Validation) says expected validation violations block checkout; `blockOnFailure` additionally governs runtime exceptions such as timeouts. `enabled` governs whether the validation is active. Its `errorHistory` concerns the most recent Function version, not a documented receipt of every successful execution joined to Order. [validationUpdate](https://shopify.dev/docs/api/admin-graphql/2026-07/mutations/validationUpdate) can toggle enablement and failure blocking; `write_validations` is required. A disabled/absent validation is not a failing invocation protected by `blockOnFailure:true`. That conclusion follows from enablement semantics, rather than a claim that Shopify violates fail-closed behavior.

The pinned `2026-07/mutations/validationDelete` URL failed retrieval in this investigation and the pinned Validation map does not list it. The [current unversioned/latest deletion reference](https://shopify.dev/docs/api/admin-graphql/latest/mutations/validationDelete) says deletion removes the checkout rule and stops its Function running. Do **not** assert this mutation is available in 2026-07 from that source. Merchant removal is independently documented above.

The [build guide](https://shopify.dev/docs/apps/build/checkout/cart-checkout-validation/create-checkout-validation) requires adding and activating the deployed validation: deployed code alone is not active protection. The [Functions overview reached through the 2026-07 route](https://shopify.dev/docs/api/functions/2026-07) is shared guidance: public App Store apps containing Functions can be used across plans except API-specific exceptions; custom Function apps require Plus. Resource bounds include 256 kB binary, 10,000 kB linear memory, 512 kB stack, and for up to 200 lines 11 million instructions, 128 kB input and 20 kB output; larger-cart dynamic scaling is documented. Query size is 3,000 bytes and oversized metafields above 10,000 bytes are omitted. Artifact-specific limits, malformed/missing inputs, runtime failure and repair behavior require actual qualification; smaller valid local cases cannot prove full profile enforcement.

## What the evidence proves

| Evidence | Proves | Does not prove |
| --- | --- | --- |
| Strict Ed25519 verification against archived installation-scoped issuer evidence | Issuer authorized the exact frozen v2 bytes/context/vector | This order traversed that validator or used that country/Market |
| Complete actual Order line/carrier and exact presentment pre-discount comparison | Read order matches signed physical members/economics, subject to correct normalization/history | The price/context was produced through the supported checkout path |
| Enabled correct artifact/configuration with failure blocking | Current inspected enforcement state | Its state at this order's completion or absence of an intervening disable/re-enable |
| Order origin/channel or checkout token | Attribution/correlation information according to field contract | Specific validation artifact executed successfully |

[Order, 2026-07](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/Order) describes `app` as the creating application, `sourceName` as origin platform, and `checkoutToken` as checkout correlation. None is documented as a validator-execution attestation; no validation receipt field was found in its field map. An authentic Shopify read proves Shopify returned those fields, not every inferred proposition about them. [OrderCreateOrderInput](https://shopify.dev/docs/api/admin-graphql/2026-07/input-objects/OrderCreateOrderInput) exposes `sourceName` as caller-provided configured channel attribution and permits imported historical `processedAt`. Do not assume arbitrary reserved `web` spoofing is permitted; the defensible claim is that attribution is not a validation receipt.

[LineItem](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/LineItem) exposes custom attributes, variant, quantity and `originalUnitPriceSet`, whose presentment component is the creation-time unit amount before discounts. [OrderCreateLineItemInput](https://shopify.dev/docs/api/admin-graphql/2026-07/input-objects/OrderCreateLineItemInput) allows properties, real variant, quantity and explicit `priceSet`. [Ajax Cart](https://shopify.dev/docs/api/ajax/reference/cart) permits buyers to add/change properties, including private underscore properties; hiding a property is not authorization. Thus copying a valid signed offer requires no signature forgery. The repository deliberately permits complete-offer reuse during D..D+2; no v2 order/checkout ID or consumption claim exists. Renewal preserves economics/context with a new set, and cannot convert a carrier into an execution receipt.

## Exact counterexamples to unconditional binding

These are contract-based constructions to test, **not observed native incidents**.

1. **API/import lookalike:** retain a valid EUR offer for country A/Market A. An authorized order-creating app supplies identical variants, quantities, properties and pre-discount presentment prices through Create Order API for an order outside that checkout context. That surface does not run Validation. Signature and actual economic comparison pass; the A/Market A assertion remains only the issuer's offer. This requires app/order-write privilege, not an ordinary buyer's API access, and shows why route provenance matters.
2. **Draft override:** copy those offer carriers and economics into a draft and override validation rules on completion. Default draft support does not protect this completion. No false signature is needed. Draft ingress must be excluded or independently proven non-overridden.
3. **Disable/re-enable interval:** inspect the correct enabled validator before and after; it is turned off for one intervening Online Store completion, then restored. A buyer carries a still-valid offer into another same-currency context with coincident garment prices. If actual economics match, carrier/economics checks cannot expose context mismatch. This is conditional on those prices materializing without validation and is not a claim about Transform behavior; its independent failure settings and context checks are additional safety premises. Current readback and absence of current errors cannot establish uninterrupted historical enforcement.
4. **Unsupported subsequent change:** a valid original checkout is later edited through unsupported Order Edit, or properties/economics are copied into a recurring/API order. Re-verifying current lines must not certify newly introduced customization as having passed original checkout. Freeze authentic original binding/history and append discrepancies, as plan §6.5 requires.

Different countries/Markets can share currency and coincident prices. Therefore economic equality is not an injective encoding of context. An earlier successful validation execution for a reusable offer is also insufficient: another order may reuse its bytes. A signature proves issuance, not purchase execution. Option A accepts unexpected total trusted **product-policy** loss/coherent rollback outside publication; it does not explicitly accept validator removal, draft override, or substituting inferred historical context for the M8 authority's independent evidence.

## Restricted alternative and smallest next decision/proof

If principal adjudication accepts **conditional enforcement-derived context assurance** instead of independently receipted historical context, keep v2 bytes and country/Market locks unchanged and restrict initial purchase binding to qualified Online Store checkout, including only separately tested accelerated paths. Exclude draft/manual/API/import/POS/recurring/edit-derived purchases; preserve original history and record excluded orders as unverified discrepancies. An origin allowlist is only one filter, not proof of execution.

The new accepted premise must explicitly trust the intended artifact/input semantics and uninterrupted enabled, failure-blocking enforcement on the accepted path, describe mutation/uninstall/deactivation/configuration-drift containment, and accept the residual where a completed order lacks independently provable execution history. Periodic/current health reads cannot erase that residual. Do not silently widen Option A. If that trust premise is unacceptable, the smallest missing proof remains an independently authenticated checkout-completion context or validator-execution receipt linked to the actual Order; other platform sources remain investigable without a global impossibility claim.

**Recommended narrow policy revision for adjudication:** allow a production purchase record when authentic original Order merchandise/complete signed offer/exact pre-discount economics establish what authorized design and physical quantity was bought, while retaining country/Market as **authorized quote context**, never independently observed historical checkout context. Require a qualified Online Store creating `Order.app` identity together with relevant origin/correlation filters and enforcement-health conditions; quarantine unknown or excluded sources. `Order.app` is stronger documented creator attribution than caller-provided `sourceName`, but the examined contract does not make it an execution attestation or prove the precise native identity/filter today. This revision could support economic/design purchase binding and first-paid processing after qualification without claiming a historical country/Market receipt. It changes the existing production-binding evidence requirement and needs explicit principal decision; it is not an already compliant implementation shortcut. Keep separate assurance facts rather than turning `contextVerified` true from signed context alone. No native observation or code implementation is made here.

Before enabling any alternative, qualify one positive permitted test order and negative same-currency country/Market change using the current artifact, complete-set/actual-price checks and immutable correlation. Add bounded negative checks for tampered/copied carriers, missing/partial/mixed members, runtime failure with both applicable failure-blocking settings, checkout-completion journey, supported accelerated paths and excluded ingress. Capture exact artifact/configuration and authentic Order original lines. Prove purchaser history/first-paid runtime privileges separately. These are proof requirements, not authorization for new native operations. Test orders remain permanently test and cannot qualify commercial usage.

The smallest decision is therefore about the **historical enforcement trust premise**, not cryptography, adding buyer properties, removing signed context, or rewriting quote history. Until adjudicated and qualified, affected context binding remains disabled under the existing M8 continuation authority.
