## Required proof and result

The required fact is Shopify's country and numeric Market identity **at the checkout completion that produced this specific order**, independently of Insignia's accepted quote and browser assertions. The receipt must authenticate those values, shop and order/checkout correlation, preserve event time, and distinguish later changes. Existing `verifyOffer` requires that independent context before binding; `readShopifyOrder` currently returns null context. Neither code alone proves platform impossibility.

Research establishes useful correlation and two partial authority candidates, but **no fully qualified production source for the complete required fact**. Missing documentation or native access is not proof that every Shopify mechanism is impossible.

## Smallest useful contract proof

Admin GraphQL **2026-07** `Order.checkoutToken` identifies the checkout that created an order; `cartToken` similarly identifies the originating cart. This is a supportable addition to a bounded independent order read, with existing order-read permissions. It authenticates correlation, not country/Market. The field arrived specifically in 2026-07. [Order fields](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/Order#field-Order.fields.checkoutToken), [release changelog](https://shopify.dev/changelog/posts/new-checkouttoken-field-added-to-the-order-object).

The public Web Pixels `checkout_completed` contract contains `data.checkout.token`, `order.id`, `localization.country.isoCode`, and `localization.market.id/handle`. It provides the desired tuple and completion timing. Localization needs Checkout Extensibility; IDs/country can be null. Completion is typically emitted on Thank you, or the first upsell page, and can be absent if that page does not load. Thus this is useful diagnostic/native comparison evidence, not a guaranteed receipt. [Event contract](https://shopify.dev/docs/api/web-pixels-api/standard-events/checkout_completed).

## Addendum — first-party server pixels, 13 October 2026

Independent challenger research identified a distinct **first-party server-event candidate**. Shopify's 3 July 2025 changelog explicitly names Server Pixel `checkout_completed` events and their snake_case `subtotal_price` field. Shopify's Help Center says server pixels transfer checkout/customer events through a server to the app owner, bypassing the browser intermediary; availability is limited to certain app owners and customer privacy/consent can restrict events. This corrects the first pass's incomplete candidate coverage. It proves existence of server checkout events, **not** that the Web Pixels JavaScript localization schema or its authenticity guarantees can be copied onto them. [Changelog](https://shopify.dev/changelog/posts/server-pixels-added-subtotalprice-to-checkout-events), [server versus web transport](https://help.shopify.com/en/manual/promoting-marketing/pixels/app-pixels#server-pixels).

The **2026-07 Admin control plane** is confirmed without redirects to another version:

| Contract | Pinned registration/read requirement |
|---|---|
| `serverPixel` / `ServerPixel` | App's configured pixel; `read_pixels` plus `read_server_pixels`. Fields `id`, nullable `status`, nullable `webhookEndpointAddress`; configuration streams customer interactions to EventBridge or PubSub. [Object](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/ServerPixel). |
| `serverPixelCreate` | Creates one unconfigured pixel per app/shop; duplicates error. `write_pixels`, `read_customer_events`, `write_server_pixels`, and user access permission. [Create](https://shopify.dev/docs/api/admin-graphql/2026-07/mutations/serverPixelCreate). |
| `eventBridgeServerPixelUpdate(arn: ARN!)` | Connects configured pixel to an EventBridge endpoint; requires `write_pixels`, `read_customer_events`, `write_server_pixels`. **Deletes previous pixel subscriptions.** [EventBridge update](https://shopify.dev/docs/api/admin-graphql/2026-07/mutations/eventBridgeServerPixelUpdate). |
| `pubSubServerPixelUpdate(pubSubProject: String!, pubSubTopic: String!)` | Google project/topic counterpart; same declared scopes and subscription replacement effect. [PubSub update](https://shopify.dev/docs/api/admin-graphql/2026-07/mutations/pubSubServerPixelUpdate). |

Both configuration mutations return the server pixel and user errors. Their pinned inputs contain **no event-payload API-version selector**, topic allowlist, localization projection or delivery-authentication options. Pinned control-plane compatibility therefore does not qualify the streamed event schema's version, field provenance, completion meaning or order join. A trusted broker transport also needs to establish that the desired tuple is Shopify-authored, rather than merely relayed browser data. Complementary challenger research owns that payload/authentication question; it remains unqualified here.

The current official scope table explicitly says Shopify grants `read_server_pixels` and `write_server_pixels` **on approval**. It generally permits public/custom apps, but that is not a promise of server-pixel approval for this app/use case. Approval scopes cannot be declared before Shopify approves the app; premature declaration can fail app-version validation. No public current first-party eligibility checklist, dev-store-specific grant or guaranteed approval route was located. A March/April 2025 Shopify maintainer [reply](https://community.shopify.dev/t/subscribing-server-pixels-instead-of-web-pixels/12193) said new requests were then closed; this historical lead cannot establish October 2026 eligibility. [Official scope/approval contract](https://shopify.dev/docs/api/usage/access-scopes).

**Resource boundary:** no relevant new scopes, provider projects/topics/ARNs, delivery identities, costs or permissions are granted by this research. Before registration, obtain app-specific Shopify eligibility/approval and approved minimal scopes; qualify an owner-allocated broker endpoint, publisher identity, consumer permissions, retained minimal receipt fields, retries/deduplication/erasure, consent behavior and cost bounds. Do not update an existing pixel speculatively because registration replaces subscriptions. No contact, registration, extension deployment or provider creation occurred.

**Revised recommendation:** prioritize clarification of the server-pixel payload/authentication contract and actual eligibility alongside safe existing-access observations. Required native proof is one Shopify-authenticated server completion event with original country/numeric Market and order or checkout token joined to independently read Admin `Order.checkoutToken`, including null/consent/unavailable paths. Then test changed-country/Market and accelerated/guest cases. This is a supported control-plane and event-existence candidate, **PAYLOAD_AUTHORITY_UNQUALIFIED / APPROVAL_RESOURCES_UNAVAILABLE / NATIVE_NOT_TESTED**, not platform impossibility and not a reason to revise locked purchase-context semantics before this candidate is resolved.
