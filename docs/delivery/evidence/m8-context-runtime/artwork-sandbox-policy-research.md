## Security and compatibility

Both profiles intentionally allow broad filesystem, network and other operations. Both child profiles still allow userns; neither is a blanket prohibition on nested namespaces. Their distinguishing restriction is capability denial after execution. Filesystem/network secrecy must therefore remain enforced by Insignia's mount/network namespaces, cleared environment, no credentials in the child, capability drop and cgroup limits. [Ubuntu's security explanation](https://discourse.ubuntu.com/t/understanding-apparmor-user-namespace-restriction/58007) recommends this purpose-built approach and warns about arbitrary-command tools with unconfined userns allowances, compatibility effects and future package updates.

NoNewPrivileges stays enabled. [Bubblewrap0.9.0 source](https://raw.githubusercontent.com/containers/bubblewrap/v0.9.0/bubblewrap.c) sets PR_SET_NO_NEW_PRIVS itself and separates namespace setup from child capability dropping. The profiles explicitly account for this using stacking. Nevertheless, [kernel documentation](https://docs.kernel.org/userspace-api/no_new_privs.html) warns that early no_new_privs can interfere with LSM exec confinement. Source intent does not prove this host's exact entry/child transitions. [Systemd255 documentation](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd.exec.xml) likewise distinguishes exec privilege protection from delegated IPC launches: the actual bwrap unit must carry NoNewPrivileges, rather than assuming the requesting agent's setting propagates through systemd-run.

Automatic executable attachment can affect every host caller of `/usr/bin/bwrap`, including Flatpak; it is not restricted to Insignia or serveradmin. Existing local includes can alter both profiles and require inspection. Namespace-enabled kernel attack surface remains; there is no zero-risk claim.

Do not disable NoNewPrivileges, adopt an unconfined profile, widen local overrides or retry probes under the current allocation. If the distro candidate fails, diagnose its exact audit before considering the pinned ABI4.0 upstream alternative. No native sandbox/deployment/storage acceptance is obtained by this note.
