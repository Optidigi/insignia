# Automatic customization FX decision record — M4-001

Researched 29 September 2026; no provider account, credential, API request, purchase or terms acceptance occurred. **No automatic FX provider is selected.** The application now has a `CustomizationFxProvider` port; required cross-currency quote construction must fail closed until a provider supplies a fresh exact decimal observation with provenance. The existing M2 pricing engine accepts a resolved exact decimal FX input and is unchanged.

## Shopify boundary

[Shopify `ProductVariant.contextualPricing`](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/ProductVariant) returns the final contextual garment price, which can include fixed local prices, conversion, price-list adjustments and rounding. A ratio of two garment prices is not a valid rate for arbitrary customization components. [Shopify `CurrencySetting`](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/CurrencySetting) documents `currencyCode`, `enabled`, optional `manualRate` and `rateUpdatedAt`; it does **not** expose a numeric automatic rate when `manualRate` is null. A deliberately configured manual rate could be a later explicit source, but the current documented automatic contract cannot supply this rate. No `read_markets` scope was requested.

The prices and terms above are vendor-published snapshots, not purchased entitlements or service guarantees. Provider rate freshness must be based on the **rate's effective/publication time**, bounded by an application expiry, not merely the HTTP fetch time. A rate's source/version/provenance, shop/presentment pair and rounding policy must be frozen with the accepted quote. For same-currency customization, M2 needs no FX lookup; for a configured exact presentment-currency override, only the uncovered shop-currency components need FX.

## Operator evidence and recommendation

The [money-open-exchange-rates integration README](https://github.com/spk/money-open-exchange-rates) describes caching by provider timestamp and a default never-expire setting. This shows why Insignia must impose its own finite expiry and avoid synchronous refresh on buyer requests; it is not independent uptime evidence. The [Magento currencyapi converter README](https://github.com/Avenyra/magento2-CurrencyApiConverter) describes missing pair/plan and timeout behavior in an integration; its plan comments do not override the vendor's current private-use-only free terms. The [FrankFurter client README](https://github.com/conficient/FrankFurter) notes weekend/holiday requests resolve to an earlier publication date, reinforcing requested-vs-observed-date separation. None of these operator examples validates a vendor SLA.

**Recommendation for principal/owner:** shortlist Open Exchange Rates Developer for a bounded production pilot after commercial/license and allowed-currency review; compare currencyapi Small if its use terms and data semantics are preferable. Select neither in M4-001. The automatic FX provider remains a named later M4 blocker for cross-currency quote eligibility. A future adapter must return an exact decimal/rational, verify pair and timestamp, enforce quota/retry limits without stale fallback, and freeze provider provenance. The current [FX port](../../../../packages/application/src/pricing/customization-fx.ts) enforces the identity and finite freshness contract without inventing a rate.
