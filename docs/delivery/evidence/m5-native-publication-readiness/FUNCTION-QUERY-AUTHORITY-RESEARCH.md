## Findings

The integration premise is feasible: a modern Function can have its query in a target's deployed configuration while the older extension-level query is absent. The [2026-07 ShopifyFunction reference](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/ShopifyFunction) declares `inputQuery: String`, not `String!`; it documents no cause or guarantee of availability. Its ID, handle, API type/version and owning app key are separate fields.

The [Function configuration reference](https://shopify.dev/docs/api/functions/2026-07#properties) places `input_query` on each target; different targets can have different queries. More decisively, Shopify CLI's [Function deployConfig implementation](https://github.com/Shopify/cli/blob/9c67f14dde86bccb79d3bdce184b7595a54380d6/packages/app/src/cli/models/extensions/specifications/function.ts#L125) loads legacy root `input.graphql` only when present, independently reads each configured target query, and emits both root `input_query` and `targets[].input_query`. It generates a separate `module_id`. Thus target query text can exist without root query text. This is source-supported feasibility, **not proof that this explains the exact Admin response**; no inspected source establishes how Admin's `inputQuery` resolver handles modern targets.

Supplied [native readiness report](REPORT.md): exact designated shop/app/installation and both Function definitions match the reviewed handles, API types, API2026-07 and Management registration UUIDs. Legacy query evidence is non-string (`kind: object`), with no digest and no separately captured null predicate. JavaScript `typeof null` is `object`, so the receipt must not be restated as confirmed null. Complete cart-transform and validation connections each contain zero nodes. Definitions exist; enabled store-level instances do not.

Supplied native Active Management evidence contains all six modules, actual target query text matching local query digests, `module_id` and registration UUID. Local query files establish expected identity only; the independently authenticated Management response establishes observed released configuration. Shopify's [Management client mapping](https://github.com/Shopify/cli/blob/9c67f14dde86bccb79d3bdce184b7595a54380d6/packages/app/src/cli/utilities/developer-platform-client/app-management-client.ts#L1437) maps `registrationUuid` from remote module `uuid`, and preserves config/target. Its [version-by-tag implementation](https://github.com/Shopify/cli/blob/9c67f14dde86bccb79d3bdce184b7595a54380d6/packages/app/src/cli/utilities/developer-platform-client/app-management-client.ts#L680) returns the version ID and its module configurations. This is first-party implementation evidence, not a promise of a generally supported public Management API contract.

## Binding decision and limits

**Registration UUID equality alone is insufficient.** It identifies the same Function registration, not a particular release or query. A defensible alternative query binding requires all of: independently authenticated current Active version identity for the exact app; exact immutable version module/config; unique correct target and export; correct Function registration UUID/handle/API version/app key; independently computed digest of actual target query text; and exact `module_id`/source-build binding in the trusted release pipeline. Reject duplicate, missing, mixed-version or mismatched observations. A local expected digest must never be copied into observed query evidence.

With those checks, Active module config plus matching Admin Function UUID is sufficient to bind **the released target query configuration** when legacy `inputQuery` is unavailable. It does not establish enabled instances, executed server Wasm bytes or instantaneous shop propagation. Shopify describes an app version as a configuration/extension snapshot and says release replaces Active, but upgrades can take minutes: [About app versions](https://shopify.dev/docs/apps/launch/deployment/app-versions). Treat immutable-version handling as the qualified existing pipeline premise; this documentation does not explicitly call the snapshot immutable.

Retain three distinct authorities: (1) native Admin definitions and enabled instance/readback state for the current installation; (2) independently authenticated current Active module target query identity; (3) independent trusted release/build record binding exact app/version/source artifact, query and Wasm digests. The current source/build record remains necessary: neither Admin nor target config supplies a server Wasm digest. `module_id` is an identity reference, not a Wasm content hash. Source-only evidence, mocks, local files, environment JSON and browser inputs confer none of these native/trusted authorities.

Existing local implementation facts: [artifact-attestation.ts](../../../../packages/application/src/keys/artifact-attestation.ts) requires an observed query digest on each Admin Function observation; its parser rejects missing evidence. [Management worker](../../../../scripts/m5-runtime/trusted-release-management-worker.mjs) already reads complete exact-version module config and brackets it with Active checks. [trusted-release repository](../../../../packages/database/src/repositories/trusted-release.ts) independently verifies digest/scope/current generation/current Active binding and fails outside the exact 30,000 ms observation window or on future observations; reading never restamps evidence. These checks are repository policy, not Shopify's freshness guarantee.

## Native setup feasibility and mutation boundaries

The [2026-07 cartTransformCreate mutation](https://shopify.dev/docs/api/admin-graphql/2026-07/mutations/cartTransformCreate) requires `write_cart_transforms`, Checkout Extensibility and the user's products/preferences permissions. Creation activates the transform; `blockOnFailure` defaults false. `functionHandle` is current; `functionId` is deprecated. The [2026-07 Cart Transform API](https://shopify.dev/docs/api/functions/2026-07/cart-transform) allows at most one transform per app per shop; `lineUpdate` requires development or Plus stores. Other apps' transforms may coexist, so never treat a foreign instance as owned or replace it.

The [2026-07 validationCreate mutation](https://shopify.dev/docs/api/admin-graphql/2026-07/mutations/validationCreate) requires `write_validations`. That reference lists no additional named staff permission; this absence does not qualify the actual token/user. [ValidationCreateInput](https://shopify.dev/docs/api/admin-graphql/2026-07/input-objects/ValidationCreateInput) defaults `enable` and `blockOnFailure` false; enabled readback is necessary. [Validation](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/Validation) links the Function and records enabled/failure-blocking state. Expected violations block checkout; runtime exceptions depend on failure policy. [Function API availability](https://shopify.dev/docs/api/functions/2026-07#api-availability) restricts custom apps containing Functions to Plus; public-app rules differ. Qualify actual designated store/distribution and required operations rather than inferring eligibility from definitions.

Neither inspected create argument list offers an idempotency key or documents an idempotent retry guarantee. Their scopes must actually be granted, not merely declared: [access scopes](https://shopify.dev/docs/api/usage/access-scopes#checking-granted-access-scopes). Native empty connections support an absence diagnosis, not permission to blindly mutate. On timeout or ambiguous response reconcile before any retry; matching already-present state can be adopted only after exact verification, and duplicates/foreign/mismatched state fail closed.
