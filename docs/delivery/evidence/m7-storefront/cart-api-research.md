# M7 Ajax cart adapter investigation

Observed 12 October 2026 against Shopify's current documentation and Dawn maintainer source. This is engineering investigation, not native store qualification.

## Sources and contract

[Shopify Ajax overview](https://shopify.dev/docs/api/ajax) specifies locale-aware requests using `Shopify.routes.root`. [Cart API reference](https://shopify.dev/docs/api/ajax/reference/cart) describes multi-item `cart/add.js`, object updates keyed by line keys, and removal with zero quantity. Variant IDs identify real merchandise; product IDs are not interchangeable. The same variant can have several lines with different properties or selling plans. Line keys change with property or discount changes, so retained historical keys are unsafe.

The same official reference explicitly describes inventory excess adding the available amount while returning an error. Therefore a non-success response is not proof of no effect. The adapter always refetches after mutation failure and never automatically repeats dispatch. Its journal is marked before dispatch; acknowledgement plus bounded readback is needed before clearing. A snapshot alone after lost acknowledgement does not establish that an in-flight operation can no longer settle. Uncertainty has no automatic expiry or unlock.

[Shopify-maintained Dawn cart implementation](https://github.com/Shopify/dawn/blob/main/assets/cart.js) uses configured routes, handles response-level cart errors, refreshes sections, publishes cart update events, and disables controls during updates. This corroborates the practical need for visible mutation/loading/error states and theme refresh integration. Dawn's theme-internal pub/sub and positional line updates are not adopted as a universal extension API. The extension uses current line keys and emits its own composed outcome for its caller; root UI owns theme communication.

No source establishes atomicity across removing old authorizations and adding replacements. Treat each call as a separate external effect. Functions remain purchase authority; Ajax success and browser vector checks do not establish valid checkout pricing or payment. Live mutation, Function journey/accelerated behavior and theme integration need separately authorized native qualification.

## Implementation bounds and recovery

`createAjaxCartAdapter` takes a same-origin locale root path and optional fetch/journal seams. `read` returns normalized decimal variant IDs, properties, selling-plan identity, full fingerprint and ordinary/customized subsets. Either reserved v2 carrier's presence identifies a customization for repair, even when its value is malformed; ordinary unmarked lines remain untouched.

Application rechecks the reviewed full fingerprint before dispatch, removes only current marked keys, refetches after removal, batch-adds the cloned accepted vector, then checks exact customized vector and unchanged ordinary merchandise/properties/quantity/selling plans. It intentionally ignores ordinary line-key changes during the sequence because discounts may change those keys. A changed ordinary subset stops progress. Empty desired vectors remove only customization; already-applied vectors avoid duplicate addition.

Ordinary scalar properties retain exact string/boolean/number/null values, while accepted signed inputs are strictly strings; complex property values fail closed. An initially failing scalar-preservation test established this compatibility correction.

Accepted vector guards use the inherited 32-bucket / 10,000-unit engineering profile and a local 64 KiB JSON admission guard. The latter is not a documented Shopify payload guarantee. No unsupported numeric precision conversion is performed; unsafe numeric input is rejected and decimal/GID strings remain lossless. Signed carrier verification is server/Function work, not browser authority.

Use a persistent minimal `CartMutationJournal` in the UI composition to retain uncertainty across adapter recreation/reload. The adapter itself provides no ambiguous-write unlock: the user sees review required, and an operator/native qualification must establish a supportable settlement/repair route. Acknowledged partial/mismatched vectors can be repaired after fresh review. A nonwaiting origin-scoped Browser Lock coordinates Insignia adapter application across product instances and locale paths/tabs where Web Locks are available. A module-level fallback coordinates the same page only. The injectable lock seam never queues stale accepted work; contention returns busy. Capture the accepted vector before asynchronous lock acquisition. External theme code does not participate in this UX lock; fingerprints and Function validation remain essential. Use one origin/cart journal key independent of locale and shared localStorage to preserve an unresolved flag across tabs; per-tab sessionStorage alone does not supply that property.

## Verification

Local TDD: initially missing module prevented the end-to-end replacement test from running; replacement test passed after implementation. A lost-acknowledgement test then observed three dispatches rather than one on repeated application (behavioral RED); write latch corrected it (GREEN). Oversized payload test observed a missing rejection (RED); local admission guard corrected it (GREEN).

Fourteen transport/seam tests, one actual loopback HTTP lost-response test and one Chromium two-tab lock test pass: locale/current keys/ordinary preservation, uncertain effects and no redispatch, stale review, clipped inventory, external edit between steps, malformed carrier repair, invalid roots/IDs/member sets, idempotent already-applied vector/removal, payload budget, persistent uncertainty and fail-closed journal writes. Actual HTTP test commits the synthetic effect and destroys its response socket; reconciliation observes exact effect without redispatch. JSON responses are streamed with a 1 MiB cap and native Fetch deadline of ten seconds. Storefront TypeScript and scoped Biome checks pass. These are external transport doubles, not native Shopify or browser delivery/checkout evidence.

Lock followup TDD: independent adapters initially allowed a second application instead of returning busy (RED); nonwaiting shared lock corrected this (GREEN). Capturing inputs inside the Browser Lock callback initially allowed quantity 99 instead of reviewed quantity 2 after asynchronous acquisition (RED); capturing before lock acquisition corrected this (GREEN). Browser tests prove actual origin Web Lock coordination and release; no native Shopify cart or third-party theme serialization is claimed.
