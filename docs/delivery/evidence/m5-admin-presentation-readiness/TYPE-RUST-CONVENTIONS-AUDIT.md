## Concrete limits and gaps

1. **Production strictness is not complete test type safety.** Most package configs explicitly exclude source tests; cart-authorization includes only `src` while its tests run using Node strip-types. Web/storefront browser tests are JavaScript. `scripts/m1-functions/check-vector.test.ts` has a dedicated strict typecheck, but that does not typecheck all other fixtures/call sites. Tests can remain behaviorally useful while failing to prove their typed API assumptions. If a change depends on a test's compile-time contract, use a narrow test tsconfig or an explicit typed fixture at that seam; do not create a second full suite.

2. **A narrow production JavaScript gap exists in signing orchestration.** `apps/web/src/server/admin/signing-owner-action.mjs` calls `scripts/m5-runtime/signing-provision-core.mjs`; its `.d.mts` describes the exported result/config but declares `ports: object`. Web tsconfig does not enable `checkJs`, and the implementation has no `@ts-check`. A strict TS caller consequently does not prove required port methods or implementation return states. Runtime assertions and behavior tests still protect real contracts, so this is not a demonstrated signing vulnerability. When consolidating that maintained service, give the port capability an explicit interface and check the action/core implementation, preserving runtime boundary validation and existing reservation/identity/ambiguity tests. A declaration shim alone is not end-to-end type safety.

3. **Some stricter claims would be inaccurate.** Storefront enables `strict` but does not explicitly enable `noUncheckedIndexedAccess`; it is not uniform across all runtime apps. Biome uses recommended rules and an explicit path list, not a repository-wide bespoke unsafe-cast policy. Double casts exist at App Bridge boundaries (`SigningSetup`, `MerchantConfigEditor`, `ReadinessPermissions`), Konva facade integration and application recovery (`availability-recovery.ts:214`). Their existence alone is not a proved bug. `skipLibCheck` is set in TS configs, and production boundary checks exclude tests. Do not claim compiler/lint validation proves runtime input shape or forbids all unsafe assertions. Prefer `unknown` plus existing boundary schemas/guards for new untrusted inputs and inspect a cast's guard/provenance when its path changes. Adding every optional compiler flag or blanket cast bans is not needed to finish M5.

4. **Rust panic prevention is reasoned, not globally enforced.** No unsafe blocks or panic/unwrap prohibition lint was found in the three crates. Fixed-array decoding uses `unwrap` after `canonical::<N>` has already established exact length; these conversions cannot fail for admitted buffers. Transform's currency `unwrap` follows successful set verification, which checked the exponent. Test harness unwraps are separate from production handling. Relevant malformed merchant data ordinarily returns empty Transform operations or explicit Validation rejection via checked conversions and `Result`/`Option`; do not rewrite safe fixed-width conversions solely to remove the word unwrap. Generated SDK deserialization/startup failure policy is not qualified by this representative inspection, so this is not a guarantee that arbitrary malformed JSON never traps.

5. **Resource measurement is not a complete enforced budget.** Runtime capacity guards bound config, cart, carriers, 32 buckets, 10,000 units and output. `replay-production-vectors.py` asserts Transform output <=16,000 bytes and calculated query cost <=30. The root replay paths record instruction counts, linear memory and Wasm/input bytes but do not contain explicit comparison assertions for every documented instruction/memory/binary/input ceiling. Runner success remains useful but is not an independently specified budget/headroom regression gate. Stack peak is explicitly unmeasured in replay and the locked ledger. This is an existing G2/live shipping-qualification boundary, not proof of an over-budget artifact or an M5 presentation defect. At capacity/release qualification, compare observed metrics to the accepted pinned limits and preserve explicit stack/live BLOCKED evidence until actually measured.

6. **Protocol decimal parsers deliberately differ in normalization.** TS domain parsing rejects `1.000` for exponent 2; Rust external subtotal parsing accepts insignificant trailing zeros by trimming them. The inspected tests and adapter context explain this distinction; it is not binary-protocol drift, whose money fields are unsigned integers. If external decimal admission semantics change, document the intended lexical policy and exercise that exact TS/Rust adapter boundary rather than requiring all functions named “parse” to behave identically.

## Proportionate future gate

For presentation-only M5 work: retain style, production build/type checks, boundaries/secrets and the targeted real route/browser tests for the changed user flow. Add a focused public-seam regression only when behavior changes; independent expected output and a real endpoint/composition check are especially valuable where mocks could repeat a mistaken route. Reuse qualified unchanged protocol/Wasm inputs with provenance where current policy permits; naturally applicable exact-head CI still must pass.

For money/protocol/Function changes: run affected domain/currency/property tests, TS shared vector tests, Rust fmt/clippy/tests, both Wasm builds and schema-aware semantic/production-vector replay. Preserve complete-set and independently fail-closed Validation negatives, exact output prices, capacity acceptance/rejection and matching golden/version changes. Run real database tests when persistence/economics/tenant transactions change. Full integrated regression belongs at milestone exit and when cross-cutting input changes justify it.

For defects: first reproduce the actual symptom at the real reachable seam, retain RED evidence, make the smallest correction, then rerun that seam and affected contracts. Avoid tests of private helpers, implementation-derived expected values and an extra browser case for a pure invariant already proved below the UI.

Do not add duplicate suites or a generic “type safety/Rust best practices” checklist. The existing complexity audit already proves the duplicate operator invocation and broad documentation triggers. Any later CI reduction needs a concrete reviewed dependency/provenance proposal preserving required statuses and security assertions. No claim about runtime bloat, whole-codebase convention compliance, native checkout qualification or milestone acceptance follows from this audit.
