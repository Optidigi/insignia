## Finishing decision

Keep the current Astro/Preact/Polaris embedded admin and installation-scoped whole-quote v2 architecture. Remove cryptographic provisioning responsibility from ordinary merchant presentation. Keep the existing backend key lifecycle, fresh Function/build evidence, public-config publication/readback and uncertain-write protections. Merchant actions remain Shopify permission consent and product configure/preview/save/publish. The smallest immediate completion is to qualify and connect the existing internal provisioning path, then prove one real product flow. Removing a signing panel does not initialize keys or close readiness. [Signing intent audit](SIGNING-UI-INTENT-AUDIT.md), [original M4 lifecycle](../../prompts/M4-003-KEYS-PUBLICATION-READINESS.md), [original M5/G7 exit](../../prompts/M5-018-M5-EXIT-G7.md).

Ed25519 signing, key/day windows and wrapping custody are Insignia architectural requirements. Shopify's documented Function configuration interfaces do not require merchants to administer cryptographic keys. Shopify supports app-managed Function-owner creation when the Function is an implementation detail; it also supports offline metafield maintenance. This supports the responsibility boundary, but does not select a safe automatic trigger for this repository's fixed one-shot provisioning action. Do not call that action automatically on editor mount. [Shopify Function metafield configuration, creation workflows and offline maintenance](https://shopify.dev/docs/apps/build/functions/input-queries/metafields-for-input-queries), [private action](../../../../apps/web/src/server/admin/signing-owner-action.mjs), [provisioning core](../../../../scripts/m5-runtime/signing-provision-core.mjs).

## Verified interfaces and their limits

| Platform interface | What official documentation establishes | Consequence for this implementation |
| --- | --- | --- |
| Function identity | `ShopifyFunction` exposes owning app/client ID, ID, handle, API type/version and input query. `shopifyFunctions` lists the querying client's installed Functions. | Preserve app identity, expected handle/API/query checks. Those fields do not identify the executed Wasm bytes. Keep independent exact Active-version/artifact attestation. |
| Native Function owner | `cartTransforms` requires `read_cart_transforms` and is API-client scoped. `validations` requires `read_validations`; `Validation` exposes the associated Function, `enabled` and `blockOnFailure`. | A deployed extension alone is insufficient. Verify the exact associated cart transform and enabled blocking validation; missing, duplicate or partial observations stay unavailable. |
| Function configuration | Metafields are valid Function inputs; reserved app namespaces protect ownership. | Retain current Shop `$app` public-config and Product `$app` registration/policy contracts. Do not replace them with unrelated app-installation metafields merely because the latter also store app data. Admin readback is observation, not runtime propagation proof. |
| Merchant permissions | Optional scopes must already be declared and deployed before dynamic request. App Bridge can query grants and open merchant consent. Granted scopes can differ from configured scopes. | Preserve the bounded explicit two-scope gesture, refresh authoritative server grants and staff permissions afterward, and handle decline/revocation truthfully. No automatic consent or guessed grant. |
| Embedded authentication/UI | App Bridge supplies short-lived ID tokens; embedded apps exchange them for access tokens. Online tokens are limited by authorizing staff permissions. Polaris web components work in any framework. | Keep Astro/Preact with current authenticated backend and genuine Shopify embedded context. Shopify's recommended React Router scaffold does not require rewriting this stack. Browser/Polaris examples do not establish this build's hydration or G7 PASS. |

## Bounded uninstall and privacy closure

Current source defers non-`app/uninstalled` topics and unqualified generic uninstall. Queue recovery/retention do not supply generation authority or privacy fulfillment. The owner-lifecycle exact private operation has local controls, native not run, and receipt disposition only; it is not full customer/shop redaction. [Worker handlers](../../../../apps/worker/src/handlers.ts), [owner-lifecycle repository](../../../../packages/database/src/repositories/owner-lifecycle.ts), [current explanation](EXPLANATION-RESEARCH.md).

Shopify's HTTPS HMAC covers raw body bytes. This is not an authenticated installation-generation assertion in delivery headers. The documented generation-bound callback candidate remains a native qualification problem: `WebhookSubscriptionInput.uri` accepts HTTPS destinations, but that interface does not prove destination preservation across late delivery/reinstall, missing-subscription recovery or independent authority after Admin revocation. Preserve the generic quarantine and newer-generation fence. Callback readback alone and passing the retained RED characterization are insufficient. Finish the separately allocated store's genuine uninstall/missing-delivery/revocation qualification under its existing pre-install effects gate, rather than reopening the webhook architecture. [Shopify HMAC verification](https://shopify.dev/docs/apps/build/webhooks/verify-deliveries), [2026-07 subscription input](https://shopify.dev/docs/api/admin-graphql/2026-07/input-objects/WebhookSubscriptionInput), [accepted authority analysis](../../M5-025-PLATFORM-ANALYSIS.md), [current worklist step 8](../m5-native-readiness-support/G7-WORKLIST.md).

Full privacy export/redaction and object/payload erasure belong to original M10. Current M5 instructions nevertheless require installation safety and settlement of actual allocated-store data/receipt/privacy obligations; do not silently import all M10 or waive those obligations. Record exactly what M5 collected and erased, what genuine obligations arrived, who owns any permitted delayed work, and retained minimal facts under the accepted contract. Owner-authorized receipt erasure does not prove customer/shop fulfillment. [Original implementation plan](../../../architecture/implementation-plan.md), [current worklist](../m5-native-readiness-support/G7-WORKLIST.md), [allocated-store destination-effect privacy](../../M5-027-DESTINATION-EFFECT-PRIVACY.md).

Shopify requires the three compliance topics, including apps that collect no personal data; response actions are normally due within 30 days subject to legal retention exceptions. `shop/redact` is documented 48 hours after uninstall. CLI manual trigger tests do not test subscription delivery. These obligations demand specific settlement evidence for the actual test store, not an inference from declared callbacks or HTTP acknowledgment. [Shopify privacy compliance](https://shopify.dev/docs/apps/build/compliance/privacy-law-compliance).

Result: **M5/G7 remains unqualified.** The practical path is internal provisioning connection and exact readiness, one native merchant publication flow, bounded installation/privacy settlement, cleanup and cumulative acceptance. Further broad security research or cryptography/framework refactoring is unnecessary for this finishing recommendation.
