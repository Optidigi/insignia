# Signing UI intent audit

Inspected source: `9960c812d4edd87d357d5c977061d34538980d28`. Source/history audit only; no implementation, native/provider execution, deployment, credentials, tests, commit or push. The findings describe this tree, not independently observed production.

## Verdict and original intent

Cryptographic signing keys are an Insignia server responsibility. The original plan assigns encrypted private keys to Insignia server storage (lines 92–93), installation-scoped Ed25519 signing to the backend (333), public-key publication/readback before issuance (393), and new generation/keys on reinstall (395). M4 creates the server signer and key/Function reconciliation (856–863). M5 asks the merchant to configure, preview and publish a product (866–874), not administer cryptographic keys. [Implementation plan](../../../architecture/implementation-plan.md), [M4 lifecycle contract, lines 57–114 and 275–280](../../prompts/M4-003-KEYS-PUBLICATION-READINESS.md).

No explicit original sentence banning every signing diagnostic from admin was found. The responsibility conclusion follows from these positive contracts. The currently exposed signing task is an engineering provisioning workflow in product presentation; backend safety controls do not establish product intent.

## Actual visibility and authority

`MerchantConfigEditor` renders both ReadinessPermissions and SigningSetup whenever the authenticated product list or config view has loaded (929–953). There is no owner-role, development-mode or signing-capability visibility condition. The heading/check appears on both ordinary picker and configuration screens. [Editor](../../../../apps/web/src/islands/MerchantConfigEditor.tsx).

SigningSetup labels the section “Signing setup”, offers “Check signing setup”, and offers “Set up signing” only after the server says `actionAvailable`. It makes no token/API calls on mount; checking is GET, setup is POST. Missing status now says unavailable; an attempted ambiguous mutation says uncertain (8–15, 54–89, 92–127). Displaying the panel alone does not create keys. [Component](../../../../apps/web/src/islands/SigningSetup.tsx).

The server creates the capability only from private startup configuration (273–334). The loader requires the fixed same-UID mode-0600 regular non-symlink `/run/insignia/signing-owner-plan.json`; the private attempt directory is fixed under `/var/lib/insignia/signing-owner` (6–48). The browser supplies no tenant, key ID/window, wrapping ring, path or release attestation. Missing allocation disables the server action, but does not hide the panel. [Production composition](../../../../apps/web/src/server/admin/production.ts), [configuration loader](../../../../apps/web/src/server/admin/signing-owner-configuration.ts).

HTTP requires authenticated read/edit permissions. POST also requires allowed origin and exactly `{action: 'setup'}` (105–150). The action binds `insignia-rewrite-dev.myshopify.com`, provider Shop/AppInstallation, tenant ID, installation generation, authorization generation/epoch, runtime app/origin and fixed release/version evidence (102–199). Both GET and POST require unexpired `canRead`/`canEdit`, staff ID and session ID. This is an exact designated-development-installation capability, not generic merchant key management. Its name “owner” does not imply a Shopify owner role: no specific owner staff-ID or owner-role check exists. Matching authorized editing staff can satisfy it. [HTTP](../../../../apps/web/src/server/admin/http.ts), [action](../../../../apps/web/src/server/admin/signing-owner-action.mjs), [runtime identity checks, lines 7–13](../../../../scripts/m5-runtime/signing-provision-core.mjs).

The core further checks online app/user `write_products`, app `read_cart_transforms`/`read_validations`, provider grants, exact active scope, trusted release/Function evidence, and merchant local-day coverage (147–217). It creates a pending key, publishes with CAS/readback, rechecks, then activates (256 onward). Exclusive durable reservations and closed settlement protect ambiguous writes. Success explicitly retains `quoteIssuanceAuthorized:false` (action 21–68). These controls should remain. [Provisioning core](../../../../scripts/m5-runtime/signing-provision-core.mjs).

## Bootstrap and consent are distinct

M5-023 specifies first-session identity verification, staff grant, provider installation read, durable tenant/generation reconciliation, then authenticated actor (42–99). Its signing section checks prerequisites (267–276), not a merchant signing button. Current production authentication calls `ensureManagedInstallation` transactionally (355–417). The repository creates the tenant or starts a new installation generation (161–277), without signing-key creation/public-config publication. Thus identity bootstrap exists; automatic per-install signing initialization is absent from this path. [Bootstrap contract](../../prompts/M5-023-INSTALL-BOOTSTRAP-TRUSTED-PROVISIONING.md), [production](../../../../apps/web/src/server/admin/production.ts), [tenant repository](../../../../packages/database/src/repositories/tenant.ts).

Key generation exists separately: SigningKeyLifecycle.createPending generates a random seed, encrypts it, stores ciphertext and wipes memory (59–86). [Lifecycle](../../../../packages/application/src/keys/lifecycle.ts).

ReadinessPermissions queries optional Shopify scopes and asks through `shopify.scopes.request` for `read_cart_transforms`/`read_validations` (3–12, 28–85). Merchant consent to provider permissions is legitimate and separate from app-owned key IDs, validity windows, wrapping custody, publication sequencing and recovery. Removing the crypto UI must preserve consent and current staff/provider permission checks. [Permissions component](../../../../apps/web/src/islands/ReadinessPermissions.tsx).

## Smallest responsibility-boundary correction

Remove SigningSetup from the ordinary merchant editor. Retain platform consent/product publication and show a plain publication-readiness blocker/support message when internal prerequisites are unavailable. Keep the narrowly authorized provisioning mechanism internal while qualification finishes. Any separate engineering screen needs explicit server authority, not merely a hidden button.

This corrects the presentation leak without changing Ed25519, wrapping custody, generation fences, CAS/readback or ambiguous-write controls. It does not complete automatic initialization. The fuller architectural completion is an app-owned installation/key initialization and reconciliation lifecycle, including new-generation keys, overlap/rotation and durable recovery. The plan leaves the precise trigger/scheduling choice open. Do not automatically invoke the existing one-shot owner POST on mount: its private allocated plan, fixed target/version and no-ambiguous-replay contract are unsuitable as a generic bootstrap hook.

A source-equivalence test enforces this and excludes stdin/log/environment from the imported core. This is not separately implemented cryptography and the original file is not merely a test driver: it is a private provisioning executable with stdin main at line 342 and separate tests. Its frozen hash and import-safe extraction rationale are documented. Identity fences, secret confinement, fresh authority, readback and uncertain-result controls solve actual problems. Nonetheless, the 275-line authenticated/filesystem bridge around a 346-line helper, fixed store/version bindings, duplicate source and browser recovery add substantial integration complexity for an internal prerequisite. Product presentation adds support burden without transferring responsibility. A later refactor can preserve historical executable/evidence while consolidating maintained production orchestration into one application service. Frozen protocol and historical record compatibility must remain; those contracts do not inherently require preserving a provisional UI or duplicated helper text forever. [Frozen protocol/decision ledger](../../../architecture/decision-ledger.md), [M4 lifecycle contract](../../prompts/M4-003-KEYS-PUBLICATION-READINESS.md).
