# Test and complexity audit

Read-only source audit of candidate `9960c812d4edd87d357d5c977061d34538980d28`, 11 October 2026. Only this findings file was written. No tests, provider calls, native qualification, commits or runtime changes were performed. The source code and repository plans are the primary evidence; this is a representative interacting-source inspection, not certification of every assertion in the repository.

## Verdict

We cannot honestly confirm that the codebase has no unnecessary tests or complexity. There is demonstrable duplicate CI execution and avoidable coupling in browser tests. There is also substantial justified safety coverage. File size alone does not establish that tests overwhelm development, and this audit has no execution-duration, flake-rate or maintenance-cost measurements to prove that stronger claim.

The original M5 explicitly requires UI/canvas agreement, concurrent editing, missing-preview handling, immutable publication and G7 session/save recovery: `docs/architecture/implementation-plan.md:866–874`. M10 adds integrated fault/recovery and release qualification (`:916–923`); it does not make the underlying M5 publication and generation fences optional until M10. The operating model expressly preserves existing security invariants while allowing provenance-based reuse for unchanged inputs and avoiding entire historical reruns for documentation-only work (`docs/delivery/operating-model.md:46–54`).

## Ranked findings

1. **High confidence: the same operator suite runs twice in a single foundation job.** `.github/workflows/m1-foundation.yml:79` runs `pnpm check`; `package.json:25` includes `test:m5-operator` in that command. Workflow `:81` runs `test:m5-operator` again before the distinct stress and missing-renderer controls. This is exact command duplication, not two different environments establishing independent evidence. Preserve the stress/negative controls and the existing operator assertions; a later scoped CI change can eliminate the second operator invocation. This affects delivery tooling, not shipped application behavior. No elapsed-time saving is asserted.

2. **High confidence: documentation changes trigger broad, overlapping runtime qualification.** Foundation, database and runtime PR filters include all `docs/delivery/**` (`.github/workflows/m1-foundation.yml:31`, `m3-database.yml:12`, `m3-runtime.yml:27`). Those jobs build the workspace and repeat style/boundary/secret checks (`m1-foundation.yml:79`, `m3-database.yml:56–60`, `m3-runtime.yml:86–106`). Foundation also executes package tests through `package.json:12,25`; runtime executes application/Shopify/observability/worker tests again under its PostgreSQL context. The latter environment differences can be valuable; they should not be erased indiscriminately. The concrete concern is that a delivery-note edit invokes the same broad jobs as code changes, despite the proportionality policy at `docs/delivery/operating-model.md:50`. A later dependency-aware CI proposal should preserve all required statuses and cross-component/release regression while defining appropriate document checks and provenance reuse. This audit does not authorize bypassing present checks.

3. **Medium confidence: browser maintenance is concentrated and partly tied to rendering internals.** `apps/web/test/admin/editor-browser.test.mjs` has 2,480 physical lines and combines signing, currency/pricing, geometry, publication retries, authorization races, permission gestures, CSP and responsive catalog behavior. Setup repeated at `:21–36` and `:57–71` launches a server/browser and installs nearly identical route fixtures; similar scaffolding surrounds later cases. The geometry case uses positional selectors `select:nth` and fixed 100ms waits (`:483–501`); the stress control requires exactly three canvas elements and specific diagnostic attributes (`:1340–1354`). These details increase change coupling and can make a harmless renderer/DOM restructuring expensive. However, actual pixel changes, saved drafts and request counts protect real behavior, so the entire browser suite is not implementation-mirroring waste. A proportionate future change would introduce one explicit fixture helper, group suites by user flow, and replace positional waits/selectors where a stable user-visible condition exists. Preserve meaningful canvas and race regressions rather than translating every assertion into a new unit test.

4. **Medium confidence: the shipped editor is a maintainability hotspot.** `apps/web/src/islands/MerchantConfigEditor.tsx` has 1,942 physical lines. It owns request/session helpers (`:98–160`), publication storage, picker/editor state, many mirrored state/ref values (`:285–312`), data loading (`:376–413`), canvas editing and the rendered controls. Its async identity/publication fences explain much of the test matrix: a late response must not restore private state or replace a newer publication. This is concentration of responsibilities, not evidence that those fences are unnecessary. If the next behavioral change touches this file, extract only a coherent seam with a clear owner, such as request lifecycle or a presentation section, while keeping locked observable contracts. A broad cleanup during unfinished M5 would create extra regression work without proving user value.

5. **High confidence about retained overhead; limited confidence about removability: historical native operators remain in current qualification.** `package.json:18,25` runs multiple milestone-numbered operator suites, including both M5-015 and corrected M5-015R. `scripts/m5-015/qualification.mjs:47–54` permanently stops its live qualification after the recorded gate breach, while its synthetic entry remains. Corrected and later variants retain similar operator/qualification machinery (`scripts/m5-015r/qualification.mjs:29–80`, `scripts/m5-017/qualification.mjs:29–73`). They use exact host handoff paths (`scripts/m5-015r/operator.mjs:9`, `scripts/m5-017/operator.mjs:9`) and exact app/shop/installation fixtures (`scripts/m5-017/documents.mjs:5–16`). Binding checks intentionally freeze source/build/history (`scripts/m5-015r/binding.mjs:8–43`), and later operators import utilities from earlier slices (`scripts/m5-015r/operator.mjs:5`, `scripts/m5-017/operator.mjs:5`). These are specialized evidence/operations tools, not merchant runtime. Their constraints are safety features for bounded historical experiments; blindly generalizing or deleting them is unsafe. The maintenance issue is an accumulating globally rerun historical harness and unclear separation from reusable current controls. Inventory that separation before any future change; preserve closed evidence byte-exact and all locked acceptance/security assertions. Sharing helpers across frozen runs may itself invalidate bindings, so no blanket deduplication recommendation follows.

## Coverage quality and contrary evidence

There is direct evidence that more tests did not guarantee the right contract: `REPORT.md:17` records that both production readiness callers and browser mocks repeated `/api/admin/products/readiness`, while Astro exposes `/api/admin/readiness`. This defect is **already corrected in this candidate**, including a real built-route fail-closed check. It supports adding narrow real endpoint/composition seams when mocks otherwise repeat the caller's assumption; it does not justify replacing the whole browser suite. Similarly, `apps/web/test/admin/signing-owner-browser.test.mjs:43` has an unused `/api/admin/signing/functions` branch, but its isolated harness renders only `SigningSetup` (`:7–20`), which calls the signing request helper. That dead branch is fixture clutter, not evidence of another live route failure.

Several inspected cases independently justify rigor. `apps/web/test/admin/merchant-config.test.mjs:460–505` races different publication keys against PostgreSQL, checks that only one immutable revision commits, and recovers the winning intent. `editor-browser.test.mjs:1414–1468` checks that retry after storage denial and a newer draft still uses the original immutable version/key. `:1774–1807` disallows mutation during passive readiness refresh, and `:1914` introduces the in-flight authorization-denial regression. These cannot be collapsed merely because they all mention publication or session state. Layered browser and database coverage tests different failure boundaries.

## Minimal strategy and limits

Keep current contract tests and historical evidence. First make a concrete, separately reviewed CI proposal around the proven duplicate command and documentation-only triggers. Measure job duration, failure causes and assertion-to-invariant coverage before claiming that test volume overwhelms work. Improve browser scaffolding/selectors opportunistically when those flows next change, and avoid adding browser cases for pure helpers already proved below that layer. Keep full integration and release qualification where input changes require it.

This audit supports **specific avoidable delivery overhead and local maintainability debt**, not a claim of systemic runtime bloat or a safe test-deletion quota. It did not measure bundle size, memory, production latency, mutation resistance or complete coverage, and did not time any suite. The root audit separately measures tracked LOC by category; repository documentation/history and operator tooling must remain distinguishable from shipped runtime when interpreting those totals.
