## What signing setup means

It establishes this store installation's cryptographic signing identity. The backend generates a private seed, encrypts it for durable storage, and publishes the corresponding public verification key and valid day range in app-owned Shopify configuration. The approved Ed25519 whole-quote protocol lets checkout Functions verify that accepted customization prices came from the authorized backend for the correct installation. This is price integrity, not a merchant signing a document or activating billing. [Frozen protocol](../../../architecture/decision-ledger.md), [key lifecycle](../../../../packages/application/src/keys/lifecycle.ts), [public config](../../../../packages/application/src/keys/public-config.ts).

The implemented helper creates a pending key, publishes/readbacks its public config, rechecks exact identity/authorization and Function/release evidence, then activates the key. Its private fixed plan contains the exact installation/authorization binding, key ID and valid day range. A persistent private journal prevents an uncertain write from being blindly repeated after disconnect/restart/rollback. The reviewed overlay exists, but the report establishes that both required native mounts are absent. Signing status GETs created no key. The local correction now distinguishes unavailable status from an actually started mutation whose result is unknown. [Configuration loader](../../../../apps/web/src/server/admin/signing-owner-configuration.ts), [owner action](../../../../apps/web/src/server/admin/signing-owner-action.mjs), [Compose overlay](../../../../deployment/m5-runtime/signing-owner-compose.yaml), [provisioning core](../../../../scripts/m5-runtime/signing-provision-core.mjs), [report](REPORT.md).

Successful setup alone does not authorize quote issuance or prove ProductConfig activation/Function propagation. The helper expressly returns `quoteIssuanceAuthorized: false`; final readiness independently requires active key, exact observed public config, correct Function/artifact evidence and effective revision. [Provisioning core](../../../../scripts/m5-runtime/signing-provision-core.mjs), [issuance readiness](../../../../packages/application/src/keys/readiness.ts). Shopify officially supports app-owned metafield configuration as Function input: [Function configuration](https://shopify.dev/docs/apps/build/functions/input-output/metafields-for-input-queries).

## Ordinary uninstall/reinstall problem

A merchant uninstalls, reinstalls, then an old uninstall notification arrives late. The app must clean up the old installation without disabling the new installation or deleting its new data. This is a normal asynchronous lifecycle problem. The generic Shop-shaped body does not contain independently qualified installation-generation authority. Body HMAC does not turn separate delivery metadata into that authority, and local receipt time means arrival time, not occurrence time. [Source platform analysis](../../M5-025-PLATFORM-ANALYSIS.md), [current trust boundary](../../../architecture/SHOPIFY-WEBHOOK-TRUST-BOUNDARY.md), [Shopify raw-body HMAC verification and delivery handling](https://shopify.dev/docs/apps/build/webhooks/subscribe/https), [pinned webhook reference](https://shopify.dev/docs/api/webhooks/2026-07).

The retained RED control records the old authority boundary's failure. A passing characterization test reproduces the flaw; it is not a security PASS. Current quarantine prevents generic unqualified metadata from authorizing newer-generation deactivation, but does not demonstrate successful genuine uninstall processing. Permanent quarantine leaves real obligations unresolved. Neither callback readback nor revoked Admin credentials alone establishes the missing authority. [M5-025 contract](../../prompts/M5-025-GENERATION-SAFE-UNINSTALL.md), [trust boundary](../../../architecture/SHOPIFY-WEBHOOK-TRUST-BOUNDARY.md).

## M5 versus M10

The original plan puts complete privacy export/redaction, end-to-end object/payload erasure and release retention/security drills in M10. Original M5 acceptance is merchant configuration/preview/publication plus assigned G7/session/staff/save recovery and Option A activation requirements; original G7 does not itself list the entire privacy subsystem. M3 begins deletion metadata and durable admission. [Implementation plan](../../../architecture/implementation-plan.md), [original exit contract](../../prompts/M5-018-M5-EXIT-G7.md).

Later explicit M5 lifecycle instructions and the current worklist require safe uninstall/privacy qualification for the allocated test resources, while milestone autonomy includes necessary supporting lifecycle work. This must be honored without treating all M10 work as implicitly brought into M5. State the exact obligations for data/resources M5 actually creates. Do not describe missing automatic handlers as merely an unrun test or present owner-authorized receipt erasure as full customer/shop redaction: the repository explicitly says it does not claim that. [Autonomy](../../authority/milestone-autonomy-2026-10-09.md), [current worklist](../m5-native-readiness-support/G7-WORKLIST.md), [owner lifecycle repository](../../../../packages/database/src/repositories/owner-lifecycle.ts), [worker handlers](../../../../apps/worker/src/handlers.ts).

Platform obligations do not vanish because full implementation belongs to M10: Shopify requires the three mandatory compliance topics and handling even where an app does not collect personal data. Its documented shop/redact delivery occurs 48 hours after uninstall and fulfillment is normally within 30 days, subject to legal retention exceptions. These platform facts were verified by the parent against [Shopify privacy compliance](https://shopify.dev/docs/apps/build/compliance/privacy-law-compliance). This note performs no native compliance test.
