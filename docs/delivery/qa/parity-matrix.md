## Comparison contract

- Compare the accepted selected composition only. Do not bring the retired MerchantConfigEditor or the developer-only StorefrontHostPreview into production parity judgments.
- Shopify owns the merchant outer chrome, storefront product page, cart, checkout, theme editor and language settings. Compare Insignia's app content only. For merchant screenshots, match the Shopify app iframe's CSS width; for customer screenshots, match the Designer frame/modal's CSS width. Crop or mask host-owned content.
- Use the same relevant data shape, names, option counts, image availability, locale, theme and workflow state on both sides. A six-view product cannot be compared with the single-view fixture to claim a missing control. Exact price parity is compared only against an authoritative live quote; local demo estimates are not purchasing authority.
- A local demo interaction proves only its explicit local fixture adapter. A built-app browser fixture proves the selected UI, request mapping and controlled host seam; it does not prove native App Bridge/Shopify lifecycle or provider durability. A native screenshot proves only the visible observation. Save/publish/upload/cart claims require their own exact request and fresh readback.
- Treat normal, pending, empty, failed, denied, conflict, uncertain, stale and recovery outcomes as separate outcomes. A retry that recovers does not erase the original error.
- Keep viewport and locale samples risk-based: wide app content, 390 CSS px, and 320 px on the densest content; desktop Chromium and Firefox for key host paths; English and Dutch full paths, then long German/French labels/errors on dense screens. These are browser checks, not physical-device or complete assistive-technology claims.

state-cases.json is a reusable plan, not a pass ledger. Every case remains not-run until a result includes build/source identity, route, content width, fixture or real product facts, user-visible outcome, request/no-request evidence and persistence/readback where applicable.

### Local preview controls

The merchant preview process is loopback-only. INSIGNIA_PREVIEW_STATE accepts normal, empty, denied, unavailable or loading. INSIGNIA_PREVIEW_SCENARIO accepts normal, order-demo or orders-rich. The variable defaults to order-demo, which opens a synthetic purchase detail. Set it to normal to open the selected Products route with the simple synthetic config; orders-rich opens the synthetic Orders list. In order-demo, the local host adds a sample order picker and substitutes the local product/Methods workflow adapters. Generic preview API commands are rejected; order-demo has a separate in-memory worker/transport. It has no backend credentials/provider effects. Its synthetic read model, local host/Bridge/Polaris shims, static settings handoffs and fake API responses must never be reported as integrated success.

The customer preview catalogs fourteen fictional ProductConfig scenarios. Its example=accordion state inserts sample artworks, and its local runtime simulates upload/cart/storage in memory. Scenario switching intentionally remounts/reset state. The local /product host page describes a simulated return result and is not a Shopify cart.

## Production composition and leak review

The production merchant routes resolve to the selected islands and real containers listed above. SelectedProductContainer uses authenticated JSON, selected client journaling, scoped media, real save/copy and publication ports. MethodsContainer uses authenticated catalog/product reads and the versioned Method transport. Orders and Settings use their respective authenticated adapters. Local example data servers are reachable only from frontend example composition, not from these route owners.

Several selected merchant presentation/reducer files intentionally remain under frontend/admin/examples/admin/support and are imported from production selected islands. The project README documents this placement. Their directory name alone is not a fake-adapter leak. In current composition, shared dialog, image picker, canvas, method picker/manager, method configuration, workflow reducer/history/price helpers and styles are selected UI building blocks; data/operation authority is injected by the authenticated container. The preview server, fixtures, synthetic order worker, local storage models and generated sample catalogs are isolated preview adapters.

The customer package entry frontend/designer/src/index.ts exports Designer/runtime types and selected styles. The production storefront entry in apps/storefront uses that selected Designer and live-config mapping, real upload service, private quote/cart API and verified Shopify Ajax cart adapter. The scenario catalog, LocalDesigner, local-runtime and StorefrontHostPreview are imported by the Vite preview shell, not the production Designer export or customer mount. The customer artwork portal is a separate secure composition; its cart port rejects. The merchant designer preview is a separate nonce-bound preview-only route; its cart port rejects and its upload is a temporary object URL.

No new reachable fake upload/cart adapter or duplicate production customer UI was identified by this import-composition review. Preserve these distinctions when investigating defaults:

- Starting with the first allowed color, zero quantities and optional sample artwork are local-preview inputs, not customer data.
- Production option definitions/labels and accepted values are passed through selected snapshots; sparse Shopify tuples must stay exact.
- Current native observation found Shopify-selected variant/quantity does not seed a fresh Designer draft (audit F4). This is a handoff-responsibility decision, not evidence that the production cart uses a fake ID.
- The production merchant customer preview is intentionally non-purchasing. Do not treat its local file upload or preview-only DesignerPorts as buyer upload/cart composition.
- /admin/settings/privacy is an explicit retained integration target; do not mark the route itself a demo leak.

The upstream native audit records: Add views X/Escape no-op and Cancel dismissal (F1); intermittent Methods/editor reads (F2, cause unresolved); one failed native cart attempt reconciled to empty cart (F3); Shopify selection handoff question (F4); missing translation group labels (F5); Home >20-product paging helper defect (F6); vague SVG inspection recovery copy (F7); and isolated web package externals (E1). The next broad test targets are:

1. **Shared modal/host lifecycle:** after the active modal correction is ready, replay the same user-driven X, Escape, Cancel, reopen, focus-return and no-write assertions across Add views, variant-photo selection, Method picker/duplicate/remove, Add language, order preview and customer artwork. Pair built local shopify.modal-aware behavior with native host scrim/hit-test. Do not let the known working Add language dialog erase the affected Add views path.
2. **Representative product coverage:** use a real simple product for first setup and the native 64-variant, six-colour, four-view T-shirt for complexity. Record exact views, placements, production options, photos and supported tuples first. Locally cover partial/missing alignment, sparse combinations, long labels and extra production options. Save/publish native mutation remains a separate owner-owned product lane.
3. **Recovery matrix:** use controlled replies for stale reads, 401/403, 404, 5xx, network loss, conflict, committed-but-lost acknowledgement, expiration and permission revocation. Cross real selected UI actions with one request/readback oracle; do not substitute synthetic success for backend evidence.
4. **Orders and secure artwork:** cover exact purchased history, expiry/retention, upload, lock, stale version, customer link, ZIP/PDF preparation and fill-missing-only secure portal using read-only native records and isolated synthetic mutations. Do not dispatch email or checkout.
5. **Responsive/locale sample:** rerun dense merchant editor/Methods/translation and customer quantity/review/long-error paths at matched 390/320 app-content widths and long locales. Record browser/host, theme, width and effective app frame for every capture.

Already-established local coverage is substantial but bounded: selected merchant browser cases exist in apps/web/test/admin/selected-*-browser.test.mts and apps/web/test/admin/editor-browser.test.mts; storefront selected flow cases exist in apps/storefront/test/buyer-browser.test.mts and apps/storefront/test/selected-*-browser.test.mts; frontend reducer/runtime/config coverage exists in the four frontend packages. Consult the exact scripts and test names before selecting an execution cohort. ## Evidence note format

For each executed case, record:

case ID → source/deployed artifact → route and owner → app content CSS width → product/order/locale/theme facts → starting UI state → user action → expected/actual visible and focus state → request or no request → authoritative readback → evidence paths → classification

Classifications: pass, fail, blocked, unsupported, or usability note. Include native vs built fixture vs preview demo. Keep operation IDs and URLs private as required; redact customer artwork and credentials. A click/toast, DOM tag, HTTP 200, local preview receipt or screenshot alone does not prove persistence, publication, upload acceptance, cart success or owner visual acceptance.
