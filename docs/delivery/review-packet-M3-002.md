## Implemented and measured

- Exact-byte HMAC verification precedes database/queue initialization. The HTTP body is bounded while streaming to 8 MiB. Header names are case-insensitive; required metadata is bounded. Current/previous app secrets are injected, not persisted. A valid delivery is acknowledged only after the inbox commit and same-ID pg-boss job are confirmed. Enqueue failure returns retryable 5xx; same-ID retry keeps one inbox UUID.
- Migration `20260929000200_runtime_ingress_credentials.sql` adds the stable `(shop_domain, delivery_id)` mapping to the existing inbox row, encrypted offline-credential metadata, and generation-active guards on publication activation/effective pointers/outbox work. A signed Shop ID may be stored with the shop; a missing or mismatched ID prevents uninstall resolution. One preinstall delivery is resolved in place under concurrent replay. Reinstall leaves the old inbox identity bound to its original generation.
- Credential envelope v1 uses AES-256-GCM with random nonce, key ID and shop/generation/version/token-kind associated data. The current and up to three prior wrapping keys may be configured; a missing key or tampered envelope fails closed. PostgreSQL serializes refresh claims and replacement. Lost network response leaves the old pair durable for retry; stale replacement and deactivated generations cannot install a late pair. The Shopify refresh adapter is exercised only with injected synthetic transport.
- Worker uses pg-boss queues `insignia.shopify-webhook.v1` and `insignia.token-refresh.v1`, bounded retries and ID-only payloads. Real PostgreSQL/queue tests cover crash then retry, same-ID replay across restart, claim contention and lost refresh response. Unhandled non-uninstall business topics are deferred. Liveness is distinct from durable readiness.
- Pino logs use an event/detail allowlist; no raw bodies, headers, HMACs or tokens enter logs. Bounded prom-client labels count ingress, inbox, queue, refresh and resolution outcomes. Worker metrics use loopback HTTP; web ingress metrics require a configured bearer token at `/api/internal/metrics` and are disabled without it. The protected scrape reads current unresolved backlog from PostgreSQL so its gauge does not depend on another delivery.

## Blocking security finding and safe disposition

Shopify's [webhook verification contract](https://shopify.dev/docs/apps/build/webhooks/verify-deliveries) authenticates the **raw body only**. Topic, delivery ID and trigger time are headers outside that HMAC. Shopify's [webhook reference](https://shopify.dev/docs/api/admin-rest/latest/resources/webhook) shows `shop/update` and `app/uninstalled` as Shop-object payloads. A captured valid Shop body can therefore be relabeled as an uninstall, or replayed after reinstall with a new header delivery ID/time. Checking its signed Shop ID prevents cross-shop targeting but cannot prove the topic or installation era.

The implementation **does not deactivate from that webhook alone**. It retains the signed delivery and marks a resolved uninstall `failed` with bounded class `unverified_uninstall_headers`; a signed Shop ID mismatch is separately quarantined as `unverified_shop_identity`. The worker defers both and excludes them from periodic retry. Tests prove no credential or installation is revoked by either unverified message. The previously proposed public application uninstall use case was removed because it could have bypassed quarantine. The tenant-scoped deactivation/fencing operation is tested with a separate local authorized call, but no independent authenticated runtime uninstall signal exists in this slice. This is a material unmet M3-002 requirement, not an accepted product/security decision. Principal direction is needed for an independent topic- and installation-bound signal or authenticated deinstallation confirmation before automatic uninstall can be enabled. A fixed topic secret alone would not fence replay after reinstall.

The fresh Spec/correctness and Standards/security reviewers identified this gap. Earlier findings about cross-shop identity, web metrics exposure and per-ID recovery were addressed. Neither local review substitutes for principal acceptance.
