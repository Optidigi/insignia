# Cloudflare outbound alerts — research, 18 October 2026

Owner direction: use Cloudflare SMTP/mailer for production alerts to `admin@optidigi.nl`. This note establishes documented platform capabilities and proposes implementation; it does not establish account entitlement, DNS custody, deployed code or successful delivery. No Cloudflare mutation, credential creation or email submission was performed by this research task.

## Verified platform facts

- Cloudflare now documents **Email Sending Beta** for transactional outbound mail, including alerts. It supports a Worker binding, HTTPS REST API and authenticated SMTP. This is distinct from inbound Email Routing. [Service overview](https://developers.cloudflare.com/email-service/)
- An application on the VPS can call `POST /accounts/{account_id}/email/sending/send` directly using a bearer token; no Worker is necessary. REST responses distinguish immediately delivered, permanently bounced and queued recipients. Missing entitlement, disabled sending and throttling have separate error codes. [REST API](https://developers.cloudflare.com/email-service/api/send-emails/rest-api/)
- SMTP uses `smtp.mx.cloudflare.net:465`, implicit TLS, username `api_token` and an API token with **Email Sending: Edit** as password. Account-owned tokens are recommended. There is no outbound port 587/STARTTLS or port 25 relay. Crucially, possession permits sending from any onboarded domain on the matching account; this is broader than one Insignia sender. A `250` submission response can still produce no delivery when all recipients are suppressed and dropping is enabled. [SMTP](https://developers.cloudflare.com/email-service/api/send-emails/smtp/)
- Cloudflare DNS is required. Sending-domain onboarding adds bounce MX/SPF, a DKIM selector and DMARC records. Sending uses `cf-bounce.<sending-domain>`; inbound Routing is a separate configuration that changes the domain's incoming MX. Sending therefore need not replace the existing root mailbox provider. Review the exact proposed records and existing DMARC before onboarding; do not enable root Routing merely to send alerts. New sending domains default to stored email previews, retained about seven days. [Get started](https://developers.cloudflare.com/email-service/get-started/send-emails/), [domain configuration](https://developers.cloudflare.com/email-service/configuration/domains/)
- A subdomain can be onboarded independently as a sending domain, with its own sending DNS records. [Subdomain onboarding](https://developers.cloudflare.com/email-service/configuration/subdomains/)
- A Worker `send_email` binding supports a fixed `destination_address`, recipient allowlists or sender allowlists. Its structured `send()` returns a message ID, rather than the REST recipient-grouped result. The public binding schema exposes fixed destination and sender allowlist together as optional fields; verify actual combined enforcement with negative probes before relying on it. [Binding restrictions](https://developers.cloudflare.com/email-service/configuration/send-bindings/), [Workers API](https://developers.cloudflare.com/email-service/api/send-emails/workers-api/), [binding API schema](https://developers.cloudflare.com/api/resources/workers/)
- Sending to a verified destination in the account is free on Free and Paid plans and excluded from monthly quota. Arbitrary-recipient sending requires Workers Paid: 3,000 emails per account/month included, then $0.35/1,000. Worker execution is separately metered. Actual account plan/enrollment must be checked before any paid enrollment. [Pricing](https://developers.cloudflare.com/email-service/platform/pricing/)
- New-account daily limits are conservative and account-specific; no fixed universal numeric quota is promised. Verified-destination sends are excluded from daily limits. Normal messages allow 50 total recipients and 5 MiB; alerts should be much smaller and rate-limited. [Limits](https://developers.cloudflare.com/email-service/platform/limits/)
- Cloudflare retries soft bounces with exponential backoff, while hard bounces fail permanently. “Delivered” means accepted by the recipient mail server, not read or guaranteed inbox placement. [Lifecycle](https://developers.cloudflare.com/email-service/concepts/email-lifecycle/)

## Recommended Insignia shape

Use display name **Insignia Alerts**, sender **`insignia-alerts@optidigi.nl`**, recipient **`admin@optidigi.nl`**, reusing the existing onboarded root domain reported below. No DNS changes are needed merely to create this sender identity. A dedicated sending subdomain such as `insignia-alerts.optidigi.nl` would permit separate authentication policy, but adds onboarding work with limited benefit for this low-volume operator route. Retain the existing root MX, SPF, DKIM and DMARC. Verify the recipient once if required, without claiming or bypassing human confirmation. A real reply mailbox is unnecessary for machine alerts; explicitly state automated sender in content.

Prefer a small Cloudflare Worker with a fixed-recipient email binding over putting an account-wide mail-sending token on the VPS. Expose an authenticated HTTPS endpoint accepting only a versioned, bounded alert schema; construct the sender, destination and subject in trusted code. Use a dedicated rotatable relay credential, bounded severity/type values, timestamp/nonce validation, persistent deduplication and rate limits. Reject arbitrary recipients, headers, HTML and attachments. The Worker can additionally run an external availability/heartbeat check so total VPS failure can produce an alert. This is an engineering recommendation, not yet deployed capability. Direct REST from the VPS is fewer components if account-token exposure is accepted; SMTP is useful when an existing monitoring tool requires it, but provides no additional credential isolation.

Keep alerts operational: environment, component, event class, incident ID, timestamps, aggregate counts and an authenticated runbook URL. Exclude customer information, artwork, tokens, presigned links and raw exception/request bodies. Preserve the existing root-domain preview policy because it may serve other applications; send sanitized operational content only. A future dedicated sender domain could use preview storage disabled if separately qualified. Deduplicate problem/recovery notices and send periodic reminders for sustained faults.

Record accepted/queued/bounced/ambiguous states separately. Do not immediately resend a queued submission: Cloudflare owns its delivery retry. No cited send API promises idempotency keys; loss of the response is ambiguous. Mark it unknown, reconcile available logs/message IDs, and permit only deliberately bounded duplicate-safe notification behavior rather than claim exactly-once mail. An inbox receipt with authentication headers and a simulated outage/recovery drill are required before calling the alert route qualified.
