# Integrated Luna QA plan — Superfunny product shapes

**Status:** test plan only. No products, configurations, customer designs, cart lines, orders, email, or code were changed for this note. Use this as the bounded native pass before extending to more surfaces. The Luna walkthroughs are simulated-agent usability lenses, not measured customer research.

Refresh the exact current variants, selected options, availability and image links from Shopify readback before seeding anything. Every QA copy needs fresh rewrite-dev product and variant IDs; never write to the external Superfunny IDs. Keep any copied photo provenance and the QA-only status with the test record. ## Bounded execution order

1. **Read-only preflight:** confirm the active rewrite-dev release, shop/currency/locale, current products and configuration IDs, publication states, existing cart state, and current product option/image matrix. Capture the baseline build/browser/viewport. Preserve all existing product, publication, order, artwork, payment and cart records. The Superfunny snapshots are dated and must be rechecked before use. Include a one-size case only if that fresh catalog read actually returns a Superfunny one-size product; the three checked-in snapshots are not one-size products.
2. **Three isolated merchant lanes:** prepare one QA-only rewrite-dev copy each from the verified Superfunny T-shirt, polo and hoodie source. Start from new Shopify products/configurations, use only verified variant/image relationships, and label every record `QA ONLY`. Give one agent exclusive write ownership per product. Each agent gets its own browser context and test sheet; no shared interactive tab, no same-product writes from another agent, and no concurrent changes to global Methods, store language, theme setup or publication settings. A conflict test may use two of that lane owner’s contexts against that lane’s one draft.
3. **Draft and recovery only:** exercise editor controls, save/discard, reload, stale-version conflict and validation recovery. Verify each saved state by a fresh authenticated product/config read after reload. Saving a draft must not change the published revision or storefront policy.
4. **Publish QA copies separately:** only after the draft readback is correct and all required fields/readiness pass. Confirm the returned publication operation/revision and independently read the effective Shopify policy/config. Do not alter existing published products. Keep QA copies out of collections/search and use their canonical test URLs only.
5. **Customer and cart lane later:** only after publication readback, in a fresh anonymous browser/cart per QA product. Test selected customer UI, upload, quantity/design review and, if that product actually enables it, logo-later intent. Do not begin checkout or create orders, accept payment, send email, change currency/scope, or touch VAT. Remove only the QA cart line(s), then read the same cart independently and confirm zero lines/zero total.
6. **Close out:** report test product/config/revision IDs, test-artwork IDs and cart cleanup readback. Leave QA products clearly labelled and unpublished after the run if no further native pass is planned; do not delete records or retained artwork as ad hoc cleanup.

The existing maintained browser suites and native review flow are sufficient; do not build a new test harness for this pass. Use isolated browser contexts and the already-qualified merchant/customer compositions. The inspected dev preview and local fixtures can help rehearse a step, but cannot substitute for the real saved product, published policy or cart readback.

## Highest-risk interaction checks

The main agent has already reproduced one native merchant issue on 8 November: **Add views** opens an image-selection dialog; its **X** and **Escape** do nothing, while **Cancel** closes it without selecting images or saving. Capture and recheck this once in the fresh browser contexts. Expected behavior for a dismissible dialog: X/Escape/Cancel all exit without changing the draft, focus returns to the opener, and the server readback has the same version/hash and semantic snapshot. Then select one valid image, use the dialog's save action, and assert that the new view and exact image reference appear after reload and backend readback. The source test should be the exact dialog path, not a broad new modal suite.

Then use one targeted recovery case per owned draft:

- Dirty geometry/price, try to leave: Keep editing preserves local values; explicit discard returns to the last server snapshot. Reload after an unsaved edit must not imply that it was saved.
- Two contexts start from the same draft version: save context A, then submit stale context B. Expect an explicit conflict; B’s local dirty edits stay available, A’s server version remains intact, and only explicit reload adopts it. No silent last-writer-wins overwrite.
- Force an incomplete publication readiness case on the QA draft: show the specific missing field, keep the previous/effective published revision unchanged, and avoid duplicate publish attempts while status is pending/uncertain.
- One bad/unsupported test file: show the supported formats and size limit before selection, a localized actionable error after rejection, and a retry/cancel route. For real upload, require visible bounded upload/inspection phases and apply artwork only after accepted server inspection. Do not inject arbitrary success percentages or retry an ambiguous write before checking its upload status.
- One bounded customer interruption: close/Escape during normal editing and reopen; retain the actual draft without a false dirty confirmation. Switch-design confirmation is tested only if the real host exposes switching and the content has actually changed; quote-review requirement alone is not a dirty edit.
- If a save/quote/cart response times out, preserve the raw timeout, reconcile the same request/cart identity by readback, and do not click a second mutation until its state is known.

Checklist Design is used only as a UI-state prompt, not as a code-quality checklist: [Modal](https://www.checklist.design/design-system/modal) (purpose, close route, decision text, responsive fit), [Input Field](https://www.checklist.design/design-system/input-field) (labels, format hints and field errors), [Loading](https://www.checklist.design/design-system/loading) (visible specific state and accessible text), [Uploading media](https://www.checklist.design/flows/uploading-media) (constraints, progress, result/retry), [Saving changes](https://www.checklist.design/flows/saving-changes) and [Submitting a form](https://www.checklist.design/flows/submitting-a-form) (disabled/active/busy/success/error), and [Showing input error](https://www.checklist.design/flows/showing-input-error) (clear resolution). These references suggest what to observe; Insignia’s product contracts determine correctness.

## Engine, viewport and locale sampling

Use pairwise, risk-based sampling rather than a full product × locale × engine Cartesian run:

- **Core native path:** Chromium and Firefox on desktop for each agent’s own product. The current native report is Firefox 155; Chromium has current preview evidence. Record exact versions and whether the host is native or an isolated preview.
- **Narrow layout:** 390 × 844 CSS viewport for customer modal, upload, quantity/review and admin dialog/recovery. A 320 × 568 spot check is useful only on the densest lane if time permits. These are responsive browser viewports, not physical-phone or mobile-UA qualification.
- **Locale:** one full path in English and Dutch; on the densest view, inspect a long German/French label and error for wrapping/focus. Keep shop currency at USD even when browser/UI language changes. Do not use translation changes as a proxy for EUR-market support.
- **Theme/accessibility:** check light/dark loader and one dialog in both engines; keyboard Tab/Shift+Tab, Enter/Space, Escape where supported, focus restoration, accessible name/status, visible validation, no clipped controls or horizontal overflow. Do not claim full WCAG/physical assistive-tech coverage.

For performance, capture three fresh openings and three warm openings of the same product, separate loader-visible, first usable Designer, first configuration response and first customer preview paint. Preserve cache state and network conditions. Report the observations and range, not a pass from one cached 1-second run; the existing 8 November timing is a reference point, not a cold-network SLA. For the customer mutation stage, separately time upload allocation/inspection and authoritative quote review. Do not retry a slow operation until its idempotent state has been reconciled.

## Evidence and reporting standard

Every lane reports product/config/revision IDs, current app version, source snapshot date, exact variant count/options, browser/OS/locale/viewport, operation ID or request correlation ID, and fresh readback. For save, assert the stored draft version/hash and the exact view/placement/method/step/price/variant IDs. For publish, assert the effective revision/policy readback. For upload, assert server asset status and returned revision. For cart, assert the signed customized line and then independent zero-line/zero-total cleanup. Save screenshots/accessibility snapshots for UI observations, but screenshots alone never establish persistence, publication, quote identity or cart success.

Classify each result as:

- **Product defect:** reproducible mismatch against a supported source/spec or explicit interaction expectation; data loss, incorrect variant/price, duplicate mutation, broken authorization/readiness boundary, stuck recovery, crash or inaccessible essential action. Include exact steps, response/readback, browser and minimal evidence.
- **Usability feedback:** the operation succeeds and persisted state is correct, but users may miss a control, misunderstand scope, or repeat costly work. Report the specific persona/task, observed friction, impact and smallest change. Call it an agent walkthrough observation, not a measured customer finding.
- **Scope limit:** the feature or product shape is unsupported/unverified (for example, text personalization, full color × size map absent from readback, or irregular camera mask). Do not file this as a regression.
- **Unknown/automation issue:** evidence is inconclusive or a selector/timeout failed. Preserve the raw failure and perform independent readback; do not relabel it PASS or silently repeat the mutation.
