## What the sources actually establish

| Evidence | Documented meaning | Consequence for qualification |
| --- | --- | --- |
| `SubscriptionStatus.occurredAt` and lifecycle type | `occurredAt` is when the event occurred. The App Pricing guide defines CREATED as a merchant subscribing to a plan, UNFROZEN as reactivation, CANCELED as cancellation and FROZEN as a store billing issue. | CREATED is a subscription-entry event, not merely when Insignia received a message. Using its occurrence as the entry boundary is a supported engineering interpretation. It does **not** identify the trial-to-paid boundary or first charge. [Status](https://shopify.dev/docs/api/partner/2026-07/objects/SubscriptionStatus), [lifecycle table](https://shopify.dev/docs/apps/launch/billing/shopify-app-pricing#app-subscription-history). |
| `state` | Its enum is CREATED, UPDATED, CANCELLATION_SCHEDULED, CANCELED, FROZEN and UNFROZEN; it has no ACTIVE value. | Preserve these transition words. CREATED must not fail merely because it is not ACTIVE. UPDATED alone does not prove the effective instant of a deferred change. [Enum](https://shopify.dev/docs/api/partner/2026-07/enums/SubscriptionStatusState). |
| `activeSubscription.currentBillingCycle` | The returned current period has an exact start timestamp and end timestamp (next charge). The cycle is null during trial. | An explicitly returned cycle can cover an earlier first-paid instant **inside that cycle**, subject to scoped lifecycle continuity and policy matching. It cannot describe an earlier cycle. [Active subscription](https://shopify.dev/docs/api/partner/2026-07/objects/ActiveSubscription), [BillingCycle](https://shopify.dev/docs/api/partner/2026-07/objects/BillingCycle). |
| `trialEndsAt`, `trialDays`, `trialDaysRemaining` | The active object supplies an exact active-trial end, null when no active trial. Historical plan fields are integers. Shopify prorates consumed trial days across reinstall within 180 days and permits staff-configured trial extensions that apply automatically. | Save the exact trial end while available. Neither configured days nor integer remaining days justify deriving an exact old end by arithmetic. Today's null end does not mean an old purchase was outside trial. [Plan](https://shopify.dev/docs/api/partner/2026-07/objects/Plan), [trials](https://shopify.dev/docs/apps/launch/billing/shopify-app-pricing/subscription-billing/offer-free-trials). |
| Cancellation | Scheduled cancellation is future; immediate and end-of-cycle cancellation are distinct. Paid-to-free downgrades are deferred to cycle end. `cancelEffectiveOn` is only a Date. | Scheduled occurrence does not terminate entitlement. A saved exact matching cycle end or actual CANCELED transition can establish the boundary; a date must not become guessed midnight. [Cancel reference](https://shopify.dev/docs/api/partner/2026-07/app-subscription-cancel#deferred-cancellations), [downgrade](https://shopify.dev/docs/apps/launch/billing/shopify-app-pricing/subscription-billing/setup-subscription-charges#plan-downgrading). |

The lifecycle descriptions in the current, unversioned App Pricing guide explain the pinned schema; they are not an additional native observation. The reference does not separately promise an activation/charge timestamp on CREATED. Requiring a nonexistent ACTIVE event would nevertheless contradict the documented API. CANCELED/FROZEN can bound inactive segments from their actual occurrence, with a known preceding installation state and complete subsequent history; CANCELLATION_SCHEDULED cannot.

## Smallest functional next slice

Implement a bounded coverage adapter around the existing page reader and active-subscription reader, rather than a new billing engine. Inputs should retain exact app/shop, original installation generation, request range, observation time, pages/cursors and the supported policy mapping. Fetch every page for the relevant interval from a known installation/subscription baseline through processing time. The history API supports inclusive bounds, at most 250 records per page and at most 365 days per query range; the documentation does **not** say 365 days is a total retention limit. Split longer required ranges and deduplicate boundary IDs. A single exhausted page proves only its requested range. [History reference](https://shopify.dev/docs/api/partner/2026-07/historical-events).

Use a small explicit supported subset first (engineering rules, not additional provider guarantees):

1. **Paid:** join the exact returned cycle with complete lifecycle coverage. For first-paid inside that cycle, require the supported plan/policy throughout the relevant segment and no unexplained update, freeze, cancellation or reinstall. Clip coverage to observed time and known transition boundaries; never extrapolate future entitlement. No preceding agent observation is required merely because a purchase is earlier than the read: the provider explicitly supplies the current period's start. An intervening update requires its effective-policy evidence; hold that case initially.
2. **Trial:** retain exact trial snapshots and their observed installation/subscription segment. A known subscription-entry boundary plus an exact trial end and consistent lifecycle evidence can describe a bounded trial segment. For retrospective classification, also account for trial extensions/changes; the reviewed documents do not establish that every extension emits one of the six selected events. Therefore do not extend today's trial end backward over an unexplained earlier period. Start retaining native trial snapshots now when an actual trial is available; resolve earlier uncovered orders as pending rather than bill them. This permits useful prospective qualification without demanding impossible historical precision.
3. **Inactive:** use an installation baseline with an actual cancellation/freeze boundary and complete history through the target instant; stop the segment at creation/reactivation or an ambiguous transition. Current null alone proves current absence, not its historical start. Uninstall/relationship boundaries must be joined from existing authoritative installation records or a narrowly scoped relationship-history read; the current six-event query omits them.
4. Output finite half-open normalized intervals only where these rules succeed. Preserve policy identity/generation, source times and explicit unresolved gaps. Feed them to the existing qualifier/ledger: trial waiver stays permanent, inactive old promises remain unbillable, and missing coverage remains unresolved. Test cycle/trial endpoints, delayed processing within the same cycle, scheduled versus actual cancellation, incomplete pages, changed plan and reinstall. No dispatch is needed for this slice.

Complete pages are necessary but are not a transactionally frozen provider snapshot. The reviewed docs give no pagination isolation or event-lateness guarantee. Reconcile changed/conflicting observations conservatively; do not invent a new timestamp or demand an unprovided cryptographic receipt. Avoid marking uncertain decisions terminal, because terminal local ledger decisions are immutable.
