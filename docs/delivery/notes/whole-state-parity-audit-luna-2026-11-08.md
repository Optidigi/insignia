## Findings

### P2 — Add views cancellation can leave Shopify's outer scrim active

**Observed outcome.** On the live embedded editor, the Add views modal's X and Escape did not dismiss it. Cancel removed the app modal, but Shopify's host scrim remained across the application content and intercepted pointer input (observed bounds: top 58.5 px, left 220 px, bottom/right 4 px). The page remained blocked after the app-owned modal disappeared. This is one confirmed route/interaction, not proof that every app modal is affected.

**Production route and state owner.** The current Astro route renders the selected production island: [config.astro](</Users/pc/Development/Insignia/insignia-ui-audit-2026-11-08/apps/web/src/pages/admin/products/[productId]/config.astro:8>) imports `SelectedProductContainer` and line 36 hydrates it. [SelectedProductContainer.tsx](/Users/pc/Development/Insignia/insignia-ui-audit-2026-11-08/frontend/admin/src/islands/SelectedProductContainer.tsx:304) builds an adapter with `kind: 'production'` at lines 304–313 and passes it to `PlacementEditor`. In [SelectedProductEditor.tsx](/Users/pc/Development/Insignia/insignia-ui-audit-2026-11-08/frontend/admin/src/islands/SelectedProductEditor.tsx:1552), `openViewDialog()` starts the `add-views` picker; the rendered branch at lines 4374–4388 supplies `closePhotoPicker` as its close callback. That callback clears the current picker session and dispatches the reducer's `closed` event immediately ([SelectedProductEditor.tsx](/Users/pc/Development/Insignia/insignia-ui-audit-2026-11-08/frontend/admin/src/islands/SelectedProductEditor.tsx:713)).

**Most likely cause (inference, not yet a captured Bridge trace).** The live Add views `<s-modal>` had `id=null`; [method-dialog.tsx](/Users/pc/Development/Insignia/insignia-ui-audit-2026-11-08/frontend/admin/examples/admin/support/method-dialog.tsx:55) sets `data-method-dialog` but no `id`. In the pinned Polaris 2 RC snapshot, the modal's internal show method calls `shopify.modal.show(this.id, options)` and its hide method calls `shopify.modal.hide(this.id)` (snapshot byte offset 686,494). Shopify documents `modal.show` and `modal.hide` as ID-based APIs with required `(id: string)` arguments, and examples pair them with an explicitly identified `s-modal` ([Modal API](https://shopify.dev/docs/api/app-home/v1.1/apis/user-interface-and-interactions/modal-api)). With a null ID, App Bridge may fail to target the active modal; this fits both X/Escape failing to dismiss and the outer scrim surviving after the app element is removed. The runtime trace did not capture whether Bridge rejected or silently ignored the null ID, so this remains the strongest source-supported hypothesis, not a verified cause.

The local unmount sequence is also relevant: the helper calls `showOverlay()` when mounted (lines 33–38); its Cancel button calls the parent `onClose` directly (lines 87–89), which clears picker state and unmounts the component; `hideOverlay()` is called by cleanup after unmount (lines 39–43). X/Escape depend on `onAfterHide` calling `onClose` (lines 70–72). The ID defect is more directly explanatory than cleanup timing alone, but it does not yet establish every event transition.

**Scope and deduplication.** The same `Dialog` helper is imported by the selected editor and [SelectedMethods.tsx](/Users/pc/Development/Insignia/insignia-ui-audit-2026-11-08/frontend/admin/src/islands/SelectedMethods.tsx:11), so those are candidate sibling surfaces sharing this lifecycle. Product publish/remove/discard/leave/copy and Methods duplicate/remove/leave also instantiate it. They are not marked as affected without native reproduction. In the comparison probes, Shopify's Translations Add language modal and Storefront setup resource picker closed by X without leaving host scrims; the working Translations modal has explicit `id="translation-add-language"` ([MerchantTranslations.tsx](/Users/pc/Development/Insignia/insignia-ui-audit-2026-11-08/frontend/admin/src/islands/MerchantTranslations.tsx:785)). This differential supports the ID hypothesis and narrows the observed issue to the app-owned Add views path rather than every Shopify overlay.

**Baseline and test limit.** At `d490e4d0`, the product route rendered the retired `MerchantConfigEditor` (`apps/web/src/pages/admin/products/[productId]/config.astro:2,30`); the local-only `method-dialog.tsx` was used by the isolated placement/Methods exploration. The current production route now uses the selected editor with that local helper. Existing browser cases spawn the built app at loopback and load the pinned Polaris snapshot as a local test asset (`apps/web/test/admin/support/selected-browser.mts:177–223`). Their `window.shopify` stand-in defines `idToken` and `saveBar`, but no `modal` API (`selected-browser.mts:254–267`), so the pinned component exercises its local dialog fallback rather than App Bridge's ID-based modal route. Tests assert that the app's `s-modal` becomes hidden after Cancel (for example `apps/web/test/admin/selected-product-browser.test.mts:141–148` and `apps/web/test/admin/selected-methods-browser.test.mts:77–81`); they neither run inside Shopify's embedded host nor inspect top-level hit testing. That lets the app-owned modal appear closed while the real host overlay remains unmanaged. The current selected browser run was blocked before browser launch by the `cookie` import issue below; no passing local result is claimed for this audit.

**Falsification.** Reject the missing-ID hypothesis if a native trace shows Polaris passes a valid unique ID to Bridge for this modal (or Bridge maps the absent ID to this exact modal) and its matching hide completes, while a separate host layer still causes the scrim. Conversely, observing `modal.show(null/"")` and a corresponding `hide(null/"")` that resolves without removing the host scrim would strengthen the hypothesis; it would still not prove the API's internal behavior without a Bridge receipt or event trace.

### P1 candidate — Flattened web server externals are not all bound in the production package

**Source and artifact evidence.** The generated [entry.mjs](/Users/pc/Development/Insignia/insignia-ui-audit-2026-11-08/apps/web/dist/server/entry.mjs:8) imports named exports `parseCookie` and `stringifySetCookie` from bare module `cookie` at top level. Other generated server chunks also contain bare `zod`, `zod/v4`, and `@noble/hashes/*` imports. The `@insignia/web` production manifest [package.json](/Users/pc/Development/Insignia/insignia-ui-audit-2026-11-08/apps/web/package.json:14) does not declare these flattened externals directly; `cookie@2.0.1` is an Astro transitive dependency ([pnpm-lock.yaml](/Users/pc/Development/Insignia/insignia-ui-audit-2026-11-08/pnpm-lock.yaml:5416), while [contracts/package.json](/Users/pc/Development/Insignia/insignia-ui-audit-2026-11-08/packages/contracts/package.json:18) declares zod and noble hashes only for that workspace package. In a temporary isolated `pnpm --filter @insignia/web deploy --prod --offline --frozen-lockfile --legacy` package, there was no runtime-root `node_modules/cookie`, and `createRequire()` based at `dist/server/entry.mjs` returned `MODULE_NOT_FOUND`. The app entry therefore lacks at least the module it imports before route startup.

The post-deploy [package-web.mts](/Users/pc/Development/Insignia/insignia-ui-audit-2026-11-08/scripts/runtime/package-web.mts:39) creates the Shopify SDK root binding; lines 56–65 verify only `aws4fetch` and `pg-boss` as flattened Astro externals. It does not bind `cookie`, `zod`, or `@noble/hashes`. On this workstation, bare imports resolve to ambient ancestor packages: `cookie@0.7.2` CommonJS instead of locked ESM `2.0.1`, then an ancestor zod v3 instead of v4.6.5. Parent's selected-browser run required temporary links under ignored `apps/web/dist/server/node_modules` for locked `cookie@2.0.1`, `zod@4.6.5`, and `@noble/hashes@2.4.0`; after those three environment-only bindings, all 40 existing selected browser cases passed in 11.9 seconds. This is evidence that the test runtime otherwise falls through to ambient versions; it is not a source or manifest change and does not qualify a packaged Linux runtime.

**Severity and limit.** This is a P1 deployment-package candidate because an unresolved external can stop server entry loading or a route's API chunk. The isolated deploy artifact was inspected, but this audit did not qualify a Linux container or inspect the running deployed server; do not report a deployed outage. The repository's [portable-web.test.mts](/Users/pc/Development/Insignia/insignia-ui-audit-2026-11-08/scripts/runtime/portable-web.test.mts:24) is intended to package and start the relocated app and request `/live` (lines 108–120), but the pinned run on this macOS ARM host failed earlier at its symlink containment check (lines 48–56) on the Darwin compiler binding. That local result does not establish whether the Linux CI/package gate is green or red for the external imports.

**Falsification.** Reclassify this as environment-only if the exact isolated Linux web package produced by the reviewed deploy pipeline resolves the locked `cookie@2.0.1` from the server entry and passes the relocated `/live` startup check without an ambient workspace or machine-level module. No Linux package/container result was available during this audit.
