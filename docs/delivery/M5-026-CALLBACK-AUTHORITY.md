## Current reconciliation source and local control

Pinned SDK15.0.0 register.ts enumerates shop-specific subscriptions, matches desired handlers by endpoint and deletes unmatched records, including topics absent from the registry. A generic uninstall handler can therefore remove an independently registered generation callback. Registry comparison is not a provider uniqueness guarantee. Its success result does not establish the full subscription binding. This is inspected installed primary source, supported by the [official SDK implementation](https://github.com/Shopify/shopify-app-js/blob/main/packages/apps/shopify-api/lib/webhooks/register.ts); local source hashes bind the pinned version, not the changing main link.

Six actual SDK public-interface controls use a synthetic external GraphQL transport with global fetch denied: empty registry deletion, generic replacement, exact-URI repeated no-op, same-URI duplicate preservation, second-page deletion and unavailable mutation ACK. The preservation assertion is explicitly RED; default green is characterization, not a correction or native proof. Source search found zero Insignia production calls to webhooks.register/addHandlers, registerWebhooks or afterAuth reconciliation. Token exchange reads currentAppInstallation; the worker recovers inbox jobs and refreshes stored credentials, not subscription registrations. Remote reconcilers and deployment shapes remain UNKNOWN. No broad register call is permitted in the proposed native phase.

The app-scoped TOML compliance records are documented as outside this SDK enumeration. That distinction limits what the deletion control proves; it does not qualify remote compliance safety. A future per-generation enrollment must coordinate with every separately discovered subscription writer. Snapshot/restore of a secret URI is not an approved way to hide a reconciliation collision.

## Mandatory registration-gap matrix

Every row separates **safe generation selection** from **complete genuine-uninstall/privacy handling**. A stopped commercial path does not discharge uninstall/erasure obligations.

| Gap | Generation-safe treatment that must be qualified | Completeness verdict now |
|---|---|---|
| Uninstall before first authenticated session | No callback has yet been registered. Retain generic/compliance receipt with no newer-generation deactivation authority. Do not create a tenant merely from unsigned delivery metadata. | UNRESOLVED: callback-only scheme cannot cover this interval. Even no merchant data does not prove no collection/logs/old-generation obligations. Independent provider authority or an explicitly reviewed lifecycle policy is required. |
| Uninstall before subscription ACK | Allocate/persist immutable expected generation and secret mapping before outbound attempt. A valid native delivery may corroborate the reserved destination; uncertainty stays explicit. | UNRESOLVED without destination/ownership proof and independent gap recovery. Lost ACK plus revoked credentials cannot be resolved by a create retry. |
| Uninstall during provider registration | Keep the attempt bound to its originally observed external installation; never rebind when provider calls fail or a new generation appears. | UNRESOLVED: provider commit timing is not client request/ACK timing. Native event before/during/after intervals must be recorded without inventing atomicity. |
| Reinstall before delayed delivery | Old confidential destination retains its old mapping; expected-generation transaction fence prevents changing the new installation. | Candidate safety condition; delayed native destination preservation NOT_RUN. Generic delayed body/time remains non-authoritative. |
| Missing/removed subscription | Mark coverage unknown, stop eligibility and reconcile through independent authority. Do not treat empty subscription enumeration as uninstall evidence. | UNRESOLVED: periodic check can detect loss only while authenticated, cannot recover an uninstall missed after access revocation. |
| Admin credentials unavailable | Preserve received evidence; no error/401/timeout/refresh failure ⇒ uninstall inference. Staff authorization is not replaced with offline credentials. | UNRESOLVED: genuine uninstall may revoke access. Independent channel or explicit bounded operator adjudication remains necessary. |
| Duplicate/out-of-order/crash | Admission independent of destructive decision; immutable capability mapping plus stable inbox ID, original generation and business idempotency survive replay/restart. | Existing generic path still fails M5-025; candidate mapping/recovery is not implemented or natively proven. |

This matrix does **not** demonstrate complete safe genuine-uninstall handling for all gaps. It demonstrates why a callback-only rollout would still be blocked. The resource plan tests the missing facts and must return PARTIAL/STOPPED when any row remains unresolved. No native “callback delivered” result can blanket-pass this matrix.

## Independent Partner timeline alternative

The [Partner events query](https://shopify.dev/docs/api/partner/2026-07/queries/events) exposes a paginated authenticated timeline. [RelationshipInstalled](https://shopify.dev/docs/api/partner/2026-07/objects/RelationshipInstalled) and [RelationshipUninstalled](https://shopify.dev/docs/api/partner/2026-07/objects/RelationshipUninstalled) carry app/Shop/provider occurrence time, not an AppInstallation ID. The uninstall reason/description are unnecessary personal data and should not be requested. A separately authorized Partner credential might outlive revoked shop Admin access; actual entitlement/access, completeness, lag, ordering, tied timestamps and external-install mapping remain unproved.

A candidate must map an independently complete install/uninstall interval to the durable generation with exact provider observations. It must handle equal timestamps, missed pages, lag, unavailable history and reinstall overlap without trusting the webhook's claimed time. No timestamp tolerance or guessed tie-break is added. A complete query with no event does not establish absence without a qualified completeness/latency contract. Existing Partner commercial credentials are not silently repurposed and no new credential store is introduced. This alternative is conditional research, not a live phase or selected production design.

## Smallest conditional contract for later principal review

Only after native facts **and every gap** are accepted: immutable per-generation callback enrollment/operation facts; confidential capability admission bound to exact signed Shop and fixed uninstall route; durable inbox authority reference separate from unsigned metadata; transactionally deactivate only the expected generation and revoke only its existing M3 credentials; business idempotency/crash recovery through existing queue. Generic/compliance receipts remain durable but cannot independently select a newer generation. Bootstrap's shared uninstall fence must consume established authority rather than replayable unsigned timing; that is an explicit later reviewed correction, not a change in this slice.

Capability material needs an approved private registration/recovery/rotation and erasure lifecycle; no ad-hoc token store, implicit upgrade, recycled mapping or indefinite raw-body tombstone is proposed. [Privacy requirements](https://shopify.dev/docs/apps/build/compliance/privacy-law-compliance), existing short-lived webhook retention, six-month identifying-payload maximum, earlier redaction and restore tombstones remain binding. Pending/alert/operator proposals must specify deadlines and independent facts before acceptance; dropping receipts or waiting forever is not compliance. The current worker's deferred privacy handling remains unpassed.

Recommended principal decision: accept the offline narrowing and SDK characterization, then separately decide whether to authorize the [bounded private resource plan](M5-026-RESOURCE-PLAN.md). Keep production uninstall/provisioning/G7 stopped. Exact-app native feasibility, callback confidentiality and complete registration-gap authority remain unqualified.
