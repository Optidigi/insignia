# Post-order customer artwork

The selected artwork-only Designer is mounted at `/artwork-upload`. Merchant order details expose a **Copy customer upload link** action for current, originally deferred missing artwork. This action requires order/artwork read and upload permission. It works before payment. A customer may fill a missing slot once; replacement remains a merchant action.

`POST /api/admin/purchases/:purchaseId/artwork-link` accepts one request UUID. The browser retains that UUID through an ambiguous response and retains the returned URL through a clipboard retry. Neither UUID nor raw capability is written to browser storage. The URL contains only a fragment capability, which the customer page removes immediately and holds in memory. API requests carry it in the explicit Authorization header.

The capability is purpose/version-separated and bound to the original tenant, installation, purchase, request and restore epoch. PostgreSQL stores only its hash. The original retained design deadline caps the grant, upload allocation, original artwork and preview URL. Revocation, an inactive installation, production lock, cancellation, erased payload or expired previous attachment cannot create new missing work. Customer attachment serializes with merchant attachment/locking and rejects concurrent second fills. It does not change prices, quantities, payment facts or purchase history.

Older frozen purchases without selected authoring use a purpose-specific `readProduct` derived from their accepted placement/step/method/variant identities, actual production measurements and immutable geometry. Missing historical display names use their real identifiers. The projection exposes no economic table or current catalogue guess. Optional captured-image loss shows an unavailable preview; it cannot erase missing-slot upload work or change accepted production choices. Missing critical production measurements still blocks the portal.

Customer view data comes from the retained accepted purchase and immutable revision, resolved for the actually purchased variant appearances: selected methods/sizes/position, captured garment images and current store wording. It never uses the current merchant draft or exposes other original artwork, recipient email, real price strings or tenant authority. Unselected appearances, methods and sizes are omitted. Zero-valued template placeholders express upload-only availability; they cannot quote, alter quantities or commit a cart. Accepted production choices remain unchanged with the order and add no post-order selectors. Effective accepted footprints can be smaller than merchant authoring handles; the purpose-specific view schema permits positive in-image footprints without weakening authoring constraints. The client uses the existing upload/inspection pipeline and acknowledges a local upload only after the missing-slot attachment succeeds.

Verified first-full-payment insertion plans one durable email notification while retained artwork is missing. Provider events cannot duplicate the purchase notification. The bounded web-owned runner requires explicit private sender configuration; development mode processes only explicitly allocated notification UUIDs and only the approved admin destination. Customer mode additionally requires current, tenant-bound evidence of arbitrary-recipient entitlement and protected order-email access. See [sender configuration and qualification](../../deployment/customer-artwork-email/README.md).

A durable claim precedes sending. A provider message ID establishes acceptance, not inbox delivery. Unknown responses, transport timeouts and expired in-flight claims never cause automatic redispatch. Cloudflare's published sending API documents send responses and suppression management, but does not currently document a sent-message lookup by custom trace header; an ambiguous attempt remains unresolved until real provider/recipient evidence establishes its outcome. The shared merchant upload link remains available independently of automatic email configuration.

Privacy cleanup removes mutable grant, submission and notification authority. Offline restore removes restored notification/grant rows and rotates the capability epoch. Restoring a backup must not recreate upload authority or replay historical email.

Verification includes PostgreSQL18 transaction/race, expiry, pre-payment attachment, tenant/lock/revocation and actual restricted-role tests; HTTP authentication/body tests; notification lifecycle/sender/recipient tests; and a browser test running the selected Designer through verified upload and atomic first fill. Local automated qualification does not establish native deployment, actual email delivery, protected-field approval or merchant visual acceptance.

The production sender rechecks the selected notice’s exact shop/install membership immediately before POST. Private sender/grant files are validated against an explicit runtime artifact boundary (the deployed working directory), canonical filesystem paths and owner-only regular files; source module depth is not trusted. Relocated compiled-loader tests cover artifact containment and parent symlinks.
