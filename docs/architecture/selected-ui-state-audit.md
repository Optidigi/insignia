# Selected UI state, effect and motion audit

Audit baseline: PR223, `d490e4d0e285b7b5be50da52cdf97474ff4a0e0f`. Integrated comparison: `897a44e48a715957881ca1117a7ba26c63da567a`. The performance branch is changing concurrently; the findings below describe that fixed integrated comparison unless a later qualification note says otherwise.

This is a source audit of both customer and merchant flows. It identifies state owners and their real triggers, compares selected presentation/motion with the original source, and records qualification limits. It is not owner visual acceptance or proof that every state has run in Shopify.

## Verdict

The selected UI is still the implementation: production uses its reducers, components, dialogs, history and CSS. Its state is deliberately split between domain/workflow reducers, effect runtimes, component-local presentation state and browser focus/hover state. PR223 did not supply a separate formal state-machine framework for every control. Replacing these owners with another framework would add complexity without restoring missing behavior.

The main confirmed storefront restriction is the integration's reuse of cart-commit pending while preparing a review quote. It makes the selected review visible but freezes navigation/editing until network preparation finishes. The performance branch now distinguishes cancellable preparation from actual cart application, retaining the selected controls and refusing stale prices/receipts. The pre-existing Q1 declined-offer recovery gap below remains outside this performance correction.

No additional removed selected layout or missing CSS animation was found in the inspected fixed comparison. Some controls are conditional on real configuration, viewport, permission and current workflow state. A one-placement/default-variant fixture cannot expose their full range.

## Actionable findings at the fixed comparison

**Q1 — pre-existing declined-offer recovery gap, outside the performance correction.** A focused actual live-adapter/selected-frame probe returned acceptance `409 REVIEW_REQUIRED`, then revisited Review without changing quantities and submitted again. It produced two identical acceptance calls, one proposal and zero cart writes; the customer stayed on generic Try again and never entered the existing repair state. The fixed comparison already has the attempted-key guard and generic error handling; the new prepared cache does not create this gap. A future correction must distinguish an authoritatively declined/resolved command from an unresolved lost acknowledgement before allocating another proposal/key. `REVIEW_REQUIRED` also covers unavailable retained lookups, so the HTTP code alone must not clear ownership. Reuse the existing repair/review presentation; no replacement layout is needed. This audit does not claim that every real integration recovery state is already triggered correctly.

**S1 — Review preparation globally blocks the selected customer controls.** `designer.tsx:306–310` calls `runtime.commit(true)` on review entry. `runtime.ts:224–229` dispatches ordinary cart pending. `designer-state.ts:225–241` rejects ordinary events while pending; the selected panels become inert and footer/back controls are disabled. The visible review therefore cannot behave like the synchronous baseline while a real quote is prepared. Required correction: cancellable, generation-bound preparation distinct from cart application; keep selected layout and gate actual purchase on a matching ready quote. The performance implementation owns this correction.

**A1 — Retired Method-route loads keep doing work.** `MethodsContainer.tsx:38–108` increments a generation on unmount, but does not abort its catalogue requests and only tests that generation after all product pages have loaded. Thus obsolete reads and catalogue-resume work can continue after departure. The final state assignment is fenced, so this audit does not claim that an old result becomes visible. Required small correction: cancel read effects/stop at await boundaries when the route retires, while preserving custody for an already-dispatched write. This is a cancellation/performance gap, not a missing baseline modal.

On the performance branch, A1 now has a small implementation: the load owns an AbortController, each read checks its live generation after completion, and route retirement aborts catalogue/product reads. A started Method write retains its original transport/journal custody; after its receipt, a retired route does not begin another read or display stale state. Two browser regressions retire the actual hydrated Astro/Preact Method island during catalogue/product reads. Both failed against the pre-change built app because no abort occurred. Both now pass against the rebuilt web application; native qualification remains separate.

No further source-confirmed missing selected screen/state/animation was identified in this pass. This is not evidence that every combination or native host transition is qualified.

## Verification and remaining qualification

Quantity-stage preparation is cancellable; Back/edit remain available and purchase waits for the current intent's quote. Actual cart application retains pending/receipt guards. The focused built-frame case verifies editing during a held quote and retirement of obsolete quantities; the selected-protocol case verifies ambiguous cart retry identity and clean Done behavior. Thirty-two reducer/runtime cases pass locally. These are implementation checks, not native deployment evidence.
- The two A1 browser cancellation regressions now pass against the rebuilt web application: retiring either catalogue or product reads aborts them. Source presentation and the Method write journal remain unchanged.
- Read-only Git comparisons used the exact PR223 and fixed integrated commits, including relocation comparisons for product/Methods presentation and unchanged CSS/reducer owners.
- Eight focused pure-state tests passed under pinned Node24.21.0: Products search/page ownership/notices; Orders filter/server-query selection; Method currency-only leave confirmation; Method translation fallback/stale-session fencing; private read revocation; confirmed artwork superseding stale reads. Commands used the four existing `index-workflow-state`, `remote-read-state`, `method-currency-state` and `method-translations-state` test files. No suite assertion, timeout or baseline was changed.
- No provider calls, deployment, global builds/checks or live-store mutations were performed by this audit. The two cancellation regressions ran against the existing built local application with synthetic network routes; their fixtures write the usual ignored failure captures.
- Final performance changes still need behavior tests for cancellation during preparation, rapid edits/late responses, close/reopen, real ready/failure/retry presentation and correct cart receipts. Browser checks must cover desktop/narrow layouts and reduced-motion mode, including keyboard focus and animation retirement.
- State families inspected in source include empty/loading/error/read-only/conflict/uncertain states as well as the happy path. Native confirmation of every permission, historical order, rich variant matrix, translated wording, media-expiry and provider-failure combination is not claimed. Source retention, local tests, native observation and owner visual acceptance remain separate results.
