# M0-007 prototype policy and publication contract

Status: candidate for local tests and bounded staging observation. The approved architecture plan and ledger retain authority. This contract does not assert a complete required-product guarantee.

## Trust boundary and truth table

The buyer controls cart attributes and can remove every carrier. They are never evidence that a product is optional or unmanaged. The preferred candidate queries **two app-owned product fields** in the same installation's reserved namespace: `m0_007_registration` (managed-product anchor, generation, revision, publication phase) and `m0_007_policy` (generation, revision, `required` or `optional`). It also queries the existing app-owned shop public key/configuration registry under a dedicated M0-007 key. Product ID and variant ID come from Shopify's Function input. The publisher alone writes product fields through the app's authenticated Admin API. The shop config carries the current installation generation and verification keys; no private key, buyer input, or detailed price rules enter these fields. The Function never trusts an unsigned line marker as policy.

| Registration observation | Policy observation | Plain unmarked line | Marked complete valid quote | Reason |
|---|---|---|---|---|
| absent | absent | allow as unmanaged **with explicit joint-loss limitation** | verify signature and economics; no marker alone authorizes | No independent product signal remains. Required and unmanaged are indistinguishable. |
| ready, current generation/revision | required, matching | reject at checkout | verify exact signed terms | Known required product. |
| ready, current generation/revision | optional, matching | allow plain | verify exact signed terms | Explicit optional product. |
| pending, current generation | any/missing | reject at checkout | verify existing valid terms if current installation's shop registry remains healthy; otherwise reject | Prevent unsigned purchase during publication without revoking an already accepted offer. |
| present, current generation | missing/malformed/stale/mismatched | reject at checkout | verify existing valid terms if current installation's shop registry remains healthy; otherwise reject | Anchor makes the missing or broken policy visible. |
| missing/malformed/stale | present | reject at checkout | verify existing valid terms only if policy unambiguously carries current installation generation; otherwise reject | Policy itself is independent evidence of management but cannot authorize plain. |
| present with wrong installation generation | any | reject at checkout | reject | Old installation cannot grant present access. |
| absent | absent, shop config missing | allow unmarked as apparently unmanaged **with joint-loss limitation** | reject (no verification keys) | A global checkout block would affect unrelated products and is not authorized. |

For a mixed cart, classify each physical variant line. Any known-managed invalid/pending line blocks checkout; unrelated unmanaged lines remain viable when alone. During `CART_INTERACTION`, Validation leaves removal and repair available; at checkout it enforces the table. Transform emits no price for invalid signatures or incomplete sets. Signed terms stay authoritative on price, quantity, context, expiry and generation; policy revision does not reprice or revoke a valid historical quote. The required/optional flag only controls **unsigned plain** eligibility. Existing verifier failure remains a rejection, never a tolerance.

The **joint-loss limitation** is fundamental for per-product metadata: if both independent product fields disappear or fail to project, an unmarked required product has the same Function input as an unmanaged product. A duplicate field narrows one-field loss only. No adapter can infer the missing fact from an empty buyer cart or current shop key registry. A complete guarantee needs a separately queryable managed-product membership anchor with bounded catalogue cost and a publication rule, or an owner-approved checkout outage policy for uncertain products. This experiment adopts neither. Its policy outcome must remain a G6 blocker if joint loss is unresolved.

## Publication state machine and ownership

`UNMANAGED → PREPARING → READY(required|optional) → PREPARING → READY(...)`. The application journal records intended product ID, expected current revision/digests, new revision, generation and phase; it is a **local test model**, not a production database/admin. Writes use `metafieldsSet` with observed `compareDigest` when supported. A stale compare fails and requires a fresh read; retries with the same desired revision are idempotent. A two-field write's Admin response is read back before proceeding. No cross-system transaction is assumed, and Admin readback alone does not prove Function propagation.

Before first required publication, keep the fixture unavailable for purchase, write registration `pending`, write policy, read back both, switch registration to `ready` only after matching policy/configuration, and observe the Function's actual projected fields before exposing the product. For required→optional, keep the product unavailable until the optional state is coherent in Function input; a transient pending/mismatch blocks unsigned checkout. For optional→required, make the product unavailable **before** writing the stricter policy so an old optional projection cannot authorize a new plain purchase during propagation. Retain current generation and historical verification keys, so already signed complete offers remain valid if current quote rules permit them. A product that remains purchasable on a channel while stale optional data projects is not ready; broad channel-publication safety is an explicit production obligation.

`ready` is a claim about the **observed Function projection**, not just a successful Admin mutation. An interrupted write leaves `pending` or mismatch: unmarked managed checkout rejects and an idempotent publisher can resume from readback. If both fields vanish, the Function cannot distinguish it from unmanaged; reconciliation after the event cannot repair an already completed purchase. Unpublishing, installation reset, deletion and key rotation need an ordered production runbook before this candidate could be adopted.

The alternative for principal consideration is a shop-level managed-product membership registry or equivalent durable per-product admission anchor independently queryable at checkout. It could cover joint product-field loss, but a full 1,000/10,000-product registry may exceed Function query/input and update bounds; it needs measured serialized size, full 200-line-cart cost, sharding/index lookup semantics and explicit failure policy. A Bloom filter's false positives could block unrelated products, while false negatives would be unsafe. No production catalogue cap or blanket outage rule follows from this local prototype.

## Test seam and acceptance

The pre-agreed seam is the two Shopify Function input/output interfaces plus a pure local publication journal model. Tests must include buyer marker removal; unsigned known-required denial; valid signed acceptance and invalid-signature rejection; all malformed/missing/stale/wrong-generation states; explicit optional and unmanaged plain acceptance; first publication, both policy-change directions, interrupted/CAS stale/retry, and historical quote validity through a same-generation policy revision. Whole-set verification still uses M0-005's unchanged v2 verifier and exact pre-discount Validation comparison. The old M0-006 missing-policy allowance stays frozen as the before-control in its historical evidence; a new M0-007 regression demonstrates the one-field-loss improvement and the joint-loss limit.
