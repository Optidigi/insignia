# M0-008 local publication and recovery contract

Status: executable **local prototype**, not a production publisher or a passed gate. The owner-approved [Option A](../../docs/architecture/OPTION-A-APPROVED.md) is the trust boundary. This contract supersedes the sample-based activation wording in the historical [M0-007 policy contract](../m0-007/policy-contract.md); its prior source and receipts remain fixed. M0-007's Rust projection and exact signed-quote verifier remain independent consumers.

## Identities and evidence layers

`PublishIntent` contains an idempotency operation ID, Product GID, resolved app namespace (`app--<id>`), installation generation, strictly increasing desired revision, required/optional mode, claimed previous mode, and both expected prior `compareDigest` values. The journal records the full immutable intent and prior policy **before any write**. Same ID with different payload, a second in-flight operation, wrong generation, conflicting revision, or unexpected prior digest is a conflict or operator action. An existing active journal entry makes a product *known managed*: missing both remote fields is an incident, never a fresh unmanaged revision 1.

Six distinct facts must not be collapsed:

1. Merchant intent selects a desired revision. It has no buyer enforcement effect.
2. A **durable** operation journal claims and resumes the exact intent. The provided `MemoryJournal` snapshot models restart only; PostgreSQL durability, transactions, cross-worker fencing and recovery latency are **not proven**.
3. A Shopify mutation acknowledgement says the Admin API accepted a CAS write. It is not exact readback or a Function observation.
4. A separate Admin read must return the exact registration/policy values with correct product, namespace, key, type and digest. It is not proof of all Function projections.
5. Function observations can identify a sampled projection and test the consumer behavior, but do not prove all future checkouts see the revision.
6. **Application activation** changes the effective configuration pointer and permits new quote issuance only after a separate admission/projection boundary can be established. The current default activation port returns `activation-pending`. No production implementation or Shopify guarantee for that boundary is supplied here.

`ready-written` means only that the exact two-field pair was read back in Admin. It is never an effective-policy assertion. An `active` journal entry requires an `ActivationPort.established` result and stores its evidence. The fake port can return this in isolated tests to exercise state transitions; that is **synthetic premise**, not Shopify evidence. The application must not expose the new ProductConfig revision or issue new quotes from a prepared, acknowledged, read-back or activation-pending operation. `newQuoteAllowed` enforces this narrow prototype rule. A pending operation conservatively suspends new quote issuance for that product, including the old revision. The last active policy remains the effective application pointer until activation; the pending journal does not rewrite it.

Accepted signed quotes from an earlier revision remain governed by their own signature, materialized pre-discount terms, installation generation, context, key validity and expiry. A routine policy revision does not itself revoke or reprice them. During pending/mismatch, the unchanged M0-007 consumer can verify a valid signed offer if a trustworthy current-generation anchor and shop keys remain; wrong generation rejects. This is a consumer contract, **not** a claim that Function propagation is uniform. Old carts with unmarked lines must satisfy the policy projected at checkout; the application must not imply a newly required policy is already enforced while an older optional projection can still be read.

## Transition controls

| Requested change | Safety condition before first mutation | Local result after exact Admin readback |
|---|---|---|
| Unmanaged → required or optional | All purchasing channels unavailable and in-flight carts drained under an independently proven admission boundary. The product cannot be treated as managed while both anchors are absent and purchasable. | Activation pending until the separate boundary is established. Publication/availability change is a distinct merchant-facing port, not automatic archival. |
| Required → required | Previous known-managed required projection remains a rejecting old state for unmarked lines; pending/mismatch also rejects. New quote issuance is embargoed. | Activation pending. Existing signed offers retain historical terms. |
| Required → optional | Independently prove all channels unavailable and in-flight carts drained before mutation. A Function that sees new optional could allow plain before application activation; an old required projection may still block plain after activation. | Activation pending; do not promise plain buying until the boundary is established. |
| Optional → required | **Before mutation**, independently prove all channels unavailable and in-flight plain carts drained, then maintain that condition through activation. A stale optional Function projection may otherwise allow an unmarked purchase. | Activation pending; no safe re-exposure without an established boundary. |

The `AdmissionPort` is checked before each state step for first publication and **either policy-mode change**. A production adapter would need a maintained, fenced all-channel and in-flight-cart guarantee; this package neither defines nor verifies one. A mere product status read, temporary Admin availability change, fixed sleep, repeated Admin reads, or two sampled Function invocations cannot implement it. If it cannot be supplied, `activation-pending` names the prerequisite and makes no Shopify mutation. Routine merchant product archival is not inferred from Option A.

The local state path is `prepared → pending-written → policy-written → ready-written → activation-pending|active`, with a terminal `retry-exhausted` operator hold. Journal phase saves use a version check, so a stale concurrent advance cannot replace an active result. Each write uses Shopify Admin GraphQL 2026-07 `metafieldsSet` with `compareDigest`; an explicit `null` creates only if absent, whereas omission would make the write unconditional and is never used. Registration is written `pending` first and never deleted to resolve a conflict. Policy is written second; registration becomes `ready` only after exact policy readback. Every ambiguous timeout is followed by an exact re-read; if the desired value is already there, replay advances without a second mutation. User errors, stale CAS, unexpected partial/malformed/missing/wrong-generation readback and conflicting revisions remain typed conflict, retry, or operator action. A three-attempt local transport budget bounds automated retry; a fourth timeout holds for operator reconciliation, including after restart. This is a prototype limit, not the plan's eventual job scheduler tuning.

App ownership is an assumption, not demonstrated live access in M0-008. The pinned write maps to `$app` and readback verifies the resolved `app--<id>` namespace, queried Product ID and each metafield's Product owner ID. App-owned definition/value access must prevent unauthorized merchant writes. The [Shopify definition documentation](https://shopify.dev/docs/apps/build/metafields/definitions) explicitly describes merchant write access as a configurable permission; choosing that access would violate the assumed exclusive publisher. The official Admin GraphQL pages for [mutation](https://shopify.dev/docs/api/admin-graphql/latest/mutations/metafieldsSet), [input](https://shopify.dev/docs/api/admin-graphql/latest/input-objects/MetafieldsSetInput), [error enum](https://shopify.dev/docs/api/admin-graphql/latest/enums/MetafieldsSetUserErrorCode) and [product query](https://shopify.dev/docs/api/admin-graphql/latest/queries/product) displayed 2026-07 as latest when checked for this package. They support the local request shapes and CAS behavior; they do **not** state a global Function propagation or linearizability guarantee. GraphQL operation strings and fake responses are exercised locally. No merchant-authenticated call was made.

## Recovery and incident boundary

The journal is the recovery key. After a process crash, load its snapshot, re-read the exact Admin state, and resume only the same operation. A timeout may have committed, so blindly repeating a write is prohibited. Same-operation replay is idempotent. If another writer changed a digest, stop for conflict. Missing or corrupted known management evidence calls for operator action; do not convert an unknown/partial state into `optional`, delete the surviving anchor, change historical purchase amounts, or claim that reconciliation undoes a plain purchase already completed. Application-controlled deletion of both fields while a required product remains purchasable is a defect, not Option A residual risk.

**Unsupported faults under Option A:** unexpected complete loss or coherent rollback of all trusted product-policy evidence outside this publication contract can make a formerly required product appear unmanaged or optional to a Function, allowing a plain purchase before detection. The fake fixtures name these cases and the journal detects them only when the application reconciles against retained journal knowledge. There is no claim of synchronous detection, frequency, or repair of the already completed purchase. Detection/containment/recovery operations and a real activation boundary remain future implementation obligations and development-gate evidence, not a new owner A/B decision.

## Verification surface

`corepack pnpm check` runs strict TypeScript and local Node tests through the public `Publisher` seam and fake GraphQL transport. `MemoryJournal.snapshot()` is loaded into a new instance at every state boundary, including saved `activation-pending`. Tests include a write-then-timeout, simulated process crash after remote mutation but before journal save, concurrent phase races, terminal retry, conflict/error/readback cases, all four transitions and the unsupported joint-loss/rollback fixtures. A [source-bound 16-state fixture](fixtures/consumer-projection.tsv) is emitted by the TS fake remote and consumed by the unchanged [M0-007 Rust projection](../m0-007/policy-model/src/projection.rs) through a small M0-008 test crate. Its `signed_allowed` result permits the independent quote verifier to check a historical quote; it is not a signature acceptance by itself. The unchanged M0-007 Function tests separately verify historical signed-price behavior, and its [publication model](../m0-007/policy-model/src/publication.rs) remains retained evidence. Synthetic GIDs and generation values in these tests are not staging receipts. See [case map](evidence/case-map.md).
