# Customer erasure exclusions during an isolated restore

This owner-only tool copies committed customer-order erasure decisions. It never calls webhook ingress, verifies a new HMAC, recovers raw customer bodies, sends an export, or deletes an R2 object. Data requests, shop/uninstall redaction and the legal basis for financial retention remain separate work.

1. Stop or detach Insignia web/worker/inspection services from this restored target before import, and keep it isolated from public readiness and external storage writes. The import rejects any other database session at admission; it cannot stop external services or prevent a later connection by itself. Restore the actual database backup into a new database using the supported PostgreSQL version.
2. Export exclusions from the authoritative source with its private schema-owner connection: `node scripts/privacy/restore-exclusions.mjs export /private/new-erasure-exclusions.json`. Supply `DATABASE_URL` privately; the CLI prints only counts and the snapshot's conservative coverage time. Existing files are never overwritten.
3. Keep this mode0600 file separately from the database backup. It contains original inbox tombstone/hash/time metadata and pseudonymous shop/order/quote/artwork exclusions, never retained webhook bodies, customer contact fields, storage credentials or signed URLs. Retain the latest complete exclusions at least through the restore window of every covered backup; erase retired copies with their no-longer-restorable backups under the approved retention policy. This is not indefinite-retention authority.
4. Against the isolated restored target, run `node scripts/privacy/restore-exclusions.mjs import /private/new-erasure-exclusions.json` using only its private schema-owner `DATABASE_URL`. No worker or public import capability is granted. Actual minimal tombstones and receipts are copied as administrative backup metadata. No Shopify delivery or HMAC verification is manufactured. Under an ACCESS EXCLUSIVE inbox lock, only the exact enabled inbox_collection_guard is disabled for the validated empty tombstone INSERT and reenabled inside the same transaction. This preserves original collection times; all other CHECK/FK/privacy guards remain active. Rollback restores the trigger on failure, and ordinary ingress still assigns collection time.
5. A checksum, schema, tenant, installation UUID/generation or existing-receipt conflict fails the transaction and leaves readiness on HOLD. Legitimate installation drift still requires fresh provider-authority reconciliation; the tool never invents or relaxes that identity. Use the authoritative latest exclusion copy; a checksum detects corruption, not independent source authenticity or freshness.
6. Reapplied private payloads are unavailable and artwork rows are DELETING/DELETED through existing guards and cleanup machinery. Source collection/expiry and immutable financial facts remain unchanged. Import always reports HOLD for storage cleanup and authority requalification. Independently qualify actual private-object cleanup, credentials/roles, provider/installation state and the reviewed runtime before enabling readiness. No storage erasure or production restore is proved by this local database qualification.

The focused test uses a fresh private PostgreSQL18 cluster and an actual pre-request `pg_dump` restored into a different disposable database. Enable only with identical explicit `PRIVACY_RESTORE_TEST_URL` and `DATABASE_URL` pointing to that owned Unix socket, plus `PRIVACY_PG_TOOLS` pointing to the existing matching `pg_dump`/`pg_restore` tools. Ordinary/native database settings never opt this test in.
